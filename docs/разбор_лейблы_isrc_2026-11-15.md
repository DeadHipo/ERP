# Лейбл трека по id и со сроком действия: решение (2026-11-15)

Статус: **предложение, ждёт ответов владельца** (§6). Кода нет, D-записи нет: D-запись пишется вместе с реализацией.
Основа: два файла рекламы по саблейблам (август и сентябрь 2026), живые данные `erp` / ClickHouse `believe` и три
независимых аудита (деньги и код; данные и файлы; альтернативный проект, сделанный без моего черновика).

## 1. Проблема

Сейчас лейбл строки Believe решает **текст**:

`believe.rows.label_name` → нормализация → `labels.label_aliases` (без периода) → лейбл → правило саблейбла.

Это делают слой 1 (`facade/layers/label-of-record.ts:10`) и реклама (`facade/ads.ts:78`). Срок действия появляется
только у правила (`label_rules`), у самой связи «трек → лейбл» его нет.

Что мешает:

- **Нет решения человека.** Что Believe напечатал, то и правда. Если строка ошибочна (первый месяц у 16 треков
  77 Records), исправить это нечем.
- **Совместные импринты** раскиданы по алиасам непоследовательно:
  - `0to8 x fate` и `0to8 / no job records` ведут в свой 0to8, хотя `fate` и `no job records` — саблейблы;
  - `Ahh Music` (467 ISRC, $155k net) — алиас **своего** 0to8 без правила. Сейчас ≈ **$81k** считается «нашим».
- **Две истории лейбла.** `owners.track_labels` (D-172) строится по книге (аккаунту файла). На 4 134 ISRC она
  расходится с лейблом по строке. Это другая ось, и заменить решение о лейбле она не может.

**Ваши файлы** — это рекламные расходы, разнесённые по артистам. Лист = строка импринта Believe за отчётный месяц.
437 из 504 строк августа сходятся с импринтами треков артиста.

В ERP есть **только лист `0to8`**, и он сдвинут на месяц: лист сентября = `ads.expenses` 2026-08 до цента ($68 920,34).
Чего в ERP нет:

- листов Echo8, Ahh Music, NoGhost, R2R и совместных импринтов: ≈ $50–53k в месяц;
- 41 артиста листа 0to8 за сентябрь: $17,4k;
- рекламы за сентябрь вообще.

Это **отдельная задача** (§7), но она подтверждает главное: владелец мыслит импринтами и саблейблами как отдельными
сущностями.

## 3. Решение

### 3.1 Модель (модуль `labels`)

| Таблица | Что это | Читают ли её деньги |
|---|---|---|
| `labels.labels` (без изменений) | Лейбл с id: `own` или `sublabel` (+ `own_label_id`). Оператор заводит любой: Ahh Music, Bleached, BIG, … | да |
| `labels.label_rules` (без изменений) | Правило саблейбла: процент, получатель-псевдоним, период, документ | да |
| **`labels.imprints`** (вместо `label_aliases`) | Строка, напечатанная дистрибьютором, с собственным id: `string`, `norm`, `suggested_label_id`, первый и последний месяц. Создаётся загрузкой Believe или оператором | **нет**, только рекомендации и отчёты по импринтам |
| **`labels.isrc_labels`** | **Решение:** ISRC → лейбл на период `[valid_from, valid_to)`, даты = 1-е число месяца (M52). Поля: `source` (`migrated` / `recommended` / `manual`), `basis`, `document_id` (только информация), `decided_by`, `created_at`, `cancelled_*` | **да**, единственный источник лейбла |

Правила для `isrc_labels` — те же, что у `links.publishing_terms` (D-188):

- запись никогда не редактируется;
- новое решение закрывает открытое с месяца нового;
- отменить можно только последнее решение, и отмена снова открывает то, которое оно закрыло;
- периоды одного ISRC не пересекаются (exclusion constraint);
- каждая запись попадает в аудит.

Почему в `labels`, а не в `links`: ISRC не принадлежит ни одному модулю (сплиты тоже держат его у себя). Индекс
`labelOfIsrc` должен отдавать лейбл вместе с правилом в силе, а правила лежат в `labels`. Шаблон pubv2 сохраняется:
отчёт создаёт сырьё (импринт), связь ставит оператор, система только рекомендует.

**Импринт оставляем сущностью**, хотя один аудит предлагал без неё обойтись. Ваши файлы группируют деньги именно по
импринтам (`0to8 x Ahh Music` отдельно от `Ahh Music`), и отчёт «по импринтам» должен опираться на id, а не на текст.

`owners.track_labels` остаётся **историей книги** (какой аккаунт и какой свой лейбл получали трек), только для
навигации. На экране подписываем её «Книга», чтобы не путать с лейблом.

### 3.2 Как читают деньги

- **Слой 1.** Вместо `ctx.labelOf(unit.labelName, date)` читается `ctx.labelOfUnit(unit, reportMonth)`:
  - есть решение в `isrc_labels` → лейбл и правило в силе;
  - ISRC пустой → по импринту строки, как сейчас (поведение `no_isrc` не меняется);
  - решения нет → новая причина C **`label_unassigned`** (механика нынешнего `label_unmapped`): «наше» и доля
    саблейбла ждут, строки артистов и carves идут как обычно.
- **Реклама.** Тот, кто несёт невозмещённую часть, определяется решением на месяц расхода. Логика «ближайшего месяца
  со строкой» уходит. Нет решения → «наше», как сейчас при отсутствии строки. Плательщик остаётся
  `ads.label_id` (D-169).
- **Охват владельца (`owner-scope.ts:60`).** Сейчас он ищет треки саблейбла по строкам; после перехода будет искать по
  `isrc_labels` (лейбл с правилом, где получатель — псевдоним владельца). **Без этого получатель саблейбла молча
  потеряет деньги.** Нужны прогон `scope.test` и `check-owner-scope.ts` на живых данных.
- **Книга (D-169) не меняется.** Решение никогда не переносит деньги между книгами. Если решение ведёт под чужой свой
  лейбл, срабатывает сигнал `labelOutsideAccount` (ключ меняется на `account|month|label`).
- **Перевести с ключа «строка» на лейбл и ISRC:** `reconcile().ourShareByLabel`, очередь C (`queue.ts`) — группы по
  ISRC и UPC, списки unmapped в `reports.ts`, explain.
- **Открытие закрытых зон.** D-запись открывает слой 1, `LayerContext` и lookup рекламы в `calculation.ts`; как
  для `recoup` в D-173, только эти места.

### 3.3 Ежемесячный поток

Экран «Новые ISRC месяца» и шаг закрытия месяца в чек-листе (`onboarding.ts`):

- **Рекомендация.** Источники по силе:
  1. другие ISRC того же UPC, у которых решение уже есть;
  2. `suggested_label_id` импринта;
  3. получатели правил среди псевдонимов сплита.

  Если источники согласны, у рекомендации есть причина. Если спорят, это конфликт, и рекомендации нет.
- **Подтверждение группой** (импринт × релиз). Одной кнопкой пишутся строки `recommended` с первого месяца ISRC,
  без конца. ~1 000 ISRC в месяц — это 10–20 групп, а не 1 000 кликов. **Сама система ничего не применяет.**
- **Сигнал `imprintDisagrees`.** Строка месяца ведёт к лейблу, отличному от решения: как 17 «переездов». Он
  **блокирует** закрытие месяца, пока его не разберут. Действие в один клик: «закрыть и открыть X с месяца M».
- В payroll и на P1 видно, сколько денег ждёт в `label_unassigned`.

### 3.4 Миграция с нулевым изменением денег

1. Скрипт по образцу `derive-track-labels.ts` (dry run по умолчанию, идемпотентный):
   - **импринты** — из 34 строк, `suggested_label_id` — из нынешних алиасов;
   - **решения** — для каждого ISRC из серий месяцев с одинаковым лейблом.
   - Периоды **непрерывные**: первый открыт в прошлое, каждая серия кончается там, где начинается следующая,
     последняя открыта. Иначе разъедется реклама «ближайшего месяца».
   - Месяц со строкой без алиаса оставляет дыру. Сейчас таких 0.
   - `source = migrated`, `basis = 'alias "<строка>" на 2026-11-15'`.
2. Переключатель **`LABEL_SOURCE=strings|links`**, как `PUBLISHING_SOURCE` (D-189).
3. **Теневой прогон** по образцу `pubv2/shadow.ts`: `calculate()`, реклама, `reconcile()` и сигналы под обоими
   источниками должны совпасть байт в байт. Только после этого включаем `links`.
4. Ahh Music и прочие переразметки — **после** включения, отдельными решениями с даты (§6).

## 4. Почему не другие варианты

- **Гибрид «строка по умолчанию + поправка по ISRC»** — вы отвергли: правда остаётся за текстом Believe.
- **Решение на уровне строки с периодами** (≈ 50 строк вместо 21 тыс.) — запасной вариант, если подтверждения окажутся
  тяжелы. По сути это тот же гибрид.
- **Деньги по `owners.track_labels`** — невозможно: это ось книги, на 4 134 ISRC она расходится с лейблом.

## 5. Риски

1. **Хвост неназначенного.** Без группового подтверждения «наше» и доля саблейблов копятся в C. Групповое
   подтверждение входит в минимум.
2. **Тихое расхождение с Believe** — закрывается блокирующим `imprintDisagrees`.
3. **Задним числом.** Переразметка (Ahh Music, 77 Records) до уже сделанных выплат и срезов (D-198) пересчитывает
   историю. По умолчанию `valid_from` ≥ текущего открытого месяца; задним числом — только по явному слову владельца и с
   корректирующей операцией.
4. **Совместный импринт = два партнёра на одном треке.** Модель даёт одному ISRC один лейбл на месяц. Если долю лейбла
   надо делить между двумя партнёрами, нужны правила с несколькими получателями. Это отдельное, более крупное
   изменение.
