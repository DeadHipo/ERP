## D-001: ORM and database layer
- Date: 2026-10-31
- Question: which ORM, given an easy later migration to PostgreSQL, and one SQLite file per module.
- Decision: Drizzle ORM with `better-sqlite3`. Sequelize is rejected (weak TypeScript typing). Prisma is rejected for iteration 1 because it needs a separate schema and generated client per module database. Keep money as exact decimals or integer cents, dates as ISO text, queries behind repositories, so the move to PostgreSQL is a schema rewrite, not a logic rewrite.
- References: `README.md` section 3
- Status: accepted

- References: `аудит/аудит_итог.md`, `07_модуль_взаиморасчётов.md`

## D-009: Layout, module boundaries and their enforcement
- Date: 2026-10-31
- Question: how to keep the modules independent.
- Decision: the layout follows README §4.
  - Each module (`owners`, `splits`, `sources`, `settlements`, `publishing`) has `schema.ts` (Drizzle tables + portable DDL), `repository.ts` (all SQL), `service.ts` (rules) and `index.ts` (public interface: `open<Module>Module(file)`).
  - Each module opens its own SQLite file: `owners.sqlite`, `splits.sqlite`, `sources.sqlite`, `settlements.sqlite`, `publishing.sqlite` under the data directory.
  - Only `src/facade/` opens and composes modules. The API calls the facade, or one module service for single-module actions.
  - `tests/boundaries.test.ts` fails if a module imports another module, the facade or the API, if the API opens a database, or if the five files are not created.
  - ESLint `no-restricted-imports` repeats the rule.
  - The structure study of the `typereal` archives (extracted only to the scratchpad, nothing run) was used for conventions only: an error class hierarchy with a JSON envelope, `index.ts` as the module boundary, strict tsconfig.
- References: `README.md` §4; `src/facade/index.ts`; `tests/boundaries.test.ts`
- Status: accepted

## D-010: Money inside the modules: pico-USD integers for source amounts (refines D-002)
- Date: 2026-10-31
- Question: D-002 says source amounts are exact decimal strings. Summing millions of lines exactly in SQL is impossible with text.
- Decision:
  - Source amounts (Believe net and gross, B17 Total Payable) are stored as INTEGER pico-USD (1e-12) and parsed without rounding. A value with more than 12 significant decimals rejects the file.
  - SQL sums are read as BigInt (`safeIntegers`). The SQLite/PostgreSQL bigint limit is about $9.2M per single SUM; per-file and per-unit sums stay far below it.
  - Calculations use decimal.js (precision 40), never floats.
  - Settlement operations and payouts are integer cents.
  - JSON carries money as plain decimal strings: a custom `Decimal.toJSON` emits no exponent and no `-0`.
  - Rounding happens only when a payout is formed: rounded DOWN to cents, so we never overpay. The exact payable is kept in the snapshot.
- References: `src/shared/money.ts`; D-002
- Status: accepted

## D-011: Portability to PostgreSQL
- Date: 2026-10-31
- Question: SQLite now, PostgreSQL later.
- Decision:
  - Each module has a hand-written portable DDL (TEXT/INTEGER, ISO text dates, plain and unique indexes, `ON CONFLICT`) applied on open, next to Drizzle table definitions used for typed queries. drizzle-kit migrations are postponed.
  - Aggregates that need BigInt use raw prepared statements inside the module repository.
  - The "attributes per pair" query uses `MAX()` instead of a bare column.
  - Known gap: the split overlap check is check-then-insert; this is safe in one process, and PostgreSQL will need an exclusion constraint or SERIALIZABLE.
- References: `src/shared/db.ts`, `src/modules/*/schema.ts`
- Status: accepted

## D-012: One consistent read per calculation ("data version", 09 principle 17)
- Date: 2026-10-31
- Question: how the facade fixes the data version for one request.
- Decision:
  - better-sqlite3 is synchronous and runs in one process. `calculate()` reads every module once at its start, with no awaits in between, so no write can interleave.
  - Uploads keep their write transaction open across awaits. They are serialized per module (D-034), and readers only see files with status `loaded`.
  - No caches: every request recalculates from scratch.
- References: `src/facade/calculation.ts`
- Status: accepted

## D-016: Document status
- Date: 2026-10-31
- Question: the statuses "not attached / not approved / approved" and the "requires manager approval" flag.
- Decision:
  - No file reference → `not_attached`.

## D-020: Merge rules
- Date: 2026-10-31
- Question: what moves on a merge, its direction, chains.
- Decision:
  - Owners: only an owner without approved documents merges, and only into a confirmed live owner. Both must be live records, so there are no chains or cycles.
  - The merge moves artists, aliases, documents and contracts. It sets `merged_into` and logs the merge in the `merges` table.
  - The facade then moves the publishing writer mappings (resolution `merged`) and settlement operations to the survivor.
  - A merge is refused while the merged owner has a payout without payment proof.
  - Artists: both must be live and have the same owner (or `from` has none). Track links and contract links move.
  - References to merged ids are resolved through `merged_into`. Merged records cannot receive new artists, documents or contracts.
  - There is no undo yet (02, open).
- References: 02 «Объединение записей»; M12
- Status: accepted

## D-025: Split periods: report date, exclusive end
- Date: 2026-10-31
- Question: the date semantics of splits.
- Decision:

## D-026: Split change semantics
- Date: 2026-10-31
- Question: changes in the middle of history and on a split's first day.
- Decision:
  - A change needs a document of kind appendix, contract or buyout.
  - The split in force at `from` is closed at `from`, and the new split lasts until that split's old end. If no split is in force, it lasts until the next existing split.
  - A split replaced from its first day remains as an empty period `[from, from)`, so history is kept (review finding).
  - Who closed a split is not recorded separately; the new split carries the document.
- References: 04 rules 6, 8, 10
- Status: accepted

## D-027: Buyout
- Date: 2026-10-31
- Question: a buyout across several periods.
- Decision:
  - The seller's share becomes 0 from the effective date, in the split in force and in every later split where the seller has a share.
  - The document must be of kind `buyout`.
  - The buyout payment is not an operation.
  - Partial buyouts from the old registry (`seller_pct` < 100) are imported as a reduction of the seller's share by that many points, as the old engine did. This is a split change confirmed by the buyout document.
- References: 04 rule 10; 07 question 1
- Status: accepted

- Date: 2026-10-31

## D-032: Line key, summing, control check
- Date: 2026-10-31
- Question: implementation of 06 decisions 2 and 11.
- Decision:
  - The key is account, reporting month, sales month, platform, country, ISRC, UPC, currency, subscription type, sales type, release type.
  - Lines with the same key are summed in SQL (`ON CONFLICT DO UPDATE`): quantity, gross, net.
  - The control check is "key sums = stream sums and the line count"; a failure rejects the whole file atomically.
  - Names (artist, label, titles, catalogue number) are stored as deduplicated attribute sets.
  - Unit price, mechanical fee and client share rate are not stored, because they vary per line and are not in the totals; the original file is kept as is.
  - When lines merge, the first attribute set is kept (not the longest title).
- References: 06 decisions 1, 2, 11; 03 item 2
- Status: accepted (stored values: needs owner review)

## D-033: Duplicates and the original file
- Date: 2026-10-31
- Question: a second file for the same period.
- Decision:

## D-034: Upload robustness
- Date: 2026-10-31
- Question: issues from the sources review.
- Decision:
  - Uploads are streamed by busboy to a temporary file. A cut-off upload over the 2 GB limit is an error, and the temporary file is removed on any failure.
  - Loads are serialized per module through a promise queue, so two uploads never share a transaction.
  - A `loading` row left by a crash is removed when the module opens.
  - The insert race on the scope index maps to `duplicate_period`.
  - The CSV parser is strict:
    - invalid UTF-8 is an error;
    - a field longer than 64 KB (an unclosed quote) is an error;
    - header columns are matched after trimming and case-insensitively, and duplicated header columns are an error.
  - An empty currency is taken as USD with a warning; any other currency rejects the file.
- References: sources review
- Status: accepted

## D-039: B17 format

## D-040: xlsx reading and number precision
- Date: 2026-10-31
- Question: streaming and float cells.
- Decision:
  - Uploads are streamed to disk, and the statement is read with the exceljs streaming reader.
  - If the archive has `workbook.xml` after the sheets (files written by exceljs), that reader fails; the statement is then read in memory. Statements are a few MB.
  - Numeric and formula cells are doubles. They keep 15 significant digits and are then cut to 12 decimals; text with `$` or `,`, or an Excel error, rejects the file.

## D-042: Writer → owner resolution
- Date: 2026-10-31
- Question: implementation of 08 decisions 4, 7 and question 10.
- Decision:
  - An exact normalized alias (or IPI) of exactly one person-owner → `matched`.
  - Else a similar person-owner (same words) or several candidates → `ambiguous`. The whole payable stays in C `writer_unmapped` until the operator maps it: `POST /api/publishing/writers/:norm/map` with an owner or `createNew`.
  - Else a new person-owner without documents is created (origin `publishing`) and accrued to; its money is C.
  - Label owners are never candidates, and terms for a label are refused.
  - IPI is not in B17 statements, so it is not stored from them.
- References: 08 decisions 4, 7; questions 9, 10
- Status: accepted

## D-049: Recoupment rules
- Date: 2026-10-31
- Question: open questions 07/6, 07/7 and the scope details.
- Decision:
  - **Order:** positions are recouped largest first by position amount, then by date. Within a position, income is taken oldest report month first.
  - **Master income:** recoups only positions of the same artist.
  - **Publishing income:** the owner's publishing recoups positions of any of the owner's artists whose scope includes publishing.
  - **Scopes:** `any`, `master`, `publishing`, `master_publishing`, `isrcs`, plus `excludeIsrcs` (ISRCs normalized). Releases (UPC) as a scope unit are not supported (07 question 9).
  - **Advances:** recouped from income whose report month is on or after the month of the advance date. The same month counts.
  - **Deductions:** no date restriction (they reduce what is payable). Review finding: the "after the date" rule is written for advances.
  - **Netting:** income is netted per artist + ISRC + report month (publishing: per report month) before recoupment, so negative lines cannot make an out-of-scope position eat other income.
  - **Unrecouped rest:** it stays and never reduces other income.
- References: 07 «Охват погашения»; settlements review
- Status: accepted (07/6 "largest" = position amount: needs owner review)

## D-094: Recoupment: negative lines use up the income they cancel
- Date: 2026-10-31
- Question: the settlements review (final round) found that two positions with overlapping scopes could recoup more than the net income.
  - A position counted the negative lines in its scope to cap itself, but it consumed only positive lines.
  - The negatives stayed, so the next position took the same positive income again.
  - Example: income A +100, A −100 and owner publishing +100. An "any" advance of 100 and a publishing advance of 50 recouped 150 from a net income of 100.
- Decision: before a position recoups, the negative and positive lines in its scope are netted, and both are used up by min(negatives, positives). The position then takes the rest. The total recouped can no longer exceed the net income in the union of scopes.
- Test: `tests/recoup.test.ts`, "positions with overlapping scopes never recoup more than the net income in total".
