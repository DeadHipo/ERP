# ADR-001: Владение треком

Статус: принято, 2026-10-29

## Контекст

Нужно определить, кому принадлежит трек и кому идут отчисления. Один и тот же человек (псевдоним) может получать деньги по разным трекам разным получателям. Участвовать в треке могут несколько артистов, а также MC (голос или семпл без статуса feat), у которых есть доля.

## Решение

- Цепочка **Владелец → Артист → Трек**. У трека свой сгенерированный id; естественный ключ — пара **ISRC + UPC**.
- Артист принадлежит ровно одному владельцу. Если нужны два получателя для одного псевдонима, заводятся **две записи артиста**.
- Трек и артист связаны «многие ко многим».
- MC — обычный артист со своим владельцем, отдельной модели нет.
- Один ISRC в разных релизах (сингл и не-сингл) даёт разные записи с разными UPC. Дубль ISRC + UPC недопустим.
- Договор заключается с владельцем-лейблом и подтверждает человека и его псевдонимы.
- Роли на связи трек–артист пока нет. 2026-10-30 возникла гипотеза, что роль (`owner` / `feat` / `mc`) нужна модулю сплитов; не решено, см. [99_открытые_вопросы.md](../99_открытые_вопросы.md).
- Выплаты считаются по ISRC: релиз для них не важен (2026-10-30).

## Почему

- Две записи артиста вместо истории владения по датам: просто и однозначно, отчисления считаются по владельцу артиста.
- MC как артист: одна сущность вместо двух с одинаковым поведением (владелец, выплаты, сплиты).
- Пара ISRC + UPC как естественный ключ: именно так строки приходят в отчётах (Believe), поэтому их можно сопоставлять без догадок. Внутренний id нужен, потому что до выгрузки ISRC и UPC ещё нет.

## Альтернативы

- Артист с несколькими владельцами и историей по датам — отвергнуто как избыточное.
- Отдельная модель MC — отвергнута, поведение совпадает с артистом.

## Последствия

- Дубли «одинаковых» артистов — штатная ситуация, различаются владельцем. Для отображения нужен составной ключ «псевдоним + владелец».
- Релиз перестал быть чисто «необязательным»: UPC входит в ключ трека. Проверить на реальных отчётах Believe (см. открытые вопросы).
