# Срезы: план реализации (D-198, черновик)

Коротко для владельца — в `README.md` рядом. Здесь — что появится в базе, в коде и в API, и в каком порядке.

## 0. Идея в одном абзаце

Срез — это **состояние книги лейбла на момент**: всё, что было до него, накопительно. «После» не хранится, это
«всё минус срез». У среза есть название, дата и граница по каждому источнику. К срезу можно отнести операцию
(выплату, корректировку, перенос) с любой датой — так оператор сводит позиции на срезе в ноль. Общий payable,
`calculate()` и слои не меняются: срез — это вид на те же данные плюс привязка операций.

Не делаем (сознательно): статусов «открыт / закрыт», снимков, срезов организации, блокировки выплат, прав для
менеджера, каталожных срезов, замены нынешнего старта (D-174 живёт как есть).

## 1. База (одна миграция `0031_cuts.sql`)

```sql
CREATE TABLE settlements.cuts (
    id               text PRIMARY KEY,
    org_id           text NOT NULL,
    label_id         text NOT NULL,         -- срез принадлежит книге лейбла
    name             text NOT NULL,         -- «До ERP», «2026»
    cut_date         date NOT NULL,         -- момент среза; операции с датой ≤ cut_date входят
    -- границы данных: первое число первого месяца, который уже НЕ внутри (как valid_to, D-025)
    master_to        date NOT NULL,         -- Believe: отчётные месяцы < master_to
    publishing_to    date NOT NULL,         -- публишинг: месяцы отчёта < publishing_to
    ads_to           date NOT NULL,         -- реклама: месяцы < ads_to
    comment          text NOT NULL DEFAULT '',
    created_at       timestamptz NOT NULL,
    created_by       text NOT NULL,
    CHECK (extract(day FROM master_to) = 1 AND extract(day FROM publishing_to) = 1 AND extract(day FROM ads_to) = 1)
);
CREATE UNIQUE INDEX cuts_name ON settlements.cuts (org_id, label_id, name);
CREATE INDEX cuts_label ON settlements.cuts (org_id, label_id, cut_date);

ALTER TABLE settlements.operations ADD COLUMN cut_id text;   -- «отнесена к срезу», без внешнего ключа (D-121)
CREATE INDEX operations_cut ON settlements.operations (org_id, cut_id) WHERE cut_id IS NOT NULL;
```

Всё. Новых видов операций нет (список из девяти, D-173, не трогаем).

**Границы по умолчанию** (считает сервис при создании, оператор правит): период данных входит, если **закончился
до** `cut_date`, то есть граница = первое число месяца `cut_date`. Для 15.10.2026: `master_to = 2026-10-01`
(сентябрь внутри), `publishing_to = 2026-10-01` (Q3 внутри, Q4 после), `ads_to = master_to`. Если кабинет видел
Believe только по август — оператор ставит `master_to = 2026-09-01`. Граница всегда первое число (правило M52):
API округляет любую дату вниз до первого числа месяца.

**Правила записи** (сервис, не CHECK):
- срезы одного лейбла накопительны: если `cut_date` A < B, то каждая граница A ≤ границы B (`409 cut_order`);
- удалить можно только срез без привязанных операций (`409 cut_in_use`); название и границы правятся всегда;
- `operations.cut_id` — только срез того же лейбла, что и операция (`409 cut_label_mismatch`).

## 2. Какая операция входит в срез C

```
если cut_id задан:  входит, когда cut_date её среза ≤ C.cut_date   (отнесённая — по своему срезу)
иначе:              входит, когда date ≤ C.cut_date
```

Так выплата, сделанная в ноябре и отнесённая к срезу 15.10, входит в него и во все следующие; обычная ноябрьская —
только в следующие.

## 3. Состояние среза (код)

`facade/as-of.ts` сейчас режет все входы одним месяцем `asOf`. Добавляем рядом одну функцию с границами:

```ts
type CutBounds = { masterTo: string; publishingTo: string; adsTo: string; date: string;
                   cutDateOf: (cutId: string) => string | undefined };
cutCalculationBy(calc, b)   // units < masterTo, publishing < publishingTo, ads/adPositions < adsTo (по первому числу месяца)
cutOperationsBy(ops, b)     // правило §2
```

Нынешний `asOf` не трогаем: новые функции стоят рядом (меньше риска, чем переписывать старую).

Новый файл `facade/cuts.ts`:
- `listCuts(label)`, `createCut`, `updateCut`, `deleteCut` — тонко поверх репозитория settlements;
- `cutState(cutId)` — один `calculate()`, затем `ownerBalance` каждого владельца книги на границах среза; ответ —
  **позиции** (D-181: по псевдониму и собственная позиция владельца) этой книги с ненулевым сальдо, плюс итог;
- `cutsUnsettled(label)` — для сигналов: по каждому срезу число позиций с |сальдо| ≥ 0.01;
- `ownerCuts(ownerId, label?)` — для страницы владельца: по каждому срезу его книг (по дате) — сальдо позиций
  владельца на срезе, **операции, отнесённые к срезу**, и **движение между срезами** (заработано / выплачено /
  прочее от предыдущего среза до этого: разница двух состояний, без нового расчёта); последним разделом — «после
  последнего среза» (текущий баланс минус состояние последнего среза). Один `calculate()` на запрос.

Сальдо позиции на срезе = тот же `payable` позиции, что считает баланс (со стартом D-174, если он есть в книге —
это тот же баланс, отдельной логики нет). Ноль = |сальдо| < 1 цента.

**Перенос** («+X на срезе / −X после») — не новый вид, а две строки `adjustment` одним действием
`POST /settlements/cuts/:id/transfer { ownerId, artistId|null, amount, documentId, date }`:
строка 1 с `cut_id = :id`, сумма гасит сальдо на срезе; строка 2 без `cut_id`, с датой после среза, обратный знак;
обе ссылаются друг на друга через `external_ref = 'cut-transfer:<uuid>'`. Документ обязателен, как у любой
корректировки (D-173). Деактивация одной деактивирует пару.

Ни один слой, `calculation.ts`, `owner-scope.ts`, `payout-gate.ts` не меняются; `boundaries.test.ts` получает
`cuts.ts` в список модулей, которые `calculate()` не читает.

## 4. API (всё `org_admin`, кроме списка: менеджер видит срезы своих лейблов — там нет денег)

| Операция | Что |
|---|---|
| `GET /settlements/cuts?label=` | срезы лейбла с границами и числом незакрытых позиций |
| `POST /settlements/cuts` | создать (`label`, `name`, `cutDate`, границы — необязательно, иначе по умолчанию) |
| `PATCH /settlements/cuts/:id` | название, дата, границы, комментарий |
| `POST /settlements/cuts/:id/delete` | удалить, если пуст |
| `GET /settlements/cuts/:id/state` | позиции с сальдо на срезе (json / csv) |
| `POST /settlements/cuts/:id/transfer` | перенос парой корректировок |
| `GET /owners/:id/cuts?label=` | разделы владельца по срезам: сальдо, операции среза, движение между срезами |

Привязка обычной операции: поле `cutId` в существующих `POST /settlements/operations` и в кнопке выплаты
(`createPayout`), плюс `PATCH /settlements/operations/:id/cut { cutId | null }` для уже записанных.
Каждая новая операция — запись в `operations.ts` и строка `x` в `tests/helpers/manager-answers.ts`.

## 5. UI

- **Страница «Срезы»** (раздел взаиморасчётов): список срезов лейбла из переключателя, кнопка «Новый срез»
  (дата → границы подставились → можно поправить).
- **Страница среза**: таблица позиций с сальдо (владелец, псевдоним, сальдо), фильтр «только ненулевые»,
  действия в строке: «Выплатить на срез», «Корректировка на срез», «Перенести».
- **Страница владельца**: вкладка «Срезы» — по разделу на срез (по дате) и раздел «После последнего среза».
  В разделе: сальдо по нику на срезе (ноль — зелёный, не ноль — с действиями «Выплатить на срез» / «Корректировка»
  / «Перенести»), список операций, отнесённых к срезу (дата, вид, сумма, документ), и строка движения от прошлого
  среза: заработано, выплачено, реклама, прочее. В списке операций владельца — колонка «Срез».
- **Диалоги операций и выплаты**: необязательное поле «Отнести к срезу».
- **Сигнал** «Незакрытые на срезе: N» в сигналах лейбла, ведёт на страницу среза.

## 6. Этапы

1. **Модель и чтение.** Миграция, репозиторий, `cutCalculationBy` / `cutOperationsBy` (+ тест: старый `asOf`
   байт в байт), `cuts.ts`, `GET/POST/PATCH/delete` и `GET …/state`. Тест: мир с двумя месяцами и выплатой —
   сальдо на срезе = ручной счёт; срез не меняет `calculate()` и общий payable.
2. **Привязка и перенос.** `operations.cut_id`, поле в операциях и кнопке выплаты, `PATCH …/cut`, `transfer`.
   Тест: недоплата 120 → выплата в ноябре на срез → сальдо 0, общий payable уменьшился на 120 ровно один раз;
   перенос аванса −300 → на срезе 0, после −300, рекупмент будущим доходом как раньше.
3. **Сигнал и владелец**: «незакрытые на срезе», `GET /owners/:id/cuts` (тест: движение между срезами + сальдо
   прошлого среза = сальдо следующего).
4. **UI**: страницы «Срезы» и среза, вкладка «Срезы» у владельца, поле в диалогах, колонка «Срез» в операциях;
   e2e на сценарий «создать срез → выплатить на срез → ноль на странице владельца».

Каждый этап — по definition of done, D-запись (D-198 — модель и правила, следующие — по этапам) и коммит.

## 7. Открытые мелочи (решаем по ходу, по умолчанию — как написано)

- Деление квартала: квартал внутри, если его последний месяц < `publishing_to`; Q3 внутри при `2026-10-01`,
  Q4 при срезе 15.10 — после. Граница посреди квартала (`2026-11-01`) относит квартал по его последнему месяцу.
- Реклама по умолчанию идёт за Believe; отдельная граница нужна редко, но поле есть, чтобы не мигрировать потом.
- Владелец с позициями в двух лейблах видит на каждом срезе только позиции его книги.
