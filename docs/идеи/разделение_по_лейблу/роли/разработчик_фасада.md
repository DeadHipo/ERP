## 0. Что уже есть в данных и коде (факты, на которых стоит всё ниже)

- **Граница лейбла есть только у юнита Believe.** Ключ юнита = файл + ISRC + UPC + отчётный месяц + месяц продаж + строка лейбла (`label_name`, D-124). Слой `label-of-record` превращает строку в `ourLabelId` через алиасы (`labels.index().labelOf(string, date)`); алиасы **не датированы**, датированы только правила саблейблов, поэтому «строка → own-лейбл» — чистая функция строки. Значит, фильтр по `label_name IN {строки лейбла и его саблейблов}` в ClickHouse даёт **ровно** множество юнитов с `ourLabelId = L`. Несопоставленная строка (`label_unmapped`) не принадлежит никому; сейчас таких юнитов 0.
- **Реальные объёмы** (ClickHouse `believe.units`, 721 975 юнитов из 75,7 млн строк): строка `0to8` — 419 457 юнитов, 8 507 ISRC, net 14,80 млн; `Echo8` — 281 776 юнитов, 10 173 ISRC, net 1,26 млн; строки саблейблов — от 9 524 (`qaraqshy records`) до 1; строки «0to8/Echo8» (194 юнита, 6 025,57) и «0to8, Echo8» (2) — алиасы 0to8 по словарю, т. е. переключатель идёт за словарём, а не за текстом строки. Ни одного ISRC под обоими own-лейблами, но 357 владельцев из 1 011 (35 %) и 358 псевдонимов из 2 011 имеют ISRC под обоими.
- **Где лейбла нет**: B17 (2,50 млн получено, строки без лейбла; файлы называются `0to8_*_Publishing_Statement.xlsx`), операции (2 663, ни одной с лейблом), выплаты и снимки (`total`, `perArtist`, `positions`, `ads`, `files` — поля `byLabel` в снимке нет), документы, владельцы, псевдонимы, писатели. Реклама лейбл **выводит** из строки ISRC (`AdResult.ourLabelId`), `GET /ads/summary` уже по месяцу и лейблу.
- **Что уже разрезано по лейблу в ответах**: `Reconciliation.ourShareByLabel` (overview/reconciliation), `OwnerBalance.byLabel` и `ArtistMoney.byLabel` (earned/waiting мастера по лейблу записи, D-130), `UnitResult.ourLabelName` в `trackMoney.months` / `explain`, `AdSummaryRow.label`. Пример владельца `733f5fb6…`: earned 4 198,19 = 0to8 3 717,40 + Echo8 480,79; waiting 1 896,20 = Echo8 1 891,93 + 0to8 4,27; adsCharged 1 667,08, paid 1 725,55, payable 805,56 — последние три без лейбла.
- **Механика сужения уже есть**: `scoped(modules, SnapshotFilter)` подменяет `sources.snapshot()`; `columnar.units()` собирает `WHERE file_id IN … AND isrc IN … AND upc IN … AND месяц`; есть `labelStrings(fileIds)` и `isrcsOfLabelStrings(fileIds, strings)`, `isrcsOfLabelAliases` нормализует строки в JS через `normalizeLabelString`. Один путь (D-164): никаких режимов, тест `scope.test.ts` получает «полный» ответ, патча **собственные** чтения теста (`withFullReads`), а не фасад.
- **Времена** (idle, dev-база): полное чтение юнитов из ClickHouse 0,85–0,91 с; то же с `label_name IN ('Echo8', …4 строки)` 0,40–0,42 с (282 тыс. юнитов); через `isrc IN (подзапрос 9 441 ISRC 0to8)` 0,63 с. API: `GET /overview` 9,9 с, `GET /owners/:id/balance` примера 0,63 с, `GET /tracks/summary?account=1055956` 5,3 с, `GET /ads/summary` 0,67 с.

## 1. Эскиз варианта A: лейбл как обязательный фильтр представления на бэкенде

### 1.1. Где лейбл входит в scope

Естественная точка — `UnitScope`/`SnapshotFilter`, потому что это единственное место, где фасад сужает юниты, а лейбл — свойство юнита.

- `SnapshotFilter` (sources) получает поле `labelStrings?: string[]` → `columnar.units()` добавляет `label_name IN {labels:Array(String)}` (пустой список = ни одного юнита, как у `isrcs`). Это ровно тот предикат, что уже есть в `isrcsOfLabelStrings`.
- Фасад не передаёт id лейбла в модуль sources (модуль не знает лейблов, D-009). Новый чистый помощник `facade/label-scope.ts`: `labelScope(labels, sources, labelId) → { labelStrings }`: берёт `labels.listLabels()`, собирает алиасы own-лейбла и всех саблейблов с `ownLabelId = labelId`, нормализует, пересекает с `columnar.labelStrings(loadedFileIds)` по `normalizeLabelString` (как `isrcsOfLabelAliases`) и отдаёт **сырые** строки. Это один SELECT DISTINCT по проекции (миллисекунды) и один список из ~25 строк.
- Почему строки, а не список ISRC: (а) фильтр по строке точно равен `ourLabelId`, а список ISRC — равен только пока ни один ISRC не живёт под двумя лейблами (сегодня 0, но ключ юнита это допускает: `scope.test` `G38` «строка решает по месяцам»); (б) 9–11 тыс. ISRC в `IN` — это ~150 КБ параметров на каждый вызов, 0,63 с против 0,40 с; (в) для охвата владельца всё равно нужен список ISRC, и обе условия просто складываются в один `WHERE` (охват ∩ лейбл = `isrc IN … AND label_name IN …`), ничего пересекать в JS не надо.
- `scoped()` остаётся как есть: `labelStrings` — ещё одно поле фильтра, которое оно уже проливает в `snapshot()`. `calculate()` не меняется (D-161).

### 1.2. Какие методы фасада могут принять лейбл и как

Правило точности D-161 переносится дословно: аллокация юнита зависит от юнита и справочных данных его ISRC, поэтому любой ответ, который является **суммой по юнитам**, под лейблом равен полному ответу, ограниченному юнитами этого лейбла.

| Метод | Под лейблом | Примечание |
|---|---|---|
| `reconciliation`, `overview` (Believe-строки) | `calculate(scoped(modules, { labelStrings }))` | строки `believe|account|month` считаются только по юнитам лейбла; `ourShareByLabel` вырождается в один ключ; `fileTotal`/`fileDiscrepancy` **теряют смысл** (итог файла — по всем строкам файла) → под лейблом `null`; `negativeRemainders` — счётчик по юнитам, корректен |
| `queue(reason, period)` | `periodScope(f)` + `labelStrings` | `cItems` по юнитам → группы точные; B17-элементы (`writer_unmapped`, `publishing_terms_unconfirmed`, `owner_unconfirmed` паблишинга) без лейбла |
| `signals` | то же | точные: `unallocated`, `isrcsWithoutSplit`, `unfunded`, `labelUnmapped` (под лейблом всегда пусто!), `sublabelWithoutRule`, `ruleRecipientIsRow`, `twoRowsOneOwner`, `assumptions` (мастер). Не по юнитам: `ambiguousWriters`, `tracksWithNote`, `participantsWithoutOwner` (у него `amount` из `byRule` — по юнитам, а список — по участиям) |
| `trackSummary` | `labelStrings` в `calcScoped` + фильтр ISRC справа | `tracks`/`splits` без лейбла; набор ISRC ответа = ISRC юнитов лейбла ∪ зарегистрированные треки — вторую половину надо резать по `pairAttributes().labelName` → лейбл через `labels.index().labelOf` |
| `trackCatalog`, `releases` | без расчёта | `pairNames`/`netByUpc` получают тот же `labelStrings`; трек без юнитов (зарегистрирован, денег нет) — ни под каким лейблом → только в «все лейблы» |
| `release(upc)`, `trackMoney`, `explainTrack` | `{ upcs|isrcs, labelStrings }` | у одного ISRC сегодня один лейбл; смысл фильтра — спрятать чужой, а не изменить цифры |
| `ownerBalance`, `ownerPayables({ids})`, `createPayout` | `{ isrcs: reach.isrcs, labelStrings }` (охват ∩ лейбл) | см. 1.4: точны только `byLabel[L]`, `period.*` мастера, `artists[].tracks`; `total.recouped/paid/adsCharged/payable` **не определены** под лейблом |
| `artistBalance`, `artistBalances({ids})` | то же через `artistReach` | то же ограничение |
| `listAds`, `getAd`, `adsSummary` | `labelStrings` к `isrcsOf(records)` | `AdResult.ourLabelId` уже есть; под лейблом фильтр по нему в JS; `allocateAd` смотрит `labelStringOf(isrc, month)` «ближайший месяц» — если сузить юниты строками лейбла, у ISRC другого лейбла месяцев не будет и запись получит `ourLabelId = null`; поэтому для ads фильтр надо применять **к результату**, а не к чтению |
| `search` | только `kinds=labels,tracks` | владельцы/псевдонимы/документы лейбла не имеют |
| `documentUses` | часть `waiting` по юнитам — точна | `splits/participations/labelRules/contracts/operations` — без лейбла |

**Не могут** принять лейбл (возвращают то же, что и без него, и это надо честно задокументировать в `operations.ts`): всё о B17 (`/publishing/*`, B17-строки сверки и очереди), `/settlements/operations`, выплаты и снимки, документы, владельцы и псевдонимы как справочники, аудит. Вариант «считать паблишинг лейблом 0to8» (по имени файлов) — решение владельца продукта, не разработчика (⚠).

### 1.3. Правило «один путь» (D-164) и тест

Фильтр по лейблу — такое же поле `SnapshotFilter`, как `isrcs`; `withFullReads` в `scope.test.ts` уже заставляет `service.snapshot()` игнорировать **любой** фильтр, так что существующая схема «scoped = full» переносится без режима в фасаде. Но утверждение для лейбла другое — не равенство, а **разбиение**:

> Для каждого метода-суммы по юнитам: ответ без лейбла = ⊕ ответов под каждым own-лейблом ⊕ ответ «несопоставленные» (строки без алиаса), где ⊕ — поэлементное сложение сумм по ключу строки (source|account|month; reason|key; isrc).

Где выполняется точно (сложение `Decimal` с 12 знаками ассоциативно, никаких округлений на уровне сумм): `A_received`, `B_notOurs`, `C_waiting`, `C_breakdown`, `ourShare`, `ourShareNoSplit`, `discrepancy` строк Believe; суммы групп очереди и `summary`; `sumUnits` трек-саммари и релиза; `byLabel[L].earned/waiting` баланса; `adSummary` по лейблу (уже разбиение); `adsCharged` — тоже разбивается по `ourLabelId` записи.

Где **не** выполняется и тест должен это фиксировать, а не обходить: `total.recouped` (позиция со scope `any` поглощает доход обоих лейблов в порядке `recoup.ts`, «рекуп под Echo8» не определён), `total.paid`, `returns`, `credits`, `payable`, `payableShown`, `payout.amountCents`, `positions[].recouped`, `artists[].recouped/unrecouped/recoupedFromMaster`, `publishing*`, `pendingOperations`, `blockingPayouts`, B17-строки сверки/очереди. Тест-формулировка: под лейблом эти поля **равны полным** (фасад их не сужает), а `byLabel` содержит один ключ. Если вместо этого отдавать `null` — ломается `balanceSchema` и R4 (кнопка выплаты решается гейтом из ответа).

Нужен golden-кейс с двумя лейблами на одном владельце: фикстура `newFacade` уже сеет own-лейблы 0to8 (`Test Label`, `0to8`) и Echo8; e2e-сценарий `overview-release.ts` (G40) грузит строки `Echo8`. Добавить к `scope.test.ts` четвёртый `describe`: два ISRC одного псевдонима под разными строками, аванс `any`, одна выплата — и проверить разбиение earned/waiting и **неразбиение** recoup/paid.

### 1.4. `createPayout` под лейблом — что платить

D-051: кнопка платит **весь** payable одной суммой; операция без лейбла; снимок — расчёт, которым кнопка пользовалась (D-053). Под лейблом возможны три поведения:

1. **Лейбл не влияет** (рекомендация): `createPayout` всегда считает по полному охвату владельца, `X-Label` игнорируется; в снимок добавляется `byLabel` (уже в `balance`, одна строка в `payouts.ts`), чтобы потом отчитаться «из выплаты N — Echo8 M». Контракт и гейт не меняются.
2. **Отказ**: при лейбле и `byLabel` с двумя ключами → 422 `label_scoped_payout`. Защищает от «я думал, плачу только за Echo8», но кнопка в интерфейсе под лейблом будет отказывать 35 % владельцев.
3. **Частичная выплата по лейблу**: операция получает `label_id`, `payable_L = byLabel[L].earned − recouped_L − paid_L − ads_L`. Требует определить `recouped_L` (позиции со scope `any` надо распределять между лейблами — новое правило рекупа), `paid_L` (у 2 400 старых выплат лейбла нет → миграция «по платящему лейблу» невозможна, только «не распределено»), это отмена «один баланс на владельца» (D-123, допущение совета) — вопрос владельца продукта (⚠), оценка от 5 дней и новая миграция settlements.

Охват: `ownerReach` даёт ISRC; «охват ∩ лейбл» = оба условия в `WHERE`. Расширять `ownerReach` не нужно (лейбл — не новый путь денег к псевдониму), но `check-owner-scope.ts` стоит дополнить режимом «Σ byLabel = earned мастера» по всем 1 151 владельцам — это дешёвый инвариант на реальных данных.

## 2. Эскиз варианта D: разрез по лейблу везде, где есть деньги

Технически D — это тот же `labelStrings` в `SnapshotFilter`, но **необязательный** и применяемый там, где у списка есть фильтр, плюс колонка/ключ `byLabel` в ответах. Что уже есть и что добавить:

| Ответ | Есть | Добавить |
|---|---|---|
| `reconciliation`/`overview` | `ourShareByLabel` | `byLabel: { A, B, C }` на строку Believe (`reconcile()` — ещё один `Map` по `u.ourLabelName`); `overviewTotals.byLabel` для KPI |
| `balance` (P10), `artistBalance` (P12) | `byLabel` earned/waiting | `adsChargedByLabel` (из `AdPosition` через `ourLabelId` записи — поле надо пронести в `AdPosition`); `tracks[].label` |
| `payables` (P9) | — | `byLabel` на строку (из того же `ownerBalance`, нулевая стоимость) → две колонки «заработано 0to8 / Echo8» |
| `artistBalances` (P11) | — | то же `byLabel` из `artistBalance` |
| `queue` группы | — | `byLabel` на группу (ключ `it.unit?.ourLabelName`) и/или query-фильтр `labelId` рядом с `account` в `queueQuery`; `summary` по лейблу для полоски P2 |
| `signals` | `labelUnmapped` | `ourLabelName` в строках `unfunded`, `isrcsWithoutSplit`, `sublabelWithoutRule`, `assumptions` |
| `trackSummary`/`trackCatalog` | — | у ISRC один лейбл (сегодня), но ключ допускает два → поле `labels: string[]` (из юнитов или `pairAttributes.labelName`); колонка в P5 и фильтр `labelId` рядом с `account` |
| `releases`/`release` | — | `labels: string[]` на UPC (из `pairNames`), фильтр `labelId` |
| `trackMoney`/`explain` | `ourLabelName` в месяцах | ничего |
| `adsSummary`/`listAds` | по лейблу; `allocation.ourLabelName` | фильтр `labelId` в `AdsQuery` (по результату) |

Фильтр `labelId` — обычный query-параметр списков: `labelQuery = z.object({ labelId: z.string().optional() })`, подмешивается в `periodQuery`-потребителей (`overview`, `reconciliation`, `queue`, `signals`, `tracks/summary`, `tracks/catalog`, `releases`, `ads`, `ads/summary`). Фасад превращает `labelId` в `labelStrings` одним помощником; неизвестный id → 404 `Label`. Для балансов и выплат параметр **не вводится**: там разрез уже отдан полем `byLabel`, а «payable под лейблом» не существует (раздел 1.3).

## 3. Эскиз варианта C: query-параметр + переключатель в шапке, без заголовка

Технически C = D плюс глобальный переключатель на фронте, который подставляет `labelId` во все денежные вызовы. Отличия от A:

- **Контракт (D-119).** Параметр живёт в `S.*Query` каждой операции → попадает в OpenAPI, `api-contract.test.ts` требует вызвать операцию в сценарии и парсит ответ схемой; значит, вариант «с лейблом» тестируется тем же сценарием (один дополнительный вызов на операцию). Заголовок `X-Label` описывается в `operations.ts` только полем `headers` (как `X-Operator`), контракт-тест его не проверяет и не вызывает, а поведение «тот же путь, другой ответ» в OpenAPI невидимо. Для заголовка пришлось бы расширять `api-contract.test.ts` отдельным проходом с заголовком.
- **Кэш TanStack.** Ключи `[domain, name, ...params]`; у `ownerQueries.balance(id, period)` период уже в ключе. Если лейбл — параметр query-объекта, он автоматически попадает в ключ (`payables(period)`, `balance(id, period)`), ничего в `MONEY_KEYS` менять не надо. При заголовке лейбл в ключах отсутствует: переключение лейбла при `staleTime: 0` отдаст старые данные из кэша и перезапросит — экран на секунды покажет цифры другого лейбла (money-страницы по 5–10 с). Пришлось бы вручную добавлять `label` во все `*Keys` или делать `invalidateMoney` при переключении — это второй механизм рядом с первым.
- **Shareable URL.** Параметр естественно живёт в URL страниц, у которых фильтры уже в URL (P1 период, P2, P5 `account&month`, P9, P11, P22): ссылка «очередь под Echo8» передаётся коллеге. Заголовок из `localStorage` (как `erp.operator`) ссылку не несёт, и два человека, открыв один URL, увидят разное.
- **Минусы C**: «всегда подставлять» нужно дисциплинированно — каждый `queryFn` денежной страницы должен читать лейбл из стора; забытая страница покажет «все лейблы» без предупреждения. Лечится одним помощником `withLabel(query)` в `api/queries/core.ts` и guard-тестом «каждый `MONEY_KEYS`-запрос вызывает `withLabel`» (как `coverage.test.ts`).

## 4. `X-Label` и `X-Operator`

Хук `operatorTrace` работает только на записях (`POST/PATCH/PUT/DELETE`): читает `x-operator`, 400 `operator_required`, после 2xx пишет `audit.actions(operator, method, route, entity_ids, summary)`. Как он мог бы работать с лейблом:

- **Чтение**: `labelOf(req)` из `x-label`; проверка, что это id own-лейбла, требует `facade.modules.labels.getLabel` — асинхронный вызов **до** `next()`, т. е. хук становится async-middleware (сегодня он синхронный до момента `res.json`). Неизвестный id → 400 `label_unknown`.
- **Запись**: либо колонка `label_id text null` в `audit.actions` (миграция `0014_audit_label.sql` + `schema.ts`, индекс не нужен), либо `summary.label` в jsonb без миграции. Колонка честнее: по ней фильтруется история (`GET /audit?labelId=`), jsonb — для «по дороге». `BODY_ID_FIELDS` уже содержит `labelId`, так что записи модуля labels и так тянут id лейбла в `entity_ids`.
- **Запросы без лейбла**: 400 `label_required` на всех записях невозможен — у документов, владельцев, псевдонимов, писателей, операций, выплат лейбла нет, а это большинство записей (в dev-аудите: `/documents`, `/documents/:id/approve`, `/settlements/operations*`, `/splits/:id/confirm` — все без лейбла). Остаются два честных варианта: (а) заголовок **необязателен**, записывается, когда есть (тогда «обязательный фильтр представления» на бэкенде не обязателен по факту); (б) обязателен только для перечня операций, где лейбл у действия есть (правила саблейблов, алиасы) — но у них `labelId` уже в params. Для GET заголовок без 400 означает «все лейблы» — тот самый тихий режим из раздела 6.
- Вывод: у записей лейбл — свойство **сущности** (`labelId` в params/body), а не сессии оператора; заголовок добавляет в аудит только «под каким переключателем оператор смотрел на экран», и это лучше класть в `summary` с фронта (если вообще нужно), не делая обязательным.

## 6. Риски

- **Точность 12 знаков.** Фильтр по юнитам точен по построению: аллокация юнита не зависит от других юнитов, суммы `Decimal` на фиксированных 12 знаках складываются без округлений, разбиение по `label_name` — разбиение множества юнитов. Неточно/не определено: `recouped` (позиция `any` ест доход обоих лейблов по порядку `recoup.ts`), `paid`, `returns`, `credits`, `payable`, B17. Их **нельзя** показывать под лейблом как «лейбловые» — только как «всего по владельцу», с пометкой в UI. `fileDiscrepancy` под лейблом — `null`.
- **Производительность.** Проекция `units_by_label` отсортирована по ключу `GROUP BY` (file_id, isrc, upc, reporting_month, sales_month, label_name): `label_name` последний, `EXPLAIN` показывает `PrimaryKey … generic exclusion search, 172/172 гранул` — отсечения гранул нет, фильтр применяется после чтения. Но вся проекция — 172 гранулы (~722 тыс. агрегированных строк), полное чтение 0,85 с, с фильтром Echo8 0,40 с (меньше передать и распарсить). Дальше всё пропорционально числу юнитов (JS-аллокация 1,9 с на 722 тыс.): overview под Echo8 ≈ 0,4 × 9,9 с, под 0to8 ≈ 0,6 ×. Новой проекции не нужно; если когда-то понадобится отсечение — проекция с `label_name` первым ключом, но она дублирует данные ради 0,4 с.
- **Забытый лейбл.** С заголовком отсутствие = тихо «все лейблы» на каждом GET, без следа в URL и в контракт-тесте. С параметром отсутствие тоже «все лейблы», но это явное состояние переключателя и видно в URL; 400 при отсутствии невозможен ни там, ни там (половина операций лейбла не имеет).
- **Кэш TanStack без лейбла в ключе** — при заголовке единственная защита — ручное добавление `label` во все `*Keys`; при параметре ключ содержит его автоматически. Инвалидация `invalidateMoney` после записи и так трогает все денежные ключи.
- **Семантика словаря.** «0to8/Echo8» — алиас 0to8: под переключателем Echo8 эти 6 025,57 не видны. Это следствие D-123/D-131, а не бага; стоит написать в описании переключателя. Несопоставленные строки — ни под каким лейблом (сегодня 0 юнитов, но `label_unmapped` — живая причина C).
- **Паблишинг** — под лейблом исчезает из сверки и очереди; правило «B17 только в “все лейблы”» или «B17 = 0to8» — решение владельца (⚠).
- **Охват + лейбл для `createPayout`** — не трогать: любая «выплата под лейблом» — отмена D-051/D-123, отдельное решение с миграцией settlements.

## 7. Рекомендация

Делать D с необязательным `labelId` как query-параметром списков и денежных агрегатов (overview, reconciliation, queue, signals, tracks, releases, ads) и глобальным переключателем в шапке, который подставляет его и отражает в URL; балансы, список выплат и псевдонимы получают разрез `byLabel` в ответе, а не фильтр; `createPayout` и операции не меняются (снимок получает `byLabel` для отчётности). Механика — одно новое поле `labelStrings` в `SnapshotFilter` поверх существующего unit scope, без миграций, без режимов, с тестом-разбиением рядом с `scope.test.ts`. Заголовок `X-Label` не вводить: он невидим контракту и URL, не попадает в ключи кэша и не может быть обязательным, потому что у большинства записей лейбла нет; изоляция данных (B) противоречит D-012/D-121 (один снимок на расчёт, 35 % владельцев под обоими лейблами). Два вопроса оставить владельцу продукта: куда относить B17 под переключателем и нужна ли когда-нибудь выплата по лейблу (это отмена «одного баланса на владельца»).
