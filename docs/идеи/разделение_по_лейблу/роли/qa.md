# QA-отчёт: разделение админки по лейблу — инварианты, что ломается, какие тесты нужны

Сессия размышления 2026-11-05, код не менялся. Источники: `facade/{balance,payouts,payout-gate,ads,calculation,owner-scope,scope}.ts`, `layers/{label-of-record,recoup}.ts`, `modules/labels/service.ts`, `tests/{scope,golden,api-contract}.test.ts`, `scripts/{check-owner-scope.ts,e2e/seed.ts}`, `docs/agents/{12,19}`, D-051, D-053, D-123, D-125, D-127, D-130, D-157, D-161…D-167. Цифры — с dev-базы `erp` через GET API.

## 0. Что код уже гарантирует (и что нет)

- **Лейбл записи юнита не зависит от даты.** `labelOfRecord` берёт строку лейбла → алиас → лейбл; у алиаса нет периода, датирован только `label_rules` (сколько саблейблу). Значит множество юнитов лейбла L = юниты со строками из алиасов L и его саблейблов, и это множество **точно** вычисляется фильтром ClickHouse (`isrcsOfLabelStrings`), без расчёта. Это главное, что делает разрез по лейблу проверяемым.
- **Каждый юнит принадлежит ровно одному лейблу или никакому** (`ourLabelId` либо null → `label_unmapped`). На реальных данных: 20 685 ISRC, ни одного под обоими лейблами, 0 несопоставленных.
- **Аллокация юнита зависит только от юнита и справочных данных его ISRC** (D-161). Поэтому «расчёт по подмножеству юнитов = полный расчёт, ограниченный на подмножество» — доказано и запинено `tests/scope.test.ts` для ISRC/UPC/счёта/периода. Для лейбла — пока нет.
- **Чего код не гарантирует:** всё, что после аллокации. `recoup()` (scope `any` ест любой мастер-доход псевдонима в порядке месяцев), `paid` (операции без лейбла), `adsCharged` (лейбл выведен из строки лейбла ISRC в месяц расхода, `'?'` если строки нет) и publishing (B17 без лейбла) складываются в **один** `payable` владельца (D-130: «one balance per owner»). Ни одна из этих величин не определена по лейблу.

## 1. Инварианты и как их проверять

**И1. Σ по own-лейблам юнитов = полный расчёт (A, B, C, наше), по счёту и месяцу — точно.**
Сейчас `reconcile()` делит по лейблу только `ourShare` (`ourShareByLabel`); A, B, C по лейблу не делятся. Нужно: в строке reconciliation добавить `A_byLabel`, `B_byLabel`, `C_byLabel` (ключ `ourLabelName ?? '?'`), либо считать строку на уровне (счёт, месяц, лейбл). Поскольку у юнита один лейбл, сумма по лейблам тождественно равна строке — это чистая арифметика над pico-целыми, точность 12 знаков сохраняется без новых округлений (все суммы — сложения). Тест: (а) в `golden.test.ts`, в `c.verify()`, добавить проверку `Σ_label A_byLabel = A`, то же для B, C, ours и `A_L = B_L + C_L + ours_L` для каждого L; (б) в `scope.test.ts` — новая строка в списке `calls`: `reconciliation({label})` / `trackSummary({label})` читают только юниты лейбла (spy: `filter.labelStrings`/`isrcs` и число юнитов) и дают байт-в-байт полный ответ, ограниченный на лейбл (через `withFullReads`). Данные для теста есть: `world()` в scope.test уже загружает 0to8, Sub One и ACC2; нужно добавить юнит `label: 'Echo8'`. На реальных данных: 9 строк (счёт 1052428, 2024-12…2025-05 и далее) с обоими лейблами в одном счёте-месяце (например 2025-05: 0to8 248 280.52 / Echo8 21 728.74) — именно их должен проверять скрипт (§3).

**И2. Баланс владельца: Σ byLabel.earned = total.earned − паблишинг; Σ byLabel.waiting = total.waiting − паблишинг-waiting.**
Держится по построению (`balance.ts`: `lb.earned`/`lb.waiting` и `tEarned`/`tWaiting` пополняются в одном цикле). Запинен частично: G08b (D-130) проверяет `{Echo8: [50,0], 0to8: [0,30], '?': [20,0]}` против `[70, 30]`. Не запинено для владельца с publishing-строками и для `artistBalance.byLabel`. Добавить в `c.verify()` проверку для каждого владельца сцены: `Σ byLabel.earned + Σ publishing(B).amount = total.earned` — одна строка, ловит любой будущий слой, забывший `byLabel`.

**И3. Payable по лейблу — не определён.** Пример владельца heqxrte: earned 0to8 3 717.40 + Echo8 480.79; adsCharged 1 667.08 — все 7 записей на 3 ISRC (FR59R2644515, FR59R2644514, DGA082515888), все три под 0to8; paid 1 725.55 двумя выплатами (2026-08-18 за 2026-05, 2026-09-30 за 2026-07) без лейбла; payable 805.56. Если относить paid «на 0to8», то 0to8 = 3 717.40 − 1 667.08 − 1 725.55 = 324.77, Echo8 = 480.79, сумма 805.56. Любое другое правило отнесения (пропорционально earned, по periodу выплаты, по снимку) даёт другие две цифры при той же сумме. Общий случай хуже: позиция `recoupable_payout` scope `any` (248 из 2 663 операций) гасится из дохода **любого** лейбла в порядке отчётных месяцев — `eligible()` не знает лейбла. Следствие: «payable под лейблом» можно определить только через **правило отнесения** (решение владельца, §5), и инвариант для него один — `Σ_L payable_L = payable` (точно, без округления, т.к. это разбиение сумм). Пока правила нет — показывать payable только как одно число владельца (D-130), а по лейблу — earned/waiting/adsCharged.

**И4. Снимок выплаты.** `createPayout` платит весь payable одной суммой (D-051), снимок = полный баланс владельца (`balanceWithFiles`, D-053, D-164; тест «a payout records the snapshot of the reach calculation»). Если выплата становится «под лейблом», нужны: сумма по лейблу (⇒ И3), `payoutByArtist` по лейблу, `blockingPayouts` — по владельцу или по лейблу? Сейчас выплата 0to8 без proof заблокирует выплату Echo8 (`payoutGate`: `blocking.length > 0`). Инвариант для любого варианта: `snapshot.amountCents == payout.amountCents` и `snapshot.total == balance.total` в момент выплаты, плюс (новое) `Σ_L amount_L ≤ payableCents` и `payable после − payable до = −amount` — тест в `scope.test.ts` по образцу существующего.

**И5. Охват владельца ∩ лейбл = баланс под лейблом?** Охват — множество ISRC; «под лейблом» — подмножество тех ISRC, чьи юниты несут строки лейбла L (на реальных данных ISRC → один лейбл, но в общем случае ISRC может иметь юниты под разными строками в разные месяцы, фильтр должен быть по юнитам, не по ISRC). Для аллокаций ограничение точное (D-161). Для `recoup` — **нет**: позиция scope `any`, в полном расчёте погашенная из дохода Echo8, в расчёте «только 0to8» погасится из дохода 0to8 (или останется unrecouped). То есть `ownerBalance(scoped by label)` ≠ «полный баланс, ограниченный на лейбл» как только есть позиции или ads под другим лейблом. Тест, который это ловит: сцена `artistsWorld()` из scope.test (у A есть аванс 30 scope any и реклама 40) + второй юнит A под `Echo8`; сравнить `ownerBalance` по лейблу против полного с `withFullReads` — ожидаемо **не** совпадёт, и тест должен это фиксировать как спецификацию выбранного правила, а не как равенство.

**И6. `label_unmapped` и `'?'`.** Наше по несопоставленной строке ждёт в C без лейбла (`labelShareCategory: 'label_unmapped'`, `ourLabelName: null`); в `byLabel`/`ourShareByLabel`/`ads/summary` это ключ `'?'`. Реклама `'?'`: 6 972.44 (recoveredFromArtists 6 272.94, borneByUs 699.50) — ISRC без строки лейбла, то есть расход на трек, которого ещё нет в отчётах (или он там без денег). В разделённой админке такая запись не принадлежит ни одному лейблу: при обязательном фильтре её **никто не увидит**. Инвариант: Σ видимого по всем лейблам + «без лейбла» = полное; тест — G08c (`Mystery Records`) плюс новая запись рекламы на незагруженный ISRC в `world()`: при любом лейбл-фильтре сумма по лейблам + `'?'` = `adsSummary({})`.

**И7. Строки «0to8/Echo8» (6 025.57) и «0to8, Echo8» (1.64) — алиасы 0to8.** Решение данных, не кода. При разделении это решение становится «несущим»: 6 025.57 целиком показываются под 0to8, Echo8 их не видит. Проверяемо только явным golden-кейсом: алиас с именем обоих лейблов → `byLabel` одного лейбла; и сигнал/отчёт «алиасы, называющие другой own-лейбл» (строковая проверка по `listLabels()`), чтобы такие строки были видны владельцу.

**И8. Смена `own_label_id` саблейбла задним числом.** У `labels.own_label_id` нет периода, у алиасов тоже. В `labels/service.ts` есть `createLabel`, `addAlias`, `setRule`, `closeRule` — **нет `updateLabel`**, через API это поле сегодня неизменяемо. Риск появляется, если его добавят: вся история саблейбла (все месяцы) переедет под другой лейбл, снимки прошлых выплат по лейблу разойдутся с текущим расчётом. Тест-страж: `rules-coverage`/`api-contract` — отсутствие операции PATCH на `ownLabelId`, либо, если её вводят, датированная принадлежность (как у правил) и golden-кейс «саблейбл переехал с 2026-06-01».

**И9. Слияние псевдонимов через лейблы.** `mergeArtists` не знает лейбла; в разделённой админке оператор 0to8 может влить псевдоним с доходом Echo8 (SXLLX: 42 806 / 128 757) в свой — охват выжившего станет двухлейбльным, деньги Echo8 «появятся» у владельца 0to8. Тест: scope.test уже проверяет merge (`merged.items … '151'`); добавить сцену, где слияние пересекает лейбл, и ожидание — либо отказ (`merge_crosses_label`), либо аудит с обоими лейблами.

**И10. Аудит.** `api/audit.ts` пишет operator, route, entityIds, summary (белый список полей тела, среди них `labelId`). Заголовок `X-Label` в summary не попадёт, если его не добавить явно; действие «под лейблом» без следа лейбла в аудите — разрыв. Тест: `api-contract` вызывает все операции и читает `/audit` (строка 49) — туда же добавить ожидание поля `label` в summary каждой записи, если заголовок/параметр вводится.

## 2. Варианты: что ломается, риски, какой тест ловит

**A. `X-Label` как обязательный фильтр представления через unit scope.**
- Балансы, payables, обзор, reconciliation, сигналы по дизайну **никогда не scoped** (D-012, D-161, `facade/CLAUDE.md`). Фильтр по лейблу на балансе — это scope на балансе: И5 ломается при позициях scope `any` (248 шт.) и рекламе. Выплата: кнопка платит весь payable владельца (D-051) — под фильтром 0to8 она заплатит и 480.79 Echo8 heqxrte, либо, если урезать, нарушит D-051 и снимок (И4). Ловит: новый scope.test «label scope» с авансом (И5), payout-тест (И4).
- A = B + C + наше по лейблу внутри счёта 1052428: выполнимо точно (И1), но строка reconciliation по счёту-месяцу под фильтром покажет часть A (например 2025-05 только Echo8 21 728.74 из ~270 000) — discrepancy 0 по-прежнему, но «полнота загрузки файла» (сравнение с A файла) проверяема только без фильтра. Ловит: golden G33/G40 (два счёта, Echo8 в обоих) с фильтром.
- Документы на владельца (контракт подтверждает владельца целиком), B17 без лейбла, `label_unmapped` и `'?'` (И6) — всё это без лейбла; при обязательном заголовке либо дублируется в оба лейбла (Σ по лейблам ≠ полное — ломается И1 для publishing), либо невидимо. Ловит: тест Σ по лейблам + без-лейбла = полное (И6).
- Контракт: `operations.ts` умеет описывать `headers`, но `api-contract.test.ts` ставит только `X-Operator` и только на записи (строка 79); обязательный заголовок на GET провалит сценарий контракта целиком, и наоборот — заголовок, описанный, но не проверяемый, не ловится. Забытый заголовок на фронте = 400 на каждом экране (громко, но e2e: все 24 спека + smoke без `X-Label` — красные). Аудит: И10.
- Один файл Believe со строками обоих лейблов (1052428: 0to8 15,07 млн + Echo8 222 130): реестр файлов без лейбла; `/sources` под фильтром покажет файл обоим; `files.believe` в снимке — все файлы (тест «every file in force … not only the reach's»).

**B. Настоящая изоляция данных (БД/схема на лейбл).**
- 357 владельцев с двумя лейблами получают два баланса, две истории выплат — а 2 663 операции без лейбла надо раскидать правилом (И3) до миграции; 2 400 выплат уже заплачены «одной суммой» — их разбиение ретроактивно. Файл 1052428 надо резать при загрузке на два (sha256 в снимках прошлых выплат перестанет совпадать с файлом в реестре); reconciliation по счёту теряет смысл (счёт ≠ лейбл). B17, документы, owners — дублировать или держать общими (тогда это не изоляция). Слияние через лейблы невозможно вовсе. Ломаются: `scope.test` (один `sources.snapshot`), `golden` G33/G40, `api-contract`, e2e seed (одни stores `erp_e2e`/`believe_e2e`), `migrate-sqlite-to-pg`, `mvp:load`. Точность: сами расчёты внутри лейбла точны, но сумма по лейблам больше ничем не проверяется — И1 нечем считать. Это самый дорогой и наименее проверяемый вариант.

**C. Лейбл как переключатель в шапке и query-параметр, без заголовка.**
- Та же семантика, что A, но параметр явный: `api-contract` его проверяет через `query` (как `ids`, `from/to`), `coverage.ts` фронта требует страницу, OpenAPI описывает. Забытый параметр = **полный** вид, а не 400 и не утечка в другой лейбл (безопасный дефолт для чтения). Остаются те же денежные дыры: И3 (payable по лейблу), И4 (выплата), И5 (recoup через лейбл), И6 (`'?'`), И9 (merge). Если параметр действует **только на списки и разрезы** (reconciliation, tracks/summary, owners list, ads/summary) и не трогает баланс/выплату — все инварианты держатся и проверяются scope.test-ом как ещё один фильтр. Риск регрессии e2e: умеренный — дефолт без параметра не меняет ни один спек.

**D. Ничего не разделять: разрез по лейблу везде, где есть деньги, и фильтр в списках.**
- Не ломает ничего существующего: D-051 (одна выплата), D-130 (один баланс, byLabel), D-161 (scope только там, где ответ — ограничение). Нужно добавить: `A/B/C_byLabel` в reconciliation (И1), `byLabel` в payables-списке и у pseudonym-списка, фильтр `label` в списках (это ровно scope по строкам лейбла — проверяется как в scope.test). Payable по лейблу не вводится — показывается earned/waiting/adsCharged по лейблу и один payable (И3 честно «не определён»). `'?'` и `label_unmapped` видны как свой столбец. Точность: только сложения. Аудит: без изменений (фильтр — чтение).

## 3. Что потребуется в тестах

1. **Unit (`tests/scope.test.ts`).** (а) `label scope = full restricted`: для `reconciliation`, `trackSummary`, `ownerPayables`, `adsSummary`, `queue` с `label` — spy на фильтр (`labelStrings` или список ISRC лейбла) и байт-в-байт равенство с `withFullReads`, ограниченным на `ourLabelName === L`. (б) `sum over labels = full`: для тех же методов `Σ_L ответ(L) + ответ('?') = ответ({})` по каждому числовому полю. (в) **Негативный пин** И5: `ownerBalance` по лейблу при позиции scope `any` ≠ полному, с точным ожиданием по выбранному правилу (пока правила нет — тест `it.todo`, чтобы факт был записан). В `world()` нужен юнит `Echo8` и реклама на незагруженный ISRC.
2. **Golden (`12_golden_cases.md`, `golden.test.ts`).** Два лейбла на одном владельце уже есть: G08b (D-130) — Echo8 50 B, 0to8 30 C, `?` 20 — но без операций и рекламы. G33/G40 — два счёта, Echo8 в обоих. Нет кейса «аванс scope `any` у владельца с доходом под обоими лейблами» и «реклама под 0to8, доход под Echo8» — это G-кейс с ручными числами: A: 0to8 100 → 50, Echo8 60 → 30; аванс 40 any; реклама 20 на ISRC 0to8; ожидание: recouped 40, adsCharged 20, payable 20, byLabel {0to8: 50, Echo8: 30}, и запись в 12: «payable по лейблу не определён, Σ = 20». Плюс кейс И7 (алиас «0to8/Echo8» → один лейбл) и `c.verify()` расширить проверками И1/И2.
3. **api-contract.** Если вводится параметр — он просто добавляется в вызовы сценария (`query: { label }`) и в `S.*Query`; если заголовок — тест надо учить слать заголовки на GET и проверять 400 без него, а `operations.ts` — описывать его в `headers` каждой операции; сейчас для GET заголовки не проверяются вовсе. Это аргумент против заголовка с точки зрения проверяемости.
4. **e2e seed.** Второй own-лейбл в seed **есть**: `scenarios/shared.ts` (S00) создаёт 0to8 (алиасы Test Label, 0to8, Ahh Music) и Echo8; `qaraqshy records` — саблейбл Echo8 под assumption; S06/S08/S10 используют Echo8 (`verify-seed.ts` строки 100–115, `10-overview.spec.ts` строки 60–65 проверяют `ourShareByLabel` Echo8). Нет сцены «один владелец, деньги под обоими лейблами, выплата» — нужна S38 по мотивам G08b + S22 (payout). При обязательном заголовке сломаются все спеки (клиент не шлёт `X-Label`), при параметре с дефолтом «все» — ни один; новый спек `35-label-filter.spec.ts` (после 34) читает P1/P9/P5 с переключателем и сравнивает суммы по двум лейблам с полным — только чтение, порядок §6 не трогается.
5. **Скрипт на реальных данных** (`scripts/check-label-split.ts` по образцу `check-owner-scope.ts`): один полный `calculate()`; для каждой строки reconciliation `Σ_L A/B/C/ours_L = A/B/C/ours` (в первую очередь 9 строк 1052428 с обоими лейблами); для 357 владельцев с ISRC под обоими лейблами `Σ byLabel = total.earned − Σ publishing(B)` и `byLabel`-сумма ads = adsCharged (6 972.44 `'?'` в сумме); затем `calculate(scoped by label strings)` → `ownerBalance` и печать владельцев, у которых по-лейбльный баланс ≠ ограничению полного (ожидаемо все с позициями scope any — это и есть размер проблемы И3/И5 в цифрах). Выход ≠ 0 при расхождении И1/И2; расхождение И5 — отчёт, не ошибка.

## 4. Риски по вариантам
