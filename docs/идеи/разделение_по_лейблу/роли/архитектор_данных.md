# Разграничение админки по лейблу: отчёт архитектора данных

Сессия размышления 2026-11-05, ветка `feature/fable-001`, код не менялся. Цифры — dev-база `erp` (46 загруженных файлов Believe: счёт 1052428 — 34 файла 2023-11…2026-08, счёт 1055956 — 13 файлов 2025-08…2026-08), ClickHouse `believe.units`, PostgreSQL, `GET /owners/:id/balance` для 357 владельцев.

## 1. Что такое «лейбл» в данных

Словарь (`labels.labels`): 2 own-лейбла (0to8, Echo8), 15 саблейблов (11 под 0to8: 77 Records, Bear catalogues, Enarma, Hoboshrine, lost, NoGhost, no job records, odds, PCR, R2R, VBR; 4 под Echo8: CATCORE, fate, qaraqshy, SF), 25 алиасов, 17 правил — все 50 % получателю-псевдониму. Единственная точка, где лейбл входит в расчёт, — слой `label-of-record.ts`: `labelOf(строка лейбла юнита, дата отчёта)` → `ourLabelId` (own или `own_label_id` саблейбла), `sublabelId`, правило. Дальше ни один слой лейбл не читает: сплит, carve, категоризация, recoup — по ISRC, псевдониму и документу.

Это не недоработка, а решение D-123 («один баланс на владельца через оба лейбла, показ по платящему лейблу — допущение») и D-130 (`byLabel` только earned/waiting мастер).

## 2. Варианты

### A. X-Label как обязательный фильтр представления на unit scope

Что хранить: ничего. `SnapshotFilter` получает `labelNames: string[]` (сырые строки, не ISRC): фасад берёт own-лейбл + его саблейблы → алиасы → `columnar.labelStrings(fileIds)` → нормализует (как `isrcsOfLabelAliases`) → сырые строки → `columnar.units` добавляет `label_name IN {…}`. Проекция `units_by_label` группирует по `label_name`, так что фильтр ложится на неё без доп. индекса; условие по строке точнее, чем по списку ISRC (не нужно передавать 9–11 тыс. ISRC, ISRC `''` и переходы ISRC между лейблами обрабатываются сами). Миграций нет.

Инварианты: scoped = full ограниченный на подмножество — верно для юнитов (аллокация юнита зависит только от юнита и справочников его ISRC, D-161). Но **для баланса, payable, recoup, кнопки выплаты фильтр по лейблу ломает ответ**: `ownerBalance` по охвату равен полному только потому, что охват — надмножество юнитов владельца; срез по лейблу — подмножество, recoup `any` съест только доход одного лейбла, payable изменится, снимок выплаты станет «частичным». Значит, обязательный заголовок на всех запросах невозможен: для владельцев/выплат его придётся игнорировать (и тогда он лжёт) или запрещать (и тогда страница владельца «вне лейбла»). Для 12 владельцев с earned под обоими и 10 из них с выплатами (908 390) ответ «payable под 0to8» не существует.

Риск точности: низкий для юнит-страниц (та же механика, что D-161/162, с тестом scoped = full), высокий, если заголовок протечёт в `balanceWithFiles`. Аудит: заголовок на записи бессмысленен (сплит, операция, документ лейбла не имеют) — см. §3. Объём: 3–5 дней (фильтр + фасад `labelScope` + параметр в 8–10 GET + тест scoped=full + UI).

### B. Изоляция: своя БД/схема на лейбл

Дублировать придётся все 7 схем PostgreSQL (`owners`, `labels`, `splits`, `settlements`, `publishing`, `audit`, `ads`) и реестр `public.source_files`, плюс либо две базы ClickHouse, либо фильтр по строке внутри одной. Нерешаемое: (1) **один файл Believe 1052428 несёт обе строки** — загружать его в обе базы (двойной учёт 15 млн net в A и сверке) или резать по строке при загрузке (тогда файл в реестре ≠ файл на диске, снимок выплаты хранит «не тот» файл, D-053); (2) **357 общих владельцев** — два владельца с одним контрактом, два баланса, два payable, две кнопки выплаты, recoup `any` перестаёт работать через лейблы (45 владельцев с авансами на 293 924), слияния псевдонимов — по две; (3) **B17** — 47 писателей без лейбла: либо в обе базы, либо в одну «домашнюю»; (4) `calculate()` читает все модули в одном `db.snapshot` (D-012/D-121) — межбазовый снимок невозможен, сверка «Σ по лейблам = итог» становится сверкой между базами. Миграции: новая структура `.env`/`Db` на лейбл, перенос данных по ISRC с разрезанием сплитов (сплит на ISRC, а не на лейбл — общий сплит дублируется). Это ровно то, чего избегали в D-121 (одна база, один снимок). Риск точности и аудита — максимальный: история выплат 4,07 млн не делится. Объём: 15–25 дней + постоянная цена двойного ведения справочников. Не рекомендую.

### C. Лейбл как переключатель в шапке UI и query-параметр

Бэкенд — тот же `labelNames` в `SnapshotFilter`, что в A; отличие только в транспорте: `?label=<id>` на GET, необязателен, нет 400. Фронт: переключатель «0to8 / Echo8 / Все» рядом с оператором, в `localStorage` (`erp.label`), клиент добавляет параметр к запросам, у которых он есть в схеме (`api-schemas.ts`), остальные — без. Хранить нечего, миграций нет. Инварианты те же, что в A, но честнее: страницы владельца, выплат, паблишинга параметр не принимают, и UI показывает «вне лейбла». Объём: бэкенд 2–3 дня (как A), UI 1–2 дня.

### D. Ничего не разделять: разрез по лейблу везде, где есть деньги, фильтр в списках

Что добавить: `byLabel` уже есть в балансе (D-130) и в сверке (`ourShareByLabel`); не хватает (а) `C_breakdown`, `B`, `A` по лейблу в сверке и обзоре; (б) `adsCharged` по лейблу (выводимо из `AdResult.ourLabelId`); (в) `recouped` по лейблу (выводимо из `consumed` recoup: `itemId = m|artist|isrc|month` → юнит → лейбл; это артефакт порядка потребления, не факт); (г) **лейбл у новых операций** — необязательная колонка `settlements.operations.label_id` (миграция `0014`), информационная: кнопка выплаты пишет в снимок `byLabel` и `payoutByLabel` пропорционально положительному earned по лейблу (то же, что уже делает `payoutByArtist`); аванс/вычет — лейбл по выбору оператора или пусто; история (2 663 операции) остаётся «без лейбла»; (д) фильтр списков: владельцы (`labels` из охвата: нужна карта ISRC→own-лейбл, 20,7 тыс. строк из `labelStrings`+`isrcsOfLabelStrings`, дёшево), псевдонимы, треки/каталог, релизы, реклама, очередь C. Инварианты определены (§4). Риск точности: нулевой для денег (ничего не фильтруется в расчёте), риск только в трактовке «paid по лейблу» — потому и информационная колонка, не фактор расчёта. Объём: 4–6 дней.

## 3. Лейбл, X-Operator и аудит

`X-Operator` — личность, нужен только на записи, хук пишет строку в `audit.actions` после 2xx. Лейбл — контекст представления, нужен только на чтении. Смешивать их в один обязательный заголовок не стоит: у записей (сплит, участие, документ, операция, правило лейбла, слияние) лейбла нет, 400 `label_required` ничего не защитит, а «запись под лейблом Echo8» на сплите ISRC из 0to8 — ложь в журнале. Предложение: лейбл — только query-параметр (или необязательный заголовок, читаемый как параметр), в `audit.actions` **не добавлять** колонку; если запрос записи пришёл с лейблом, скопировать его в `summary.label` (как `scope`, `kind` сейчас) — информационно, нулевая цена. Чтения не аудируются и так. Запрос без лейбла = «все лейблы», сегодняшнее поведение; это и есть значение по умолчанию для всех скриптов (`check-owner-scope.ts`, загрузчик, сверки) и контрактного теста, им ничего менять не нужно. Аудит сейчас почти пуст (7 действий, 1 оператор): менять шаблон записи дёшево, но поздно будет дорого — поэтому не вводить лейбл в ключ записи.

## 4. Инвариант «сумма по лейблам = полному»

Верен точно (суммы по юнитам, каждый юнит ровно в одном лейбле):
- юниты: Σ_label units = units; A_label, B_label, C_label (мастер), ours_label — все суммы по юнитам, ⇒ A = B + C + ours выполняется **внутри каждого лейбла и по счёту/месяцу** (`reconcile()` достаточно сгруппировать ещё по `ourLabelId`; `'?'` для `label_unmapped`: сейчас 0 несопоставленных юнитов, но пустой ISRC и будущие строки — туда);
- баланс владельца: Σ byLabel.earned = earned мастер, Σ byLabel.waiting = waiting мастер (D-130, уже проверяется);
- реклама: Σ по `ourLabelId` + «?» = Σ `adsCharged`, «?» = 33 записи без ISRC;
- сверка ours: `ourShareByLabel` уже есть.

Не определён:
- **payable** = earned − recouped − paid − ads + returns + credits: определён по лейблу, только если определён каждый член; paid и returns — нет; поэтому payable по лейблу — не число, а соглашение (D-123 допущение «один баланс»);
- **recoup**: позиция `any` потребляет income-items в порядке месяцев через оба лейбла; «recouped по лейблу» = сумма потреблённых items лейбла — вычислимо, но меняется от порядка, а не от бизнеса; scope `publishing` вообще вне лейблов;
- **выплаты**: 2 400 без лейбла; для 10 владельцев с earned под обоими и выплатами (908 390) любое деление — допущение;
- **B17**: лейбла нет по архитектуре; `b17`-строки сверки не делятся;
- **паблишинг-ours**: «наше» без лейбла.

Предложить: (1) в ответах различать «точный разрез» (`byLabel` на units/B/C/ours/ads) и «вне лейбла» (paid, recouped, returns, credits, publishing, payable) явным полем, а не «?»; (2) тест `tests/scope.test.ts`-стиля: `reconcile(calc, {label})` по каждому лейблу суммируется в `reconcile(calc)` байт в байт, и `ownerBalance.byLabel` суммируется в мастер-итоги для всех 1 151 (скрипт на реальных данных, как `check-owner-scope.ts`); (3) для новых выплат — `payoutByLabel` в снимке (пропорция earned−recouped по лейблу на момент выплаты) и `label_id` у операции, чтобы с этого дня «paid по лейблу» стал фактом, а старое — «без лейбла» навсегда.

## 5. Рекомендация

Не изолировать (B) и не делать заголовок обязательным (A): данные — один денежный конвейер, где граница лейбла существует только на юните, а владелец (35 % общих), контракт, recoup, выплаты и B17 её не имеют, и это закреплено D-123/D-130. Делать **D с транспортом C**: необязательный `?label=<id own-лейбла>` на юнит-уровневых чтениях (обзор, сверка, очередь C, треки/каталог, релизы, реклама, сигналы) как `labelNames` в `SnapshotFilter` (строки лейбла и его саблейблов, `label_name IN` на `units_by_label`), с тестом scoped = full; на владельце/псевдониме/выплатах — не фильтр, а разрез `byLabel` (уже есть) плюс `adsCharged`/`recouped` по лейблу и явное «вне лейбла»; в списках владельцев и псевдонимов — колонка «лейблы» из охвата и фильтр по ней; новая выплата пишет `byLabel` в снимок и необязательный `label_id`. Переключатель «0to8 / Echo8 / Все» в шапке рядом с оператором, по умолчанию «Все».

Места: `modules/sources/service.ts` (`SnapshotFilter.labelNames`), `columnar.ts` (`units` WHERE, новый `isrcLabels(fileIds)` для карты ISRC→строка), `facade/scope.ts` (`labelScope(labelId)`: own + саблейблы → алиасы → сырые строки), `facade/{reports,aggregates,ads-api,calculation(reconcile по лейблу)}.ts`, `facade/balance.ts` (ads/recouped по лейблу), `facade/payouts.ts` (снимок `byLabel`, `payoutByLabel`), `modules/settlements` + миграция `0014_operations_label.sql` (nullable `label_id`, CHECK не нужен — soft reference), `api/routes/*` + `operations.ts` + `packages/shared/src/{api-schemas,api-responses}.ts` (параметр `label`, поля `byLabel`), `api/audit.ts` (`label` в `SUMMARY_FIELDS`), фронт: `api/client.ts` (параметр из `localStorage`), шапка, `pages/owners`, `pages/catalog`, i18n; тесты: `tests/scope.test.ts` (Σ по лейблам = полному), `scripts/check-owner-scope.ts`-подобный скрипт по лейблам; D-168 в 97 и индекс.

## Вопросы владельцу

1. 357 владельцев (35 %) имеют деньги под обоими лейблами, у 96 второй лейбл даёт >20 %; earned под обоими — у 12, из них 10 с выплатами на 908 390 без лейбла. Баланс и выплата остаются одной суммой на владельца (D-123), а лейбл на странице владельца — разрезом, не фильтром? Или нужны две кнопки выплаты по лейблу (тогда аванс `any` — 248 операций — придётся переопределить)?
2. 1 152 исторические выплаты на 4,07 млн (59 % всех выплаченных денег) не имеют лейбла. Оставить «без лейбла» навсегда или разнести допущением (пропорция earned по лейблу на дату)?
3. Счёт 1052428 несёт строку Echo8 на 222 130 net (1,39 млн строк) кроме 0to8. Подтвердите: лейбл = строка лейбла, не счёт, и «Echo8-администратор» видит эти юниты из счёта 0to8.
4. Нужен ли срез по саблейблу (15 штук; 17 ISRC перешли из «0to8» в «77 Records» между месяцами, 150 762 net у саблейблов 0to8), или только по own-лейблу? Куда относить юниты без ISRC (2 216 net, строки обоих лейблов)?
5. Связан ли лейбл с оператором (оператор ↔ лейбл-роль)? Если да — это аутентификация/роли, сейчас вне объёма; без неё параметр остаётся представлением, не ограничением доступа.
