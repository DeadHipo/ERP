# Разделение админки по лейблу: идея и рекомендация

Дата: 2026-11-05, после разбора четырьмя ролями (архитектор данных, продакт, разработчик фасада, QA; отчёты в
`роли/`). Статус: **идея, не решение** — код не менялся, D-запись не писалась, действующие документы не трогались.
Там, где отчёты ролей расходятся с этим файлом, прав этот файл. Цифры — dev-база `erp` (46 загруженных файлов
Believe, два счёта; B17 за 7 кварталов) на 2026-11-05.

Вопрос владельца продукта: у нас два собственных лейбла (0to8, Echo8) и 15 саблейблов; владелец открыл карточку
владельца с деньгами под обоими лейблами и предложил «всегда слать `X-Label` с id лейбла из `labels` в заголовке
запроса и прямо разграничить». Что это значит для каждого модуля и страницы, и как сделать просто и гибко.

## 1. Ответ в пяти строках

1. **Граница лейбла в данных есть ровно в одном месте — у юнита Believe** (строка лейбла в ключе юнита → алиас →
   own-лейбл; саблейбл принадлежит own-лейблу через `own_label_id`). Всё, что из юнита выводится — ISRC, реклама,
   охват владельца, «наше» в сверке, `byLabel` баланса — делится по лейблу **точно**. Всё остальное — владельцы,
   псевдонимы, документы, контракты, операции, выплаты и их снимки, B17, аудит, **счета Believe** — лейбла не имеет.
2. **Заголовок `X-Label` не делать, изоляцию данных не делать.** Обязательным он быть не может (у большинства
   записей и у шести страниц лейбла нет), контракт-тест и OpenAPI его не видят, в ключи кэша и в URL он не попадает.
   Изоляция (своя база на лейбл) противоречит данным: 357 из 1 011 владельцев с деньгами (35 %) имеют ISRC под
   обоими лейблами, один файл счёта 1052428 несёт строки обоих лейблов, B17 и договоры общие.
3. **Делать разрез по лейблу везде, где есть деньги, и необязательный фильтр `label=<id>` на чтениях по юнитам**
   (обзор, сверка, очередь C, сигналы, треки, релизы, реклама) через уже существующий unit scope: одно новое поле
   `labelStrings` в `SnapshotFilter` (строки own-лейбла и его саблейблов, `label_name IN` в ClickHouse). Переключатель
   «0to8 / Echo8 / Все» в шапке рядом с оператором, по умолчанию «Все», значение в URL. Миграций нет, ≈ 9–10 дней.
4. **Деньги не трогать:** один баланс и одна выплата на владельца (D-123, D-051) остаются. `payable`, `paid`,
   `recouped` по лейблу **не определены** (2 400 выплат без лейбла, аванс со scope `any` гасится доходом любого
   лейбла), и никакой транспорт этого не решает — только правило от владельца (вопросы §6). До него карточки
   владельца и псевдонима показываются целиком с подсветкой лейбла, никогда не урезаются.
5. **Проверка одна и точная:** для каждого ответа-суммы по юнитам Σ по лейблам + «без лейбла» = полный ответ, байт в
   байт (тот же аппарат, что `tests/scope.test.ts`); для полей операций — равенство полному. Плюс скрипт на
   реальных данных по образцу `check-owner-scope.ts`.

## 2. Что владелец мог иметь в виду

| Толкование «разграничить» | Признаки в вопросе | Чем решается |
|---|---|---|
| (а) рабочее место оператора одного лейбла: «сегодня я Echo8, покажи только Echo8» | «админку», «всегда слать» — сессионный контекст, как оператор в шапке | переключатель в шапке + параметр `label=`; заголовок тут не лучше параметра |
| (б) отчётность: сколько каждый лейбл заработал и должен | владелец открыл карточку владельца с деньгами под обоими | разрез `byLabel`; во многом уже есть (`ourShareByLabel` на P1, `byLabel` на P10/P12, `/ads/summary`); не хватает у B/C сверки, у P9/P11, у `adsCharged` |
| (в) раздельные сальдо и выплаты: аванс 0to8 не гасится доходом Echo8 | «прямо разграничить» звучит как «не смешивать» | доменное правило, не транспорт; меняет D-123; нужны ответы §6 Q2–Q4 |
| (г) права: оператор Echo8 не видит 0to8 | «заголовок с id» похож на токен | заголовком не решается вовсе (фронт ставит его сам из `localStorage`, как `X-Operator`); нужны логин и роли, сейчас вне объёма |

Признаков (б) и (в) больше, чем (а) и (г). Заголовок закрывает только (а). Рекомендация §5 закрывает (а) и (б)
сразу, (в) — после ответов владельца, (г) — отдельным этапом.

## 3. Что такое «лейбл» в данных

### 3.1. Факты на реальных данных

- Словарь: 2 own-лейбла, 15 саблейблов (11 под 0to8: 77 Records, Bear catalogues, Enarma records, Hoboshrine, lost,
  NoGhost, no job records, odds, PCR, R2R PRODUCTION, VBR; 4 под Echo8: CATCORE, fate, qaraqshy, SF), 25 алиасов,
  17 правил, все 50 % получателю-псевдониму. Принадлежность саблейбла own-лейблу уже в данных (`own_label_id`,
  обязательна по CHECK), без периода; эндпоинта, меняющего её, нет.
- **Счёт Believe ≠ лейбл.** Счёт 1052428 (34 файла, 2023-11…2026-08) несёт строки 0to8 и его саблейблов (net
  15 065 401) **и строку «Echo8» на 222 130 net (1,39 млн строк)**; счёт 1055956 (13 файлов, с 2025-08) — только
  Echo8 и его саблейблы (1 050 945). В сверке наше 0to8 7 662 974 / Echo8 131 848 внутри одного счёта 1052428.
- **ISRC → один own-лейбл:** 20 685 ISRC с юнитами, ни одного под обоими own-лейблами (9 441 только 0to8, 11 244
  только Echo8, 0 несопоставленных строк). 18 ISRC имеют больше одной строки лейбла: 17 — переход own ↔ саблейбл
  внутри 0to8 между месяцами («0to8» → «77 Records»), 1 — пустой ISRC (юниты без ISRC, 2 216 net, строки обоих
  лейблов). Инвариант «ISRC — один лейбл» ничем не гарантирован, только наблюдается; поэтому фильтр надёжнее по
  строке юнита, а не по списку ISRC.
- **Владелец → оба лейбла:** из 1 011 владельцев с юнитами 357 (35 %) имеют ISRC под обоими; псевдонимов 358 из
  2 011. У 96 из них второй лейбл даёт больше 20 % мастер-денег; **заработано (B) под обоими — только у 12**
  (медиана доли меньшего лейбла 2,6 %), остальное — C под вторым лейблом. Примеры (псевдонимы, net юнитов
  0to8 / Echo8): heapper 362 125 / 120 441, RD12 697 432 / 60 543, SXLLX 42 806 / 128 757.
- **Операции без лейбла:** 2 663 (2 400 выплат, 159 возвратных выплат со scope: 248 `any`, 14 `publishing`,
  1 `isrcs`; 104 вычета). На владельцев под обоими лейблами приходится 1 152 выплаты на 4 066 581 из 6 924 256
  всех выплаченных (59 %, 112 владельцев) и 68 возвратных выплат на 293 924 (45 владельцев).
- **Реклама:** 2 686 записей на 1 019 513; лейбл записи выводится из строки лейбла ISRC в месяц расхода:
  0to8 967 935 / Echo8 44 606 / «?» 6 972 (33 записи без ISRC, на псевдоним).
- **B17:** получено 2 496 582, B 682 348, C 845 990; 47 писателей; лейбла нет по архитектуре (08 решение 7,
  D-130); паблишинг-earned у всех 357 «двухлейбльных» владельцев = 0.
- **Пример владельца** `733f5fb6…` (один псевдоним heqxrte): earned 4 198,19 = 0to8 3 717,40 + Echo8 480,79;
  waiting 1 896,20 = Echo8 1 891,93 + 0to8 4,27; реклама 1 667,08 (7 записей на 3 ISRC, все под 0to8); выплачено
  1 725,55 (2026-08-18 1 183,30 за период 2026-05; 2026-09-30 542,25 за 2026-07; без лейбла); payable 805,56,
  кнопка открыта. Если считать «все выплаты на 0to8»: 0to8 = 3 717,40 − 1 667,08 − 1 725,55 = 324,77,
  Echo8 = 480,79; любое другое правило даёт другие два числа при той же сумме.

## 4. Варианты

### A. `X-Label` как обязательный фильтр представления (предложение владельца)

- **Суть.** Заголовок с id own-лейбла на каждом запросе; бэкенд сужает расчёт до юнитов лейбла через unit scope.
  Технически ложится хорошо: новое поле `SnapshotFilter.labelStrings` (сырые строки лейбла и его саблейблов, как
  `isrcsOfLabelAliases`) → `label_name IN {…}` в `columnar.units()`; множество юнитов с `ourLabelId = L` получается
  **точно**, без расчёта. Строки лучше списка ISRC: не зависят от допущения «один ISRC — один лейбл», 25 строк
  вместо 9–11 тыс. ISRC, 0,40 с против 0,63 с на чтение, и для охвата владельца — второе условие в том же `WHERE`.
- **Что даёт.** Толкование (а). След «под каким лейблом работал оператор» в аудите.
- **Что ломает.** (1) Обязательность фиктивна: у документов, владельцев, псевдонимов, писателей, операций, выплат,
  аудита, поиска, загрузки (~25 операций, 6 страниц) лейбла нет — либо игнорировать (заголовок лжёт), либо
  400 (ломает загрузку счёта 1052428 и общие договоры). (2) Балансы, payables, выплата: фильтр по лейблу на
  `balanceWithFiles` — это scope на балансе, которого по дизайну нет (D-012, D-161): recoup `any` сожрёт доход
  только одного лейбла, payable изменится, снимок станет «частичным», кнопка под 0to8 заплатит и 480,79 Echo8
  heqxrte, либо нарушит D-051. (3) Контракт: `api-contract.test.ts` ставит заголовки только на записи и только
  `X-Operator`; OpenAPI не покажет «тот же путь, другой ответ». (4) Кэш TanStack: лейбл не в ключах — при
  переключении экран на секунды покажет цифры другого лейбла. (5) URL не несёт лейбл: два человека по одной
  ссылке видят разное. (6) Забытый заголовок = тихо «все лейблы» или 400 на каждом экране (все 24 e2e-спека
  красные).
- **Объём.** 3–5 дней бэкенд + UI; сверх рекомендованного — ещё ~2 дня (async-хук, миграция аудита, `headers` в
  `operations.ts`, отдельный проход контракт-теста, ручные ключи кэша) и больше тихих ошибок.
- **Как проверять.** scoped = full для юнит-методов (есть аппарат); для баланса под лейблом тест должен
  **фиксировать неравенство** (И5 в `роли/qa.md`), а не обходить его.

### B. Настоящая изоляция данных (своя БД / схема на лейбл)

- **Суть.** Два экземпляра всех семи схем PostgreSQL и реестра файлов, две базы ClickHouse (или фильтр по строке).
- **Что даёт.** Толкование (г) без ролей; аванс 0to8 «сам» не видит доход Echo8.
- **Что ломает.** Один файл 1052428 несёт обе строки: грузить в обе базы (двойной учёт 15 млн в A) или резать при
  загрузке (файл в реестре ≠ файл на диске, sha256 в снимках прошлых выплат не совпадёт, D-053). 357 общих
  владельцев — два владельца с одним контрактом, два баланса, две кнопки, 2 400 исторических выплат режутся
  ретроактивно, слияния по две. B17 — в обе базы или в одну «домашнюю». `calculate()` читает все модули в одном
  `db.snapshot` (D-012, D-121) — межбазовый снимок невозможен, сверка A = B + C + наше по счёту-месяцу (сегодня

### C. Лейбл как переключатель в шапке UI и query-параметр, без заголовка

## 5. Рекомендация: D как данные, C как его интерфейс

### 5.1. Правило

Лейбл — **параметр представления, не заголовок и не граница данных.** Необязательный `label=<id own-лейбла>` на
чтениях, где ответ — сумма по юнитам (обзор, сверка, очередь C, сигналы, треки, каталог, релизы, реклама), через
одно новое поле `labelStrings` в `SnapshotFilter` поверх существующего unit scope (D-161), с тем же тестом

`adsCharged` по лейблу и явное «вне лейбла» у `paid`, `recouped`, `returns`, `credits`, `payable`, паблишинга.

### 5.3. Лейбл, `X-Operator` и аудит

`X-Operator` — личность, нужен только на записи, хук `api/audit.ts` пишет строку в `audit.actions` после 2xx.
Лейбл — контекст представления, нужен только на чтении. Смешивать их в один обязательный заголовок не стоит: у
записей (сплит, участие, документ, операция, правило лейбла, слияние) лейбла нет, 400 `label_required` ничего не
защитит, а «запись под лейблом Echo8» на сплите ISRC из 0to8 — ложь в журнале. У записей лейбл — свойство
**сущности** (`labelId` уже в `BODY_ID_FIELDS` и `entityIds`), не сессии оператора.

Предложение: колонку в `audit.actions` не добавлять, ключ записи не менять (аудит пока почти пуст — менять дёшево,
но потом будет дорого). Если запрос записи пришёл с параметром `label`, скопировать его в `summary.label` (как
`scope`, `kind` сейчас) — информационно, нулевая цена, без миграции. Чтения не аудируются и так.

**Запрос без лейбла = «все лейблы»**, сегодняшнее поведение. Это же умолчание для всех скриптов
(`check-owner-scope.ts`, загрузчик, сверки), контрактного теста и e2e — им ничего менять не нужно. 400 при отсутствии
невозможен ни у заголовка, ни у параметра: половина операций лейбла не имеет.
