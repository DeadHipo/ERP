2026-11-17. Предмет: `проект_привязок.md`. Решение владельца (раздел 1) не оспариваю. Проверено кодом (путь:строка) и

## Блокер

**Б1. Порядок перехода открывает к выплате 15 140,97, которые после включения станут нашими.** Шаг 3 (договоры
саблейблов) идёт до шага 7 (включение). Договор подтверждает владельца 77 Records (`categorise.ts:25`, `owner_unconfirmed`
снимается). Документ правила 77 Records (`other`) уже утверждён (SELECT `label_rules ⋈ documents`). Значит, после шага 3
и до шага 7 вся доля 77 Records, 16 456,38 (цифры № 50), считается по строкам и переходит в B. В эту сумму входят
15 140,97 сольных треков, которых нет в приложении. Сегодня выплату держит только `no_payee`: у 15 получателей 0 строк
`settlements.payees`, 0 выплат (SELECT). Если менеджер заведёт получателя выплаты, кнопка заплатит. После включения
у 77 Records останется минус. У NoGhost тот же риск меньше: 55,64 в B вне приложения. Значит, «риск снимается сам»
верно только при правильном порядке. **Исправить:** договоры получателей саблейблов заводить после включения
(шаг 3 → после 7). Или прямо записать условие включения: «до включения у получателей саблейблов нет получателя выплаты
и нет выплат».

## Важно

**В1. Документ привязки не попадёт в расчёт.** `calculate()` загружает статусы только тех документов, id которых
вернули индексы (`facade/calculation.ts:176-181`: `labelIndex.documentIds()` берёт документы правил,
`modules/labels/service.ts:274-276`). Если не добавить туда документы привязок, `documentStatus` вернёт `missing`.
Тогда деньги каждой привязки с утверждённым договором ждут как `rule_unconfirmed`. В §9 нет проверки на этот случай,
есть только «без документа → ждёт». **Исправить:** одна строка в §7 и один тест «привязка с утверждённым документом →
B».

**В2. Охват получателя потеряет рекламу.** По §7 `owner-scope.ts` перестаёт искать ISRC по строкам
(`owner-scope.ts:61-64`). Но реклама по решению владельца остаётся на строке и правиле: `ads.ts:79,83`, а получатель
берётся из правила, `ads.ts:123`. Сегодня саблейбл несёт рекламу на двух ISRC: FR10S2695088 (240,20 + 265,58) и
FR10S2695089 (91,00), строка `NoGhost Records / 0to8`, всего 596,78 (SELECT `ads.expenses` + CH). Если их не будет
в привязках NoGhost, баланс по охвату ≠ полному. **Исправить:** пока реклама на строках, охват = ISRC привязок **плюс**
нынешний поиск по алиасам получателя. Это ничего не стоит.

**В3. Неверная фраза «расчёт больше не читает `label_name`, `label_aliases`, `label_rules`» (§3).** Реклама считается
внутри `calculate()`: `calculation.ts:288-353` (`labelStringOf`, `ctx.labelOf`). Таблица §4 говорит иначе («читает
реклама»). **Исправить:** «доли не читают; читает только реклама».

**В4. Нет пути «документ пришёл позже».** Решение 4: без документа деньги ждут. Решение 3: записи не правятся. Как
тогда подтвердить запись, проект не говорит. Повтор той же записи с документом попадёт в класс `unchanged`, если тот
сравнивает без документа. **Исправить:** записать правило. Тот же список, то же начало, с документом. По правилу
«равное начало — созданная позже» новая запись подтверждает старую. В `unchanged` сравнивать и документ.

**В5. Отменяется строка, а владелец сказал «запись».** Владелец: «ошибочную запись можно отменить». Запись — это
партия (`batch_id`). API отменяет только одну привязку (`/labels/bindings/:id/cancel`). Неверный документ на 31 треке
77 Records — это 31 отмена. **Исправить:** `cancel` принимает `batchId` или `id`. Маршрут один.

**В6. Запрет отмены «по выплаченным деньгам» не реализуем и непоследователен.** Снимок выплаты хранит позиции по
никам и треки, обрезанные до 200 (`payouts.ts:275-296`). Id привязки в нём нет, поэтому «по этой привязке платили»
не вычислить. А задним числом новая запись или закрытие меняют прошлые месяцы так же, но их проект не запрещает.
**Исправить:** отмена разрешена всегда, как любое изменение задним числом (решение 6). Переплата видна отрицательной
позицией ника (D-181). Это закрывает и открытое место 2.

**В7. Очередь рассыплется на сотни строк.** Очередь группирует по `a.ruleId` (`queue.ts:171-181`). Сегодня это
16 правил, при привязках будет id каждой привязки: около 1 756 групп (цифры № 19). Подпись группы всё ещё строка
отчёта (`queue.ts:179`). **Исправить:** ключ группы — «саблейбл + документ», подпись — название саблейбла. Файл вне
закрытой зоны.

## Правило версий: одно, без «конца»

В проекте два механизма: «самое позднее начало» и «конец записи» (`valid_to`, `close`). В сплитах и условиях pubv2
действует цепочка «новая закрывает старую, отменить можно только последнюю» (D-188). Сравнение на трёх примерах:

| пример | «позднее начало» без конца | цепочка (как D-188) |
|---|---|---|
| выкуп с 2026-09 | новая партия с 2026-09; готово | новая закрывает старую; готово |
| ошибка в начале: стояло 2026-03, надо 2025-11 | добавить с 2025-11; до марта действует она, с марта старая; процент тот же — готово, отмена не нужна | отменить последнюю, завести новую (2 действия) |
| переезд с X | новая привязка к другому саблейблу с X | то же |

Сюрприз при «позднем начале» один: новая запись с ранним началом не перекрывает позднюю. Его ловит класс `shadowed`.
Сюрприз при «конце»: если у записи 2026-03…2026-06 есть конец, с июля снова действует более ранняя запись. **Предлагаю**
«позднее начало» без `valid_to`. «Трек перестал быть саблейбла» — новая запись 0 % с X: расчёт это уже поддерживает,
`carve.ts:167`. Человеку это объясняется одной фразой: «в каждом месяце действует запись с самым поздним началом».
Записи только добавляются и отменяются, ни одна не правится. Решение 3 соблюдается буквально.

Что потеряется: «конец» как отдельная кнопка (её заменяет запись 0 %). Уходят колонки `valid_to`, `closed_by`,
`closed_at`, CHECK, маршрут `close`, статус «закрыта», поле `validTo` в строке.

## Самая маленькая первая поставка

**Обязательно:** таблица привязок без конца; колонка получателя; `POST /labels/sublabels`; `GET` и `POST` привязок
(пробный прогон: ошибки плюс четыре предупреждения `overrides`, `shadowed`, `no_document`, `isrc_not_in_catalog`);
отмена по id или партии; подсказки месяца по строке; кнопка «все действующие треки»; теневой прогон.

**Отложить:** импорт csv/xlsx (теряется только загрузка 5 000 строк файлом: список вставляется текстом, страница
сама разбирает csv); подсказки по UPC и приложению; классы `new` и `unchanged` (повтор той же записи безвреден по
правилу «созданная позже»); отдельный маршрут истории трека.

**Переключатель `LABEL_SOURCE`:** оставить на время перехода, но назвать срок удаления старой ветки. Пока ветка жива,
жива и вторая модель в коде.

**Выгрузка 12 саблейблов «потом»:** не ждать её для включения. Решение 10 и ответ владельца «сделаем выгрузку потом»
означают, что включение по проекту откладывается без срока. Проще другое. Подсказка по строке один раз предлагает
партии для 12 саблейблов: ISRC под их строкой в месяцы их правила, документ — сегодняшнее допущение. Человек
утверждает партию. Числа 12 саблейблов те же (ждут 5 164,02 как `assumption`). Строка здесь только подсказка, решает
человек, как и разрешил владелец. Выгрузка потом заменит эти партии отменой и новой записью.

## Слова для владельца: три фразы переписать

1. «саблейбл получает процент **доли лейбла после артистов и участий**» → «Из денег трека сначала платим артистам и
   тем, у кого есть отдельная доля. Из того, что осталось лейблу, саблейбл получает свой процент».
2. «Из них действует та, у которой самое позднее начало; при равном начале — созданная позже … **не** перекрывает
   привязку с более поздним началом» → «В каждом месяце работает запись с самым поздним началом. Если начала равны —
   более свежая».
3. «Чего расчёт больше не читает: `label_name`, `label_aliases`, `label_rules`» и таблица «строка → алиас → лейбл» →
   «Название лейбла в отчёте Believe больше не решает, чей трек. Решает только ваш список треков саблейбла. Название
   мы покажем рядом как подсказку. Исключение пока одно — реклама».
