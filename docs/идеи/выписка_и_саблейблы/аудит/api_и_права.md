# Аудит проекта привязок: база, API, права, след, страницы

2026-11-17. Предмет: `проект_привязок.md` (далее «проект»), разделы 4–6, 8, 10. Решение владельца не оспаривается.
Все SELECT — только чтение живой базы `erp`; ClickHouse — только загруженные файлы (48 из 48, `source_files.status='loaded'`).

## Блокеры

**Б1. «Закрыть привязку» возвращает к жизни предыдущую.** Правило проекта (строки 47–49): из неотменённых привязок с
`начало ≤ M` и `(конца нет или конец > M)` действует та, что начинается позже. Закрытая с месяца X привязка B выпадает
из кандидатов — и с X снова действует более ранняя открытая A. Примеры из самого проекта: NoGhost (стр. 207: допущение
Q12 с 2026-02 без конца и договор с 2026-06) — закрыли договор, и деньги снова ждут как «допущение» вместо «наше»;
выкуп 50 % → 25 % — закрыли 25 %, вернулись 50 %. Это противоречит строке 56 («трек перестал быть саблейбла»).
*Проще:* брать **одну** привязку с самым поздним началом ≤ M; если у неё конец ≤ M — трека у саблейблов нет (доля наша).
Ещё проще — как условия паблишинга v2 (D-185/D-188, `operations.ts:1763–1790`, миграция `0029_isrc_terms.sql`):
уникальный индекс `(org_id, isrc, valid_from) WHERE cancelled_at IS NULL` и отказ `409` на привязку с началом ≤ уже
действующего начала; отменять можно только последнюю, предыдущая снова действует. Тогда исчезают класс `shadowed`,
правило «при равном начале — созданная позже» и ошибка оператора из п. 5 ниже. Записи по-прежнему не правятся.

**Б2. Охват получателя нельзя строить «вместо» строк, пока реклама читает строки.** Проект (стр. 185) заменяет поиск
по строкам в `owner-scope.ts` привязками. Но тот же поиск нужен рекламе: `owner-scope.ts:11` («ads borne by the
sublabel are looked up by the same strings»), `owner-scope.ts:62–64`; `facade/ads.ts:79` берёт саблейбл через
`ctx.labelOf(строка, дата)`. Реклама остаётся по строкам (решение 9), значит рекламная запись на треке со строкой
NoGhost вне привязок (29 треков вне приложения) выпадет из охвата, и баланс получателя по охвату ≠ полному (у NoGhost
сегодня 596,78 рекламы). *Проще:* охват = ISRC привязок **плюс** нынешний поиск по строкам, пока реклама не переедет;
и `LayerContext.labelOf` в `layers/types.ts` оставить рядом с `bindingAt` (его читает `ads.ts:58`), а не заменять.

## Важно

**В1. Нет пути «приложить документ потом».** Решение 4: без документа деньги ждут бессрочно. Записи не правятся,
значит подтвердить такую привязку можно только повторной записью тех же ISRC с документом (с тем же началом —
выигрывает созданная позже; при Б1 «проще» — вообще нельзя). Для 12 саблейблов это удвоит строки. Прецедент есть:
`POST /splits/assume` ставит документ сплитам, у которых его нет (`operations.ts:1350–1357`).
*Проще:* одно разрешённое изменение, как закрытие: `POST /labels/:id/bindings/document { documentId, batchId }` —
ставит документ строкам пакета, где `document_id IS NULL`. Отдельная таблица пакета не нужна: `batch_id` в строке
хватает; документ и автор дублируются, но это три колонки, а не новое понятие.

**В2. Пробный прогон оставит строку в аудите, а след будет без ISRC и без лейбла.** Хук пропускает предпросмотр только
для маршрутов из `RESPONSE_SUMMARY_ROUTES` (`api/audit.ts:350`); без записи там `dryRun=1` (ответ 200) запишется как
действие. ISRC из `items[].isrc` в `entityIds` не попадут (читается только `body.isrcs`, `audit.ts:232`) — поиск в
аудите по ISRC «кто привязал» не найдёт. Лейбл строки аудита будет `null`: `:id` — саблейбл, а он «never recorded»
(`audit.ts:53`); менеджер своего лейбла этих записей не увидит. *Исправить:* по записи в `RESPONSE_SUMMARY_ROUTES` для
`POST /labels/:id/bindings` (preview по `dryRun`, summary `{sublabelId, documentId, batchId, created, unchanged}`,
ids = id созданных строк + ISRC), и ответ несёт `labelId` = свой лейбл саблейбла, маршрут — в `RESPONSE_LABEL_ROUTES`.
Ответ `{ created: число }` сломает `createdIdsOf` (ждёт массив объектов с `id`, `audit.ts:237–248`): назвать
`createdIds`. `cancel.reason` — свободный текст, в `SUMMARY_FIELDS` его нет (`audit.ts:28`) — так и оставить.

**В3. Отмена «если нет выплаты по привязке» не проверяема.** Снимок выплаты хранит итоги баланса и до 200 треков на
ник, но ни id правил, ни id привязок (`facade/payouts.ts:275–301`). Сегодня `settlements.payout_snapshots` = 0 строк,
выплат владельцам-получателям саблейблов = 0 (SELECT по `operations.kind='payout'` × `label_rules.recipient_artist_id`).
Правки сплитов задним числом никакой проверки выплат не делают (`blockingPayoutsOf` используют только выплата и
слияние). *Проще и честнее:* отменять можно всегда; переплата станет отрицательной позицией ника и закроется будущим
доходом того же ника (D-181). Единственная проверяемая и полезная защита — отказ, пока у владельца-получателя есть
выплата без подтверждения (`settlements.blockingPayouts(ownerId)`, как `mergeOwners`, `owner-view.ts:151`).

**В4. Получатель «ставится один раз» и миграция.** SELECT: 15 саблейблов, 16 правил, у каждого саблейбла ровно один
ник-получатель, ник не слит, владелец вида `label`, у владельца ровно один ник; договор (`owners.contracts`) есть только
у владельца NoGhost. Значит, п. 2 перехода делается **в самой миграции** одним `UPDATE … FROM label_rules`, и тогда
сразу можно поставить CHECK `kind='own' OR recipient_artist_id IS NOT NULL`; иначе CHECK нельзя, а `POST /labels`
по-прежнему создаёт саблейбл без получателя (`modules/labels/service.ts:91–117`) — его нужно закрыть для
`kind=sublabel` (только через `/labels/sublabels`). Слияния: `mergeOwners` двигает ники, колонку не трогает — верно;
после `mergeArtists` колонка указывает на слитый id, читать её только через `artistIndex()` (как `ads.ts:123`,
`label-scope.ts:78`). Смена контрагента = новый саблейбл и «переезд» привязок с месяца X, не правка колонки (правка
переписала бы получателя всей истории задним числом).

**В5. Подсказки несут деньги — это `read_money`, и они дорогие.** `GET …/suggestions` с суммой net при классе `read`
отдаст деньги лейбла менеджеру другого лейбла (`read`/`org` у менеджера = `allow`, `abilities.ts:101–105`). Нужен
`read_money` со scope `record` (свой лейбл саблейбла). Что есть в коде: строки → ISRC через алиасы
(`sources.isrcsOfLabelAliases`, 2 запроса ClickHouse; сумма за месяц — третий); тот же UPC — `isrcsOfUpcs`
(1 запрос); индекса договоров в рантайме нет (только скрипт `scripts/stage3/add-index-contracts.ts`) — третий источник
пока убрать. В деньги строка не протечёт, если подсказки живут в фасаде вне `calculation.ts`; закрепить тестом как
`boundaries.test.ts` для каталога.

**В6. Правило ISRC и менеджер.** Варианты (не решаю):
- A (проект): только администратор. Цена 0; менеджер просит администратора.
- Б: менеджер заводит привязки **только класса `new`** к саблейблам своего лейбла, документ не обязателен; закрытие,
  отмена, документ — администратор. Класс `write`, scope `record` (фасад: `ownLabelId` ∈ лейблы зрителя и
  `mayTouchIsrc` для каждого ISRC, `viewer.ts:104`), строки `overrides` — запрещённые, как у импорта сплитов
  (`operations.ts:774`: «A label manager may only create»). Риск: доля лейбла уходит из «наше» в «ждёт», но выплатить её
  нельзя без утверждения. Цена: 1 проверка в фасаде, строки `R` в `tests/helpers/manager-answers.ts`. Учтите: трек
  саблейбла Echo8 из файлов 0to8 менеджер Echo8 тронуть не сможет — это верно, деньги в книге 0to8.
- В: «предложение» с отдельным статусом — новое понятие, не советую.

**В7. Месячная работа.** ClickHouse (новые ISRC под строками саблейблов по месяцу первого появления): 2025-10 125,
2026-02 108, 2026-05 134, 2026-06 344, 2026-07 231, 2026-08 200. На странице каждого саблейбла: открыть, вкладка,
выделить, документ, процент, предпросмотр, записать ≈ 7 кликов × 15 = ~105 кликов и 15 переходов. *Проще:* одна
страница «Подсказки месяца» по всем саблейблам (группы), процент и документ по умолчанию — из последней привязки
саблейбла (правил больше нет, иначе 50 % вводится руками каждый раз): ≈ 3 клика на группу.

## Мелочи

- `org_id uuid` в проекте неверно: во всех таблицах `text` (`0016_organizations.sql:8`, `0024_links.sql:7`,
  `labels/schema.ts:10`). Нужны `orgId notNull()` в `schema.ts`, `<таблица>_org` индекс, все SQL через `orgWhere`;
  `tests/org-scope.test.ts:59` ждёт 42 таблицы — станет 43.
- Конец: проект шлёт `{ from }`, а все закрытия проекта — `{ validTo }` (`closeValidToBody`, `/labels/rules/:id/close`,
  `/participations/:id/close`). Взять `validTo`.
- Два GET (`/labels/:id/bindings`, `/tracks/:isrc/bindings`) — лишний: вкладка «Правила» трека уже показывает
  «правило каждого месяца» из `months[].rule` (`RulesTab.tsx:168–201`) — подменить id правила на id привязки; полный
  список — один `GET /labels/bindings?sublabel=&isrc=`.
- Два POST (JSON и файл) — оставить один; `jsonBody` держит 1 МБ (`api/http.ts:69`), 5 000 строк влезают. Предел
  5 000 записать в схему.
- Повтор той же записи: при `created = 0` не заводить пустой `batch_id`, отвечать `batchId: null`.
- Документ привязки: проверить вид по `SPLIT_DOCUMENT_KINDS` и, если у документа есть владелец, что это владелец
  получателя (как `409 document_owner_mismatch` у условий v2). Сегодня у 16 документов правил `owner_id` пуст.
- «Завести саблейбл» с документом договора: `createContract` берёт только `contract | label_decision`
  (`document-kinds.ts`), а документы 77 Records и R2R — вида `other`. Либо заводить договор отдельным шагом, либо
  поменять вид — решение владельца прошлого совета.
- Маршрут `/labels/bindings/:id/close` объявить до `/labels/:id/…` (как `routes/labels.ts`, комментарий над `rules`).
- Старые маршруты: правила и алиасы после включения **влияют на рекламу** (`ads.ts:79–124`); страница должна писать
  «только реклама и подсказки», а не «ни на что». Закрыть их нельзя до решения по рекламе: новый саблейбл без правила
  не понесёт свою рекламу.
- `GET /labels/:id/bindings` с `read`/`org` покажет менеджеру привязки чужого лейбла (без денег; `GET /labels` уже так
  делает) — допустимо, но лучше `record`.

## Что в проекте верно и проверено

- Один ISRC в одном месяце никогда не идёт под двумя строками саблейблов и под строкой саблейбла вместе со своей:
  0 пар ISRC×месяц (ClickHouse, `map(alias_norm→label_id)` по загруженным файлам). Привязка по ISRC выражает все
  сегодняшние данные (открытое место 5 снято).
- У всех 48 загруженных файлов есть книга (`source_files.label_id IS NULL` — 0): «наше» по книге файла считается для всех.
- У каждого из 15 саблейблов ровно один получатель (SELECT выше) — колонка на лейбле вместо правила корректна.
- Класс действия `approve` для привязок верен по D-171 («binding income to an owner», `abilities.ts:9`); для менеджера и
  поддержки `approve` и `admin` одинаково запрещены (`abilities.ts:105,125`), так что разница только смысловая.
- Образец «предпросмотр + всё или ничего» есть (`/splits/import`, `operations.ts:769–790`; аудит предпросмотра —
  `audit.ts:350`), отмена с причиной без удаления — `links.publishing_terms` (`0027_terms_cancel.sql`).
- Новых причин ожидания не нужно: `rule_unconfirmed` и `assumption` уже есть (`packages/shared/src/reasons.ts:6–7`).
