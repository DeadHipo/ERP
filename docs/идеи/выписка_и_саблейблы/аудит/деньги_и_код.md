## Блокеры (2)

**Б1. Если закрыть привязку, снова начинает действовать старая привязка того же трека.**
Правило проекта (§3): «из привязок, которые покрывают месяц, действует та, у которой самое позднее начало».
Закрытая привязка месяц больше не покрывает, поэтому снова начинает действовать более ранняя открытая.
Проект сам заводит NoGhost двумя записями на трек: допущение Q12 с 2026-02 и договор с 2026-06, причём первую не закрывает.
Пусть потом человек «закрыл трек с месяца X» так, как велит §3. Тогда с X снова действует допущение Q12, и деньги опять уходят NoGhost (в C «допущение»).
У 77 Records так же: после «выкупа 25 % с X» и его закрытия вернутся прежние 50 %.
Человек ждёт обратного: «трек больше не саблейбла».
*Как исправить проще:* брать привязку с самым поздним началом **среди всех, у кого начало ≤ M**, не глядя на конец.
Если у неё есть конец и он ≤ M — привязки нет. Тогда новая запись навсегда заменяет старые с месяца своего начала, а закрытие означает «с X ничей».
Новых понятий и таблиц не нужно. Так же пересчитать классы `overrides` и `shadowed` в пробном прогоне.

**Б2. Охват получателя потеряет рекламу, если реклама останется на строках.**
`owner-scope.ts:61-64` находит ISRC получателя саблейбла по строкам (`isrcsOfLabelAliases`).
Проект (§7) заменяет это поиском по ISRC привязок, а реклама при этом читает строку и старое правило (`ads.ts:77-83`, `calculation.ts:327`).
`labelStringOf` строится по юнитам расчёта (`calculation.ts:308`), а под охватом это только юниты из охвата.
Значит, у объявления на ISRC со строкой NoGhost, которого нет в привязках, в расчёте по охвату строки нет. Его непокрытая часть уйдёт «нам», а не NoGhost.
Баланс по охвату ≠ полный баланс: это ломает `tests/scope.test.ts` и `check-owner-scope.ts`, а через `balanceWithFiles` и снимок выплаты меняет сумму к выплате.
Цифра: саблейблы сегодня несут рекламу на 596,78 (NoGhost, 2026-02…04; `get-ads-summary`, `borneBySublabels`).
*Как исправить:* либо (а) пока реклама на строках, оставить в `owner-scope.ts` и путь по строкам, и путь по привязкам (объединение двух множеств; правка одной строки);
либо (б) сразу дать рекламе `bindingAt(isrc, месяц)` — см. В7.

## Важно

**В1. Документы привязок не попадут в статусы.** Статус документа расчёт знает только для id из `docIds`: `calculation.ts:177-183` собирает их из `splitIndex`, `labelIndex.documentIds()` (правила) и условий.
Если индекс привязок не отдаёт свои `documentIds()`, то `documentStatus` вернёт `missing` для каждого документа привязки (`calculation.ts:201-202`).
Тогда все деньги привязок уйдут в C `rule_unconfirmed`, даже по утверждённому договору.
Предложение: явно вписать это в §7 и добавить в тест слоя случай «утверждённый документ → B».

Грепом по `labelOf|setRule|addAlias|label_unmapped|labelUnmapped|labelOutsideAccount|rules:|aliases|ourLabelId|ourShareByLabel` в `tests/` находится 20 тестовых файлов плюс помощники (`layers/world.ts`, `helpers/golden-case.ts`, `helpers/fixtures.ts`).

**В4. Q11 включится там, где его сегодня нет.** `categorise.ts:14,18` помечает допущением и выплату саблейблу, и участие из доли лейбла (`label_share`), если они стоят на одном юните.

Предложение: в пробный прогон добавить предупреждение `q11` («у трека есть участие из доли лейбла: обе части будут ждать»). Новых понятий не нужно.

**В5. Отмену нельзя проверить по снимку выплаты (§5).** В снимке (`payouts.ts:275-298`) нет ни `ruleId`, ни id привязки: там только `perArtist.tracks` (первые 200) и позиции.

Проще правило: отменять можно, только если у ника-получателя нет выплаты в книге, датированной после `valid_from` привязки. Иначе — «закройте с месяца».

**В6. Получатель «ставится один раз» на саблейбле.** Сегодня получатель задаётся на каждом правиле и периоде (`label_rules.recipient_artist_id`, 16 строк, 15 разных ников). Если перенести его на `labels.labels`, его смена перепишет прошлые месяцы и оплаченные позиции.

## Мелочи

- М1. Сигнал `sublabelWithoutRule` (`reports.ts:234-243`) при привязках всегда пуст, а проект называет только `labelOutsideAccount` и `labelUnmapped`. `ruleRecipientIsRow` (`:245`) продолжает работать.
- М2. Очередь подписывает группу саблейбла строкой отчёта (`queue.ts:180`: `${u.labelName} → ник`). Это противоречит п. 7 решения; лучше подписывать названием саблейбла.
- М3. `ruleId` в выплате = id привязки (`carve.ts:172`). Тогда очередь C строит одну группу на ISRC (`queue.ts:181`): у NoGhost это 360 групп вместо одной. Проще класть в `SublabelRule.id` значение `batch_id` (одна запись = один документ), а id привязки показывать в пояснении.
- М4. Причина `r1` (`categorise.ts:19`) мертва уже сегодня: без сплита `split.ts:14` ставит `no_split`, и `carve.ts:167` не запускает выплату саблейблу. Строка таблицы §3 «трека нет в привязках → доля наша» верна только при наличии сплита. Без сплита доля ждёт `no_split` (D-175).
- М5. Порядок «начало, время создания, id»: `created_at` одинаков у всех строк одной записи, но в одной записи ISRC не повторяется (`duplicate_in_request`). Записи сериализованы advisory-lock, так что порядок полный. Записать, что `created_at` берётся из `nowIso()` приложения, а не из `now()` транзакции.
- М6. Привязку ISRC к саблейблу другого своего лейбла (книга Echo8, саблейбл 0to8) стоит пометить в пробном прогоне. В этой книге ворота выплаты потребуют договор этой книги (`no_contract_for_label`). Сегодня таких юнитов 0.
- М7. `label-scope.ts:77-78` (видимость под лейблом) должен брать получателей привязок, ISRC которых лежат в файлах лейбла, а не получателей правил саблейблов с `ownLabelId`.
