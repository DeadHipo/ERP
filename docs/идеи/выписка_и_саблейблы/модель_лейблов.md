# Модель лейблов и саблейблов

2026-11-17, третья редакция. **Раздумья, кода нет.** Записывает решения владельца от 17.11 (привязки по ISRC, «просто
`kind = sublabel`», принцип «каждому своё») и то, что из них следует. База, API и переход — в `проект_привязок.md`;
сверка договоров — в `периметр.md`; вопросы — в `вопросы.md`. Прежняя модель совета («привязка только как
исключение») осталась в `консилиум/` и в истории git. Суммы — в долларах США, из живой базы и ответов ERP.

## 1. Коротко

- **Лейбл** — свой лейбл организации. **Саблейбл** — внешний партнёр внутри него. Человек видит только эти два слова:
  ника-кошелька и «владельца саблейбла» для него нет.
- **Трек становится треком саблейбла, когда его привязали:** ISRC, с какого месяца, сколько процентов доли лейбла, по
  какому документу. Текст отчёта Believe на деньги не влияет.
- **Саблейбл получает свой процент доли лейбла после артистов** — формула прежняя.
- **Отчёт саблейбла** — его треки по месяцам: доля лейбла по договору, его процент, его часть, что из неё ждёт и
  почему. Чужих денег в отчёте нет.
- **Ник-получатель не убираем, а прячем:** внутри расчёта он остаётся, человек его не видит и не заводит. Расчёт при
  этом не меняется ни на знак.

## 2. Словарь (пять слов)

| слово | что это | пример |
|---|---|---|
| **лейбл** | свой лейбл организации; его книга — отчёты его аккаунта Believe | 0to8, Echo8 |
| **саблейбл** | внешний партнёр внутри лейбла (`kind = sublabel`). Он же получает деньги | NoGhost внутри 0to8; всего 15 |
| **привязка** | «этот трек с такого-то месяца — такого-то саблейбла, столько-то процентов доли лейбла». Это и есть «сплит нашей стороны» | трек приложения 77 Records, 50 %, с 2025-11 |
| **документ** | основание привязки; без утверждённого документа её деньги ждут | договор #13112026-77RECORDS |
| **отчёт саблейбла** | его треки и его часть по месяцам | NoGhost, сентябрь 2026: 10 596,47 |

Что уходит из слов человека: ник-получатель, владелец саблейбла, алиас, импринт, правило саблейбла, лейбл записи.

## 3. «Просто kind = sublabel»: ник прячем, а не убираем

**Что сегодня.** Один саблейбл записан трижды: лейбл вида `sublabel`, владелец вида «лейбл» и его ник, на который
приходят деньги. Проверено по базе: саблейблов 15, правил 16 (действующих 14); у каждого саблейбла ровно один ник;
у всех 15 имя ника равно имени саблейбла; на этих никах нет ни одной строки сплита, участия, операции и получателя
выплаты. Ник чисто технический.

**Два пути.**

| | убрать ник совсем | оставить внутри и спрятать |
|---|---|---|
| что это значит | получателем денег становится сам лейбл | ник и его владелец создаются автоматически при заведении саблейбла и не показываются |
| закрытые файлы расчёта | 7–8 (типы, аллокация, вырезки, категории, погашение аванса, баланс, охват, расчёт) плюс реклама и выплаты | **0** сверх проекта привязок |
| числа | поменялись бы причины ожидания; нужно новое понятие «подтверждённый саблейбл» | **те же, по построению** |
| аванс, реклама, выплата | всё это сегодня держится на правиле «каждый получатель — ник»: аванс гасится из дохода того же ника, реклама списывается на ник, выплата делится по никам | работает как сегодня |
| для человека | разницы нет | разницы нет |

**Выбор: спрятать.** Все три независимых участника пришли к этому. Для человека оба пути выглядят одинаково, а
первый стоит перестройки расчёта без единой выгоды.

**Как это выглядит.**

- «Завести саблейбл» — одно действие: название и свой лейбл. Лейбл, технический владелец и ник создаются разом.
- Признак «технический» не хранится: ник технический, если он — получатель какого-то саблейбла.
- Технические ники и их владельцы не показываются в списках артистов и владельцев, в поиске, в подсказке дублей, в
  формах сплитов. Их карточка — это карточка саблейбла: привязки, документы, отчёт.
- В привязке получатель — **саблейбл**; ник расчёт находит сам.
- Договор и документы саблейбла технически лежат на его владельце (так расчёт узнаёт, что получатель подтверждён), а
  показываются на карточке саблейбла.

## 4. Запрос «треки саблейбла и сколько они заработали для него»

**Самый простой путь — проекция существующего расчёта.** Расчёт уже считает для каждого трека и месяца вырезку
саблейбла. Отчёт берёт эти же вырезки по трекам саблейбла и группирует по треку и месяцу. Нового расчёта нет, новых
умножений нет.

**Сходится ли с балансом.** Да, по построению: баланс ника суммирует те же вырезки. Проверено оркестратором по ответам
ERP:

| саблейбл | треков | сумма по трекам | баланс ника | состав |
|---|---|---|---|---|
| NoGhost | 336 | 35 250,903002566597 | 35 250,903002566597 | подтверждено 29 732,99; ждёт 5 517,92 |
| 77 Records | 53 | 16 456,382973283450 | 16 456,382973283450 | всё ждёт |
| R2R PRODUCTION | 104 | 603,205465895361 | 603,205465895361 | всё ждёт |

Один трек, один месяц (R2R, FRX452634470, отчёт за сентябрь 2026): доля лейбла после артистов 41,304537607783, часть
саблейбла 20,652268803892 — ровно столько стоит по этому треку в балансе ника; весь сентябрь R2R — 132,126924314409 и
там, и там.

**Чего сегодня не хватает.** Таблицы «трек × месяц» одним ответом нет: есть «по трекам за всё время» и «итог по
месяцам». И сегодняшний ответ показывает валовой доход трека, чего саблейбл видеть не должен.

**Что видит саблейбл (принцип «каждому своё»).**

| показываем | не показываем |
|---|---|
| месяц, код и название трека | валовой доход трека (у NoGhost за сентябрь это 40 614,49 при его части 10 596,47) |
| доля лейбла по договору (то, от чего считается его процент) | сплиты и суммы артистов |
| его процент | нашу часть |
| его часть | строку отчёта Believe, ник, владельца |
| из неё подтверждено, ждёт и почему | слои расчёта и промежуточные суммы |
| итог по месяцу и за период | треки, где его часть равна нулю (у NoGhost за сентябрь таких 22) |

«Доля лейбла по договору» — единственная промежуточная сумма в отчёте. Она не чужие деньги: это база его собственного
пункта договора («50 % доли лейбла»). При 50 % она ничего нового не раскрывает. Показывать ли её — вопрос 2.

Оператору тот же отчёт нужен раньше ссылки для саблейбла: он входит в поставку привязок. Ссылка и вход саблейбла —
отдельная цель.

## 5. Привязка по датам на примерах

**Выкуп части лейбла.** Трек NoGhost FRX282688758, отчёт за сентябрь 2026: доля лейбла после артистов 5 784,45,
часть NoGhost при 50 % — 2 892,23. Новая привязка «25 % с сентября 2026» по документу выкупа: часть NoGhost
1 446,11, наша прибавка 1 446,11. По всем трекам NoGhost за сентябрь: 10 596,47 → около 5 298,24. Прошлые месяцы
не меняются: прежняя привязка действует до сентября.

**Переезд трека.** Трек FRX282623697 в июле 2026 пришёл под строкой Hoboshrine (его часть 1,49 ждёт), а в августе и
сентябре — под строкой 0to8. По привязкам строка ничего не решает: если привязка к Hoboshrine без конца, он получит
ещё 3,54 за август и сентябрь; если трек ушёл — привязку закрывают с августа, и доля наша. Переезд к другому
саблейблу — новая привязка к нему с месяца X.

**Совместный импринт «0to8 x …».** Строка не решает ничего. Треки партнёра привязаны к нему, остальные — наши.

**Исключённый проект.** Договор 77 Records исключает сольные релизы основателя. В привязках их просто нет: 22 трека,
15 140,97 остаются у 0to8 (сегодня эти деньги ждут в пользу 77 Records).

## 6. Что меняется и что нет

| | меняется | не меняется |
|---|---|---|
| слова | два слова для человека вместо трёх записей; «привязка» вместо алиаса и правила | — |
| таблицы | +1 привязки, +1 колонка «получатель саблейбла»; позже уходят правила, алиасы, история каталога (48 → 49 → 46) | владельцы, ники, сплиты, операции |
| расчёт | откуда берётся «чей трек и какой процент» (4 закрытых файла, `проект_привязок.md`) | формула доли саблейбла, доли артистов, баланс, аванс, реклама, выплаты |
| скрытие ника | только показ: списки, поиск, формы | расчёт: 0 файлов, 0 изменений чисел |
| отчёт саблейбла | новое чтение существующих сумм | сами суммы |
| числа при включении привязок | 77 Records −15 133,87; NoGhost −68,23; R2R 0 (`проект_привязок.md` §8) | всё остальное |

**Аванс и реклама** (решаются позже). Модель им не мешает: обе вещи уже работают на нике получателя — аванс гасится
из дохода того же ника, невозмещённая реклама списывается на него (сегодня у NoGhost 596,78). Раз ник остаётся внутри,
ничего не надо перестраивать.

**Получатель выплаты, канал, порог, ведомость** — вне этой модели, как вы и сказали.

## 7. Что пересмотреть в итоге совета «модули и документы»

| решение совета | что с ним теперь |
|---|---|
| **Р6, шаг 1** — срок действия у строки отчёта | снимается: вы ответили на В1 «да», строка в деньгах не участвует вовсе. Шаг 2 (решение по ISRC) становится единственным |
| **Р7** — переразметки только вперёд с открытого месяца | меняется: задним числом можно. Остаётся оговорка: если по месяцу уже была выплата, получатель уходит в минус |
| **Р19** — владелец как единственный центр «кто есть кто» | дополняется исключением: у саблейбла центр — карточка лейбла, а его технический владелец скрыт |
| **Р26 / В7** — выписка артиста и партнёра отдельной целью | остаётся, но отчёт саблейбла для оператора делается раньше, вместе с привязками. Принцип «каждому своё» делает выписку уже карточки: в ней только «моё» |
| **Р13 / В2** — история каталога трека | без изменений: её место в навигации занимает история привязок |
| метрика «закрытых зон 0» | не выполняется: привязки открывают 4 закрытых файла. Это цена решения «строго по ID» |
