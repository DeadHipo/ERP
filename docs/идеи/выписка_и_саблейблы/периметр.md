# Периметр трёх саблейблов: приложение договора против ERP

Сверщик периметра, 2026-11-17. Вопрос 6 брифа: NoGhost, 77 Records, R2R PRODUCTION. **Только отчёт, решения — у
владельца.** В базе только SELECT, в ERP только чтение. Имена людей, реквизиты и тексты договоров не перенесены.

## Что проверено и чем

| Что | Чем |
|---|---|
| Состав приложений | текстовый слой PDF (`pypdf 6.4.0` во временном окружении вне репозитория): записи режутся по дате релиза, ISRC = префикс + пятизначный хвост из соседней строки. 360 / 31 / 149 записей, все ISRC уникальны |
| Что склейка верна | (1) название из PDF совпало с названием трека в Believe или `owners.tracks` у **всех** ISRC, у которых трек есть в ERP: 360 из 360, 31 из 31, 142 из 149; (2) навык `contracts-0to8` (`/contracts/…?catalog=1`) даёт по договорам #13112026-77RECORDS и #13112026-R2RPRODUCTION те же 31 и 149 ISRC, совпадение 100 %, `state: done`, `level: high`, конфликтов нет |
| Правила и основания | `labels.label_rules` ⋈ `owners.documents` |
| Строки Believe | ClickHouse `believe.rows`, только 48 файлов `status = 'loaded'` (`file_id IN (…)`), группировка (ISRC, отчётный месяц, `label_name`), `sum(net_revenue)`; книга 0to8 — отчёты по 2026-09 |
| Сплиты | `splits.splits` ⋈ `split_shares` (сумма долей на месяц отчёта) |
| Доля саблейбла по треку | ответ ERP: `GET /artists/{ник получателя}/balance` (тот же, что MCP `get-artists-by-id-balance`), поле `tracks[]`: `amount` (B) + `waiting` (C). Это **фактическая** доля, не оценка |
| Помесячно и к выплате | `GET /owners/{id}/balance` (MCP `get-owners-by-id-balance`): `period.byMonth`, `total`, `payout` |

**Множество «ERP»** = ISRC, у которых есть строка Believe с `label_name`, ведущим через `label_aliases` на саблейбл, в
отчётный месяц, где действует его правило. Месяцы правил: NoGhost с 2026-02 (2026-02…05 — допущение Q12, с 2026-06 —
договор от 19.06.2026); 77 Records с 2025-11; R2R с 2026-05. Начала правил совпадают с датами вступления договоров
(05.11.2025 → 2025-11, 18.05.2026 → 2026-05, 19.06.2026 → 2026-06) по правилу первого числа месяца (M52).

Строки ERP: NoGhost — 6 строк Believe (`NoGhost Records`, `NoGhost Records / 0to8`, `0to8, NoGhost Records`,
`0to8 x NoGhost`, `0to8 x NoGhost Records`, `0to8 x NoGhost Recorsd`); 77 Records — `77 Records`, `0to8 / 77 Records`;
R2R — `R2R PRODUCTION`.

**Главное, что надо знать до таблиц.** В книге написано, что у 77 Records и R2R в приложениях «префиксы ISRC», которые
«машинно не читаются». Это не так: текстовый слой разбит на две строки, но пара «префикс + хвост» всегда стоит подряд.
Все 31 и 149 ISRC полные. Индекс договоров независимо дал те же коды. **Неоднозначных склеек по ISRC нет.** Неоднозначны
только 7 записей R2R, у которых ISRC ещё нет в каталоге ERP (ниже).

## Что не удалось проверить и почему

- **Откуда в книге 317 / 50 / 100 и «44 без доли».** Методика книги не описана; я воспроизвёл только 50 (гипотеза
  «без сентября»). 317 и 100 не получаются ни по строке, ни по сплиту, ни по доле > 0.
- **Доля для треков «только в приложении».** У них нет ни одной строки Believe, поэтому оценивать нечего: 0 и в
  приложении, и в ERP.
- **Оценки US$7,10 и US$64,70 / 129,39** посчитаны как net × (100 − Σсплита) × 50 % без запуска расчёта. Участия у
  этих ISRC есть только с базой `artist_share`, долю лейбла они не меняют, но порядок карвов и квантование расчёта
  могут дать расхождение в центах.
- **Месяц отчёта и дата получения денег.** Допник NoGhost говорит о Net Receipts, полученных до 13.11.2026. Я считал по
  отчётным месяцам 2026-02…09. Отчёт за 2026-10 не загружен, поэтому его часть до 13.11 не вошла.
- **7 ISRC R2R без каталога.** Склейка только по названию релиза в `owners.releases`; ISRC в ERP подтвердить нечем.
- **Сольность `onimanxd`** определена по строке артиста Believe (ровно один псевдоним, без фитов) и по сплиту (одна
  строка). Метаданные релизов (featuring в названии) отдельно не сверялись.
- **Изображения страниц PDF** не смотрел: текстовый слой, индекс договоров и каталог ERP совпали на 100 %, расхождений
  для визуальной проверки не было.
