# Модель лейблов: взгляд архитектора границ (цикл 1, 2026-11-17)

Только раздумья: кода нет, база только SELECT. Запросы в конце каждого числа: `PG` — PostgreSQL `erp`, `CH` — ClickHouse
`believe.rows` по 48 загруженным файлам (`source_files.status='loaded'`), `MCP` — `erp` только чтение.

Главная мысль. В лейблах три слоя, и каждый должен жить в одном месте:
**сырьё** (строка отчёта и аккаунт файла) → **решение человека** (чей трек на нашей стороне с какого месяца; какой
процент у саблейбла по договору) → **проекция** (деньги, список треков саблейбла, выписка). Сегодня решение «чей трек»
подменено сырьём: его решает текст Believe. Я предлагаю одну новую запись — **привязку трека** — и больше ничего.

выписка = тот же баланс владельца по ссылке. Итого **7 шагов**.

Проверка «три записи»: у всех 15 получателей правил владелец `kind=label`, ник совпадает с названием лейбла, ровно 1
ник, 0 строк сплита и 0 участий (`PG`: join `label_rules → artists → owners`, счётчики `split_shares`, `participations`).

## 1. Словарь

Сегодня слов восемь: лейбл, саблейбл, импринт, строка, алиас, аккаунт, книга, правило, плюс «история лейбла трека»
(`owners.track_labels`). Сливаются: *импринт = строка = алиас* (это одно: как дистрибьютор напечатал лейбл);
*аккаунт = книга* для человека (книга — это свой лейбл аккаунта); *история лейбла трека* становится привязкой.

| Слово | Одна фраза | Пример |
|---|---|---|
| **Лейбл** | Свой лейбл, в чью книгу ложатся деньги отчётов его аккаунта | 0to8 (аккаунт 1052428), Echo8 (1055956) |
| **Саблейбл** | Внешний партнёр, которому по договору идёт процент доли лейбла на его треках | NoGhost: 50 % доли лейбла |
| **Строка отчёта** | Название лейбла, как его напечатал Believe; подсказка, а для непривязанного трека — запасной ответ | `NoGhost Records / 0to8` |
| **Привязка** | Решение человека: этот ISRC с такого-то месяца — трек такого-то лейбла или саблейбла | FR10S2684638 → 77 Records с 2026-01 |
| **Правило** | Процент саблейбла и ник-получатель на период, по документу | 77 Records, 50 %, с 2025-11 |
| **Получатель** | Владелец и его ник, на которого падают деньги саблейбла; ему делают выписку | владелец «R2R PRODUCTION» |

Шесть слов вместо девяти.

## 2. Кто что решает и границы

| Что | Тип | Модуль | Почему там |
|---|---|---|---|
| строка, ISRC, месяц, net, аккаунт файла | сырьё | `sources` | приходит извне, не правится |
| книга юнита = лейбл аккаунта файла | решение один раз на аккаунт | `labels.label_accounts` | D-169; деньги не переносятся между книгами |
| строка → лейбл | решение (запасное) | `labels.label_aliases` | подсказка и ответ для непривязанного |
| **ISRC → лейбл с месяца** | **решение** | **`labels`** | ISRC ничей модуль; второй конец — лейбл; правило рядом |
| процент саблейбла, получатель, период, документ | решение | `labels.label_rules` | меняется по договору, а не по треку |
| артисты и участия трека, в т. ч. продюсеры из доли лейбла | решение | `splits` | сторона артистов |
| кто получает деньги, договор, порог | решение | `owners` | получатель — ник владельца |
| выплаты саблейблу | факт | `settlements` | как любому владельцу |
| деньги, список треков саблейбла, выписка | проекция | фасад | пересчёт из сырья и решений |

**Почему не `links`.** `links` соединяет id двух модулей, которые друг друга не знают (автор pubv2 ↔ владелец, D-183).
Привязка соединяет ISRC (сырьё, ничей id) с лейблом — как сплит, который тоже держит ISRC у себя (`splits`). Положить её
в `links` — значит учить `links` правилам лейблов.

**Почему не `splits`.** Мысль владельца «сплит нашей стороны» верна по смыслу, но это **два решения с разной частотой**:
*чей трек* — по треку (1 645 ISRC), *какой процент* — по договору (16 правил на 15 саблейблов). Слить их в процент на
каждом ISRC — значит, что выкуп «с месяца X 25 % вместо 50 %» у NoGhost закрывает и открывает 351 строку вместо одной.

**Одно место чтения.** `labels.index().labelOf(строка, isrc, дата)`: есть привязка на месяц отчёта — её лейбл, иначе
строка → алиас. Читают трое: слой `label-of-record.ts:10`, реклама `ads.ts:79`, охват `owner-scope.ts:61-64`.
Правило в силе берётся у найденного лейбла, как сегодня (`modules/labels/service.ts:279-300`).

Почему В не байт в байт: на юните без сплита (D-175) карв саблейбла сегодня не идёт (`carve.ts:167`), а участие из

`ourLabelId`, отчёт по саблейблу и «кто несёт рекламу» (на треках саблейблов **104 записи рекламы, 43 ISRC,
US$30 605,24**, `PG ads.expenses` ∩ ISRC строк саблейблов). Пересечение с продюсерскими участиями `label_share` — 0 ISRC.

**Выбор — Д.** Таблица привязок — это `owners.track_labels`, перенесённая в `labels`: та же форма (ISRC, лейбл, период,
`source`, заметка, запрет пересечений `track_labels_no_overlap`), плюс документ. Её строки `files` (23 635, все сегодня)
— проекция книги, их выводят на чтении (вопрос В2 прошлого совета). Привязку не правят: новую ставят, старую закрывают
(как `links`, D-188). Процент живёт только в правиле.

### Случай 1. Выкуп части лейбла (с месяца X 25 % вместо 50 %)

Решение: закрыть правило с месяца X, открыть новое 25 % с тем же получателем и документом выкупа. Привязки не трогаются.
Пример NoGhost, сентябрь 2026: net 40 614,49, артисты 19 421,55, доля лейбла 21 192,95, NoGhost 10 596,47, наше
10 596,47 (`MCP get-owners-by-id-balance` NoGhost `from=to=2026-09`). Если бы выкуп был с 2026-09: NoGhost 5 298,24,
наше +5 298,24. Записей — одна. Настоящего выкупа саблейбла в базе нет; ближайший живой пример — поправка NoGhost
(до 13.11.2026 плоские 25 % нета, после — 50 % доли лейбла): по M52 это новое правило с 2026-11.

### Случай 2. Переезд трека

Решение: закрыть привязку с месяца, открыть новую. Настоящие переезды по строке — 17 ISRC (`CH`: ISRC с двумя
`label_name`). FRX282623697: 2026-07 «Hoboshrine» net 5,97 (доля лейбла 50 %, саблейблу 1,49 — ждёт, правило
`assumption`), 2026-08…09 «0to8» net 14,14, всё наше. В модели: привязка Hoboshrine [2026-07, 2026-08), дальше без
привязки → строка «0to8». Числа те же.

### Случай 3. Совместный импринт «0to8 x …»

Строка становится подсказкой, а трек — чей скажет человек. `NoGhost Records / 0to8`: 25 ISRC, net 39 802,70, сегодня
NoGhost через алиас — первичное заполнение даст 25 привязок к NoGhost, числа те же. `0to8 x fate`: 1 ISRC
FRS182648319, сентябрь 2026, net 1,55, сегодня алиас ведёт в 0to8, хотя fate — саблейбл (Echo8). Сплита нет, вся доля
ждёт в C `no_split`; привязка к fate чисел не меняет, пока нет сплита. Доля одного трека на двух партнёров — вопрос П4.

### Случай 4. Трек под чужой строкой

16 треков 77 Records в первые месяцы шли под «0to8» (`CH`): net 528,29, из них до правила (2025-10) 287,20, с 2025-11
— 241,08. У всех 16 сплит 50 % артистам (`PG`). Привязка к 77 Records с релиза даст саблейблу 25 % net =
**US$60,27**, за 2025-10 — 0 (правила ещё нет). Пример: FR10S2684638 «Mercenary», 2026-01 под «0to8»: net 4,07, доля
лейбла 2,04, всё наше; с привязкой — 77 Records 1,02. Деньги 77 Records сейчас ждут целиком в `owner_unconfirmed`
(US$16 456,38 за всё время): договора нет (`MCP` баланс 77 Records). Меняет числа → вопрос П1.

### Случай 5. Саблейбл внутри саблейбла

В базе 0 (сервис запрещает: `own_label_id` только у `own`, `modules/labels/service.ts:106-108`). Саблейбл — внешний
контрагент; ERP знает только того, с кем у нас договор. Если «внук» тоже подписал договор с нами — это отдельный
саблейбл нашего лейбла со своими привязками. Если не подписал — он дело саблейбла. Вопрос П5.

### Случай 6. Второй лейбл и вторая организация

Внутри организации второй лейбл уже есть: Echo8, своя книга (13 файлов), свои саблейблы CATCORE, fate, qaraqshy, SF
(`PG labels`). Привязка ведёт к лейблу, но **книгу не меняет** (D-169): трек fate в файле аккаунта 0to8 остаётся в
книге 0to8, сработает сигнал `labelOutsideAccount`. Вторая организация (D-170) — свои аккаунты и свои привязки, `org_id`
на строке; между организациями ничего не переносится. Организация в базе одна (`PG orgs.organizations`).

## 4. Переход без изменения чисел

1. **Код без данных.** `labelOf` получает ISRC. Пустая таблица → поведение сегодняшнее по построению. Тест: golden,
   `exactness`, новый «без привязок `calculate()` байт в байт».
2. **Первичное заполнение** скриптом с пробным прогоном: на каждый ISRC строк саблейблов — привязка с первого месяца
   его строки без конца; где строка ушла на свой лейбл — привязка закрывается этим месяцем. Это **1 645 ISRC**, net
   US$214 537,04, 13 строк без ISRC остаются на строке (`CH`, 22 строки, ведущие к саблейблам). Реклама «ближайшего
   месяца» совпадает: до первого месяца привязки нет → строка того же саблейбла.
3. **Теневой прогон** по образцу `pubv2/shadow.ts`: `calculate()`, реклама, `reconcile()`, сигналы и `check-owner-scope.ts`
   с привязками и без них (флаг индекса «не читать привязки») — разница 0. Только потом флаг снимается.
4. **Решения, меняющие числа**, — по одному, с суммой, вперёд с открытого месяца (Р7).

**Что открывается в закрытых зонах:** `layers/label-of-record.ts` (строка 10: передать `s.unit.isrc`),
`layers/types.ts` (подпись `LayerContext.labelOf`), `calculation.ts` (строка 207, проброс), `owner-scope.ts`
(строки 61-64: добавить ISRC привязок к лейблам, где правило называет ник владельца; без этого саблейбл молча потеряет
деньги). Плюс `ads.ts:79`. `carve.ts`, `categorise.ts`, `balance.ts` не меняются: процент и получатель приходят тем же
`rule`.

## 5. Саблейбл как внешняя сторона

В модели саблейбл — **лейбл-контрагент** (`labels`, для привязок и правила) и **получатель** (владелец `kind=label` с
одним ником, для денег и выписки). Своих данных у него нет. Видит: свои треки по месяцам (привязки, а для
непривязанных — по строке, с пометкой), net трека, долю лейбла после артистов, свою часть, что ждёт и почему, рекламу
(у NoGhost `adsCharged` 596,78), выплачено, к выплате. Это уже есть в балансе: у R2R за сентябрь 2026 — 101 трек с
net и своей частью, всего ждёт 132,13 (`MCP`). Сплиты артистов не видит (С4).

Путь: **ссылка** (отзываемый токен только на чтение, принципал «владелец видит своё») → при желании **вход** (приглашение
создаёт пользователя с тем же принципалом) → **своя организация** (D-170), если он грузит свои отчёты; наша выписка ему
остаётся чтением нашей организации, данные не копируются.

## 6. Периметр договоров

По `CH` (все месяцы): NoGhost — 351 ISRC в шести строках (spec: 317 при сверке с приложением на 360), 77 Records —
54 ISRC (из них 16 начинали под «0to8»), R2R — 104 (приложение: 149 префиксов). Модель закрывает расхождения одним
видом решения: импорт «привязать по приложению» с пробным прогоном показывает три списка — есть в обоих; в приложении,
без привязки (NoGhost 44, US$269 по spec); привязан, но не в приложении (NoGhost 1, US$157). Первое ничего не меняет,
второе и третье — решения с суммой. Исключённые сольные релизы основателя 77 Records — привязка этих ISRC к 0to8.
Подробная сверка — у другого участника.
