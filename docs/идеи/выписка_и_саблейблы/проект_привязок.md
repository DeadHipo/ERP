# Проект: саблейблы по привязкам ISRC

2026-11-17, вторая редакция — после четырёх независимых аудитов (`аудит/`). **Проект, кода нет.** Заменяет выбор модели
из `модель_лейблов.md` («привязка только как исключение»): владелец 17.11 решил иначе, и этот документ записывает его
решение. Все суммы — в долларах США, пересчитаны аудитом данных по ответам ERP (`аудит/данные_и_суммы.md`).

## 1. Решение владельца

1. Организация (Zero to Infinity) → свой лейбл (0to8, Echo8) → саблейблы.
2. У саблейбла человек указывает его треки **по ISRC**, прикладывая документ. Процент — общий на все треки записи или
   свой у отдельных треков. Срок начала — у каждого ISRC свой.
3. Новый трек — новая запись со своим документом. Прежние записи **не правятся и не заменяются**.
4. Привязку можно завести **без документа**: её деньги ждут как неподтверждённые, бессрочно.
5. Ошибочную запись можно отменить с причиной (запись остаётся, но не считается).
6. Задним числом — можно; прошлые месяцы пересчитаются. Предпросмотр денег «до и после» не нужен.
7. **Текст отчёта Believe на деньги не влияет.** Работаем строго по ID: аккаунт файла, ISRC, саблейбл, документ.
   Строку лейбла из отчёта можно показывать только как подсказку.
8. Строки без ISRC идут как в основном сплите: выручка релиза раскладывается по его трекам, дальше действует привязка
   трека.
9. Реклама пока остаётся как есть; разбирается отдельно.
10. Списки треков для 12 саблейблов без приложений — отдельной выгрузкой позже.

## 2. Словарь (пять слов)

| слово | что это |
|---|---|
| **лейбл** | свой лейбл организации; его книга — отчёты его аккаунта Believe |
| **саблейбл** | внешний партнёр внутри лейбла; у него один получатель |
| **привязка** | «этот ISRC с такого-то месяца — такого-то саблейбла, столько-то процентов доли лейбла, по такому-то документу». Несколько привязок, заведённых разом, — одна **запись** |
| **документ** | основание привязки; без утверждённого документа деньги привязки ждут |
| **получатель** | владелец с ником, на которого пишется доля саблейбла (не путать с «получателем выплаты» — каналом и реквизитами) |

Уходят из денег: строка отчёта (алиас, импринт), правило саблейбла, лейбл записи. Реклама до отдельного решения ещё
читает строку и правило.

## 3. Как считаются деньги

Формула не меняется: саблейбл получает процент **доли лейбла после артистов и участий**. Меняется только то, откуда
расчёт узнаёт «чей трек и какой процент».

| вопрос расчёта | сегодня | по проекту |
|---|---|---|
| Чей это свой лейбл («наше» какого лейбла) | строка отчёта → алиас → лейбл | **книга**: лейбл аккаунта, под которым загружен файл |
| Есть ли у трека саблейбл в этом месяце | строка отчёта → алиас → саблейбл | **привязка** ISRC на месяц отчёта |
| Какой процент и кому | правило саблейбла на период | процент привязки; получатель саблейбла |
| Подтверждено ли | документ правила | документ привязки |
| Трека нет в привязках | — | доля лейбла наша (если у трека есть сплит; без сплита она ждёт, как сегодня) |

**Какая привязка действует — одно правило.** Для трека и месяца отчёта берётся неотменённая привязка **с самым поздним
началом не позже этого месяца** (при равном начале — созданная позже). Она одна и решает всё:

- если у неё нет конца или конец позже месяца — трек этого саблейбла, с её процентом и документом;
- если её конец уже наступил — трек ничей, доля наша. Более ранние привязки при этом **не оживают**.

Первая редакция проекта выбирала «из действующих», и закрытие привязки возвращало к жизни предыдущую (нашли два
аудитора). Теперь новая привязка навсегда заменяет прежние с месяца своего начала.

| что хочет человек | что он делает |
|---|---|
| выкуп: с месяца X у трека 25 % вместо 50 % | новая привязка на тот же ISRC с 25 % с X |
| выкуп по всем трекам саблейбла | то же одной записью: «взять все действующие треки саблейбла», процент 25, месяц X |
| трек переехал к другому саблейблу | новая привязка к другому саблейблу с X |
| трек перестал быть саблейбла | закрыть привязку с месяца X |
| документ пришёл позже | приложить документ к записи, у которой его нет |
| ошибка в начале, проценте или списке | отменить запись (или отдельную привязку) и завести верную |
| сменился контрагент саблейбла | новый саблейбл с новым получателем и привязки к нему с месяца X |

Привязка «с более раннего месяца», добавленная позже, действует только до начала уже существующей более поздней —
пробный прогон это показывает (класс `shadowed`).

**Когда деньги привязки ждут.** Документа нет или он не утверждён — существующая причина «правило не подтверждено».
Документ — допущение — причина «допущение». У получателя нет подтверждённого договора — «владелец не подтверждён».
У трека есть участие из доли лейбла (таких треков 98, все под 0to8) — обе части ждут как допущение (существующее
правило Q11); пробный прогон об этом предупреждает. Новых причин ожидания нет.

**Строки без ISRC.** Существующее правило D-211 раскладывает строку релиза без ISRC по трекам релиза ещё до расчёта;
каждая часть идёт по привязке своего трека. Проверено: под строками саблейблов таких строк 13 на 16,97, все
раскладываются; потерь от перехода нет.

**Чего не читают доли:** текст `label_name`, алиасы, правила саблейблов. Их до решения по рекламе читает только
реклама (она считается внутри того же расчёта).

## 4. База

Одна новая таблица и одна новая колонка, модуль `labels`. `org_id` — `text`, как во всех таблицах; репозиторий — через
общий помощник организации (`tests/org-scope.test.ts`: 42 таблицы → 43).

```
labels.labels
  + recipient_artist_id text NULL     -- ник-получатель саблейбла. Заполняется в самой миграции из действующих
                                      -- правил (у каждого из 15 саблейблов ровно один ник), после чего
                                      -- CHECK (kind = 'own' OR recipient_artist_id IS NOT NULL).
                                      -- Не меняется: смена контрагента = новый саблейбл. Читается через индекс
                                      -- ников (слитый ник ведёт к живому).

labels.isrc_bindings                  -- привязка: ISRC -> саблейбл с месяца
  org_id        text NOT NULL
  id            text PRIMARY KEY
  batch_id      text NOT NULL         -- одна запись человека = один batch_id
  sublabel_id   text NOT NULL         -- labels.labels.id, kind = 'sublabel' (FK внутри модуля)
  isrc          text NOT NULL         -- CHECK формата ISRC
  percent       numeric(9,6) NOT NULL -- 0 < percent <= 100
  valid_from    date NOT NULL         -- первое число месяца (M52)
  valid_to      date NULL             -- первое число месяца, исключительно; ставится один раз
  document_id   text NULL             -- owners.documents.id; NULL = деньги ждут; ставится один раз, если был NULL
  note          text NULL
  created_by    text NOT NULL
  created_at    timestamptz NOT NULL  -- время приложения, одно на запись
  closed_by, closed_at
  cancelled_at, cancelled_by, cancel_reason
  INDEX (org_id), INDEX (org_id, isrc) WHERE cancelled_at IS NULL, INDEX (org_id, sublabel_id), INDEX (org_id, batch_id)
  CHECK valid_to IS NULL OR valid_to > valid_from
```

Разрешённые изменения строки: поставить конец (один раз), приложить документ (если его не было), отменить. Остальное
неизменно. Запрета пересечений периодов нет: однозначность даёт правило «позднее начало».

Отдельной таблицы записи не нужно: документ, заметка и автор повторяются в строках одной записи.

Число таблиц: 48 → **49**. Дальше, отдельными решениями: 48 (уходят `label_rules`, после решения по рекламе), 47
(`label_aliases`, если не останутся подсказками), 46 (`owners.track_labels`, вопрос В2 прошлого совета).

## 5. API

Все маршруты — под `/api/v1`. Запись — `POST`; пробный прогон не оставляет следа в аудите; запись оставляет след:
саблейбл, документ, `batchId`, счётчики, id созданных привязок и их ISRC, свой лейбл саблейбла (чтобы след был виден под
лейблом). Свободный текст в след не попадает.

| метод и путь | что делает | право |
|---|---|---|
| `POST /labels/sublabels` | **«Завести саблейбл» одним действием:** название, свой лейбл, получатель (существующие владелец и ник или новые, с подсказкой дубля). Создаёт лейбл вида `sublabel`, владельца вида `label`, ник, ставит получателя. Старый `POST /labels` саблейблы больше не создаёт | admin |
| `GET /labels/bindings` | список привязок: фильтры `sublabel`, `isrc`, `month` (что действует в месяц), `batch`, `status` (действует / заменена / закрыта / отменена / без документа); постранично. Один маршрут и для страницы саблейбла, и для истории трека | read, по лейблу записи |
| `POST /labels/:id/bindings?dryRun=1\|0` | **добавить запись привязок** (тело ниже), до 5 000 треков. Пробный прогон отдаёт классы строк и линию времени трека «было → станет»; запись — всё или ничего. Повтор той же записи ничего не создаёт (`batchId: null`) | approve |
| `POST /labels/bindings/document` | приложить документ `{ batchId, documentId }` строкам записи, у которых его нет | approve |
| `POST /labels/bindings/close` | поставить конец `{ id \| batchId, validTo }` | approve |
| `POST /labels/bindings/cancel` | отменить `{ id \| batchId, reason }`. Разрешено всегда (как любое изменение задним числом); отказ только пока у получателя есть выплата без подтверждения платежа | approve |
| `GET /labels/bindings/suggestions?month=` | **подсказки, не решения,** по всем саблейблам лейбла сразу: треки, у которых в отчёте стоит строка саблейбла, а привязки на месяц нет (с суммой); треки того же релиза, что уже привязанные. Процент и документ по умолчанию — из последней записи саблейбла | read_money, по лейблу записи |

Тело `POST /labels/:id/bindings`:

```
{
  "documentId": "…" | null,
  "percent": "50",                 // на все треки
  "validFrom": "2025-11",          // на все треки
  "note": "…",
  "allActiveOfSublabel": false,    // true: взять все действующие треки саблейбла (выкуп целиком); items не нужен
  "items": [
    { "isrc": "FR10S2500001" },
    { "isrc": "FR10S2500002", "percent": "25", "validFrom": "2026-03", "validTo": "2027-01" }
  ]
}
```

Классы строк пробного прогона:

| класс | вид | смысл |
|---|---|---|
| `new` | сведение | у трека не было привязки |
| `overrides` | сведение | с месяца начала заменит привязку такую-то (к тому же или другому саблейблу) |
| `shadowed` | предупреждение | у трека есть привязка с более поздним началом: новая действует только до него |
| `unchanged` | сведение | такая же привязка уже есть (тот же саблейбл, процент, начало, конец и документ) |
| `isrc_not_in_catalog` | предупреждение | ISRC ещё нет в каталоге и отчётах: привязка заведётся впрок |
| `no_document` | предупреждение | деньги будут ждать |
| `label_share_participation` | предупреждение | у трека есть участие из доли лейбла: обе части будут ждать (Q11) |
| `other_book` | предупреждение | трек приходит в книге другого своего лейбла, чем лейбл саблейбла |
| `isrc_invalid`, `percent_invalid`, `date_invalid`, `empty_period`, `duplicate_in_request` | ошибка | — |
| `document_not_found`, `document_kind`, `document_owner_mismatch` | ошибка | документ не найден, не того вида (годятся виды документов сплита) или принадлежит другому владельцу |
| `not_sublabel` | ошибка | лейбл не саблейбл |

Что видит оператор о деньгах саблейбла: существующий баланс ника-получателя уже отдаёт треки с суммами и ожиданием;
отдельного маршрута не нужно. Очередь ожидания группирует деньги привязок по «саблейбл + документ» и подписывает
названием саблейбла (сегодня — по правилу и строке отчёта; иначе вышло бы около 1 700 групп). Выписка саблейбла по
ссылке — отдельная цель.

Старые маршруты правил и алиасов остаются до решения по рекламе; страница говорит прямо: «влияет только на рекламу и
подсказки».

## 6. Страницы

- **Лейбл → саблейблы:** кнопка «Завести саблейбл» (одна форма).
- **Саблейбл → «Треки»:** привязки с периодом, процентом, документом и статусом; «Добавить треки» (вставить список
  ISRC, общий процент и месяц, документ; предпросмотр), «Приложить документ», «Закрыть с месяца», «Отменить».
- **«Подсказки месяца»** — одна страница на все саблейблы лейбла: группы «саблейбл → новые треки со строкой саблейбла
  без привязки»; выделить, подтвердить одной записью на группу. Около трёх кликов на саблейбл в месяц.
- **Трек:** на вкладке «Правила» — чей трек на нашей стороне по месяцам (привязка вместо правила).

## 7. Что меняется в коде расчёта

Закрытые файлы, которые открываются отдельной D-записью:

| файл | что меняется |
|---|---|
| `facade/layers/label-of-record.ts` | свой лейбл берётся из книги файла; саблейбл и «правило» — из привязки ISRC на месяц |
| `facade/layers/types.ts` | юнит несёт лейбл файла; контекст получает `bindingAt(isrc, дата)`. Прежний `labelOf(строка, дата)` **остаётся** рядом: его читает реклама |
| `facade/calculation.ts` | в том же снимке собирает индекс привязок, отдаёт его слою, и **добавляет документы привязок** в список документов, чьи статусы знает расчёт (иначе утверждённый договор читался бы как отсутствующий и все деньги привязок ждали бы) |
| `facade/owner-scope.ts` | охват получателя = ISRC его привязок **плюс** нынешний поиск по строкам, пока реклама читает строки (иначе баланс по охвату разойдётся с полным) |

Не меняются: `layers/carve.ts` (функция саблейбла получает ту же форму: id, получатель, процент, документ),
`layers/categorise.ts`, `layers/split.ts`, `recoup.ts`, математика `balance.ts`, `facade/ads.ts`.

Вне закрытой зоны: модуль `labels` (таблица, сервис, индекс привязок), фасад (действия, подсказки), `queue.ts`
(группировка и подпись), `reports.ts` (сигналы «строка без лейбла», «строка вне аккаунта», «саблейбл без правила»
теряют смысл; «наше по лейблу» совпадает с книгой), `label-scope.ts` (видимость получателя под лейблом — по привязкам),
`aggregates.ts`, `onboarding.ts`, общие схемы ответов, `operations.ts`, таблица прав менеджера.

## 8. Переход

Числа **изменятся**, и это решение владельца. Задача перехода — знать их поимённо и не выплатить лишнего по дороге.

**Порядок.**

1. **Миграция, API и страницы; расчёт по-старому.** Получатели саблейблов заполняются в миграции. Переключатель
   `LABEL_SOURCE=strings|bindings`, по умолчанию `strings`.
2. **Документы привязок.** Документы договоров от 13–16.11.2026 заводятся и утверждаются как документы. **Записи
   договора владельцам-получателям 77 Records и R2R пока не заводятся** (см. шаг 6).
3. **Привязки:**
   - 77 Records: 31 трек приложения, 50 %, с 2025-11;
   - R2R PRODUCTION: 149 треков, 50 %, с 2026-05;
   - NoGhost: 360 треков; две записи: с 2026-02 по документу-допущению (как сегодня) и с 2026-06 по договору от
     19.06.2026;
   - 12 саблейблов без приложений: списки подтверждает человек по подсказкам (или по выгрузке владельца), на тех же
     12 документах-допущениях, что у сегодняшних правил, — тогда и сумма, и причина ожидания остаются прежними.
     Два исключения решаются явно: `lost` (с концом 2025-11) и трек Hoboshrine, ушедший под 0to8.
4. **Теневой прогон** (`scripts/labels/shadow.ts`, по образцу `pubv2/shadow.ts`): расчёт в обоих режимах. Жёсткое
   условие: у каждого юнита все суммы артистов и участий равны байт в байт; различаются только доля саблейбла, остаток
   доли лейбла и её категория. Ещё: расхождение сверки 0 в обоих режимах, «к выплате» каждого владельца, реклама,
   проверка охвата в режиме привязок. Итог разницы по саблейблам должен совпасть с таблицей ниже.
5. **Включение** `LABEL_SOURCE=bindings`. Условие: до включения у получателей саблейблов нет получателя выплаты и нет
   выплат (сегодня так и есть). Откат переключателем честен только до первой выплаты в новом режиме.
6. **После включения** — записи договора получателям 77 Records и R2R: их деньги перестают ждать уже в верном составе.
7. Позже, отдельными решениями: реклама; удаление правил и алиасов; история каталога.

Почему договоры после включения: договор подтверждает получателя, и по старому расчёту вся доля 77 Records
(16 456,38, включая 15 140,97 за сольные треки, которых нет в приложении) стала бы «к выплате». Сегодня её держит только
отсутствие получателя выплаты. Этот порядок нашли три аудитора независимо.

| саблейбл | сегодня | по привязкам | разница | состав |

## 9. Проверки

- Слой: трек с привязкой 50 % — саблейбл получает половину доли лейбла после участий; без привязки — доля наша.
- Правило выбора: позднее начало решает одно; закрытая привязка не оживляет предыдущую; отменённая не считается; равное
  начало — созданная позже.
- Документ: утверждённый → подтверждено; без документа → «правило не подтверждено»; допущение → «допущение».
- Участие из доли лейбла на привязанном треке → обе части ждут (Q11).
- Golden и точность: суммы артистов не меняются. Ожидания меняются там, где закреплено «наше по строке» и сигналы
  строк: случаи G08c, G40, G51; всего строками лейблов пользуются около 20 файлов тестов и три помощника мира.
- Охват: баланс получателя по охвату = полный (`tests/scope.test.ts`, `scripts/check-owner-scope.ts` на живых данных, в
  обоих режимах).
- Строки без ISRC: часть релиза, пришедшая на привязанный трек, идёт саблейблу.
- API: контракт, права (менеджер — отказ), след (пробный прогон — без следа), «всё или ничего», повтор записи.
- Подсказки не читаются расчётом (тест границ, как для каталога).
- Теневой прогон на живой базе до включения.
