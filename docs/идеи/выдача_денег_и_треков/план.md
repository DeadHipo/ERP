# План: единая выдача денег и треков

2026-11-18, по обсуждению с владельцем. Версия 4 — урезанная; исполнение — `GOAL.md` и `SPEC.md` (аудиты 06, 07). Учтены два раунда аудита (`аудит/01…05`, §8) и
ответы владельца (§2). Код по плану ещё не писался.

## 1. Зачем

**Трек** сегодня описан пятью способами:

- только `isrc`;
- `isrc` и наше `title`;
- `meta` в строке;
- `trackMeta` отдельным списком;
- строка каталога.

`TrackName` стоит в 12 местах. Версию от названия отрезает фронт (`TrackName.tsx:17`).

**Деньги** отдаются тремя способами:

- суммы в строке;
- отдельный запрос по видимым ISRC (P5, `GET /tracks/summary?isrcs=`);
- сводки внутри ответа.

**Цели:**

1. одна модель трека везде;
2. один способ спрашивать начисления мастера по набору треков;
3. общие блоки на страницах;
4. баланс остаётся отдельным серверным ответом.

Первая версия делает **только то, у чего есть экран**. Остальное перечислено в §6 «Отложено» вместе с условием,
когда это делать.

## 3. Модели

### 3.1 Справочник: `TrackView`, `ReleaseView`, `ArtistView` (без денег)

Имена с `View`: `Track`, `Artist`, `ArtistRef`, `releaseSchema` уже заняты ответами `GET /tracks`, `GET /artists` и
релиза. `View` — готовый вид для показа, собранный из нескольких таблиц, а не запись модуля. Внутри модуля owners есть
свои типы `TrackView` / `ArtistView` / `ReleaseView` (`modules/owners/service.ts`); в `facade/tracks.ts` их не
импортировать, а при нужде импортировать под другим именем.

```ts
TrackView {
  isrc: string;
  catalogTitle: string | null;   // наше название: первая непустая строка owners.tracks по (upc, id)
  reportTitle: string | null;    // из отчёта Believe; null — нет или не видно
  meta: TrackViewMeta | null;    // D-238 + baseTitle от сервера
  catalogLabel: { id: string; name: string } | null; // открытый интервал owners.track_labels; не книга (D-172)
  upcs: string[] | null;         // релизы трека → мапа releases; null — не видно
  artists: string[] | null;      // id ников сплитов и участий → мапа artists; null — не видно
}
TrackViewMeta { title, baseTitle, version, artists, durationMs, explicit, releaseDate, coverUrl, primaryPlatform }
ReleaseView { upc, title, version, releaseDate, labelName, trackCount }  // строка реестра своего лейбла; нет — название из отчёта
ArtistView { id, pseudonym, ownerId }               // ownerId — как в GET /splits для этого пользователя
```

**Нормализация.**

- Релиз и артист приходят один раз в своих мапах, а не повторяются в каждом треке.
- По сети релиз и ник идут один раз. В кеше фронта запись трека хранит его `TrackView` вместе с нужными ему
  `ReleaseView` / `ArtistView` (ключ `['tracks', 'view', isrc]`).
- Отметки MC в справочнике нет: правило по версиям сплита и участиям не определено, а для названия она не нужна.
  Она остаётся на вкладке правил трека.

**Названия отдаются как есть.** Поля `titleSource` нет. Выбор делает один помощник фронта:
`meta?.baseTitle ?? catalogTitle ?? reportTitle ?? isrc`. ISRC без названия не повторяется (D-243).

**`baseTitle` считает сервер.** Функция `baseTitleOf(title, version)` в `@erp/shared` — это логика `TrackName.tsx:17`,
перенесённая на сервер.

**Права по полям (Р13).** Сегодня у менеджера мета и история лейбла открыты (`O`), сплиты — по записи (`R`),
релизы — по лейблу (`L`) (`manager-answers.ts:97,100`). Поэтому:

- `meta`, `catalogTitle`, `catalogLabel` отдаются для любого ISRC организации;
- `reportTitle`, `upcs`, `artists` — только для видимых ISRC, иначе `null`;
- в мапы `releases` и `artists` попадает только то, что видно: строка реестра только своего лейбла.

### 3.2 Строки мастера

```ts
MoneySums { net, B, C, ours, cByReason }       // = Sums, aggregates.ts (sumUnits / cItems)
MasterGrain = 'isrc' | 'month' | 'isrc,month'  // закрытый список
MasterRow { isrc?: string; month?: 'YYYY-MM'; sums: MoneySums; months?: { from, to, count } }  // months — у зерна 'isrc', не деньги
```

- Строка — группа единиц отчёта по зерну.
- Зерно — закрытый список; новый набор добавляется вместе с экраном, которому он нужен.
- Строк без единиц нет: нулевые зарегистрированные треки берутся из справочника, фронт ставит «—».
- Порядок фиксирован: по ключам зерна по возрастанию. Сортировку и фильтр делает AG Grid на клиенте.

## 4. API

### 4.1 `POST /money/master/query?label=`

```ts
запрос: {
  scope: { kind: 'release'; upc: string }
       | { kind: 'isrcs'; isrcs?: string[] },   // без списка — все ISRC книги, как GET /tracks/summary без isrcs
  grain: MasterGrain,
  period?: { from?: 'YYYY-MM'; to?: 'YYYY-MM' },
}
ответ: { rows: MasterRow[], totals: MoneySums, calculatedAt }
```

- **Расчёт.** `calcScoped` по ISRC среза (D-161), затем `sumUnits` по группам. Сам расчёт не трогаем.
  - `totals` = `sumUnits` всей выборки.
  - Срез `release` берёт единицы с этим UPC, а не все ISRC релиза (`aggregates.ts:449`).
  - Период — по месяцу отчёта (Р15).
- **Книга** передаётся в `?label=` (`labelGuard`, `can()`), как у `GET /releases/:upc` и `GET /tracks/summary`
  сегодня.
- **Лимит:** `isrcs` ≤ 5 000. Чужие ISRC молча отбрасываются, как в `trackSummary`.
- **Права (Р13):** менеджер — `L`, как у обоих заменяемых ответов. Строка в `manager-answers.ts`.

### 4.2 `POST /tracks/query`

- Запрос `{ isrcs }`, не больше 1 000.
- Ответ — `{ tracks: Record<isrc, TrackView>, releases: Record<upc, ReleaseView>, artists: Record<id, ArtistView> }`.
- Отдельных `/releases/query` и `/artists/query` нет, пока экран не попросит релиз или артиста без трека.
- ISRC, который организация не знает, в ответе отсутствует.
- Видимость — по полям (§3.1).
- Менеджер — `R`.

### 4.3 POST-чтение: признак `readOnly`

Имя `query` занято: `ApiOperation.query` — это схема строки запроса (`operations.ts:17`).

| Где | Что |
|---|---|
| `operations.ts` | `readOnly: true` — только у `POST` с `read` / `read_money` (проверяет тип); `needsOperator` (`:1871`) = false |
| `api/audit.ts` `traceWrites` (`:331-338`) | решает по `operationOf(req).readOnly`, а не по методу |
| `originGuard`, `noStore`, `authorize` | без изменений (`authorize` решает по способности, не по методу) |
| сервис | только `db.snapshot()` |
| тест | после вызова ни одной новой строки в журнале и в модулях |
| фронт `client.ts` `call()` (`:69-73,91`) | `readOnly`-операция — это чтение: без оператора и без `X-Audit` |
| e2e `helpers.ts:112-123` | `MONEY_PATH` видит `POST /money/*`; счёт ведётся по блокам (Р12) |
| `coverage.ts`, `api-contract.test.ts`, `manager-answers.ts`, `api/fields` | по строке на операцию |
| MCP | вне задачи: не трогаем и не учитываем |

**CSRF.** Тело в JSON требует `Content-Type: application/json`, поэтому чужой сайт не отправит такой запрос без
preflight; `originGuard` остаётся. Это записывается в D-запись.

## 5. Фронт

- **Хуки:**
  - `useTracks(isrcs)` — кеш по ISRC. Из кеша берётся то, что есть; `POST /tracks/query` — только для недостающих.
    Запись кеша — `['tracks', 'view', isrc]` с треком и его релизами и никами. Кеш сбрасывается после записей,
    меняющих трек, релиз или ника. Мета из денежных ответов снимается (T4.4).
  - `useMasterRows(scope, grain)` — ключ в `MONEY_KEYS`, `staleTime: 0`.
- **Срез берётся из адреса:** `useParams` + `useLabel()` + `?from&to`. Отдельного контекста нет.
- **Блоки** «по трекам» и «по месяцам» — общие компоненты над `MasterRow` + `TrackView`. Они стоят на P8 и P5; баланс
  P10 / P12 их не использует (Р8).
- **`TrackName`** принимает `TrackView`. Старые пропсы удаляются последним коммитом линии.
- **P5** (около 26 тыс. ISRC) собирает `TrackView` из строк каталога, без `POST /tracks/query` на весь список.

## 6. Шаги

Каждый шаг — один коммит. Готовность — всё из определения готовности, D-запись в 97 и строка в индексе.

**Линия «Трек»**

| Шаг | Что | Проверка |
|---|---|---|
| T1 | `baseTitleOf` в shared; схемы `TrackView`, `TrackViewMeta`, `ReleaseView`, `ArtistView` в `api-responses.ts`. Поведение не меняется | тест `baseTitleOf` на строках, которые сегодня режет `TrackName` |
| T2 | `facade/tracks.ts`: `tracksOf(isrcs, viewer)` из тела `trackCatalog`; `trackCatalog` переписан поверх него | `catalog.test.ts` и `aggregates.test.ts` без изменений; `boundaries.test.ts`: `tracks.ts` не импортирует расчёт |
| T3 | Признак `readOnly` (§4.3) и `POST /tracks/query` | тест «без побочных эффектов»; тест видимости по полям; строка менеджера `R`; контракт |
| T4 | `useTracks` + `TrackName` на `TrackView`, по коммиту на группу: P8 + P5 → P10 + P12 → P15 + P16 → P36 + P37 (+ снятие меты с ответов) | e2e тех же спецификаций и проверка в браузере |

**Линия «Деньги»**

| Шаг | Что | Проверка |
|---|---|---|
| M1 | `facade/money.ts`: `masterRows(scope, grain, period, label, viewer)` поверх `calcScoped`, `sumUnits`, `cItems` | равенство: JSON-строки денежных полей по ISRC с ненулевыми суммами против `release().tracks` / `months` и `trackSummary().items`; кейс в `scope.test.ts` |

| M3 | Скрипт `scripts/check-master-rows.ts`: на живой базе, только чтение, по каждой книге сравнивает M1 со старыми ответами, меряет время и размер | 0 расхождений; медиана 5 замеров: новое ≤ 1,2 × старого или разница ≤ 0,3 с; отчёт в `data/mvp-load/verify/` |
| M4 | R2′ в `frontend/CLAUDE.md`; `MONEY_KEYS` + `['money','master']`; e2e-счётчик видит POST | e2e зелёный, экраны не менялись |
| M5 | P8 на блоках: `useMasterRows` (release, `isrc` и `month`) + `useTracks` | e2e `11-release` + «экран = API»; проверка в браузере |
| M6 | P5, вторая фаза (D-162): `useMasterRows(isrcs видимых, 'isrc')`; «посчитать все» — срез без списка | e2e `40-catalog` и P5; проверка в браузере |

**Порядок.** Линии независимы. «Трек» идёт первым: он нужен везде и не зависит от денег.

**e2e (Р11).** Проверки чисел до действий переносятся в бэкенд только там, где у них уже есть двойник
(`golden.test.ts`, `verify-seed.ts`). Переносятся после M7, по файлу на коммит. Выигрыш по времени небольшой:
основное время уходит на сид, сборку и пересчёт.

### Отложено, и когда делать

| Что | Почему не сейчас | Когда |
|---|---|---|
| Паблишинг-метод, срез паблишинга по треку | экрана нет; паблишинг владельца — в балансе; по треку нужны поля в закрытом расчёте (Р14) | когда попросит экран |
| Реклама POST | `GET /ads?isrc=` уже даёт нужное | когда общий блок рекламы понадобится на нескольких страницах |
| Срезы `owner` / `artist` | это баланс (Р8); `waiting` в книге смешивает мастер и паблишинг (`balance.ts:598,650`) | не делаем |
| Срез `track` и `byArtist` P6 | заменяемый ответ имеет `scope: 'org'` (у менеджера `x`) и считается без книги; под `?label=` P6 показал бы другое число | вместе с разграничением прав (Р13) |
| Срез `book` и P7 `net` | `net` P7 — сумма файлов ClickHouse без расчёта (`aggregates.ts:401`), это не начисления | не делаем |
| `/artists`, `/songs`, `/owners/query` | экрана нет | когда попросит экран |
| Серверное листание, `sort`, семафор | P5 уже листает по видимым (D-162); выборка не больше 5 000 | когда замер M3 покажет нужду |
| `decimal.js` во фронте, `money()`, `MoneyView`, правило eslint (Р1, Р2) | ни один блок пока не складывает на клиенте | при первом сложении на клиенте |
| `basis: 'sales'` | считаем по месяцу отчёта (Р15) | при смене правила |

## 7. Риски

| Риск | Что делаем |
|---|---|
| Число на экране изменилось | M1 сравнивает со старым ответом, M3 — на живой базе; экран переводится только при 0 расхождений |
| Права расширились или сузились | только `L` / `R`, как у заменяемых ответов; права по полям трека; проход менеджера в контракте |
| POST-чтение пишет или требует оператора | `readOnly` в сервере, журнале, клиенте; `db.snapshot()`; тест |
| Скорость | `calcScoped` по ISRC среза; замер M3 до перевода экранов |
| e2e-счётчик ложно зелёный | M4 до первого экрана |

## 8. Аудит

**Раунд 1** (`аудит/01_деньги.md`, `02_api_права_скорость.md`, `03_фронт_этапы_тесты.md`) нашёл 10 блокеров; они
внесены в версии 2–3.

**Раунд 2** (`аудит/04_проверка_v3.md`, `05_реализуемость.md`) проверял версию 3 против кода и на простоту.

| Блокер раунда 2 | Решение в версии 4 |
|---|---|
| Вид `book` закрывает менеджеру P5 «все» и противоречит «вид `label` убран» (04 Б1, 05 Б3) | вида `book` нет; P5 «все» — срез `isrcs` без списка, права `L` |
| Паблишинг по песне не построить без закрытого расчёта (04 Б2) | паблишинга в первой версии нет |
| Равенство с балансом по владельцу не сходится (04 Б3, 05 Б2) | срезов `owner` / `artist` нет (Р8) |
| `grain` без списка значений (05 Б1) | закрытый `MasterGrain`, порядок фиксирован |

Важное из раунда 2, тоже учтено:

- имя `readOnly` вместо занятого `query`;
- строка несёт `sums`, а не `amount`;
- сравнение без нулевых строк;
- права трека по полям;
- форма отчёта саблейбла не нужна (Р9);
- e2e-счётчик учтён; MCP вне задачи;
- P7 `net` не трогаем;
- работа урезана до экранов: шаги T1–T4 и M1–M7.

**Порядок отказов.** Новые операции дают те же коды, что заменяемые (`L` ↔ `L`, `R` ↔ `R`). Закрытых видов в первой
версии нет.

**Попутно:** в `docs/agents/03_decision_index.md` номер D-237 стоит у двух решений, это надо поправить отдельно.
