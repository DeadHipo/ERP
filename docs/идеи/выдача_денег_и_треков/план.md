# План: единая выдача денег и треков

2026-11-18, по обсуждению с владельцем. Версия 2: в неё внесены итоги аудита (`аудит/01…03`, §9). Код по плану ещё
не писался.

## 1. Зачем

Сегодня ответы API описывают трек и деньги по-разному на каждом экране.

- **Трек** описан пятью способами:
  - только `isrc`;
  - `isrc` и наше `title`;
  - `meta` в строке;
  - `trackMeta` отдельным списком рядом;
  - строка каталога `{ id, isrc, upc, title, note }`.

  ISRC называют около 30 схем ответов. `TrackName` стоит в 12 местах 11 файлов.
- **Деньги** отдаются тремя способами:
  - суммы прямо в строке — почти везде;
  - отдельный запрос по видимым ISRC пачками по 200 в адресе (P5, `GET /tracks/summary?isrcs=`);
  - сводки внутри ответа: `totals`, `months`, `byArtist`.
- **Часть решений уехала во фронт.** Фронт сам отрезает « - Slowed» от названия и сам сводит мету со строками.

Каждая точка входа выбирает набор единиц отчёта, считает `calculate()` и группирует начисления. Точки входа: лейбл,
саблейбл, владелец, артист, релиз, трек. Цель плана:

- один способ спрашивать **начисления** мастера, паблишинга и рекламы;
- один способ описывать трек;
- экраны, собранные из общих блоков.

**Что это не трогает.** Баланс, выплата, допуск, ведомость, срезы и сверка остаются серверными ответами со своими
правилами.

## 2. Решения владельца

## 3. Модели

### 3.1 `Money`

```ts
type Money = string;                       // точная десятичная строка, как сегодня
// @erp/shared/money:
export const MONEY = { scale: 12, precision: 40, rounding: 'HALF_UP' } as const;
export const money = (s: Money) => D(s);   // D = Decimal.clone({ precision: MONEY.precision, rounding })
```

- `decimal.js` подключается в `@erp/shared` с точной версией. Сегодня его нет ни во фронте, ни в shared.
- По умолчанию у decimal.js 20 значащих цифр, поэтому без `clone` суммы теряют знаки.
- **Неаддитивное не складывается.** Сюда относятся:
  - `payableShown`, `byArea.payableShown`;
  - гейт и сумма выплаты;
  - часть саблейбла: она считается `pct` на каждую единицу, а не от суммы;
  - всё, что уже приходит итогом.
- Для таких полей есть тип `MoneyView` — только показ, без `money()`.
- **eslint.** `money(` разрешён только в блоках показа (`components/money-blocks/`). В действиях, кнопках и диалогах
  он запрещён.

### 3.2 `Track` (справочник, без денег)

```ts
Track {
  isrc: string;
  title: string | null;        // наше название: первая строка каталога; нет в каталоге — из отчёта Believe
  titleSource: 'catalog' | 'report' | null;
  meta: Meta | null;           // D-238 + baseTitle от сервера
  releases: TrackRelease[];    // строки каталога ISRC × UPC с реестром релизов Believe
  catalogLabel: LabelRef | null; // лейбл каталога сейчас (owners.track_labels), не книга (D-172)
  artists: ArtistRef[];        // ники трека: сплиты и участия, без процентов, с отметкой MC
}
Meta { title, baseTitle, version, artists, durationMs, explicit, releaseDate, coverUrl, primaryPlatform }
TrackRelease { trackId, upc, title, release: { title, version, releaseDate, labelName, trackCount } | null }
```

- Показ названия: `meta?.baseTitle ?? title ?? isrc`.
- ISRC без названия не повторяется (D-243).
- Отметка MC и разница «строка или участие» берутся из справочника, а не из строки денег.
- `TrackCard` нужен только странице трека: `Track` плюс площадки, история лейбла, сплиты, участия, условия
  саблейблов, заметки.

### 3.3 Строки денег

```ts
Recipient = { kind: 'artist'; id } | { kind: 'ours' }       // кому начислено (саблейбла здесь нет: D-232)
Status    = 'B' | 'C' | 'ours'                               // + reason: CReason при C

MasterRow {                     // зерно задаёт, какие ключи заполнены
  // ключи
  isrc?, upc?, month?, salesMonth?, account?, labelString?,
  book?: LabelRef,              // лейбл файла (D-169) — единственный «лейбл» строки денег
  recipient?, status?, reason?,
  // суммы
  amount: Money,                // сумма начислений группы
  net?: Money,                  // поступление (только для зёрен без recipient/status)
}
MoneySums { net, B, C, ours, cByReason }   // = Sums из facade/aggregates.ts
```

- **У ника в C ник не теряется.** Если в зерне есть `recipient`, строка C хранит и ник, и `reason`. Это нужно для
  `byArtist`, D-237.
- **Лейбл строки однозначен.** Строка денег знает только `book`. Лейбл записи — это `labelString` → `label-of-record`.
  Лейбл каталога живёт в справочнике `Track`.
- **Срез `release` идёт по единицам с этим UPC**, а не по всем ISRC релиза (`aggregates.ts:449`).

```ts
PublishingRow {                 // одна песня — одна строка (D-184: у песни много ISRC)
  songId?, songwriterId?, ownerId?, quarter?, book?, status?, reason?,
  payable: Money, authorAmount: Money, labelAmount: Money,   // writer_unmapped: весь payable в C, author = label = 0
}
AdRow { adId, isrc: string | null, month, payer: LabelRef, status, amount, recoveryPercent,
        parts: { artistId, amount }[], unrecovered, bearerSublabelId }
```

### 3.4 Отчёт саблейбла (отдельная форма)

Часть саблейбла — это часть доли «наше» (`u.labelShare`), а не отдельное начисление (D-229, D-232). Если положить её
строкой рядом с `ours`, она посчитается дважды, и A = B + C + ours перестанет сходиться.

```
POST /money/sublabel/query  { sublabelId, period, grain: month|isrc|artist, limit, offset }
→ { rows: { …ключи, labelShare, amount, status: SublabelReportReason }[], total,
    totals: { labelShare, amount, confirmed, waiting, ads, amountAfterAds } }
```

- Часть по условию считает сервер (процент на единицу).
- Фронт только перегруппирует строки и показывает `totals`.
- CSV тоже идёт с сервера.

## 4. API

### 4.1 Методы

```
POST /money/master/query?label=      POST /money/sublabel/query
POST /money/publishing/query?label=  POST /money/ads/query?label=
POST /tracks/query  { isrcs } → Record<isrc, Track>      POST /artists/query { ids }
POST /songs/query   { ids }                               POST /owners/query  { ids }
```

Запрос денег:

```ts
{
  scope: { kind: 'owner' | 'artist' | 'release' | 'track'; id } | { kind: 'isrcs'; isrcs: string[] } | { kind: 'book' },
  period?: { from?: 'YYYY-MM'; to?: 'YYYY-MM'; basis?: 'report' | 'sales' },
  grain: string[],
  filter?: { account?, labelString?, salesMonth?, status?, reasons?, recipients?, hasSplit?, catalog?: 'current' },
  sort?: { by; dir },
  limit, offset,
}
→ { rows, total, totals: MoneySums, calculatedAt }
```

**Книга — только в `?label=`.** Так её видят `labelGuard` и `can()` (`label-guard.ts:12-31`). Поле `label` в теле
они не видят.

**Как определён срез.** Срез — это набор единиц плюс фильтр аллокаций. Срез `owner` / `artist`:

- единицы — охват (`owner-scope.ts`);
- аллокации — только `ownerId === owner` или `artistId === artist`, как в балансе (`balance.ts:545`);
- охват шире нужных строк (ISRC за любой период), поэтому без фильтра аллокаций равенство с балансом не сойдётся.

**Вид `label` убран.** Итог книги — это обзор (`reconcile`) со своими правилами: B17 внутри и единицы без ISRC.
Его не повторяем.

**Паблишинг.**

- Срезы `owner` и `book` работают сразу.
- Срезы `track` / `release` / `isrcs` ждут решения В3: в `PublishingResult` нет `songId` и `songwriterId`
  (`calculation.ts:71-85`).
- Срез `artist` всегда пуст.

**Реклама.** Период не передаётся в `scoped()` (D-161): фильтр по месяцу накладывается после расчёта.

### 4.2 Лимиты и скорость

- **Каждый запрос — полный `calculate()` своего сужения.** Кеша денег нет (R2), а `totals` и сортировка требуют всей
  выборки.
- **Сужение по виду среза обязательно на этапе 1** (D-161). Для владельца это новое сужение через `ownerReach`.
- **Экран берёт всё зерно одним запросом и листает на клиенте** до потолка строк. Серверное листание (`limit` /
  `offset`) нужно только спискам, которые не помещаются: P5 по всему лейблу.
- **Лимиты:**
  - `isrcs` ≤ 5 000;
  - `ids` справочников ≤ 1 000;
  - `limit` для токена чтения ≤ 500;
  - размер тела в `express.json` проверить.
- **Семафор расчётов на организацию.** Это не кеш: два одинаковых тяжёлых расчёта не идут параллельно.
- **Сортировка** — по `Decimal`, порядок устойчивый, по ключам при равенстве.
- **Замер до перевода экранов:**
  - время и размер ответа по целому лейблу;
  - время по владельцу с большим охватом.

### 4.3 POST-чтение: признак `query`

| Где | Что меняется |
|---|---|
| `operations.ts` | `query: true` — только у `POST`, только с `read` / `read_money` (проверяет тип); `needsOperator` = false |
| `api/audit.ts` `traceWrites` | решает не по методу, а по `operationOf(req).query` |
| `originGuard`, `noStore` | без изменений |
| сервис | только `db.snapshot()`: побочных эффектов нет по построению; тест «ни одной записи в журнале и модулях» |
| фронт `client.ts` `call()` | `query` — это чтение: не требует оператора и `X-Audit` (`client.ts:69-73,91`) |
| `download()` | научить POST (CSV отчёта саблейбла) |
| MCP (`mcp.ts:18-20,58`, `scripts/mcp-erp.ts`) | инструменты из `query`-операций со схемой тела, вызов POST, лимит строк, тест в `read-token.test.ts` |
| `coverage.ts`, `api-contract.test.ts`, `manager-answers.ts` | по строке на операцию |

`preview` (`dryRun=1` импортов) — это **не** `query`: он остаётся записью-предпросмотром.

### 4.4 Права

**Менеджер лейбла.**

- Права зависят от вида среза (В2). Сегодня менеджеру закрыты (`manager-answers.ts`):
  - деньги трека `GET /tracks/:isrc/money`;
  - отчёт саблейбла (D-219);
  - обзор и сверка.
- Новые методы не должны молча расширить права. Нужна таблица «вид среза × принципал» с решением владельца и
  замороженная таблица ответов по видам среза.
- **Запись в `scope.id` проверяет фасад** через `Viewer`:
  - `owner` и `artist` — видимость под книгой;
  - `track` и `release` — 404 на чужое;
  - чужие ISRC в `isrcs` молча отбрасываются, как в `trackSummary`.

**Справочники.**

- Невидимые ключи не возвращаются: ответ 200 с подмножеством, без 403.
- Видимость проверяют `mayTouchIsrc`, `ownerVisible`, `artistVisible`.
- Так справочник не раскрывает ники и владельцев чужих книг.

### 4.5 Что остаётся своими ответами

Своими ответами остаются:

- баланс владельца и артиста, вместе с таблицами «по трекам», позициями, `asOf` и срезом;
- выплата;
- ведомость;
- срезы;
- допуск;
- обзор и сверка.

## 5. Фронт

### Контекст

`MoneyScope` — вычисление, а не состояние: `useParams` + `useLabel()` + `?from&to` из адреса. Период P37 сейчас в
`useState`, его надо перенести в адрес. Ссылка на экран воспроизводит его целиком (В5 снят).

### Хуки

- Денежные: `useMasterRows`, `usePublishingRows`, `useAdRows`, `useSublabelReport`.
  - Ключи берутся из `MONEY_KEYS`, `staleTime: 0`.
  - Индикатор пересчёта и инвалидация `money` их видят.
- Справочники: `useTracks(isrcs)`, `useArtists(ids)`.
  - Пакетный загрузчик: соседние запросы одного кадра собираются в один `POST /tracks/query`.
  - Результат раскладывается в кеш по ключу `['track', isrc]`, `staleTime` долгий.
  - Такого кеша «по ключу» в TanStack из коробки нет, его надо написать.
- `QueryView` на несколько запросов: деньги + справочник, состояния пусто / долго / ошибка.

### Блоки

- Блоки: «по месяцам», «по трекам», «по артистам», «реклама», «паблишинг», «отчёт саблейбла».
- У блока два режима:
  - **полный набор** — клиентская сортировка, фильтр и CSV AG Grid, до потолка строк;
  - **страница сервера** — `pagination={false}`, сортировка и фильтр уходят в запрос.
- Поиск P5 по названию, версии и нику идёт по справочнику; `hasSplit` и `catalog` идут в `filter` запроса.

### `TrackName`

Принимает `Track`. Старые пропсы (`meta`, `fallbackTitle`) живут до этапа 3.

### Строки

Новые строки i18n — в `i18n/ru/money-blocks.ts`.

## 6. Этапы

**Принципы.**

- Расчёт не меняется: `calculation.ts`, слои, `balance.ts`, `owner-scope.ts`. Исключение — только по В3.
- Новое строится рядом со старым.
- Равенство доказывается тестом и сверкой на живой базе до перевода экрана.
- Один экран — один коммит.
- Старое сначала помечается `deprecated` и удаляется отдельным шагом, когда на нём не осталось ни одного клиента.
- **Каждый этап — своя D-запись в 97** и строка в индексе.

| Этап | Что | D-записи | Готово, когда |
|---|---|---|---|
| 0 | `MONEY`, `money()`, `decimal.js` в shared; `Track` и `tracksOf(isrcs)` в фасаде; ничего не вызывает | R1′ (смена D-139) | тесты на `money()` (40 знаков, неаддитивное) и `tracksOf` |
| 1 | Признак `query` (сервер, клиент, MCP); методы §4.1 с сужением; права §4.4; лимиты | `query` (исключение из D-140), права срезов (В2), R2′ (В1) | тесты равенства §6.1 = 0 расхождений; сверка на живой базе = 0; замер §4.2; тест менеджера по каждому виду среза |
| 2 | Контекст, хуки, блоки; перевод экранов по одному: **P8 релиз → P7 релизы (`net`) → P6 «По артистам» (сначала e2e на него) → P37 отчёт саблейбла → реклама трека (P6) → `TrackName` на `Track` (12 мест: P5, P6, P7, P8, P10, P12, P15, P16, P36, P37 и др.) → P5 последним** | по экрану, если меняется поведение | каждый шаг: коммит, e2e, проверка в браузере |
| 3 | Удаление старого (§6.2) после `deprecated` | удаления | на старом нет ни экрана, ни скрипта, ни MCP-инструмента без замены |
| 4 | e2e: проверки чисел **до действий** переходят в бэкенд-тесты (`golden.test.ts`, `verify-seed.ts`); браузер проверяет «экран = API» по образцу `49-sublabels.spec.ts:58-72`; числа после действий остаются | e2e-правило | у каждого убранного числа есть двойник в бэкенде; выигрыш по времени небольшой — основное время уходит на сид, сборку и пересчёт |

Из этапа 2 убраны:

- **таблицы «по трекам» P10 / P12** — они часть баланса (Р8): там период, `asOf`, позиции, а `t.net` прибавляется на
  каждую аллокацию;
- **реклама релиза** — это новая функция, а не перевод, её делать отдельно.

| Двойной счёт части саблейбла | своя форма отчёта (§3.4), саблейбла нет в `Recipient` |
| Задвоение паблишинга по трекам | строка на песню; срез по ISRC — только после В3 |
| Расхождение копеек фронт / сервер | 40 знаков; итоги выборки — `totals` с сервера; неаддитивное не складывается |
| Сумма строк ≠ баланс на одном экране | таблицы баланса остаются в балансе (Р8) |
| POST-чтение пишет или требует оператора | признак `query` в сервере, клиенте, журнале; `db.snapshot()` |
| MCP теряет инструменты | POST-инструменты до удаления старых |
| Потеря проверок e2e | сначала двойник в бэкенде, потом удаление; числа после действий остаются |
| Откат | `deprecated` → отдельное удаление; новое рядом со старым до этапа 3 |
