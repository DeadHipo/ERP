## 2. Блокеры

### Б1. P5 не может собрать `TrackView` из строки каталога «помощником T2»

**Что в SPEC.** T4, пункт P5: «`TrackName` получает `TrackView`, собранный из строки каталога помощником T2. Ответ
`/tracks/catalog` не меняется». T4.4: «Остаётся только `GET /tracks/catalog`: из него P5 ищет по названию и собирает
`TrackView`».

**Почему не выходит.**

1. Помощник T2 живёт в `facade/tracks.ts`, то есть на бэкенде. Фронт его вызвать не может. Если ответ каталога не
   меняется, собирать придётся на фронте из полей строки.
2. В строке каталога (`trackCatalogItemSchema`, `api-responses.ts:1708-1721`; `aggregates.ts:294-307`) не хватает:
   - **`catalogTitle` и `reportTitle` раздельно.** Есть только `title = ts[0]?.title ?? names?.trackTitle ?? ''`
     (`aggregates.ts:297`). По `registered` можно угадать источник, но при `ts[0].title = ''` название отчёта
     теряется (`??` не пропускает `''`).
   - **Полной меты.** `meta` там лёгкая (`trackMetaLiteSchema`, `:271-276`): `isrc, title, version, coverUrl`. Нет
     `baseTitle`, `artists`, `durationMs`, `explicit`, `releaseDate`, `primaryPlatform`. `baseTitle` фронту пришлось бы
     считать самому, а это против GOAL п. 1 («`baseTitle` считает сервер»).
   - **`isMc`** у ников: там `ArtistRef { id, pseudonym }` (`:268`).
   - **`ArtistView.ownerId`.**
   - **`ReleaseView`.** Названий релизов, реестра и `trackCount` в строке нет вовсе.
3. В режиме «account / month» (и до M6 в «Посчитать все») строки P5 берутся не из каталога, а из `GET /tracks/summary`
   (`TracksPage.tsx:35-46, 68, 121-122`). Мета там — из ответа summary (`TracksPage.tsx:44`). Если T4.4 снимет `meta`
   с `/tracks/summary`, поиск и названия этого режима сломаются (`TracksPage.tsx:114, 279-280`).

**Заменить в SPEC T4 пункт «P5» на:**

> - **P5** (25 854 ISRC в каталоге) не вызывает `POST /tracks/query` на весь список.
>   - Поиск и фильтр по названию работают, как сейчас, по строкам `GET /tracks/catalog`: `title`, `meta.title`,
>     `meta.version`. В режиме «account / month» строки берутся из `GET /tracks/summary`, а мета для поиска — из строки
>     каталога того же ISRC (`catalogOf`, каталог в этом режиме уже читается, `TracksPage.tsx:69`).
>   - `TrackName` получает `TrackView` из `useTracks` **для показанных строк** (тот же список `asked`, что для денег,
>     D-162; не больше размера страницы грида). Пока `TrackView` не пришёл, `TrackName` показывает ISRC.
>   - `valueGetter` колонки трека и экспорт берут текст из строки каталога (как сейчас), а не из `TrackView`.
>   - Ответ `/tracks/catalog` не меняется.

**Заменить в SPEC T4.4 строку «Остаётся только `GET /tracks/catalog`…» на:**

> Остаётся `meta` в `GET /tracks/catalog`: по нему P5 ищет по названию во всех режимах. `TrackView` P5 получает из
> `POST /tracks/query` по показанным строкам.

### Б2. Кеш по сущностям: релизы и артисты пропадают и не обновляются

**Что в SPEC.** T4: ключи `['tracks','view',isrc]`, `['releases','view',upc]`, `['artists','view',id]`; ответ
раскладывается через `queryClient.setQueryData`; хук берёт из кеша «треки, которые там есть»; сброс — через
`useAction` с `invalidate: 'reference' | 'all'`; тест — vitest фронта без DOM.

**Проверено.**

- Все записи, которые меняют трек, релиз или ника, действительно идут через `'reference'` или `'all'`: мета и площадки
  (`MetaTab.tsx:160, 215, 256`), интервал каталога (`TrackLabelsDialog.tsx:85`), `PATCH /tracks/:id`
  (`TrackPage.tsx:160`), сплиты и участия (`SplitDialogs.tsx:145, 207`, `ParticipationDialogs.tsx:55, 122`, `work/actions/dialogs.tsx`),
  реестр (`ReleaseImportDialog.tsx:43`), ник и владелец (`CreateArtistDialog.tsx:22`, `owner-dialogs.tsx:192, 282`),
  загрузка отчёта (`SourcesPage.tsx:46`). `'money'` есть только в `dev/StatesPage.tsx:107`. Переименования ника в API
  нет. `invalidateReference` сбрасывает все немонетные ключи (`queries/core.ts:61-63`), значит и три новых. Смена
  входа и организации чистит кеш (`LoginPage.tsx:56`, `UserMenu.tsx:66, 71`, `AppShell.tsx:78`, `OrgPage.tsx:76`).
- **Но механизм в SPEC не работает в TanStack Query 5.105 так, как написано:**
  1. Ключ, заполненный `setQueryData`, без наблюдателя удаляется сборщиком через `gcTime` (по умолчанию 5 минут;
     `createQueryClient`, `core.ts:49-56`, его не меняет). Трек на экране живёт (у него наблюдатель), а его релиз и
     ники через 5 минут исчезают. «Только недостающие ISRC» трек не перезапросит, и `release(upc)` / `artist(id)`
     вернут `undefined` до следующей записи.
  2. `invalidateQueries` перезапрашивает только **активные** запросы **с `queryFn`**. Ключ из `setQueryData` без
     `queryFn` после сброса остаётся со старыми данными и флагом `isInvalidated`. Если хук проверяет «есть в кеше»
     через `getQueryData`, он этот флаг не видит, и трек после записи меты остаётся старым до `staleTime` (10 мин).
  3. Чтение через `getQueryData` не подписывает компонент: после ответа экран не перерисуется.
  4. vitest фронта идёт в `environment: 'node'` и берёт только `tests/**/*.test.ts` (`vitest.config.ts`); React там не
     рендерится. Хук так не проверить, проверить можно только чистый загрузчик.
  5. `staleTime` 10 мин больше `gcTime` 5 мин: для ключей без наблюдателя он ничего не даёт.

**Заменить в SPEC T4 «Общее», пункт `src/api/queries/tracks.ts`, на:**

> - `src/api/track-cache.ts` (новый, чистый, без React): загрузчик `loadTrackViews(queryClient, isrcs)`.
>   - Копит ISRC одного кадра в очередь и через `setTimeout(0)` шлёт один `POST /tracks/query` на недостающие,
>     пачками по 1 000.
>   - Ответ раскладывается `setQueryData` по `['tracks','view',isrc]`, `['releases','view',upc]`, `['artists','view',id]`.
>     ISRC, которого нет в ответе, получает `null` (неизвестен организации), чтобы его не спрашивать снова.
>   - Для `['releases','view']` и `['artists','view']` — `queryClient.setQueryDefaults(…, { gcTime: Infinity })`:
>     у них нет своего `queryFn`, их обновляет только ответ по треку.
> - `src/api/queries/tracks.ts`: `useTracks(isrcs)` = `useQueries` по `['tracks','view',isrc]` с
>   `queryFn: () => loadTrackViews(…)` (пакетный загрузчик), `staleTime` 10 мин, `gcTime` 10 мин. Так TanStack сам
>   спрашивает только недостающие и устаревшие ключи, а после `invalidateQueries` перезапрашивает показанные одним
>   пакетом. `release(upc)` / `artist(id)` читаются через `useQueries` с `enabled: false` по ключам из `track.upcs` /
>   `track.artists` (подписка без запроса).
> - Сброс: проверено, что все записи, меняющие трек, релиз или ника, идут через `useAction` с `'reference'` или `'all'`
>   (`invalidateReference` сбрасывает все немонетные ключи). Новые записи — так же.
> - Тест `tests/track-cache.test.ts` (node, без DOM) на `loadTrackViews` с `new QueryClient()` и подменённым
>   `fetch`: два вызова одного кадра — один запрос; второй вызов тех же ISRC — без запроса; один новый ISRC —
>   запрос только его; после `invalidateQueries({ queryKey: ['tracks','view'] })` — снова запрос; релиз двух треков
>   лежит в кеше один раз.

## 3. Важно

### В1. `ArtistView.ownerId` «как в `GET /artists`» — неверный эталон

`GET /artists` — `L` (`manager-answers.ts:16`): только с `?label=`, список ников, видимых **под этим лейблом**
(`artist-view.ts:26-29, 66`). У `POST /tracks/query` метки нет, а ники приходят и по ISRC без файла, которых в
`GET /artists` нет. Буквально правило не исполнить. Тот же `pseudonym` и `ownerId` по ISRC правила
`isrcFilter` сегодня отдают `GET /splits` и `GET /participations` (`R`, `splits.ts:216-217, 266-267`).

**Заменить в SPEC T2, таблица «Правила полей», строку `ArtistView`:**

> | `ArtistView` в мапе | только ник из `artists` видимого трека; `{ id, pseudonym, ownerId }` — как у строки `GET /splits` / `GET /participations` того же ISRC (индекс ников, слитый id → выживший; нет в индексе → `pseudonym '?'`, `ownerId null`) |

### В2. `ReleaseView`: «`title` из отчёта видимого файла» не построить; выбор строки реестра не задан

- `sources.pairAttributes` возвращает пары по всем загруженным файлам без номера файла
  (`modules/sources/service.ts:413-431`). «Видимый файл» отличить нельзя, нужен новый метод модуля sources.
- Сегодня `GET /releases/:upc?label=A` отдаёт `releaseTitle` первой пары UPC из всех файлов
  (`aggregates.ts:450, 456, 475`). Правило «из видимого файла» строже сегодняшнего `L` и ничего не защищает.
- У менеджера может быть несколько лейблов (`labelsViewer(ids)`, `viewer.ts:19-21`), а правило говорит о «строке
  лейбла, который видит `viewer`» в единственном числе.
- Для `ALL_VIEWER` SPEC берёт последнюю обновлённую строку (`registryRows`, `aggregates.ts:105-111`). Администратор на
  странице лейбла A увидит в `ReleaseView` `labelName` / `title` строки лейбла B. Ключ кеша метку не несёт. Это не
  права, но расхождение с шапкой P8 (она из `GET /releases/:upc?label=`).

**Заменить в SPEC T2, таблица «Правила полей», строку `ReleaseView`:**

> | `ReleaseView` в мапе | UPC из `upcs` видимого трека. Поля реестра — строка реестра лейблов `viewer` (для менеджера — среди его лейблов, для `ALL_VIEWER` — среди всех): последняя по `updatedAt`, при равенстве — меньший `labelId`, как `registryRows`. Строки нет → поля реестра `null`. `title` = `releaseTitle` строки реестра, иначе `releaseTitle` первой пары UPC по ключу `isrc\|upc` из всех загруженных файлов, как в `GET /releases/:upc`; нет пары → `null` |

**Добавить в SPEC T4 «Общее»:**

> - `ReleaseView` не зависит от метки страницы. P8 берёт шапку релиза из `GET /releases/:upc?label=`, а не из
>   `release(upc)`.

### В3. «Первая строка `owners.tracks`» недетерминирована

- `repo.allTracks` идёт без `ORDER BY` (`modules/owners/repository.ts:156-162`). Уникальность — `(org_id, isrc, upc)`
  (`migrations/postgres/0016_organizations.sql:115`), то есть у ISRC может быть несколько строк с разными `title`.
- `trackCatalog` читает `listTracks()` без фильтра (последовательный просмотр), `tracksOf` — `listTracks({ isrcs })`
  (`IN`, может пойти по индексу `tracks_isrc`). Порядок строк в двух вызовах может разойтись. Тогда `catalogTitle`
  в `POST /tracks/query` и `title` строки P5 у одного ISRC будут разными, и тест «`GET /tracks/catalog` байт в байт»
  этого не поймает: в мирах тестов одна строка на ISRC.
- Правило D-243 «`''` = `null`» вместе с «первой строкой» даёт `null`, даже если у второй строки название есть.

**Заменить в SPEC T2 первый пункт под таблицей:**

> - `catalogTitle` — `title` строки `owners.tracks` этого ISRC с непустым названием, первой по `(upc NULLS LAST, id)`;
>   нет такой — `null`. Одна функция `catalogTitleOf(rows)` в `tracks.ts`; `trackCatalog` берёт `title` через неё же
>   (`catalogTitleOf(ts) ?? names?.trackTitle ?? ''`). В D-записи: порядок строк каталога теперь задан; ответ меняется
>   только у ISRC с несколькими строками `owners.tracks`, где он раньше зависел от плана запроса. Тест в
>   `tests/tracks.test.ts`: ISRC с двумя строками разных UPC и названий даёт одно и то же название в `tracksOf` и в
>   `trackCatalog`.
> - `reportTitle` — `trackTitle` первой пары ISRC по ключу `isrc|upc` (как `byIsrc` в `nameMaps`, `aggregates.ts:86-90`).
>   Каждое поле отдаётся как есть, выбор делает фронт. Пустая строка считается `null` (D-243).

### В4. `isMc` не определён

- Отметка MC лежит на строке сплита (`modules/splits/schema.ts:31`, `service.ts:80`). `listSplits({ isrcs })` отдаёт
  **все версии** сплита за всё время. Ник может быть MC в одной версии и не MC в другой.
- У участий отметки нет. Слитые id сводятся к выжившему (`track-artists.ts:25-28`): у двух id может быть разная отметка.
- `artistsByIsrc` возвращает `ArtistRef[]` без отметки и общий с каталогом, релизами и отчётом саблейбла
  (`aggregates.ts:202, 264, 399, 468`; `sublabel-report.ts:78`). Если добавить поле в него, изменится
  `GET /tracks/catalog`, а T2 требует его байт в байт.
- Экрана, который показывает `isMc` из `TrackView`, план не называет (P15 берёт MC из `shares`, `SplitsPage.tsx:91-101`).

**Добавить в SPEC T2 после «Правил полей»:**

> - `artists` — ники строк всех версий сплитов и участий ISRC, слитые id сведены к выжившему, по `pseudonym`, затем
>   `id`, как `artistsByIsrc`. `isMc = true`, если хотя бы одна строка сплита этого ника (по любому его id, в любой
>   версии) помечена MC (D-216). Ник только из участий — `isMc = false`.
> - Отметку считает отдельная функция `artistMarksByIsrc` в `track-artists.ts`; `artistsByIsrc` и его ответ
>   (`ArtistRef`) не меняются.

### В5. Имена `TrackView`, `ArtistView`, `ReleaseView` уже заняты в модуле owners

SPEC (строка 13) и план §3.1 обосновывают суффикс `View` тем, что `Track` / `Artist` заняты. Но в
`src/modules/owners/service.ts` уже есть `export type ReleaseView = ReleaseRow` (`:32`), `export interface ArtistView`
(`:81`) и `export interface TrackView` (`:89`). Их импортируют `facade/release-registry.ts:3` и сервис owners
(`listTracks(): Promise<TrackView[]>`, `:703`). В `facade/tracks.ts` встретятся оба `TrackView` (строка модуля из
`listTracks` и новая модель) и оба `ReleaseView`.

**Заменить в SPEC строку 13–14 («Имена.») на:**

> **Имена.** `trackSchema` / `Track` / `trackMetaSchema` уже заняты: это ответ `GET /tracks` и полная мета D-238. В
> модуле owners уже есть типы `TrackView`, `ArtistView`, `ReleaseView` (`modules/owners/service.ts:32, 81, 89`) — это
> строки модуля. Модель плана — типы `TrackView`, `ReleaseView`, `ArtistView` из `@erp/shared/api-responses`. В
> бэкенде, где нужны оба, типы модуля импортируются с псевдонимом (`type TrackView as TrackRow`), типы модуля не
> переименовываются. Везде ниже «трек-справочник» — это `TrackView` из shared.

### В6. Список T4.4 неверен: не те ответы, пропущенные ответы, режим P5

### В7. `valueGetter` гридов и `useMemo([])`

SPEC: «`valueGetter` гридов читают `TrackView`». Колонки P15 / P16 / P37 собраны в `useMemo(() => [...], [])`
(`SplitsPage.tsx:76, 124`; так же `ParticipationsPage.tsx`, `TermsTab.tsx`). `valueGetter`, который читает хук,
замкнётся на первом (пустом) состоянии кеша: фильтр, сортировка и экспорт будут видеть ISRC без названия. P15 и P16
листаются на сервере, так что все строки страницы — «показанные», и это решается зависимостью. На P5 `valueGetter`
должен остаться на строке каталога (Б1).

**Заменить в SPEC T4 строку «Хуки `track-name-<isrc>`…» на:**

> - Хуки `track-name-<isrc>` / `track-version-<isrc>` прежние. На P8, P10, P12, P15, P16, P36, P37 `valueGetter`
>   колонки трека читает `displayTitle(track(isrc))` и `track.meta?.version`; функция `track` входит в зависимости
>   `useMemo` колонок (или грид обновляет ячейки после ответа). На P5 `valueGetter` читает строку каталога.

### В8. e2e не проверяет названия треков

Ни одна спецификация `e2e/` не обращается к `track-name-*` / `track-version-*` (поиск по `packages/frontend/e2e` пуст).
`golden/50-track-meta.spec.ts` проверяет только вкладку «Мета» и шапку P6, а шапка читает `trackQueries.meta`
(`TrackPage.tsx:201, 207`), не `TrackName`. «e2e тех же спецификаций» (план §6) для T4 ничего не доказывает про
названия, а сброс кеша после записи меты не проверяет никто.

**Добавить в SPEC T4 «Общее»:**

> - e2e: в `golden/50-track-meta.spec.ts` после сохранения меты открыть P15 (`/splits?isrc=…`) и P8 релиза этого
>   трека и проверить `track-name-<isrc>` (название без версии) и `track-version-<isrc>`; затем изменить версию на P6,
>   вернуться на P15 без перезагрузки и проверить новую версию (сброс кеша). Писать в T4.1 (P8), дополнять в T4.3.
