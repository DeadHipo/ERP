# Аудит плана 05: реализуемость и простота

2026-11-18. Обзор только для чтения, версия 3 плана (`план.md`). Вопрос обзора: можно ли завтра реализовать этапы 0 и 1
по одному этому документу и не делает ли план лишнего для ERP одного лейбла с одним оператором. Аудиты 01–03 я
просмотрел только после своих выводов. То, что они уже сказали (`MONEY_PATH`, MCP по GET, батчер справочника, R2), здесь
не повторяю. Исключение — там, где я предлагаю другое решение.

## Сводка

План верен по направлению, но для этапов 0–1 он **одновременно недоопределён и избыточен**.

- **Недоопределён.** Не перечислены допустимые `grain` по методам. Не определены `amount` / `net` / `totals` для
  срезов с фильтром аллокаций. Нет семантики `sort`, `filter.hasSplit` и `filter.catalog`. Нет кодов ошибок.
- **Избыточен.** Этап 1 строит четыре денежных метода и четыре справочника, но у половины из них нет ни одного экрана
  в этапе 2:
  - паблишинг;
  - срезы `owner` / `artist`;
  - `/songs`, `/owners`, `/artists/query`;
  - реклама и саблейбл заменяют уже работающие ответы того же вида.

  Сюда же относятся семафор, серверное листание с сортировкой, `MoneyView` с правилом eslint и пакетный загрузчик с
  «кешем по ключу». Всё это — лишняя работа без выгоды для владельца на этом этапе.

**Главное предложение.** Разделить план на две независимые линии.

- **Линия «Трек»** (без денег, низкий риск):
  - `Track`, `POST /tracks/query`;
  - `baseTitle` на сервере;
  - `TrackName` на `Track`.

  Это закрывает цель «один трек везде» и снимает решения фронта (`TrackName.tsx:17`).
- **Линия «Деньги»:** **один** метод `POST /money/master/query` с тремя срезами `track` / `release` / `isrcs` и
  несколькими перечисленными зёрнами. Остальное — по мере появления экрана.

Этапы 0–1 сокращаются примерно с 15 до 8 коммитов. Ни одна цель владельца не теряется.

## Блокеры

### Б1. `grain` — произвольный `string[]`: нет списка зёрен, а значит нет схемы, теста и реализации

**Где.** `план.md:163` (`grain: string[]`), `план.md:104-111` (все ключи `MasterRow` необязательны), Р10.

**Почему это блокер.** Без списка непонятно, что делать:

- в zod-схеме тела (`api-schemas.ts`);
- в схеме ответа (`api-responses.ts`): все ключи optional, и `api-descriptions.test.ts` потребует `.describe()` на
  каждом;
- в реализации.

Конкретные вопросы без ответа:

- Что значит `grain: []`?
- Что значит `['upc','recipient']`?
- Допустим ли `labelString` вместе с `book`?
- Что значит зерно `status` без `recipient`? Это B / C / ours юнита — но у юнита их несколько.

`api-contract.test.ts` должен вызвать операцию в сценарии. Для «любого сочетания» он проверит одно сочетание из сотен.

**Что поменять.** Перечислить в плане закрытый `z.enum` допустимых наборов. Для этапа 2 нужно ровно столько:

| Набор | Кто | Старый двойник |
|---|---|---|
| `isrc` | P5, P8 «треки» | `trackSummary`, `release.tracks` |
| `month` | P8 «месяцы» | `release.months` |
| `isrc,month` (Р10) | будущие блоки | — |
| `recipient,month` | P6 «По артистам» | `byArtistOf` (`aggregates.ts:563-603`) |

Остальное добавлять со своим экраном. Сортировку фиксировать на сервере (ключи по возрастанию) и убрать `sort` из тела:
блок сортирует сам (§В2 ниже).

### Б2. Что такое `amount`, `net` и `totals` при срезе `owner` / `artist` с фильтром аллокаций — не определено

**Где.** `план.md:110-113`, `план.md:174-178`, `план.md:168` (`totals: MoneySums`).

`MoneySums` = `Sums` из `aggregates.ts:42-63`: `net` и `ours` юнитов, B аллокаций, C из `cItems`. При фильтре «только
аллокации владельца» эти поля перестают иметь смысл:

- `net` юнита ISRC с двумя владельцами не принадлежит ни одному из них;
- `ours` к владельцу не относится;
- C из `cItems` включает C доли лейбла (`no_split`, `label_unmapped`), которая владельцу не начислена.

Без определения разработчик выберет одно из трёх. Тест «равенство с `ownerBalance`» сойдётся только при одном выборе.

Есть и вторая неясность. У `AreaBook` (`balance.ts:95-111`) нет `waiting` по областям. Поэтому строка
`publishing, owner, grain book,status` из §6.1 не имеет поля-двойника в балансе: `waiting` книги — это мастер и
паблишинг вместе.

**Что поменять.**

- Либо сразу определить: при срезе `owner`/`artist` строки — только аллокации, `totals = { B, C, cByReason }` без
  `net`/`ours`. Тест: B = `byArea.master.earned` книги, C мастера = `waiting` книги − C паблишинга книги.
- Либо (предпочтительно, см. В1) **убрать срезы `owner`/`artist` и метод паблишинга из этапа 1**: у них нет экрана в
  этапе 2. P10 и P12 остаются балансом по Р8.

### Б3. P5 и P7 под менеджером: сопоставление прав §4.4 ломает экраны, которые менеджеру открыты сегодня

**Где.** `план.md:233-242`, `план.md:199-200`, `план.md:320`.

- **P5 «все деньги».** Сегодня это `GET /tracks/summary` без `isrcs`, под `?label=`. Менеджеру открыто: `'L'`,
  `manager-answers.ts:26`; книга лейбла — `aggregates.ts:185-192`. План переводит «P5 по всему лейблу» на серверное
  листание. Единственный вид, который это даёт, — `book`, а `book` по таблице §4.4 «заменяет `GET /overview`» →
  менеджеру 403 (`manager-answers.ts:70`). Получается, что Р13 («ни шире, ни уже») нарушено в сторону «уже».
- **P7 колонка `net`.** Она стоит в порядке этапа 2 (`план.md:320`). Сегодня это `sources.netByUpc` **без расчёта**
  (`aggregates.ts:401`; `GET /releases` менеджеру `'L'`, `manager-answers.ts:31`). Перевод на денежный метод:
  - по книге: менеджер получит 403;
  - по `isrcs`: не тот зерно-ключ, `upc`;
  - в любом случае полный `calculate()` вместо суммы ClickHouse.

  Это медленнее и не даёт ничего: `net` — поступление, а не начисление.

**Что поменять.**

- P7 `net` убрать из этапа 2: это не деньги расчёта.
- Для P5 сохранить существующую двухфазную схему D-162. Строки берутся из `GET /tracks/catalog`, деньги видимых строк — из
  `POST /money/master/query { scope: { kind: 'isrcs' } }`. «Все деньги» = срез `isrcs` со всеми ISRC каталога лейбла.
  Права у него те же, что у `GET /tracks/summary` (`L`), и серверного листания не нужно.
- Вид `book` из этапа 1 убрать.

## Важно

### В1. Половина методов этапа 1 не имеет экрана в этапе 2 (YAGNI)

**Где.** Сверка §4.1 (`план.md:150-155`) с порядком экранов этапа 2 (`план.md:320`) и со списком исключённого
(`план.md:324-328`).

| Метод / срез | Экран этапа 2 | Вывод |
|---|---|---|
| master `track` | P6 «По артистам» | нужен |
| master `release` | P8 | нужен |
| master `isrcs` | P5 | нужен |
| master `owner` / `artist` | нет: P10/P12 остаются балансом (Р8) | отложить |
| master / publishing `book` | нет (Б3) | убрать |
| `POST /money/publishing/query` | нет: паблишинг на P10 — баланс, на страницах v2 — `pubv2` | отложить целиком |
| `POST /money/ads/query` | «реклама трека (P6)»: тот же ответ, что `GET /ads?isrc=` уже даёт | отложить; Р3 выполнить, когда появится блок рекламы на нескольких страницах |
| `POST /money/sublabel/query` | P37 | **не нужен** (В3) |
| `POST /artists/query`, `/songs/query`, `/owners/query` | нет: `ArtistRef` уже в строках (`artistRefSchema`, `api-responses.ts:269`) | отложить |

Каждая операция стоит одинаково:

- две схемы;
- строка `operations.ts`;
- строка `manager-answers.ts`;
- строка `coverage.ts` (до экрана — `refusal`);
- вызов в сценарии `api-contract.test.ts`;
- описания полей (`api-descriptions.test.ts`);
- кейс `scope.test.ts` (scoped = full);
- тест менеджера.

Восемь операций — это около 64 правок до первого экрана. Две операции — около 16.

### В2. Серверное листание, сортировка по `Decimal` и семафор — лишние

**Где.** `план.md:164-166`, `план.md:198-207`, `план.md:292-294`.

- **Листание и сортировка.** Единственный потребитель листания — P5 целиком. По Б3 его закрывает схема D-162, которая
  уже работает: страница видимых строк, `onVisibleRowsChanged` (`frontend/CLAUDE.md`, P5). Без серверного листания:
  - у блока остаётся один режим (AG Grid на клиенте);
  - не нужны `limit` / `offset` / `sort` в теле;
  - отпадает «два режима блока» (`план.md:292-294`).
- **Семафор.** Он защищает от двух одинаковых тяжёлых расчётов у ~одного оператора. TanStack уже не шлёт одинаковый
  ключ дважды, и ни одна текущая точка (`ownerPayables` целиком, `overview`) семафора не имеет. Отложить до замера,
  который покажет проблему.
- **Лимиты.** Оставить `isrcs ≤ 5000`. `limit` для токена чтения не нужен без листания. Тело 5000 ISRC — около 80 КБ,
  это под `1mb` (`http.ts:66-71`): проверять нечего, достаточно теста на 5001 → 400.

### В3. Отчёт саблейбла уже серверный и уже сгруппирован: новый метод ничего не даёт

**Где.** `план.md:131-144`, `план.md:337`, `план.md:352`.

`sublabel-report.ts:46-62` уже отдаёт `rows`, `months`, `tracks`, `artists`, `total`, `ads`, `amountAfterAds`, CSV. Это
ровно `grain: month|isrc|artist` и `totals` плана, причём под правами D-219 (`manager-answers.ts:63`: `x`). Перевод на
`POST /money/sublabel/query` даёт:

- ещё одну операцию;
- тест равенства «новое = старое»;
- `download()` для POST (`план.md:221`);
- удаление старого;
- правку `shadow-dump.ts` и `golden/49-sublabels`.

Всё это ради того же ответа.

**Что поменять.** Оставить `GET /sublabels/:id/report`. Единственное, что нужно для цели «один трек», — названия в его
`tracks[]` строить через `Track` (линия «Трек»). Строку `download()` для POST из §4.3 убрать.

### В4. Цель «один трек» не зависит от денег — поставить её первой и отдельно

**Где.** Этап 0 (`план.md:318`) кладёт `Track` и `tracksOf` в фасад, «ничего не вызывает». `TrackName` на `Track` стоит в
середине этапа 2 после денежных экранов.

Почти всё для `Track` уже есть.

- **Мета.** `metaLookup` (`facade/track-meta-lite.ts`). Его надо расширить до полной `Meta` (`trackMetaSchema`,
  `api-responses.ts:~2157`).
- **Наше название, UPC, ники, «есть сплит / участия», лейбл каталога** собраны в `trackCatalog`
  (`aggregates.ts:252-310`). Если вынести его тело `db.snapshot` в `tracksOf(isrcs)`, получится `Track`, и
  `trackCatalog` станет `tracksOf(все ISRC)` плюс фильтр. Код не дублируется.
- **`baseTitle`.** Сегодня вычисляется во фронте (`TrackName.tsx:17`). Перенести в shared как чистую функцию, взять её
  в `tracksOf` и покрыть тестом (версия в скобках, через « - », регистр, отсутствие версии).
- **`releases` с реестром.** Готов `registryByUpc` (`aggregates.ts:94-103`).

Линия «Трек» = `POST /tracks/query` плюс перевод 12 мест `TrackName`. Денег она не касается, поэтому:

- R2, `MONEY_PATH`, `MONEY_KEYS` не трогаются;
- расчёт не нужен (тест «не импортирует `./calculation`», как в `onboarding.ts`);
- e2e меняются только по `data-testid` названий.

### В5. Пакетный загрузчик и «кеш по ключу» не нужны для первой версии

**Где.** `план.md:282-286`, Р5.

Блок и так знает свои ISRC. Хватит обычного `useQuery(['tracks','query', sortedIsrcs])` с долгим `staleTime`. При
необходимости можно делать `setQueryData(['track', isrc])` в `onSuccess`, но не обязательно. Сборщик запросов одного
кадра можно добавить, когда на странице окажется больше одного блока со справочником. Сегодня таких страниц нет:
P8 — один блок треков, P6 — один трек.

Ещё проще другой вариант: денежный ответ несёт `tracks: Record<isrc, Track>` для своих строк. Тогда это один запрос на
блок, без второго круга. Но это меняет Р5/Р6 владельца, поэтому решение за ним. По умолчанию — отдельный
`/tracks/query` без батчера.

### В6. `money()`, `MoneyView` и правило eslint — раньше потребителя

**Где.** `план.md:56-74`, этап 0.

Фронт сегодня денег не складывает (R1, `Money.tsx` только форматирует строку). На бэкенде точность уже 40 знаков
(`backend/src/shared/money.ts:5`, `Decimal.set` глобально). Первым, кто сложит деньги на фронте, станет «итог по
отмеченным строкам» или перегруппировка в блоке этапа 2.

Предложение:

- `decimal.js` в shared и `money()` — в том коммите этапа 2, где появляется первое сложение;
- тест на 40 знаков там же;
- `MoneyView` и правило eslint отложить: тип `string` и так не складывается, а неаддитивные поля (`payableShown`) живут
  в балансе, который по Р8 не переходит в блоки.

Кроме того, нужна одна точная версия в трёх `package.json`: сейчас в бэкенде `^10.6.0`. Иначе получатся две копии
`decimal.js` с разной глобальной настройкой. Надо явно сказать, что shared использует `clone`, а не `Decimal.set`.

### В7. Флаг `query`: реализация меньше, чем выглядит, но порядок важен

**Где.** `план.md:212-225`.

Места, которые решают по методу:

- `audit.ts:11,332`;
- `originGuard` (`auth/middleware.ts:203`);
- `needsOperator` (`operations.ts:1871`);
- `client.ts:71,92`;
- `mcp.ts:18-20`;
- e2e `helpers.ts:111-129`.

`authorize` решает по `ability`, а не по методу (`authorize.ts:44-50`): там ничего менять не надо.

`originGuard` оставить. JSON-POST и так требует предварительного запроса браузера, а комментарий `middleware.ts:194`
опирается на «непростой» `X-Operator`. Для POST-чтения защиту даёт `Content-Type: application/json`. Это надо
записать в D-записи, иначе следующий агент «упростит» заголовок.

MCP можно отложить целиком: пока старые GET живы, инструменты не теряются. POST в MCP нужен только перед удалением на
этапе 3.

Флаг `query` — **отдельный первый коммит этапа 1**, с тестом на холостой операции, ещё до любого метода.

### В8. Тесты равенства §6.1: часть строк не определена как сравнение

- **P6 «По артистам».** `byArtistOf` (`aggregates.ts:563-603`) отдаёт `amount`/`waiting` по нику и месяцу без причин,
  плюс серии `ours` и `net` по `u.ours`. C доли лейбла (`no_split`, `label_unmapped`) туда не входит. Тест должен
  сказать: строки `recipient=artist` новой выдачи, сложенные по причинам, равны `byArtist.rows`. Строка
  `recipient=ours, status=ours` равна `byArtist.ours`. Строки `recipient=ours, status=C` — новое, без двойника.
- **Срез `isrcs` против `trackSummary`.** `trackSummary` отдаёт и ISRC **без** денег (из `owners.listTracks`,
  `aggregates.ts:220`). Денежная выдача по построению отдаёт только ISRC с единицами. Тест: множество ключей новой
  выдачи — подмножество; у отсутствующих в старом все суммы нулевые.
- **«Посимвольно».** Сравнивать строки JSON после `toJSON` (`money.ts:8`), не `Decimal.eq`. Иначе «посимвольно» не
  проверяется.

### В9. «Сверка на живой базе = 0» и «замер» — не сказано, чем

**Где.** `план.md:319`.

Нужен скрипт, например `scripts/check-money-query.ts`: обойти все UPC, ISRC с деньгами и треки лейбла, сравнить старое
с новым, распечатать расхождения и время. По образцу `check-owner-scope.ts` и `check-label-books.ts`. Это отдельный
коммит. Без него критерий готовности этапа 1 не проверяем.

### В10. Скрытые расходы на операцию — перечислить в плане явно

Для каждого нового метода:

- `operations.ts`: `access: 'org'`, `ability: { action: 'read_money', subject, scope: 'label' }`, `query: true`;
- `api-schemas.ts` (тело) и `api-responses.ts` (ответ, `.describe()` на каждом поле);
- `manager-answers.ts`: одна буква на операцию;
  - при разных ответах по видам среза таблица одной буквой их не выразит;
  - если оставить только `track`/`release`/`isrcs`, то у `track` будет `x`, у остальных `L`;
  - проще сделать `GET /tracks/:isrc/money` (`x`) отдельным видом и не мешать его в одну операцию — либо принять
    «вид `track` → 403 в маршруте» с отдельным тестом;
- `coverage.ts`: до экрана — `refusal: 'stage 1: used from stage 2 (D-xxx)'`; `coverage.test.ts` требует точный
  набор ключей;
- `api-contract.test.ts`: вызов в сценарии, обе ветви — админ и менеджер;
- `scope.test.ts`: scoped = full для нового метода (D-164);
- `read-token.test.ts`: только если MCP включается сейчас (В7);
- i18n — ничего до этапа 2.

## Мелочи

- **М1. Сужение для владельца не новое.** `план.md:197` пишет «новое сужение через `ownerReach`». На деле
  `ownerReach` / `ownersReach` / `artistReach` уже есть (`owner-scope.ts:14-44`) и используются балансом и
  `ownerPayables`. Это переиспользование, а не новая работа (и при В1 оно не нужно).
- **М2. `filter.hasSplit` и `filter.catalog: 'current'`** — свойства справочника, а не денег (`план.md:164`,
  `план.md:295`). Если оставить их в денежном фильтре, денежный метод начнёт читать `track_labels`.
  `boundaries.test.ts` это запрещает только для `calculation.ts` и слоёв, но смысл D-172 тот же. При схеме D-162 (Б3)
  оба фильтра применяются к строкам каталога, до денег, и из тела уходят.
- **М3. `Track.artists` «с отметкой MC».** `artistRefSchema` = `{ id, pseudonym }`. MC — свойство строки сплита во
  времени (D-216), а не ника. Нужно определение: «есть открытая строка с `is_mc`» или «когда-либо была».
- **М4. `titleSource: 'report'`** требует `sources.pairAttributes` (ClickHouse) в справочнике. Это не расчёт, но запрос
  к ClickHouse на каждый `/tracks/query`. Записать это или читать `report`-название только для ISRC без строки
  каталога.
- **М5. Неопределённые коды ошибок.**
  - 400 `validation` на неизвестный набор зёрен — общий код `parse`.
  - 404 — на чужой или неизвестный `track` / `release` (как `release()` `NotFoundError`, `aggregates.ts:455`).
  - 403 `forbidden` — на вид, закрытый менеджеру.

  Записать это в §4.
- **М6. Р15 / `period.basis: 'sales'`.** На этапе 2 его не использует ни один экран: P8 и P6 идут по месяцу отчёта.
  Убрать `basis` из тела до появления экрана.
- **М7. Число `TrackName`.** «12 мест в 11 файлах» верно (11 файлов страниц плюс сам компонент). Перечень полезно
  положить в план, чтобы шаг этапа 2 был проверяем.
