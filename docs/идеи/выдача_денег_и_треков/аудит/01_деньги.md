# Аудит плана «единая выдача денег и треков»: правильность денег

2026-11-18. Независимый просмотр `план.md` против кода (`facade/calculation.ts`, `layers/`, `balance.ts`,
`owner-scope.ts`, `aggregates.ts`, `sublabel-report.ts`, `ads.ts`, `queue.ts`, `as-of.ts`) и решений 97. Код не
менялся. Строки указаны по состоянию ветки `feature/fable-003` на 5ce158c.

Итог: сама идея (новое рядом со старым, `calculate()` и слои не трогаем, равенство до перевода экрана) совместима с
D-161/D-164. Но модель строк и срезов в §3.3/§4.1 недоопределена так, что три теста равенства из §6 **не могут
сойтись** без уточнений, а срез `sublabel` как получатель денег противоречит D-232. Ниже — по убыванию важности.

## Блокеры

### Б1. `Recipient { kind: 'sublabel' }` — получатель, которого в деньгах нет (D-229, D-232)
- Доказательство: D-232 убрал вырезку саблейбла из слоёв, `Allocation.layer` без `sublabel`; `ads.ts:44-46`
  (`borneBy` всегда `ours`); `sublabel-report.ts:14-17` («the part lives only here»). Часть саблейбла — это
  **часть доли «наше»** (`u.labelShare`), а не отдельная аллокация.
- Что сломается: если строки мастера с `recipient = sublabel` попадут в ту же выборку, что и `ours`, сумма по
  получателям станет больше `net` (часть посчитана дважды), `totals` перестанут давать A = B + C + ours. Статус
  «подтверждено / ждёт» у части свой (документ условия, `SublabelReportReason`: `no_document`,
  `document_not_approved`, `assumption`, `no_split`, `not_allocated`), это не категория B/C и не `CReason` —
  `MoneySums.cByReason` его не вмещает.
- Исправление: убрать `sublabel` из `Recipient`. Срез `sublabel` у мастера — **отдельная форма ответа** (как
  сегодня `rows` отчёта): строка `{ isrc, month, termId, percent, documentId, labelShare, amount, status, reason:
  SublabelReportReason }` и свои итоги `SublabelSums { labelShare, amount, confirmed, waiting }`; без `net`, `B`, `C`,
  `ours` (спецификация §9: саблейбл не видит валовой суммы и чужих долей). Записать в D-записи, что это вид отчёта,
  а не деньги.

### Б2. Срез `owner` / `artist` = охват (reach) — это надмножество, а не набор строк
- Доказательство: `owner-scope.ts:1-12, 54-63` — охват = все ISRC строк и участий ника **за любой период** плюс ISRC
  рекламы; точен только потому, что `ownerBalance` дальше читает лишь единицы, где у владельца есть аллокация
  (`balance.ts:545-548`, `mine.length === 0 → continue`; `ownerIndex` `balance.ts:1060`).
- Что сломается: `POST /money/master/query { scope: owner }` по ISRC охвата вернёт месяцы до начала сплита
  владельца, строки других получателей и `ours` тех же единиц. Тест «master + publishing, scope owner = `ownerBalance`
  earned / waiting» не сойдётся.
- Исправление: в §4.1 определить срезы как **(набор единиц для чтения) + (фильтр аллокаций)**:
  `owner` — `scoped({ isrcs: reach })`, затем только аллокации `a.ownerId === owner`; `artist` — `artistReach`, затем
  `a.artistId ∈ ids` (id уже канонический). `net` / `ours` для этих срезов — только по единицам, где есть такая
  аллокация, ровно как `period.received` / `period.ourShare` (`balance.ts:553-559`). Получатели «другие» — отдельная
  строка `others` (как `otherParticipants`), если нужна.

### Б3. Паблишинг по треку / релизу / ISRC и строки `songId` / `songwriterId` нельзя получить из `calculate()`
- Доказательство: `PublishingResult` (`calculation.ts:71-85`) несёт `writerName`, `workTitle`, `ownerId`, `labelId`, но
  **не** `songId` и не `songwriterId`; они теряются в `calculation.ts:266-289`, хотя строки их имеют
  (`pubv2/service.ts:178-187`, `publishing-source.ts:116-124` отдаёт `writerNorm` = songwriterId). Сопоставлять по
  `workTitle` нельзя: у разных песен бывают одинаковые названия.
- План говорит «расчёт не меняется» (§6), а `calculation.ts` — закрытая зона (D-173).
- Исправление (выбрать одно и записать D-запись): (а) с разрешения владельца добавить в `PublishingResult` два поля
  только для чтения (`songId`, `songwriterId`), без нового умножения, с тестом «деньги посимвольно прежние»
  (`golden`, `exactness`, `shadow-dump.ts`); или (б) отказаться от `PublishingRow.songId` и среза паблишинга по треку
  до такого решения. Пересчитывать `allocateLine` второй раз в фасаде — нельзя (второй путь, дрейф).

## Важно

### В1. Срез паблишинга по треку / релизу удваивает деньги песни
- D-184: у песни **много** ISRC (`links.song_isrc`); D-185: деньги паблишинга идут владельцу и «не делятся по песне»;
  на живой базе ISRC песням почти не проставлены (D-184 «no ISRC was set»).
- Сломается: песня с двумя ISRC одного релиза покажется на обоих треках целиком; Σ по трекам релиза ≠ деньги песен
  релиза. Пустой паблишинг на треке будет читаться как «нет денег», а не «нет связи».
- Исправление: в §4.1 записать: для `track` / `release` / `isrcs` строки паблишинга — по **песне** (ключ `songId`),
  каждая песня один раз, со списком своих ISRC как справочным полем; итог среза = Σ по уникальным песням; ответ
  отдельно говорит «у N песен нет ISRC». Срез `artist` = пусто — верно (D-181: паблишинг в собственной позиции
  владельца, `OWNER_POSITION`).

### В2. `PublishingRow.amount` не хватает для A = B + C + ours и для `writer_unmapped`
- `publishing-categorise.ts:21-22`: без владельца `authorAmount = labelAmount = 0`, а в C идёт **весь** `payable`
  (`queue.ts`, `cItems`, ветка `!p.ownerId`); `reconcile()` `calculation.ts:462-474` считает A = `payable`,
  B = `authorAmount`, ours = `labelAmount`.
- Исправление: строка паблишинга несёт `payable`, `authorAmount`, `labelAmount`, `category`, `reason`, `percent`;
  `MoneySums` для паблишинга собирается теми же правилами, а C — **только** через `cItems` (D-141: одно место решает,
  что такое C).

### В3. Тест «totals, scope label = обзор» сравнивает разное
- `reconcile().byLabel` (`calculation.ts:396, 441-474`) — по книге и **вместе** с B17; `ourShareByLabel` — по лейблу
  записи (`ourLabelName`), не по книге; плюс `discrepancy`, `ourShareNoSplit`, строка на (источник, счёт, месяц).
- Исправление: в таблице §6 записать точное соответствие: master-totals среза `label` = Σ по месяцам строк
  `source = believe` из `byLabel[книга]`, publishing-totals = строки `b17`; `ours` мастера сравнивать с
  `byLabel.ourShare`, не с `ourShareByLabel`. Единицы без ISRC (`no_isrc`) **входят** в итоги лейбла (иначе A не
  сойдётся), хотя `trackSummary` / `release` их отбрасывают (`aggregates.ts:208, 452`) — правило для ключа
  `isrc = ''` нужно назвать явно.

### В4. `labelId` в строке мастера неоднозначен: три разных «лейбла»
- Книга (`bookLabelId`, лейбл файла, D-169), лейбл записи (`ourLabelId`, по строке лейбла, решает
  `ours / label_unmapped`), лейбл каталога (`track_labels`, D-172, **деньги его не читают**). В плане
  `Track.label` — каталог, `label?` запроса — книга, `MasterRow.labelId` — не сказано.
- Исправление: два ключа `bookLabelId` и `ourLabelId`; срез `label` и параметр `label` — только книга;
  `Track.label` подписать «каталог, не деньги»; тест в `boundaries.test.ts`, что новый метод денег не читает
  `track_labels`.

### В5. Срез `release` — по UPC единицы, а не «все ISRC релиза»
- `aggregates.ts:449-452`: `release()` берёт `scoped({ upcs })` и `u.upc === upc`. Трек на сборнике и на сингле —
  деньги другого UPC сюда не входят. Кроме того, `release().tracks` содержит треки без единиц с нулями.
- Исправление: в §4.1 «release = единицы этого UPC (`scoped({ upcs })`)»; тест равенства — по множеству ISRC с
  ненулевыми суммами, нулевые строки — справочник.

### В6. «Деньги по трекам» в балансе P10/P12 отличаются от новой выдачи по построению
- `balance.ts:594, 604` — `artist.earned` / `waiting` в строке ника и треках считаются **за период**, а
  `total.earned` — за всё время (`book.earned`, `balance.ts:564`). `balance.ts:608` — `t.net` прибавляется
  **за каждую аллокацию** ника в единице: ник с двумя участиями на одном ISRC (разный `funded_from` разрешён,
  `splits/service.ts:393`) получит `net` дважды. Плюс `asOf` и срезы (`as-of.ts:12-21`, D-198): баланс режет
  входы по месяцу отчёта, в запросе плана `asOf` нет.
- Исправление: либо оставить таблицу треков частью ответа баланса (Р8 и так держит баланс целиком) и не переводить
  её в этапе 2, либо добавить в запрос `asOf` с той же семантикой (`reportingMonth ≤ asOf` при любом basis) и
  заранее решить, что `net` трека считается один раз на единицу (тогда это осознанная правка старого числа с
  D-записью, а не «тест равенства»).

### В7. `byArtist` (D-237) не собирается из `MasterRow` без уточнений
- `aggregates.ts:563-605`: строка ника = Σ **всех** его аллокаций (B и C) и отдельно `waiting` (C);
  `Recipient { kind: 'waiting'; reason }` в плане теряет ника у ожидающей аллокации; ряды `ours` и `net` по месяцам;
  сортировка `amount desc, pseudonym`.
- Исправление: `recipient` = кто получает (`artist` / `ours` / `labelShareC`), а `status` (B/C) и `reason` —
  отдельные ключи зерна; `labelShareC` — для доли лейбла в C (`no_split`, `label_unmapped`, `unknown_pair`,
  `no_isrc`; `cItems` вторая ветка). Сравнивать в тесте множества строк, не порядок (порядок задаёт справочник).

### В8. Реклама: модель `AdRow` уже ответа `GET /ads`
- `ads.ts:24-47`: у записи `isrc` может быть `null` (расход на ника, `pre_allocated`), есть `status`
  (`no_split`, `no_artist`), `scope`, части `amount` и `recovered` по нику, плательщик `ourLabelId` (книга расхода =
  лейбл записи, R9, не книга единиц), `incomeBookLabelId` (информация).
- Исправление: `AdRow { adId, isrc: string | null, artistId?, month, payerLabelId, status, scope, amount,
  recoveryPercent, parts: { artistId, ownerId, amount, recovered }[], unrecovered, bearerSublabelId }`; срез `label` —
  по плательщику; срез `owner` — по `parts.ownerId` (как `adPositionsByOwner`); период запроса **не** передавать в
  `scoped()` для рекламы (D-161: «all months», иначе меняется `incomeBook` / строка лейбла ближайшего месяца).

## Мелочи

### М1. Сложение на фронте точно, но только при условиях
- Все суммы — 12 знаков (`exact.ts`), сложение decimal.js при `precision: 40` точно и не зависит от порядка;
  сервер ставит 40 глобально (`shared/money.ts:5`). У decimal.js по умолчанию `precision: 20`: итог 1,4 млн с 12
  знаками — уже 19–20 значащих цифр, суммы лейбла за всё время её превысят. В `@erp/frontend` и `@erp/shared`
  decimal.js сейчас не подключён.
- Исправление: `money()` = `Decimal.clone({ precision: 40 })`, eslint запрещает `new Decimal` вне него; тест:
  Σ строк на фронте = `totals` сервера посимвольно на выборке с большими суммами. Округлять (`formatMoney`) только
  после сложения; Σ показанных копеек строк ≠ показанный итог — это нормально, не «чинить».
- Неаддитивное фронту не складывать никогда: `payableShown` (Σ положительных позиций, D-181), `byArea.payableShown`
  (Σ областей ≥ книги), `floorToCents` гейта, часть саблейбла от агрегированной базы (часть — `pct` **на единицу**,
  `sublabel-report.ts:105`; `pct(Σ base)` ≠ `Σ pct(base)`). Записать список в D-записи смены R1.

### М2. `MONEY = { scale: 12, rounding }` не должен подменять серверный Decimal
- Сервер квантует явно (`q`, `pct`), а `toJSON` пропатчен на прототипе (`shared/money.ts:7-10`). Константу читать
  можно, но сервер пусть остаётся на своём `Decimal` из `shared/money.ts`; `scale`/`rounding` на фронте применимы
  только к умножению, которого там быть не должно (Р9).

### М3. Отчёт саблейбла: период, книга, csv
- Покрытие условием — по месяцу отчёта (`sublabel-report.ts:89`), реклама — по месяцу расхода; книгу отчёт не
  фильтрует. `basis: 'sales'` и `label` для среза `sublabel` должны быть запрещены (400) или явно описаны.
  `GET /sublabels/:id/report.csv` строится из того же `report()` — при удалении метода в этапе 3 csv должен
  собираться на сервере из нового запроса, не на фронте (это документ для контрагента).

### М4. MCP и правило «не складывать на глаз»
- Инструкция MCP-сервера ERP прямо говорит клиенту: суммы не складывать, цитировать поля. Удаление `byArtist` и
  `/tracks/summary` (этап 3) переложит сложение на модель. Исправление: MCP получает те же запросы с `totals` по
  нужному зерну, итоги всегда с сервера.

### М5. Флаги, которых нет в строке
- Метка MC (D-216, D-237) деньги в строке не меняет (уже учтена в слоях и рекламе), но экрану трека она может
  понадобиться — брать из справочника сплитов, не из строки денег. Строка vs участие (`Allocation.layer`
  `split | top | carve`, `ruleId`, `documentId`) нужны для объяснения и `earnedMasterByLayer` (D-212) — последнее
  остаётся в балансе (Р8); для P6 «по месяцам» оставить `explain` как есть.
- `labelShare` (база саблейбла, `months[].labelShare` трека) и `salesMonth` как ключ — добавить в список зёрен;
  `account` и строку лейбла (ключ единицы, D-124) — тоже, иначе не повторить строки месяца P6 (тот самый баг ключа месяца P6 без месяца продаж из записи этапа 5 фронта в 97).

### М6. Р11 и проверка «экран = API»
- Если итог на экране посчитан фронтом, e2e «экран = API» его не проверит. Исправление: такие итоги — только из
  `totals`, или фронтовый юнит-тест на `money()`-свёртку.

## Что в плане верно
- `calculate()` и слои не меняются; срезы `track`, `isrcs`, `release`, `label` прямо ложатся на
  `scoped({ isrcs | upcs | labelIds, publishingLines: false })` (D-161/D-162) и дают посимвольно полный ответ,
  потому что аллокация единицы зависит только от единицы и справочника.
- `MoneySums { net, B, C, ours, cByReason }` совпадает с `Sums` из `aggregates.ts:42-63`; при C через `cItems`
  тесты «release tracks / months» и «tracks/summary» сойдутся по деньгам (кроме нулевых строк без единиц, В5).
- Баланс, выплата, ведомость, срезы, допуск — остаются серверными (Р8): D-181, D-176, D-198 не задеты.
