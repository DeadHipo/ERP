# Аудит 04: проверка версии 3 плана против кода

2026-11-18. Независимая проверка `../план.md` (версия 3): я пытался опровергнуть утверждения плана, сверяя их с кодом
ветки `feature/fable-003` (коммит 80ab214). Код не менялся. Строки указаны в виде `файл:строка` на момент чтения.
Все пути бэкенда начинаются с `packages/backend/`.

Итог: в главном версия 3 верна. Саблейбла нет среди получателей, книга задаётся через `?label=`, баланс остаётся
баланс, POST-чтение описано. Но три утверждения не выдерживают проверки кодом:

- **тест равенства по владельцу** сравнивает с полем, которого в балансе нет.

## 2. Блокеры

### Б1. Вид `book`: план закрывает менеджеру то, что сегодня ему открыто, и противоречит сам себе

**Доказательство.**

- Менеджер уже сегодня видит деньги всей своей книги по каждому ISRC:
  - `GET /tracks/summary` без `isrcs` под `?label=` берёт все видимые ISRC книги (`src/facade/aggregates.ts:187`:
    `only = asked ?? [...lc.visible.isrcs]`). Право — `L` (`tests/helpers/manager-answers.ts:26`).
  - P5 так работает в режиме «Посчитать все» и при переходе из P1 с `?account&month`.
  - `GET /releases` отдаёт `net` по каждому UPC книги, право тоже `L` (`manager-answers.ts:31`).
- План при этом:
  - сопоставляет вид `book` с `GET /overview` и закрывает его менеджеру (§4.4);
  - ограничивает `isrcs` ≤ 5 000 (§4.2);
  - называет «P5 по всему лейблу» единственным списком с серверным листанием (§4.2).
- По аудиту 03 (В1) в каталоге около 26 тыс. ISRC. Значит, P5 «целиком» для менеджера в новой модели не выразить:
  либо 403, либо отказ по лимиту. Это прямое нарушение Р13 («ни шире, ни уже»).
- Внутреннее противоречие:
  - §4.1 пишет «Вид `label` убран… Его не повторяем», но в схеме запроса остаётся `{ kind: 'book' }`, а паблишинг
    получает срез `book` «сразу»;
  - `book` и есть итог книги под другим именем;
  - §6.1 при этом прямо отказывается сравнивать его с чем-либо.
- Пропущены ещё два потребителя:
  - `scripts/compare-reference.ts:546` читает `/tracks/summary` целиком, без ISRC и без книги;
  - MCP-инструмент `get-tracks-summary` можно вызвать так же.

  Для `book` без `?label=` у администратора поведение не определено.

**Что исправить.**

- `book` = все единицы книги из `?label=`. Он заменяет `GET /tracks/summary` без `isrcs` (с фильтрами `account` и
  месяц) — это `L` под своей книгой. С `GET /overview` его не сопоставлять.
- Тест равенства: `master, book, grain isrc, filter account/month` = `GET /tracks/summary?account&month&label`.
- Записать, что `book` без `?label=` у администратора означает все книги (или 400).
- Фразу «вид `label` убран» заменить на «итоги обзора (`reconcile`, B17 и единицы без ISRC) не повторяем».
- P7 см. В12.

### Б2. `PublishingRow` по песне не построить: в `PublishingResult` нет ни песни, ни автора v2

**Доказательство.**

- `PublishingResult` (`src/facade/calculation.ts:71-86`) несёт `writerName`, `workTitle`, `ownerId`, `labelId` — и
  ничего больше.
- Ключ строки отчёта теряется при построении: `writerNorm` = `songwriterId` есть в строке
  (`src/facade/publishing-source.ts:116-124`), но в результат он не попадает (`calculation.ts:266-289`). `songId` не
  доходит даже до `PublishingLine`.
- План откладывает срез по треку (Р14), но оставляет:
  - `PublishingRow { songId?, songwriterId?, … }` с комментарием «одна песня — одна строка» (§3.3);
  - строку в §9 «песня — одна строка»;
  - риск в §7 «Задвоение паблишинга по трекам → строка на песню».
- Сгруппировать по `workTitle` нельзя: у разных песен бывают одинаковые названия (аудит 01 Б3).

**Что исправить.** Пока решение (а) из 01 Б3 не принято владельцем:

- ключи `PublishingRow` = `ownerId`, `quarter` / `reportMonth`, `book`, `status`, `reason`, а `writerName` и
  `workTitle` — только для показа;
- строка — это строка расчёта (автор × название × квартал), а не песня;
- `songId` / `songwriterId` из модели убрать;
- строку риска в §7 и пункт §9 переписать.

### Б3. Тест равенства «master, owner, grain `book,status` = earned / waiting мастера по книгам» не может сойтись

**Доказательство.**

- В балансе нет ожидающих денег мастера по книге:
  - `BookAcc.waiting` складывает C мастера (`src/facade/balance.ts:598`) и C паблишинга (`:650`) в одно поле;
  - у `AreaAcc` поля `waiting` нет вовсе (`balance.ts:284-296`, только `earned`, `recouped`, …).
- `earned` мастера по книге есть: `byLabel[…].byArea.master.earned` (`:565`). Значит, сравнивать можно только `B`.
- Кроме того, не определены `totals: MoneySums` для среза владельца:
  - `sumUnits` (`aggregates.ts:51-63`) считает `net` и `ours` единицы целиком;
  - его C через `cItems` включает долю лейбла в C (`src/facade/queue.ts:37-45`), которая владельцу не принадлежит;
  - баланс берёт `net` / `ours` только по единицам, где у владельца есть аллокация, и только в периоде
    (`balance.ts:553-559`).
- Балансу при этом менять ничего нельзя (§6 «Принципы»).

**Что исправить.**

- Тест: мастер B по книге = `byArea.master.earned`; паблишинг B по книге = `byArea.publishing.earned`;
  `Σ (C мастера + C паблишинга)` по книге = `byLabel[книга].waiting`.
- В §4.1 записать `totals` для срезов `owner` / `artist`:
  - `B` и `C` — только аллокации владельца или ника;
  - доля лейбла в C не входит;
  - `net` и `ours` — по единицам с такой аллокацией, как `period.received` / `period.ourShare`;
  - `cByReason` — только из этих аллокаций.

## 3. Важно

### В1. Имя признака `query` уже занято
- `ApiOperation.query?: z.ZodObject` (`src/api/operations.ts:17`) — это схема строки запроса. Её читают:
  - `mcpInputSchema` (`src/api/mcp.ts:27-29`);
  - генератор OpenAPI.
- Денежным методам такая схема нужна самим: в ней `?label=` (`labelQuery`).
- `query: true` из §4.3 и `operationOf(req).query` в `traceWrites` с ней столкнутся. Фильтр MCP
  `op.method === 'get' || op.query` (аудит 02 №7) тогда пропустит любую POST-операцию со строкой запроса, например
  `POST /splits/import?label=`.
- **Исправить:** другое имя — `readOnly: true` или `kind: 'query'` — с union-типом «только `post` + `read` /
  `read_money`».

### В2. «Порядок отказов тот же, что у заменяемого ответа» (§4.4) — неверно
- Все три закрытых ответа имеют `scope: 'org'`:
  - `GET /tracks/:isrc/money` (`operations.ts:607`);
  - `GET /overview` (`:1106`);
  - `GET /sublabels/:id/report` (`:948`).

  `can()` отказывает им первым шагом: `403 forbidden` при любой метке (`src/auth/abilities.ts:103, 156-160`).
- У новой общей операции `scope: 'label'` отказ другой:
  - без `?label=` — `400 label_required`;
  - с чужой меткой — `403 label_forbidden`;
  - и только со своей меткой маршрут ответит `403 forbidden`.
- **Исправить:**
  - в замороженной таблице видов записать реальные коды по каждому случаю (без метки, чужая метка, своя метка);
  - `POST /money/sublabel/query` — отдельная операция со `scope: 'org'`, без `?label=`: тогда у неё сохранится точный
    ответ `x`;
  - в §4.4 убрать фразу про одинаковый порядок отказов.

### В3. `MasterRow` не несёт B / C / ours по группе
- Тесты §6.1 «isrcs, grain `isrc` = `/tracks/summary`» и «release grain `isrc` / `month` = `tracks[]` / `months[]`»
  требуют на каждую строку `{ net, B, C, ours, cByReason }` (`sumUnits`, `aggregates.ts:234, 483, 489`).
- У `MasterRow` есть только `amount` и необязательный `net` (§3.3). Что такое `amount` для зерна без `status`, не
  сказано.
- **Исправить:** при зерне без `status` строка несёт `sums: MoneySums`. Иначе тесты переписать на зерно
  `isrc,status,reason` плюс отдельный `net`.

### В4. `byArtist` (D-237) и метка в срезе `track`
- В `byArtist` есть ряды `net` и `ours` по месяцам (`aggregates.ts:602-603`).
  - `net` по плану отдаётся только для зёрен без `recipient` / `status`, а значит одним зерном
    `recipient,status,reason,month` его не получить.
  - Не определено, кто получатель у доли лейбла в C (`no_split`, `label_unmapped`, …). `Status = 'B' | 'C' | 'ours'`
    вместе с `Recipient 'ours'` дублирует смысл.
- `trackMoney` считает без книги:
  - `aggregates.ts:316-318`;
  - маршрут `src/api/routes/aggregates.ts:59`;
  - фронт `packages/frontend/src/api/catalog.ts:18`.

  Новый срез `track` под `?label=` из `useLabel()` (§5) покажет на P6 только книгу. Это меняет числа на экране.
- **Исправить:**
  - получатель доли лейбла в C = `ours` со `status: 'C'` и `reason`;
  - тест вести двумя зёрнами;
  - для `track` записать, что книга не применяется или что P6 её не передаёт.

### В5. «Посимвольно» не держится из-за нулевых строк

### В6. Форма отчёта саблейбла (§3.4) расходится с кодом и экраном
