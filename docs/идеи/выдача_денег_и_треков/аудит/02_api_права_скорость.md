## 1. Журнал и `X-Operator` решают по методу — блокер

**Факт.** `operatorTrace` → `traceWrites` (`src/api/audit.ts:331-338`) проверяет `WRITES.has(req.method)`
(`audit.ts:11`: POST, PATCH, PUT, DELETE) и без `X-Operator` отвечает `400 operator_required`; после 2xx пишет строку
в журнал. Операцию он не спрашивает. `needsOperator` (`src/api/operations.ts:1871`) = `method !== 'get' && access !==
'public'` — отсюда заголовок в OpenAPI и проверка «одна строка журнала на запись» в `tests/api-contract.test.ts:172,
187-202`. Единственное исключение сегодня — `preview` через `RESPONSE_SUMMARY_ROUTES` (строка не пишется, но
`X-Operator` всё равно обязателен).

**Правка плана (§4.3).** Явно перечислить три места:
- `operations.ts`: `needsOperator = o.method !== 'get' && o.access !== 'public' && !o.query`;
- `audit.ts` `traceWrites`: перед проверкой заголовка `if (operationOf(req.method, req.path)?.query) return next();`
  (`operationOf` уже есть, путь в роутере организации относительный, как в `authorize`). Не пропускать по префиксу
  пути: только по признаку операции;
- `originGuard` (`src/auth/middleware.ts:200-215`) **не менять**: POST-чтение с cookie — та же поверхность CSRF
  (утечка через ответ невозможна из-за SOP, но нагрузочный CSRF возможен); это совпадает с планом. MCP-запрос по
  loopback без `Origin` / `Sec-Fetch-Site` проходит, как сейчас.

## 2. Книга в теле: `label` не видит цепочка прав — блокер

**Факт.** `requestLabelsOf` (`src/api/label-guard.ts:12-31`) читает только `?label=`, `body.labelId`,
`body.items[].labelId`. `authorize` (`src/api/authorize.ts:40-60`) передаёт их в `can()`; `labelGuard` проверяет, что
метка своя для организации (404 иначе). Поле `label` в теле (план §4.1) не увидит никто:
- со `scope: 'label'` в `ability` менеджер получит `400 label_required` на любом запросе;
- если, чтобы обойти это, поставить `scope: 'record'`, `can()` пропустит запрос (`abilities.ts:156-167`), и книга
  будет проверена только тем, что фасад не забыл; `labelGuard` не проверит принадлежность метки организации.

**Правка.** Книга — в адресе: `POST /money/master/query?label=<id>` (как у всех денежных чтений и у
`POST /splits/import?label=`), либо поле тела называется `labelId`. Предпочтительно `?label=`: тогда `labelQuery`
переиспользуется, а TanStack-ключ = путь + тело. `ability` у всех трёх денежных методов — `scope: 'label'`.

## 4. `recipient = sublabel` в строках мастера — блокер

С D-232 у расчёта нет «отщипа» саблейбла (CLAUDE.md: «no sublabel carve since D-232»); D-219: часть саблейбла — чтение
поверх расчёта (`facade/sublabel-report.ts`), `boundaries.test.ts` запрещает слоям, `calculation.ts`, `balance.ts`,
`scope.ts` читать условия саблейблов. Значит строка `recipient: { kind: 'sublabel' }` — не начисление, а доля от
`ours`. Если положить её в те же строки и `MoneySums`, `B + C + ours` перестанет равняться `net` или часть посчитается
дважды.

**Правка.** Срез `sublabel` у `POST /money/master/query` убрать; либо оставить отдельную форму ответа
(`SublabelRow { isrc, month, base, percent, part, status }`), которая строится тем же `sublabelReport`, без
`recipient` и без `MoneySums`. Тест равенства с `GET /sublabels/:id/report` остаётся. Р9 плана переписать: «часть по
условию» — поле этой формы, а не получатель.

## 5. `scope.id` не проверяется цепочкой: проверка в фасаде по виду — важно

`can()` видит только книгу. Что именно смотрим (`scope.id`), проверяет только фасад через `Viewer`
(`facade/viewer.ts`: `viewerScope` → `mayTouchIsrc`, `ownerVisible`, `artistVisible`). Маршрут обязан передать
`viewerOf(res)` (`src/api/viewer.ts`). Предлагаемые правила по видам (все — при `?label=` книги менеджера):

| scope | Правило | Образец сегодня |
|---|---|---|
| `label` | `scope.id` должен совпадать с `?label=`; лучше **убрать вид `label`**: «нет scope + `?label=`» = вся книга | — |
| `owner` (несколько лейблов) | `ownerBalance(id, period, label, viewer)`: видимость владельца под этой книгой, деньги только книги (D-169) | `GET /owners/:id/balance` (`L`) |
| `artist` | `artistVisible`, деньги книги | `GET /artists/:id/balance` (`L`) |
| `release` | UPC в файлах книги; иначе 404 | `facade.release(upc, label)` |
| `track` | `mayTouchIsrc`; иначе 404 (как чужая запись) | — |
| `isrcs` | чужие ISRC **молча отбрасываются**, как `trackSummary` (`facade/aggregates.ts:184-186`: `lc.visible.isrcs`); ни списка, ни счётчика отброшенных (иначе оракул существования) | `GET /tracks/summary?isrcs=` |
| `sublabel` | менеджеру 403 (п. 3) | D-219 |

`totals` — только по отфильтрованной выборке; итог по `isrcs` с чужими ISRC не должен совпадать с итогом «как
просили». `filter.recipients` с чужими id — только фильтр, утечки нет. Токен чтения и `support` — `labelIds: 'all'`
(`abilities.ts:195-204`), фильтра нет, как сегодня.

Отдельно: для `org_admin` без `?label=` срез идёт по всем книгам; с `?label=` — только книга. Это надо записать, иначе
«итог владельца» без книги и с книгой разойдутся с балансом (баланс читается по книге, D-169).

## 6. Справочники — фильтр видимости и выбор поля `access`/`ability` — важно

- `POST /tracks/query { isrcs }` → `Track` с `artists` (из сплитов и участий), `releases`, `label`. Сегодня
  `GET /tracks/:isrc/meta` и `GET /tracks/:isrc/labels` — `O`, но `GET /splits` — `R`, `GET /releases` — `L`. Без
  фильтра менеджер узнаёт ники и релизы чужих треков. **Правка:** `ability { read, tracks, record }`, в фасаде
  `mayTouchIsrc`; не видимый ISRC отсутствует в ответе (`Record` без ключа), либо (если владелец хочет мету чужих
  ISRC, как `O` сегодня) — только `{ isrc, meta }` без `artists` / `releases`.
- `POST /owners/query { ids }` → `OwnerRef` с именем (это персональные данные, D-090). `GET /owners` — `L`,
  `GET /owners/:id` — `R`. **Правка:** `ownerVisible`, невидимые id отсутствуют в ответе; поля `OwnerRef` —
  минимальные (id, имя для показа), без юридических имён и реквизитов.
- `POST /artists/query` — `artistVisible`; `POST /songs/query` — `ability { read, publishing, label }` с
  `?label=` (pubv2 живёт по книгам, `GET /publishing-v2/songwriters` — `scope: 'label'`).
- Ответ на смешанный набор «свои + чужие» — 200 с подмножеством, не 403: иначе 403 — оракул существования.
- `action: 'read'` (не `read_money`): тогда у менеджера `org` — `allow`, `record` — проверка фасада
  (`abilities.ts:102`); справочник не должен содержать денег (Р6) — тест схемы ответа на отсутствие money-полей.

## 7. MCP: POST не поддержан ни удалённо, ни локально — важно

- Удалённый `/api/mcp`: `MCP_OPERATIONS` = `op.method === 'get' && readsWithToken(op)` (`src/api/mcp.ts:18-20`);
  `mcpInputSchema` строится из пути и `op.query` (`:27-37`); вызов — `fetch` без метода и тела (`:58`). Нужно:
  фильтр `op.method === 'get' || op.query`; входная схема = свойства `op.body` (`z.toJSONSchema`) плюс `?label=`;
  вызов `method: 'POST'`, `content-type: application/json`, тело — аргументы без `label`; тест в
  `tests/read-token.test.ts` (список инструментов содержит `post-money-master-query`, вызов отвечает 200, запись
  POST — по-прежнему `isError`).
- Локальный пакет (`@erp/shared/mcp-connection`, `mcp-connection.ts:25-26`: `--operation get`) POST-операции не
  возьмёт; `--operation post` добавит в список ~80 записей (сервер их отклонит 403, но контекст Claude раздуется).
  **Правка:** либо помечать query-операции отдельным тегом (`query`) и фильтровать пакет по тегу, если он это умеет
  (проверить версию 1.17.0), либо закрыть D-180 О2 — оставить только удалённый `/api/mcp`.
- Токен чтения пагинируется по умолчанию (50, `src/api/paging.ts:16-17`) через `?limit`; в теле `limit` обязателен
  по плану, но для токена нужна верхняя граница (≤ 500, как D-177) — иначе один вызов инструмента вернёт мегабайты.
- `MCP_INSTRUCTIONS` («find ids with get-search first… a list takes about 10 seconds») и `explain: true` надо обновить
  для новых методов; старые GET держать до этапа 3 (план это говорит).
- Проверка «каждая не-чтение операция отклоняет токен» (`read-token.test.ts:80`) фильтрует по `ability.action` —
  query-операции с `read`/`read_money` её не нарушат. Хорошо.

## 8. Скорость — важно

Факты: `calculate()` по всем единицам 7–11 с (D-161); сужение (`scoped`, `SnapshotFilter` по `isrcs`, `upcs`,
`accounts`, месяцам, `labelIds`) даёт 2–4 с; **баланс владельца, обзор, сверка не сужаются намеренно** (D-161: выкуп
аванса нужен по всем доходам владельца); расчёт по охвату владельца (`ownerReach`, D-163/164) — отдельный путь.
`paging.ts` режет страницу **после** полного ответа фасада.

Следствия для плана:
- Каждая страница (`offset`) = новый полный расчёт той же выборки. `totals` «по всей выборке» и `sort` по сумме
  требуют всей выборки на каждом запросе, так что страница экономит только размер JSON, но не время.
- Хуки «листают сами» → N расчётов на экран. Для лейбла целиком это N × 3–10 с.
- Кеш денег запрещён (D-012, D-139 R2: «no server-side cache»; D-161: «no cache»).

**Правка плана:**
1. Сужение по виду среза — обязательная часть этапа 1, а не риск: `track`/`isrcs`/`release` → `isrcs`/`upcs`
   (как D-161/162, `publishingLines: false` для мастера); `label` → `labelIds`; `owner`/`artist` → `ownerReach`
   (`isrcs` охвата), с тестом «срез = полный расчёт, ограниченный выборкой» в духе `tests/scope.test.ts` и
   `FACADE_SCOPE=off`. Для `owner` это **новое** сужение, которого D-161 избегал ради выкупа: суммы начислений по
   охвату точны (D-161 «why it is exact»), но это не баланс — в плане явно сказать, что `master/query` по владельцу
   не даёт `recouped` / `payable` (Р8 это подразумевает).
2. Экран берёт **всю выборку зерна одним запросом** (`limit` до разумного потолка, например 5 000 строк) и листает
   на клиенте (Р1 это разрешает для показа); серверные страницы — для MCP и больших зёрен. Записать порог: если
   строк больше потолка — экран предлагает сузить период/зерно, а не листает расчётами.
3. `totals` и строки — из одного расчёта одного запроса (не отдельный вызов итогов).
4. Замер «лейбл целиком, зерно `isrc,month`» до этапа 2 с числами строк и байтов: у 0to8 тысячи ISRC × ~20 месяцев =
   десятки тысяч строк — проверить размер ответа (сжатие ответа сейчас не включено: стоит проверить `compression`
   в `server-app.ts`).
5. `/tracks/query` и прочие справочники — без расчёта (как `trackCatalog`, D-162); проверить это тестом «не читает
   snapshot».

## 9. R2 «один денежный запрос на экран» и e2e — важно

D-139 R2 и e2e `expectMoneyCalls(page, 1)` (`packages/frontend/e2e/helpers.ts:112-133`, `MONEY_PATH`) считают денежные
запросы. План: блоки «по месяцам», «по трекам», «реклама», «паблишинг» на одной странице, каждый со своим хуком и
листанием → 3–4+ денежных запроса на экран, плюс по запросу на страницу таблицы. R2 уже имеет исключения (D-162 P5,
P10 cuts). **Правка:** D-запись, переформулирующая R2 («один запрос на блок и вид данных; листание — без нового
расчёта» или «экран делает не больше K денежных запросов»), и расширение `MONEY_PATH` на `/money/*/query` (POST!
сейчас помощник, вероятно, смотрит путь без метода — проверить), иначе e2e перестанет видеть новые денежные запросы.

## 10. Размеры и лимиты — важно

- `express.json` — 1 МБ (`src/api/http.ts:67-71`); 5 000 ISRC ≈ 80 КБ — помещается. Проблема не в теле, а в чтении:
  `splits.index({ isrcs })`, `owners.listTracks({ isrcs })` и т. п. — `IN (...)` в PostgreSQL (≤ 65 535 параметров на
  запрос) и `isrc IN` в ClickHouse. **Правка:** `isrcs: z.array(isrc).min(1).max(5000)` (как
  `splitAssumeBody`, `api-schemas.ts:618`), `ids` справочников `.max(1000)`; `grain` — `z.enum` массивом без повторов;
  `limit` 1–5 000 для сессии, ≤ 500 для токена чтения.
- Старый `GET /tracks/summary?isrcs=` ограничен 500 из-за 16 КиБ заголовка (`facade/aggregates.ts:15,24-27`); POST
  это снимает — но ограничение по стоимости остаётся (п. 8).

## 11. Тест контракта, OpenAPI, таблица менеджера, покрытие — важно

- `operations.ts`: новые операции с `body`, `response`, `access: 'org'`, `ability`, `query: true`, `explain: true`
  (D-178); `operationOf` — конфликтов нет (`POST /owners/query` против `POST /owners/merge` — оба статические;
  `POST /tracks/query` — не пересекается с `POST /tracks/:isrc/label` по числу сегментов), но в Express роуты
  `/x/query` регистрировать до любых `POST /x/:id`.
- `tests/api-contract.test.ts`: в ветке вызова (`:187-202`) для `op.query` — проверка «число строк журнала не
  изменилось» (как для preview, `:199-200`) и ответ без `X-Operator` = 200; сценарий должен вызвать каждую новую
  операцию (D-119, `:866`).
- «Нет побочных эффектов» лучше обеспечить **конструктивно**: фасадные методы query выполняются в `db.snapshot()`
  (только чтение; запись внутри упадёт), а тест проверяет это (вызов метода из write-транзакции не требуется). Тест
  «ни одной строки в модулях» по всем таблицам — дорогой и хрупкий; оставить его одним проходом в `api-contract`.
- Статический тест: у каждой `query`-операции `method === 'post'` и `ability.action ∈ {read, read_money}`; у
  каждой не-query POST — по-прежнему `needsOperator`.
- `tests/helpers/manager-answers.ts`: строки новых операций + таблица по видам среза (п. 3); `abilities.test.ts`
  (счётчик операций организации) обновится.
- `packages/frontend/src/api/coverage.ts`: каждая новая операция — запись (на этапе 1 — `refusal: 'этап 1: экраны
  переводятся на этапе 2'`), иначе `coverage.test.ts` упадёт.
- OpenAPI: тело POST уже поддержано генератором (`openapi.ts`), `x-ability` выводится; заголовок `X-Operator`
  исчезнет сам при правке `needsOperator`.

## 12–15. Мелочи

12. **Тип.** `query?: true` допустим только при `method: 'post'` и `ability.action` чтения — выразить в union-типе
    `ApiOperation`, чтобы ошибка ловилась `typecheck`, а не тестом.
13. **Сортировка.** `sort.by` — `z.enum` допустимых полей по зерну; денежные поля сравнивать `Decimal`
    (`shared/money.ts`), не строкой; при равенстве — по ключам зерна (D-161 уже ловил неустойчивый порядок
    `breakdown`), иначе `offset` даёт повторы/пропуски. В ответе — `calculatedAt`: между страницами мог загрузиться
    файл, страницы разных расчётов не согласованы; клиент при смене `calculatedAt` сбрасывает листание.
14. **Нагрузка.** Любой менеджер или токен может запускать полные расчёты подряд (POST дешевле сформировать, чем
    GET-ссылку). Кеш запрещён, но семафор на организацию (например, ≤ 2 одновременных `calculate()`, остальные ждут)
    кешем не является; таймаут `fetch` в `mcp.ts` (сейчас нет).
15. **`preview`.** POST, который ничего не пишет, уже есть (D-172 `preview`, `RESPONSE_SUMMARY_ROUTES`), но он
    требует `X-Operator` и проходит `operatorTrace`. В D-записи явно развести: `preview` — запись в режиме проверки
    (оператор нужен), `query` — чтение (оператора нет).
