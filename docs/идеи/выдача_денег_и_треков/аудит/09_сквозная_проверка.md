## 1. Блокеры

### Б1. M4: e2e-счётчик не увидит `POST /money/master/query`, и M5 упадёт

**Код.** Запрос засчитывается, только если выполнены оба условия: метод — фильтр SPEC, путь — `MONEY_PATH`
(`e2e/helpers.ts:122`):

```ts
if (r.method() === 'GET' && MONEY_PATH.test(new URL(r.url()).pathname)) calls.push(...)
```

**Что не так в SPEC M4.**

- SPEC меняет только фильтр метода, а в `MONEY_PATH` (`:112-113`, якоря `^…$`) пути `money/master/query` нет. POST
  не засчитается ни разу.
- M5 ждёт `expectMoneyCalls(page, 3)`, а насчитает 1. M5 красный.
- Переменной `path` в этом месте кода нет.
- План §4.3 говорит то же, что и предлагаемая замена: «`MONEY_PATH` видит `POST /money/*`». Значит, расходится именно
  SPEC.

**Заменить в SPEC M4 третий пункт на:**

> - `e2e/helpers.ts`:
>   - в `MONEY_PATH` (`:112-113`) добавить альтернативу `money\/master\/query`;
>   - фильтр в `openAs` (`:122`):
>     `const p = new URL(r.url()).pathname; if ((r.method() === 'GET' || (r.method() === 'POST' && p.startsWith('/api/v1/money/'))) && MONEY_PATH.test(p)) calls.push(p);`
>
>   `GET /releases/:upc` остаётся в `MONEY_PATH`: он по-прежнему считает. Проверка шага: временный прогон
>   `11-release` с `expectMoneyCalls(page, 1)` зелёный и после M4 (экран ещё не переведён).

### Б2. `org-scope.test.ts` не пропустит POST-чтение, а правку SPEC не разрешает

**Код.** Тест обходит **все** операции организации (`tests/org-scope.test.ts:559`).

   `ops…filter(!CASES && !ID_LESS)`.
2. Для любой не-GET операции тест требует, чтобы запрос с id организации B был отказом:

   ```ts
   if (o.method !== 'get') expect(rb.status, `${key}: a write with B's ids succeeded`).toBeGreaterThanOrEqual(400);
   ```

**Что произойдёт.**

- `POST /tracks/query` с ISRC организации B ответит 200: ISRC просто нет в ответе (SPEC T3, план §4.2).

- Правка строки `:576` — изменение защитного теста. Её нет среди исключений §1.2.

Итог: T3 и M2 не проходят DoD, не нарушив правило §1.2. Ревьюер обязан отклонить шаг.

**Добавить в SPEC §1.2 к списку исключений:**

> становится `o.method !== 'get' && !o.readOnly` (POST-чтение проверяется как чтение: тот же ответ, что на неизвестный
> id, и без утечек), а `CASES` дополняется.

**Добавить в «Обвязку» T3 и M2:**

### Б3. M7: ISRC релиза из пар всех файлов расширяет ответ менеджеру

**SPEC M7.** «ISRC берутся из `sources.pairAttributes({ upcs })` ∪ `owners.tracks`».

**Код.**

- `pairAttributes` читает пары **всех** загруженных файлов. Фильтра по лейблу у неё нет
  (`modules/sources/service.ts:413-419`).
- Сегодня набор ISRC под `?label=` — это единицы файлов книги (`aggregates.ts:449, 452`) ∪ треки, видимые лейблу

- Менеджер лейбла A на `GET /releases/:upc?label=A` получит строки треков (ISRC, название отчёта, ники) из файлов

Это изменение прав. GOAL велит в таком случае остановиться.

**Заменить в SPEC M7 первый пункт на:**

> - `release()` больше не считает. ISRC — пары `(isrc, upc)` файлов книги (под `?label=` — только файлы `lc.book`; без
>   метки — все файлы) ∪ `mine` (как сейчас, `aggregates.ts:451`).
>   - Для этого `sources.pairAttributes` получает необязательный фильтр `labelIds`, как `netByUpc` (`SnapshotFilter`,
>     `service.ts:35, 394`).
>   - 404 — как раньше: нет ни `mine`, ни пар книги, ни строки реестра.
>   - Ники — через `owners.artistIndex()` вместо `calc.artistIndex`.
