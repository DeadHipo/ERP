## Блокеры

### Б1. `POST`-чтение во фронте и в MCP — это запись: план меняет только сервер
- Фронт: `call()` считает запросом-записью всё, что не `GET`: требует оператора и без него бросает
  `operator_required` (`packages/frontend/src/api/client.ts:69-73`), читает `X-Audit` (`:91`). С выключенным входом
  и пустым оператором ни один экран на новых хуках не покажет денег. `ActionButton`/`useAction` тут ни при чём, но
  `useQuery` с `POST` пройдёт через тот же `call()`.
- MCP: инструменты строятся только из `GET` (`packages/backend/src/api/mcp.ts:18-20`: `op.method === 'get'`), вход
  инструмента — `op.query` и параметры пути (`mcpInputSchema`, там же `:26-36`), тела нет. Пункт 4.3 плана «MCP с
  токеном чтения такие запросы проходит» сейчас неверен: новые методы в MCP не появятся, а этап 3 удалит
  `get-tracks-summary` (и с ним всё, что Claude читает по трекам) без замены.
- Исправление плана: этап 1 добавляет (а) в `client.ts` вариант `call('POST', …, { read: true })` без оператора и без
  `X-Audit`, с тестом в `tests/` фронта; (б) в `mcp.ts` — `op.method === 'get' || op.query === true`, вход инструмента
  из схемы тела, тест в `read-token.test.ts`/`api-contract.test.ts`. Готовность этапа 1: «инструменты MCP
  `post-money-master-query` и др. видны и отвечают с токеном чтения».

### Б2. R2 «один денежный запрос на экран» и его e2e-проверка ломаются первым же блоком
- Правило R2 (`packages/frontend/CLAUDE.md:18`) и помощник `expectMoneyCalls(page, 1)` — 27 вызовов в 10 спеках
  (10, 11, 12, 14, 20, 21, 24, 33, 34, 35). Счётчик видит только `GET` из списка `MONEY_PATH`
  (`packages/frontend/e2e/helpers.ts:112-123`).
- План собирает экран из блоков с собственными хуками: P8 = master(isrc) + master(month) + ads + `useTracks` — это
  3–4 денежных запроса, и все `POST`, т. е. счётчик покажет 0 и тест упадёт с «ожидали 1».
- Также `RecalcIndicator` и инвалидация смотрят только ключи из `MONEY_KEYS` (`src/api/queries/core.ts:10-37`): новые
  ключи хуков, не внесённые туда, не покажут «идёт пересчёт» и не обновятся после действия.
- Исправление: (а) решить и записать D-запись «R2′»: либо один запрос с несколькими зёрнами (`grains: [[isrc],[month]]`
  в одном `POST`, одна `calculate()`), либо «N запросов, одна `calculate()` на сервере в пределах запроса» — и тогда
  `expectMoneyCalls` считает разрешённое число по экрану; (б) этап 2, шаг 0: `MONEY_PATH` учитывает `POST /money/*`,
  ключи `['money', …]` — в `MONEY_KEYS`. Без этого «каждый шаг — e2e» невыполнимо.

### Б3. Таблицы «по трекам» P10 / P12 противоречат Р8 и не знают срез / `asOf`
- Р8: баланс — один серверный ответ. Таблица `balance-track-<artistId>-<isrc>` — часть этого ответа (строки треков
  внутри артиста, `src/pages/owners/BalanceTab.tsx:250-251`). Баланс читается и на срез / `asOf`
  (`BalanceTab.tsx:394`, D-173, D-208), а запрос `POST /money/master/query` (план 4.1) не имеет ни `asOf`, ни `cut`,
  ни охвата владельца (`owner-scope.ts`, D-163).
- Перевод этой таблицы на мастер-запрос даст на одном экране две независимые выборки: итог баланса и сумму строк по
  трекам, которые разойдутся под срезом, под `asOf` и при сменённом охвате.
- Исправление: убрать «таблицы по трекам P10 / P12» из этапа 2 либо добавить в запрос `asOf`/`cut` и тест «Σ строк
  по трекам = `earned` баланса» на срезе, на `asOf` и под лейблом. Рекомендация: убрать, таблица остаётся в балансе
  (её единственное изменение — `TrackName` по `Track`).

## Важно

### В1. Серверное листание против AG Grid на клиенте: P5 нельзя перевести, не решив режим
- `DataGrid` листает, сортирует и фильтрует на клиенте (`src/components/grid/DataGrid.tsx:9-11`, `:110-123`;
  `pagination={false}` — для списков, которые листает сервер). P5 сейчас: две фазы, деньги видимой страницы, денежные
  колонки без сортировки, «Посчитать все» = один полный ответ, сортируемый (`src/pages/catalog/TracksPage.tsx:50-82`).
- `MasterRow` не несёт названия, артистов, `hasSplit`, лейбла каталога (Р5), а быстрый поиск `q` и фильтр колонки
  «Название» ищут по названию, версии и ISRC (D-242), фильтр `hasSplit` — клиентский (`TracksPage.tsx:112`). Значит,
  серверная сортировка по сумме и клиентский фильтр по названию в одном гриде несовместимы.
- Исправление: в плане явно два режима блока «по трекам»: (1) «полный набор» — `limit` до потолка (26 тыс. ISRC),
  сортировка и фильтр AG Grid, `useTracks` по всему набору; (2) «страница сервера» — `pagination={false}`, свой пейджер,
  сортировка только по колонкам запроса, фильтры только полями `filter` запроса; текстовый поиск — отдельный параметр
  `q` справочника. Записать, какой экран в каком режиме. Указать потолок `limit`, как у `/signals?limit=5000`.

### В3. `useTracks(isrcs)` с «кешем по ключу» — нет механизма в TanStack

  строк — 26 тыс. записей кеша и наблюдателей.
- Исправление: в плане описать пакетный загрузчик (сбор ISRC за тик → один `POST /tracks/query` пачками по N →
  `queryClient.setQueryData(['tracks','ref',isrc])` для каждого) и тест на него; `staleTime` справочника; инвалидация
  после `PATCH /tracks/:isrc/meta` и после часового загрузчика D-241 (меняет мету вне фронта).
