Точка отсчёта (принятое решение, «уровень 0»): узлы-слои в коде, порядок `MASTER_LAYERS` (после 1б: четыре слоя

Два факта, на которые опирается всё ниже:

- **Открытые случаи гибкости живут почти только в хвосте, в доле лейбла.** Q11 (порядок «carve из доли лейбла /
  половина саблейбла», 63.30 в C), C23 (NoGhost «25 % of net» против половины доли лейбла, 14 094.78 + 9 930.53 в C),
  M58/C03 (исключение артиста или ISRC из правила саблейбла, «open, not expressible»), M3a (лейбл держит фиксированную
  долю), M48 (налог на остаток лейбла). На стороне артистов открыт только Q1 (база лицензиара «за вычетом других»).
- **Стоимость нового вида участия сегодня 12–14 мест** (README §8), из них компилятор напоминает только о части:
  `FundedFrom` в `splits/service.ts`, `fundedFrom` zod в `@erp/shared`, CHECK в `0008`, `AllocationKind` в
  `layers/types.ts`, `allocKind` в `i18n/ru/catalog.ts`, фильтр `!p.percent.isZero()` и ветка в `carve()` —
  это пять независимых списков одного enum.

Подходы решают **разные** задачи: подход 1 удешевляет новый вид узла, подход 2 даёт произвольную топологию,
подход 3 делает данными ровно то, что владелец может решить по-разному. Это важно для вердикта.

## Подход 1. Реестр видов узлов (plugin registry)

### Суть в 10 строках

1. Каждый вид участия — одна папка `kinds/<kind>`: объявление (без кода денег) и реализация (функция узла).
2. Объявление живёт в `@erp/shared` (его читают фронт и бэкенд): имя, корзина-источник, допустимые базы, zod
   параметров, ключ подписи, причина «не подтверждено», флаги формы.
3. Реализация живёт в `facade/layers/kinds/<kind>.ts`: `run(state, ctx, parts)` и кросс-строчная валидация
   (`top_above_100`).
4. Один объект `KIND_DECLS` в shared и один `KIND_IMPLS` в бэкенде; второй типизирован
   `satisfies Record<FundedFrom, KindImpl>`, поэтому забытая реализация — ошибка компиляции.
5. `FundedFrom = keyof typeof KIND_DECLS`; `fundedFrom` zod, `FUNDED_ORDER`, `SOURCE_OF`, `AllocationKind`,
   подписи i18n (`Record<FundedFrom, string>`) выводятся из реестра, а не перечисляются.
6. Порядок — не число в базе, а позиция узла вида в `chain(...)` из `код/graph.ts`; `FUNDED_ORDER` выводится из
   цепочки, тест сверяет его с полем `order` объявления (фронту порядок нужен без кода узлов).
7. БД не умеет импортировать TypeScript: CHECK `funded_from` остаётся в миграции, тест под стеком читает
   `pg_get_constraintdef` и сравнивает множество с реестром.
8. `exactness.test.ts` перебирает `KIND_DECLS` и строит случайные участия по zod-схеме: новый вид попадает под
   проверку точности без новой строки теста.
9. Слои, `allocateUnit`, `edgesOf`, категоризация, снимок — без изменения формы; меняется только откуда берутся
   списки.
10. Это рефакторинг «одна правда для enum», а не новая модель денег: топология по-прежнему одна на источник.

### Интерфейс модуля вида

```ts
// packages/shared/src/kinds/types.ts (без decimal.js и без кода денег: это читает фронт)
import { z } from 'zod';

export type Bucket = 'net' | 'scaledNet' | 'row' | 'pool' | 'labelShare';
export type KindBase = 'net' | 'bucket';

export interface KindDecl<P extends z.ZodRawShape = z.ZodRawShape> {
  /** Совпадает со значением funded_from в БД. */
  kind: string;
  /** Корзина, из которой берутся деньги: SOURCE_OF[kind] для edgesOf. */
  bucket: Bucket;
  /** Какие base допустимы; первое — значение по умолчанию в форме. */
  bases: readonly [KindBase, ...KindBase[]];
  /** Нужен ли источник-артист (artist_share). */
  fromArtist: 'required' | 'forbidden';
  /** Дополнительные параметры сверх общих (isrc, artistId, percent, период, документ). */
  params: P;
  /** Позиция в цепочке (для фронта и FUNDED_ORDER); тест сверяет с MASTER_GRAPH. */
  order: number;
  /** Слой аллокации и причина C при неутверждённом документе. */
  layer: 'top' | 'carve';
  unconfirmed: 'rule_unconfirmed';
}
export const decl = <const D extends KindDecl>(d: D) => d;
```

```ts
// packages/shared/src/kinds/index.ts
import { decl } from './types';
export const KIND_DECLS = {
  top:          decl({ kind: 'top',          bucket: 'net',        bases: ['net'],           fromArtist: 'forbidden', params: {}, order: 10, layer: 'top',   unconfirmed: 'rule_unconfirmed' }),
  artist_pool:  decl({ kind: 'artist_pool',  bucket: 'pool',       bases: ['net'],           fromArtist: 'forbidden', params: {}, order: 30, layer: 'carve', unconfirmed: 'rule_unconfirmed' }),
  artist_share: decl({ kind: 'artist_share', bucket: 'row',        bases: ['bucket'],        fromArtist: 'required',  params: {}, order: 40, layer: 'carve', unconfirmed: 'rule_unconfirmed' }),
  label_share:  decl({ kind: 'label_share',  bucket: 'labelShare', bases: ['net', 'bucket'], fromArtist: 'forbidden', params: {}, order: 50, layer: 'carve', unconfirmed: 'rule_unconfirmed' }),
} as const;

export type FundedFrom = keyof typeof KIND_DECLS;                     // 'top' | 'artist_pool' | ...
export const FUNDED = Object.keys(KIND_DECLS) as [FundedFrom, ...FundedFrom[]];
export const fundedFrom = z.enum(FUNDED);                              // вместо руками перечисленного enum
export const FUNDED_ORDER = [...FUNDED].sort((a, b) => KIND_DECLS[a].order - KIND_DECLS[b].order);
export const SOURCE_OF = Object.fromEntries(FUNDED.map((k) => [k, KIND_DECLS[k].bucket])) as
  { [K in FundedFrom]: (typeof KIND_DECLS)[K]['bucket'] };

/** Тело POST /participations: общая часть + параметры вида, размеченное объединение по fundedFrom. */
export const createParticipationBody = z.discriminatedUnion('fundedFrom', FUNDED.map((k) =>
  common.extend({ fundedFrom: z.literal(k), base: z.enum(KIND_DECLS[k].bases), ...KIND_DECLS[k].params,
    fromArtistId: KIND_DECLS[k].fromArtist === 'required' ? z.string().min(1) : z.null().optional() }),
) as never);
```

```ts
// packages/backend/src/facade/layers/kinds/types.ts
export interface KindImpl<K extends FundedFrom> {
  /** Узел в стиле код/graph.ts: входы и выходы — интерфейсы; chain проверит порядок компилятором. */
  node: Node<any, any>;
  /** Активно ли правило на юните (вместо общего !percent.isZero(): у фиксированной суммы процент 0). */
  active(p: ParticipationOf<K>): boolean;
  /** Проверки, которым нужны соседние строки (top_above_100); вызывается из splits/service в транзакции. */
  validate?(p: ParticipationOf<K>, existing: ParticipationView[]): void;
}
// packages/backend/src/facade/layers/kinds/index.ts
export const KIND_IMPLS = { top, artist_pool, artist_share, label_share } satisfies { [K in FundedFrom]: KindImpl<K> };
```

`ParticipationOf<K>` — это `RuleOf<K>` из `код/rules.ts`, только выведенный из реестра: `rulesOf(ctx, unit, kind)`
сужает тип на границе модуля, и узел вида получает уже правильные поля.

### Сочетание с `chain` из `код/graph.ts`

Порядок не выносится в число в БД (это был бы уровень 1 без периода и документа, худший из вариантов). Он остаётся
в одной цепочке, которую проверяет компилятор:

```ts
export const MASTER_GRAPH = chain(
  labelOfRecord, perimeter,
  KIND_IMPLS.top.node,            // off-the-top
  split,
  KIND_IMPLS.artist_pool.node, KIND_IMPLS.artist_share.node, rowsToArtists,
  KIND_IMPLS.label_share.node,
  sublabel, categorise,
);
```

Тест `kinds-registry.test.ts` (без стека):

```ts
const kindNodes = MASTER_GRAPH.map((n) => n.name).filter((n) => FUNDED.some((k) => KIND_IMPLS[k].node.name === n));
it('каждый вид ровно один раз и в порядке order', () => {
  expect(kindNodes).toEqual(FUNDED_ORDER.map((k) => KIND_IMPLS[k].node.name));

```

### Миграция CHECK и реестр

Два варианта, оба честные:

- **(а) CHECK остаётся, тест сверяет.** Новый вид = новая миграция `DROP CONSTRAINT … ADD CONSTRAINT`. Тест под
  `REQUIRE_STACK`:

  ```ts
  const [{ def }] = await sql`select pg_get_constraintdef(oid) def from pg_constraint
                               where conrelid = 'splits.participations'::regclass and conname = 'participations_funded_from_check'`;
  expect(new Set(def.match(/'([a-z_]+)'/g)!.map((s) => s.slice(1, -1)))).toEqual(new Set(FUNDED));
  ```

  Комбинационный CHECK `participations_combination` (база и источник по виду) тоже дублирует реестр. Его тест
  строит из `KIND_DECLS` все запрещённые сочетания (`bases` и `fromArtist`) и ожидает отказ вставки.
- **(б) Справочник видов.** `splits.participation_kinds(kind text PRIMARY KEY, bucket text, bases text[], from_artist text)`,
  `participations.funded_from REFERENCES splits.participation_kinds`, триггер проверки сочетаний читает справочник.
  Тест: строки справочника = `KIND_DECLS`. Плюс: новый вид = `INSERT`, без смены ограничений. Минус: триггер вместо
  декларативного CHECK, а это код в БД, его труднее читать.

Рекомендую (а): ограничения видны в одной миграции, тест ловит рассинхрон в CI.

### Новый вид «фиксированная сумма с доли лейбла» (`label_fixed`)

Сначала ловушка, которую реестр не снимает: **сумма в месяц — не слой** (README §6). Трек-месяц состоит из
нескольких юнитов (два UPC, поздние месяцы продаж, две строки лейбла); узел, который «берёт 50 USD», возьмёт их по
разу на юнит. Значит у вида два этапа: до юнитов цель месяца раскладывается на юниты, в юните узел берёт свою часть
из доли лейбла.

```ts
// shared/src/kinds/label_fixed.ts
export const label_fixed = decl({
  kind: 'label_fixed', bucket: 'labelShare', bases: ['bucket'], fromArtist: 'forbidden',
  params: { amountUsd: money },            // в месяц на трек; percent хранится 0
  order: 55, layer: 'carve', unconfirmed: 'rule_unconfirmed',
});
```

```ts
// backend/src/facade/layers/kinds/label_fixed.ts
/** До юнитов (в calculate, один snapshot): цель месяца → цели юнитов пропорционально max(net, 0). */
export function fixedTargets(units: MasterUnit[], ctx: LayerContext): Map<string, Decimal> {
  const out = new Map<string, Decimal>();
  for (const [key, group] of groupBy(units, (u) => `${u.isrc}|${u.reportingMonth}`)) {
    for (const p of rulesOf(ctx, group[0], 'label_fixed')) {
      const w = group.map((u) => ({ key: unitKey(u), weight: Decimal.max(u.net, 0) }));
      if (sumOf(w.map((x) => x.weight)).isZero()) continue;            // месяц из одних возвратов: недостача целиком
      distribute(new Decimal(p.amountUsd), w).forEach((a, i) => out.set(`${w[i]!.key}#${p.id}`, a));
    }
  }
  return out;
}

export const labelFixed: KindImpl<'label_fixed'> = {
  active: (p) => !new Decimal(p.amountUsd).isZero(),
  node: node<Pick<Seed, 'unit'> & Pick<LabelShared, 'labelShareAfterCarve'>, { labelShareAfterFixed: Remainder }>({
    name: 'carve:label_fixed',
    run({ unit, labelShareAfterCarve }, ctx) {
      const parts = rulesOf(ctx, unit, 'label_fixed');
      const targets = parts.map((p) => ctx.fixedTargetOf(unitKey(unit), p.id) ?? ZERO);   // уже 12 знаков (distribute)
      const { amounts, notes } = fund('labelShare', ctx, parts, targets, labelShareAfterCarve);
      const edges = parts.map((p, i) => transfer('labelShare', `artist:${canonical(ctx, p.artistId)}`, amounts[i]!, {
        kind: 'label_fixed', ruleId: p.id, documentId: p.documentId, base: null, percent: null, target: targets[i]! }));
      return { out: { labelShareAfterFixed: minus(labelShareAfterCarve, edges) }, edges, notes };
    },
  }),
};
```

Решения, которые нужны D-записью до кода: вес раскладки (`max(net, 0)` или доля лейбла после carve — второе требует
двух проходов), что делать с месяцем возвратов, ставится ли фиксированная сумма до или после саблейбла (это снова
Q11-вопрос, только про новый узел).

### Что остаётся вручную (честный чеклист нового вида)

| № | Место | Напомнит ли компилятор/тест |
|---|---|---|
| 1 | `shared/src/kinds/<kind>.ts` + строка в `KIND_DECLS` | — |
| 2 | `layers/kinds/<kind>.ts` + строка в `KIND_IMPLS` | да: `satisfies Record<FundedFrom, …>` |
| 3 | место узла в `MASTER_GRAPH` | да: `kinds-registry.test.ts` и `chain` |
| 4 | миграция: CHECK `funded_from`, `participations_combination`, новые колонки | да: тест `pg_get_constraintdef` |
| 5 | i18n `allocKind` и подсказка формы | да: `Record<FundedFrom, string>` |
| 6 | новая колонка (`amount_usd`): Drizzle `schema.ts`, `repository.ts`, `ParticipationView`, `api-responses` | частично (типы ответа) |
| 7 | поле формы участия, если параметр не процент | нет, если форма не строится из zod |
| 8 | межъюнитный этап (только для «в месяц») | нет |
| 9 | тест слоя + золотой кейс в `12_golden_cases.md` и `golden.test.ts` | нет (точность — да, генератор по реестру) |
| 10 | D-запись, индекс 03, `docs/agents/10` §3 | нет |

Итого: вид «процент от корзины» — **6 мест** (1–5, 9–10 считаем одним шагом документации), из них о трёх напоминает
компилятор; вид с новым параметром — **9–10 мест**. Против 12–14 сегодня. «Один файл + миграция + золотой кейс»
недостижимо: shared и бэкенд физически разные пакеты, БД не читает TypeScript, а форма и документация не выводятся.

### Q11, C23, M58

Реестр их **не выражает**: он не про топологию.
- Q11: порядок — позиция в `chain`; другой порядок для NoGhost = вторая цепочка + привязка (это уже Р20) или код
  на все месяцы.
- C23: либо `bases: ['labelShare', 'net']` у объявления `sublabel`, если саблейбл тоже станет видом в реестре
  (правило лейбла, не участие: объявление с `source: 'label_rule'`), либо Р22. Реестр делает это дешевле, но не решает.
- M58: нужны данные-исключения, реестр их не даёт.

### Остальные ответы

- **Что хранится:** ничего нового (вариант а) или справочник видов из 4–5 строк (вариант б).
- **Откуда данные:** как сейчас: один `db.snapshot` в `calculate()`, `ctx.participationsAt`; для `label_fixed`
  дополнительно `ctx.fixedTargetOf`, посчитанный до юнитов из того же snapshot.
- **Кто выбирает правило по дате:** индекс модуля `splits` (`participationsAt(isrc, reportDate)`), без изменений.
- **Точность:** узлы видов обязаны пользоваться `pct`/`fund`/`distributeCapped`/`minus`; типы `Quantised`/`Remainder`
  из `код/types.ts` не дают собрать ребро из неквантованной суммы; `exactness.test.ts` генерирует участия всех
  видов из реестра.
- **Риск для золотых:** низкий; это шаг 1б плюс вывод enum. Опасное место — фильтр `!p.percent.isZero()`, который
  переезжает в `active()`: у четырёх существующих видов он должен остаться тем же.
- **Трудоёмкость:** 2.5–3 дня поверх шага 1б (объявления в shared 0.5, вывод zod/i18n/`FUNDED_ORDER`/`SOURCE_OF` 0.5,
  `KIND_IMPLS` и перенос `carve` 0.5, тесты реестра и CHECK 0.5, генератор exactness по реестру 0.5, документы 0.25).
- **Главные риски:** discriminatedUnion в zod меняет форму ошибок 400 (контракт-тест); дженерики `KindImpl<K>`
  быстро становятся нечитаемыми; соблазн положить в реестр «порядок числом» и потом вынести его в БД без периода.
- **Джуниору за 5 минут:** «Вид участия — это папка. В shared описано, что это такое (откуда берёт, какие базы,
  какие поля); в бэкенде — как считает. Списки видов нигде руками не пишутся: всё выводится из `KIND_DECLS`.
  Порядок — место в `MASTER_GRAPH`. Забудешь реализацию или подпись — не соберётся; забудешь миграцию — упадёт
  тест реестра. Цифры правь только через `exact.ts`».

## Подход 2. Граф как данные целиком (уровень 2), честная переоценка

### Суть в 10 строках

1. Схема — запись `flows.schemes(id, name, version)`; узлы `flows.nodes(id, scheme_id, kind, params jsonb, x, y)`;
   связи `flows.links(id, scheme_id, from_node, from_port, to_node, to_port, role)`.
2. Привязка `flows.bindings(scheme_id, label_id | isrc, valid_from, valid_to, document_id)`.
3. Виды узлов (`take_percent`, `split_rows`, `pool`, `remainder`, `sink`) — код; всё остальное — данные.
4. Движок: по схеме топологическая сортировка → скомпилированный план (кэш на версию) → на юните каждый узел
   получает Σ входящих связей, считает выходы по портам, один порт помечен `remainder`.
5. Редактор React Flow рисует и сохраняет схему; сохранение проверяет ацикличность, типы портов, «один остаток на
   узел», «все деньги дошли до стока».
6. Параметры правил: либо в `params` узлов (второе место хранения договоров), либо узел ссылается на справочник
   (`params: { source: 'participations', fundedFrom: 'label_share' }`).
7. Аудит: снимок выплаты хранит `scheme_id@version`, по нему воспроизводится расчёт.
8. Q11, C23, M58 выражаются схемами и привязками без кода.
9. Золотые кейсы становятся «золотыми схемами»: стандартная схема в виде данных должна дать те же 126 рёбер.
10. Это «редактор в духе Unity», отклонённый консилиумом. Ниже — что именно ломается и что нет.

### Что ломается (по пунктам)

| Свойство | Вердикт | Почему |
|---|---|---|
| **Строки сплита** | ломается | число портов `row:*` зависит от сплита на дату (13 610 сплитов). Хранимый граф либо по ISRC (13 тыс. схем, дубль справочника сплитов), либо узел `split_rows` с динамическими портами, и тогда связи `rows → pool` — не провода, а «пучок», семантику которого знает только код узла. Граф в данных перестаёт быть графом денег |
| **База ≠ вход** | ломается тихо | MC 5 % **от net** из пула; A&R 15 % **от доли лейбла**, а `base: net` у участия label_share. Нужен второй тип связи (`role: base`). Каждый узел теперь проверяется на две оси: откуда берёт и от чего считает. Ловушка «4.5 вместо 5» из §5 переезжает из кода (где её держит тест слоя) в данные, где её держит человек с мышкой |
| **12 знаков, остаток вычитанием** | держится | движок может требовать ровно один порт `remainder` на узел и считать его `in − Σ`, квантование — внутри видов узлов. Это не аргумент против |
| **«Один остаток на узел»** | держится | проверка при сохранении, тривиальна |
| **Недостача, масштабирование, `distributeCapped`** | держится внутри узла `pool` | но порядок «сначала цели, потом масштаб, потом draw» — код узла; в данных не видно |
| **Валидация схемы** | дорого | ацикличность, типы портов, полнота стоков, «база доступна выше по графу», совместимость `params` с видом, «узел саблейбла не перед label_share без документа» — 6–8 правил, каждое со своим тестом и сообщением на русском |
| **Тестирование произвольных графов** | не решается | свойства (Σ стоков = net, знак, баланс узлов) проверяются генератором случайных DAG. Но ни один тест не скажет, что схема **соответствует договору**. Золотые кейсы проверяют только схемы, которые есть в репозитории; схема, которую нарисовал оператор, не проверена ничем, кроме сохранения |
| **Миграции схем** | дорого | `params jsonb` по видам с версиями; смена формы вида = миграция jsonb во всех схемах всех версий, включая те, на которые ссылаются снимки выплат (их менять нельзя: значит, движок держит все версии всех видов) |
| **Золотые кейсы** | переписываются | `golden.test.ts` вызывает `allocateUnit` со слоями; движок заменяет слои → тесты проходят через новый код. «Без единой правки» из DoD шага 1 невыполнимо |
| **Объяснение бухгалтеру** | хуже | сейчас ответ «почему 15.30» — «правило саблейбла 50 % от остатка доли лейбла, документ X». В модели 2 — «так провёл схему такой-то оператор в версии 3, привязка с июня». Два источника истины для одного договора: документ и картинка |
| **Где договор** | раздваивается | процент в участии, а проводка в схеме; договор «25 % от net» записан наполовину там, наполовину здесь |
| **Производительность** | не проблема | план компилируется раз на версию схемы; на юните — тот же fold |

Итого: отказ консилиума **подтверждаю**, но по другой причине, чем было записано. Точность и «один остаток»
делаются; ломаются **динамические строки сплита**, **второй тип связи для базы** и **проверка против договора**.
Граф, который можно хранить, — это шаблон с «пучками», а такой шаблон ровно уровень 1 с лишними таблицами.

### Урезанный вариант «граф фиксированный, параметры узлов в данных»

Ключевое наблюдение: **параметры узлов уже в данных.** Процент, база, источник, период, документ — это строки
сплитов, участий и правил лейбла. «Фиксированный граф + параметры в данных» — это и есть текущее состояние. Значит
урезанный вариант имеет смысл, только если в данные переезжают **параметры самого узла, а не правила**: база узла
саблейбла (C23), его место относительно соседа (Q11), его отсутствие на части каталога (M58). Это ровно подход 3
ниже. Отдельно от него урезанный уровень 2 смысла не имеет.

### Q11, C23, M58

- Q11: вторая схема `master/sublabel-first`, привязка к лейблу с даты и документом. Выражается.
- C23: `params.base = 'net'` у узла саблейбла в схеме NoGhost. Выражается.
- M58: схема без узла саблейбла, привязка к ISRC. Выражается.
Это главный плюс подхода: всё без кода. Но то же даёт подход 3 малыми средствами.

### Остальные ответы

- **Что хранится:** 4 таблицы (`schemes`, `nodes`, `links`, `bindings`) + версия схемы в снимке выплаты.
- **Откуда данные:** schemes/bindings читаются в том же `db.snapshot` (новый модуль `flows`, своя схема PostgreSQL,
  без FK к другим модулям — D-121); ctx получает `schemeFor(unit)`.
- **Кто выбирает правило по дате:** два уровня: привязка схемы по `reportDate`, затем правила узлов по
  `participationsAt` и т. п. Если параметры перенести в `params`, периоды придётся вести у версий схем — третий
  механизм периодов.
- **Новый вид узла:** вид в коде + `params` zod + проверка совместимости портов + отрисовка в редакторе + миграция
  jsonb, если меняется форма — **8–10 мест**, не меньше, чем сегодня. Зато новая **проводка** — 0 мест кода.
- **Точность:** держится в движке (один `remainder`, квантование в видах), тест генератором DAG.
- **Риск для золотых:** высокий; движок заменяет `allocateUnit`.
- **Трудоёмкость:** 15–25 дней: модуль `flows` и миграции 1.5, движок и компиляция плана 3, валидация схем 2–3,
  перевод стандартной схемы в данные и сверка 126 рёбер 1.5, редактор React Flow 5–8, версии в снимке 1,
  генератор DAG-тестов 1.5, e2e и документы 2.
- **Главные риски:** договор раздваивается (документ + картинка); оператор рисует неверную проводку, и её никто не
  ловит; динамические порты; вечная поддержка всех версий видов ради старых снимков.
- **Джуниору за 5 минут:** «Расчёт — это граф из базы. Узлы — виды из кода, провода — строки `links`, у каждого
  узла один выход-остаток. Схему рисуют в редакторе, привязывают к лейблу с даты. Почему число такое — смотри
  схему, её версию и правила». Пять минут хватает на «как работает», но не на «как проверить, что схема верна».

## Подход 3 (свой). Водопад доли лейбла: хвост проводки как данные

### Суть в 10 строках

1. Признать асимметрию: сторона артистов (сверху, сплит, пул, доля артиста) открытых кейсов почти не имеет и остаётся
   в коде как есть. Все открытые вопросы проводки — в **хвосте**: что происходит с долей лейбла после сплита.
2. Хвост становится **водопадом** (royalty waterfall, привычное в индустрии слово): упорядоченные ступени, каждая
   берёт из доли лейбла и платит псевдониму.
3. Ступени — это **уже существующие строки**: участия `label_share` (по ISRC) и правила лейбла (саблейбл, по лейблу).
   Новых справочников правил нет.
4. У строки появляются два параметра узла: `seq` (номер ступени) и `base` (`start` — доля лейбла в начале водопада,
   `remaining` — что осталось к этой ступени, `net`).
5. Плюс одна таблица исключений `labels.rule_exclusions(rule_id, isrc | artist_id, период, документ)` — M58.
6. Ступени с одинаковым `seq` берутся **вместе** с одной базой и масштабируются вместе (ровно нынешняя семантика
   label_share); разные `seq` — по очереди.
7. Значения по умолчанию воспроизводят сегодняшний расчёт до пико: участия `label_share` — `seq 10`, база из строки;
   правило саблейбла — `seq 20`, `base remaining`.
8. Явно заданный `seq`/`base` с утверждённым документом снимает допущение Q11 у этой строки; по умолчанию — Q11 как
   сейчас.
9. Узел в коде один (`label-waterfall`), он заменяет `carve:label_share` и `sublabel` из шага 1б; порядок между
   ступенями — данные с периодом и документом, как у любого правила.
10. Не схема, не граф, не шаблон: два параметра у строк, которые уже есть, и одна таблица исключений.

Почему этого нет в §10 и консилиуме: там гибкость рассматривалась **для всей цепочки** (шаблоны схем, `stage` у
всех участий, граф целиком). Водопад ограничивает гибкость одним узлом, где она реально нужна, и прикрепляет её к
строкам правил, а не к схеме. `base` у правила лейбла (Р22) — частный случай; `seq` и исключения — новое.

### Хранение

### Узел в коде

```ts
// facade/layers/label-waterfall.ts
interface Step { id: string; seq: number; base: 'start' | 'remaining' | 'net'; percent: Decimal;
                 artistId: string; documentId: string | null; kind: 'label_share' | 'sublabel'; explicit: boolean }

/** Ступени юнита: участия label_share на ISRC + правило саблейбла лейбла, если не исключено; по (seq, kind, id). */
export function stepsOf(s: UnitState, ctx: LayerContext): Step[] {
  const d = reportDate(s.unit);
  const carves = ctx.participationsAt(s.unit.isrc, d)
    .filter((p) => p.fundedFrom === 'label_share' && !p.percent.isZero())
    .map((p) => ({ id: p.id, seq: p.seq ?? 10, base: p.base === 'net' ? 'net' : 'start', percent: p.percent,
                   artistId: p.artistId, documentId: p.documentId, kind: 'label_share', explicit: p.seq !== null }) as Step);
  const r = s.rule;
  const rule = r && !r.percent.isZero() && s.labelShareCategory === 'ours' && !ctx.excluded(r.id, s.unit.isrc, d)
    ? [{ id: r.id, seq: r.seq, base: r.base, percent: r.percent, artistId: r.recipientArtistId,
         documentId: r.documentId, kind: 'sublabel', explicit: r.seq !== 20 || r.base !== 'remaining' } as Step]
    : [];
  return [...carves, ...rule].sort((a, b) => a.seq - b.seq || a.kind.localeCompare(b.kind) || a.id.localeCompare(b.id));
}

export const labelWaterfall: Layer = (s, ctx) => {
  const steps = stepsOf(s, ctx);
  if (steps.length === 0) return s;
  const start = s.labelShare;
  let remaining = s.labelShare;
  const rows = [...s.rows];
  const shortfalls = [...s.shortfalls];
  for (const group of groupBySeq(steps)) {                      // одна база на ступень: порядок внутри не важен
    const baseOf = (st: Step) => (st.base === 'net' ? s.unit.net : st.base === 'start' ? start : remaining);
    const targets = group.map((st) => pct(baseOf(st), st.percent));                // квантование сразу
    const amounts = fundSteps(s, ctx, group, targets, remaining, shortfalls);      // масштаб к остатку, недостача
    rows.push(...group.map((st, i) => allocation(ctx, { artistId: st.artistId, layer: st.kind === 'sublabel' ? 'sublabel' : 'carve',
      kind: st.kind, ruleId: st.id, documentId: st.documentId, percent: st.percent, amount: amounts[i]! })));
    remaining = remaining.sub(sumOf(amounts));                                     // остаток только вычитанием
  }
  return { ...s, rows, labelShare: remaining, shortfalls };
};
```

В `categorise` правило Q11 становится точнее: допущение `q11` ставится, только если на юните есть и `label_share`, и
`sublabel`, **и** ни одна из этих строк не задала порядок явно (`explicit`) с утверждённым документом. Это одна
строка условия; категории `assumption` по документу остаются как есть.

Совместимость с шагом 1: `edgesOf` не меняется по форме — рёбра `labelShare → artist:*` (виды `label_share`,
`sublabel`) и остаток `labelShare → ours`; на ребре уже есть `base` (Р3), в нём просто будет `start`, `remaining`
или `net`-значение. Схема в ответе: `scheme: 'master/standard'` плюс `waterfall: [{ruleId, seq, base}]` юнита, то есть
аудит видит проводку **данными** без шаблонов.

- **Q11 (саблейбл раньше A&R у NoGhost):** правило NoGhost `seq 5, base start` с документом «ответ владельца 2f»,

- **C23 (25 % от net):** правило NoGhost с 2026-06 `percent 25, base net, seq 20`:

  ступень берёт что есть, недостача в `shortfalls` (`bucket_short`), денег не создаётся.
- **M58 (исключение артиста из саблейбла):** `rule_exclusions(r1, artist_id = <псевдоним>, с 2026-01, документ)` →
  у юнитов, где этот псевдоним строка сплита, ступени саблейбла нет, доля лейбла: A&R 5.40, ours 30.60.
  Вариант по ISRC — `isrc = …`. C03 (77 Records `onimanxd`) выражается так же.
- **Попутно:** M3a (лейбл держит фиксированную долю) — правило с `base start` и процентом «всё, кроме доли лейбла»;
  M48 (налог 9 % на остаток) — ступень `seq 90, base remaining` к псевдониму налога. Фиксированная сумма в месяц
  **не** выражается: это межъюнитная функция (README §6).
- **Не выражается:** Q1 (база лицензиара «за вычетом других участников») — это сторона артистов; если владелец её
  подтвердит, тот же приём (`seq` у участий `artist_share`/`artist_pool`) применим и там, но пока не нужен.

### Остальные ответы

- **Что хранится:** две колонки у `label_rules`, одна у `participations`, одна таблица исключений. Рёбра, схемы,
  шаблоны — не хранятся.
- **Откуда данные:** тот же `db.snapshot` в `calculate()`; индекс модуля `labels` отдаёт правило с `seq`/`base`
  (`labelOf(...).rule`), новый `ctx.excluded(ruleId, isrc, date)` строится из `rule_exclusions` и сплитов на дату
  (для исключения по псевдониму: «псевдоним — строка сплита этого ISRC на дату»).
- **Кто выбирает правило по дате:** как сейчас: индексы модулей (`labels` — правило, `splits` — участия),
  исключения — индекс `labels` по `reportDate`. Порядок ступеней — функция этих строк, не отдельная сущность с
  собственным периодом.
- **Новый вид участия:** не облегчается (это задача подхода 1). Новая **ступень хвоста** (налог, фиксированная
  доля лейбла, ещё один саблейбл) — 0 мест кода, строка данных.
- **Точность:** одна база на ступень, `pct` сразу после умножения, `remaining` только вычитанием, масштаб ступени к
  остатку через `distribute` (остаток к наибольшей). `exactness.test.ts` получает генератор `seq`/`base` для обеих
  строк; инвариант `Σ аллокаций + labelShare = net` не меняется.
- **Риск для золотых:** низкий. При значениях по умолчанию ветки те же: `label_share` вместе с базой «на начало вида»
  (пул долю лейбла не меняет, 10 §3), затем саблейбл от остатка. Доказательство — золотые без правок и хэш
  `/tracks/summary` на `data/real` до и после. Тонкое место: `label_share` с `base net` и масштабированием —
  сейчас база масштаба = доля лейбла на начало, в водопаде = `remaining` на ступени 10, при умолчаниях это одно и то же.
- **Трудоёмкость:** 3–4 дня: миграция и Drizzle 0.5; индексы `labels` (`seq`, `base`, исключения) и `ctx.excluded`
  0.5; узел `label-waterfall` вместо `carve:label_share` + `sublabel` 0.5; `categorise` (явный порядок снимает Q11)
  0.25; API: поля в формах правила лейбла и участия, маршрут исключений, `operations.ts`, контракт 0.75; фронт:
  поля «ступень» и «база» в диалогах, список исключений на правиле, i18n 0.75; золотые кейсы на `seq 5`, `base net`,
  исключение по ISRC и по псевдониму, недостача на `net` 0.5; D-запись, индекс 03, `docs/agents/10` §3 0.25.
- **Главные риски:** (1) свобода `seq` без смысла: два саблейбла и три carve в разном порядке на одном лейбле —
  ограничить `seq` набором из трёх значений (`5`, `10`, `20`) и `90` для налога, пока владелец не попросит больше;
  (2) исключение по псевдониму зависит от сплита на дату — при смене сплита исключение «переезжает» само, это надо
  показать в форме; (3) явный `seq` снимает допущение Q11 — нужен утверждённый документ, иначе мы тихо переведём
  деньги из C в B; (4) владелец может ответить «как сейчас для всех» — тогда 3–4 дня потрачены на гибкость без
  пользователя, поэтому запускать только по ответу на Q11/C23/M58.
- **Джуниору за 5 минут:** «Доля лейбла после сплита течёт вниз по ступеням. Ступень — это строка, которая уже есть:
  участие "из доли лейбла" или правило саблейбла. У каждой два числа: номер ступени и от чего считать (от начала,
  от остатка, от net). Одинаковый номер — берут вместе, от одной базы. Что осталось внизу — наше. Исключение снимает
  ступень саблейбла с артиста или трека. По умолчанию номера 10 и 20 — ровно то, что было».

### Рассмотренный и отброшенный вариант 3б: «вид участия = три оси»

Разложить `funded_from` на оси данных `source` (`net`, `rows`, `row:<id>`, `labelShare`) × `base` (`net`, `start`,
`remaining`) × `slot` и считать всё одним универсальным узлом. Новые «виды» стали бы сочетаниями без кода. Отброшено:
универсальный узел должен воспроизвести четыре разных семантики (пул с пропорциональным draw и `distributeCapped`,
доля артиста с группировкой по источнику и особенностью `carve.ts:99`, масштаб вида целиком), то есть превратится в
`switch` по тем же видам; половина сочетаний бессмысленна (`source row`, `base net`, `slot до сплита`) и требует
белого списка. Выигрыш — только на стороне артистов, где открытых кейсов почти нет.

## Вердикты

- **Подход 1, реестр видов — брать частично, вместе с шагом 1б.** Брать: вывод `FundedFrom`, zod, `FUNDED_ORDER`,
  `SOURCE_OF`, `AllocationKind`, `allocKind` из одного `KIND_DECLS`; `KIND_IMPLS satisfies Record<…>`; тест CHECK по
  `pg_get_constraintdef`; генератор `exactness` по реестру. Это закрывает пять независимых списков одного enum и
  снижает чеклист с 12–14 до 6 (вид-процент) / 9–10 (вид с новым параметром). Не брать: порядок числом в БД, форму
  из zod автоматически, discriminatedUnion в теле запроса до тех пор, пока не появится первый вид с собственным
  параметром. Гибкости под владельца не даёт, и продавать его так не надо.
- **Подход 2, граф как данные целиком — не брать.** Отказ консилиума верен, но по уточнённой причине: точность и
  «один остаток» выполнимы, ломаются динамические порты строк сплита, второй тип связи для базы, проверка схемы
  против договора и раздвоение договора на документ и картинку. Урезанный вариант «граф фиксирован, параметры в
  данных» — это текущее состояние; его осмысленная часть (параметры **узла** в данных) и есть подход 3.
- **Подход 3, водопад доли лейбла — брать как шаг 2 вместо шаблонов Р20, если владелец ответит на Q11/C23/M58
  неединообразно.** Он выражает все три кейса и попутно M3a и M48 строками данных с периодом и документом, не вводит
  ни схем, ни привязок, не меняет сторону артистов и при значениях по умолчанию даёт те же цифры. Шаблоны Р20
  остаются запасным вариантом на случай, если гибкость понадобится на стороне артистов (Q1, M44). До ответа
  владельца — не делать; в шаге 1 достаточно, чтобы `sublabel` и `carve:label_share` после 1б стояли рядом в
  `MASTER_LAYERS` (их потом заменит один узел) и чтобы ребро несло `base` (Р3).

Предлагаемый порядок: шаг 1 (рёбра) → 1б (порядок в одно место) + реестр видов (подход 1, +2.5–3 дня) → по ответу
владельца на вопросы 4–6 README §9 — водопад (подход 3, 3–4 дня), а не шаблоны схем.
