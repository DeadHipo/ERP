## 0. Факты кода, на которых держится вся оценка

Их стоит знать до чтения отчётов: на каждом из них спотыкается хотя бы один архитектор.

1. **Саблейбл сейчас не ходит через `fund()`.** `carve.ts:148–161`: `amount: pct(s.labelShare, rule.percent)` —
   голый процент от остатка. Он всегда помещается: при `percent ≤ 100` (CHECK в `0006`) |q(x·p/100)| ≤ |x|.
   Любая другая база (`net`, доля «до carve») может не поместиться — значит, у саблейбла появляется новая ветка
   с `fund()` и `Shortfall` с `ruleId` правила лейбла. Это **новая арифметика**, а не «ноль строк».
2. **`fund()` в `carve.ts:11` типизирован `ParticipationAtDate[]`**, хотя читает только `id` и `artistId`.
   Для правила лейбла (`SublabelRule.recipientArtistId`) его надо обобщить до `Pick<…, 'id' | 'artistId'>[]` —
   поведение не меняется. Как он считает недостачу при базе `net` у саблейбла (C23, доля лейбла 20, цель 25):
   `fits(25, 20)` = false → `distribute(usable(25, 20) = 20, [{weight 25}])` = [20] → `missing = 5`,
   `why: 'bucket_short'`. При доле лейбла ровно 0: `usable` = 0 → 0 и недостача 25. При отрицательном юните
   (−25 против −20) — то же с минусом. Деньги не создаются, утверждение отчётов 01/02/03 о `fund()` верно —
   **при условии, что саблейбл переведут на `fund()`** (в 01 §2 и 03 §2.1 это подано как «уже так»).
3. **Доля лейбла не меняется пулом и долей артиста.** `pool()` и `artistShare()` (`carve.ts:58–127`) правят только
   `rows`. Поэтому «доля лейбла после split» = «перед `carve:label_share`» = база `bucket` у участия `label_share`.
   `labelShare@before:label_share` из 03 и `labelShare@split` из 02 — одно и то же число (36 на §5). Верно.
4. **Q11 в `categorise.ts:14`:** `q11 = rows.some(kind==='label_share') && rows.some(kind==='sublabel')`.
   Пометка зависит от **наличия аллокации** вида `sublabel`, а не от правила. Нулевая аллокация саблейбла держит
   A&R в C `assumption`; её отсутствие тихо переводит A&R в B (если документ утверждён).
5. **Аллокация саблейбла читается не только категоризацией:** `reports.ts:106` (сигнал D-136 «получатель правила —
   строка сплита» ищет `a.layer === 'sublabel'`), `reports.ts:95` (`noRule`: `sublabelId && !ruleId`),
   `reports.ts:128` (`byRule`). Любой подход, который «выключает» саблейбл или подменяет его аллокацию, задевает
   три сигнала.
6. **`label_rules`: одно правило на лейбл на дату** (`label_rules_no_overlap`, `0006`), правило ставится **только
   саблейблу** (`setRule` → `rule_for_own_label`), `labelOfRecord` отдаёт `rule` только при `kind === 'sublabel'`.
   «Вторая ступень хвоста на том же лейбле» (налог, второй получатель) строкой данных не вводится.
7. **`participations.base`** — CHECK `IN ('net','bucket')` (`0008`, авто-имя `participations_base_check`), сервис
   (`splits/service.ts:394`) проверяет то же. Новое значение базы = миграция + сервис + zod.
8. **Сумма `label_share` не ограничена 100** (сервис проверяет только `top_above_100`), поэтому `fund()` у
   `label_share` нужен уже сейчас и статическая проверка «Σ ≤ 100 в группе» данных не защищает.
9. **Порядок участий внутри вида** задаёт `participationsAt`: `FUNDED_ORDER`, `validFrom`, `id`. От него зависит
   разрешение ничьей в `distribute` при двух участиях **одного канонического** псевдонима с равными весами
   (`best` остаётся первым индексом) — пико-остаток может переехать между `ruleId`.
10. **Шаг 1б не «без единой правки»:** `tests/layers/index.test.ts` перечисляет имена слоёв (`'carve'`) и состояния
    после каждого; i18n `layerNames.carve` во вкладке «По слоям». Golden и exactness не трогаются, но `index.test`
    и i18n — да. Это надо записать в D-запись 1б честно.
11. **`exactness.test.ts`** строит мир через `world.ts`: правила лейблов фиксированы (`DEFAULT_LABELS`, 50 %),
    случайных правил нет. Любой параметр хвоста требует расширить `LabelSpec.rule` и генератор (новые строки, не
    правки утверждений).

## 1. Оценка каждого подхода

Шкала 1–5: **простота** реализации; **риск** регрессии (5 = мал); **поддержка** через год (5 = легко). Дни —
честные, включая тесты, API, фронт, D-запись.

### A. Принятое: слои в коде + рёбра + `GET /allocations`

- **Что меняется:** новый `layers/edges.ts` (`edgesOf(afterSplit, final, ctx)`, `SOURCE_OF`), `calculation.ts`
  (рёбра при `traceIsrc`, `scheme`), `aggregates.ts`/`reports.ts` (общий маппер), `api-responses.ts`
  (`edgeSchema`), `operations.ts`, маршрут `/allocations` с CSV, фронт. Слои не трогаются.
- **Риск:** exactness/golden/`layers/*` — ноль (слои не меняются). 1б — см. факт 10: правка `index.test.ts`.
- **Скрытая ошибка в README §8:** «1б: golden без правок» верно, но «`layers/*.test.ts` без единой правки» в DoD
  шага 1 нельзя распространять на 1б: `index.test.ts` ждёт `'carve'`. Плюс Р7 (`carve.ts:99`, первая строка
  канонического id) — открытая D-запись, без неё `base` на ребре artist_share при слиянии врёт.
- **Оценка:** простота 4, риск 5, поддержка 4, **4.5–5.5 д** (с 1б).

### B. Водопад-таблица схем в БД (01 §1, вариант 1б)

- **Что меняется:** новый модуль `posting` (3 таблицы), движок вместо цикла `MASTER_LAYERS` в `allocateUnit`,
  операции-обёртки над `pct/capToBase/fund/distributeCapped`, `ctx.schemeAt(unit)`, теневой прогон.
- **Риск:** высокий — весь `carve.ts` переписывается в интерпретатор. Golden проходят через новый код.
- **Скрытая ошибка:** в таблице схемы `ord 45 close_rows` стоит в **том же ярусе 4**, что `ord 40 take_pct
  artist_share`, а правило 4 подхода — «все шаги яруса берут базу на начало яруса». Если движок честно применит
  ярус, `close_rows` закроет строки суммами **до** вычета доли артиста (36/18) и создаст деньги. Закрытие строк
  должно быть отдельным ярусом или операцией «вне ярусов» — то есть ещё одна неявная семантика движка.
  Верно в отчёте: двa A&R по 15 % без яруса дали бы 5.4 и 4.59 (база бежит), ярус действительно обязателен.
- **Оценка:** простота 1, риск 1, поддержка 2, **8–11 д**.

### C. Наследование правил с исключениями, только саблейбл (01 §2)

- **Что меняется:** таблица `labels.rule_overrides` (ключ-значение текстом), резолвер `layers/posting.ts`,
  `UnitState.posting`, ветки в саблейбле, `categorise`, `ctx.layersFor` для `sublabel.order = before_carves`.
- **Риск:** средне-низкий для золотых (по умолчанию дефолты), но см. ошибки.
- **Скрытые ошибки:** (1) «Слои не меняются по арифметике… новый код арифметики — ноль строк» — неверно, факт 1:
  `sublabel.base = net` требует `fund()` в саблейбле. (2) `before_carves` — перестановка слоёв; в типизированной
  цепочке `код/graph.ts` узел `sublabel` требует вход `LabelCarved` (`labelShareAfterCarve`), так что `chain`
  перестановку не соберёт — нужны узлы-варианты, как у F. (3) Ключ `sublabel.percent` дублирует
  `label_rules.percent`: два источника процента одного договора, `trail` обязан объяснять, какой победил.
  (4) `value text`, тип проверяет сервис — БД не держит инвариант.
- **Оценка:** простота 3, риск 4, поддержка 2 (ключи расползаются), **4–5 д** (+0.5 на узлы-варианты).

### D. Поправка к стоку против нашей доли (01 §3)

- **Что меняется:** `labels.sink_overrides`, поле `labelShareAfterSplit` в `UnitState`, слой `overrides` между
  `carve` и `categorise`, переписывающий суммы аллокаций `sublabel`/`label_share` и `labelShare`.
- **Риск:** при пустой таблице — тождество (низкий). С записями — средний: слой правит чужие аллокации задним числом.
- **Скрытые ошибки:** (1) поправка с получателем S на юните **без правила** создаёт аллокацию `sublabel`, а
  `u.ruleId` остаётся null → сигнал `noRule` (`reports.ts:95`) продолжает гореть; `byRule` получает id поправки
  вместо правила. (2) Поправка на `label_share` на уровне лейбла меняет деньги участия, заведённого на ISRC, —
  договор A&R правится записью «лейбла». (3) На строке `label_unmapped` поправка по ISRC обязана проверять
  `labelShareCategory`, иначе выплатит из доли, которая ждёт в C.
- **Оценка:** простота 3, риск 4, поддержка 2 (хранит результат, а не условие; составные 7.5 %), **3.5–4 д**.

### E. Текстовый DSL проводки (02 §1)

- **Что меняется:** парсер, AST, интерпретатор (третий движок рядом со слоями и B17), `flows.*`, редактор.
- **Риск:** высокий при замене слоёв; ноль в тени.
- **Скрытая ошибка:** статическая проверка «Σ литералов группы ≤ 100 %» ничего не гарантирует для данных

### F. Шаблоны проводки Р20 (02 §2)

- **Что меняется:** `layers/flows.ts` (`FLOWS`), `labels.flow_bindings`, `ctx.layersFor(unit)` (нужен `labelOf`
  до слоёв), узлы-варианты (`sublabelFirst`, `sublabelOfNet`, вариант `labelShare` с другим входом).
- **Риск:** низкий для существующих кейсов (нет привязки = `MASTER_LAYERS`).
- **Скрытая ошибка:** §2.4 «C23 + Q11 на одном саблейбле не дают пятую схему: при базе `net` порядок влияет только
  на недостачу». Но недостача у C23 — **реальный** случай (сплит ≥ 75 % → доля лейбла < 25 % net; см. 03 §2.4,
  S 7.65 вместо 25). Кто первым забирает из узкой корзины — S или A&R — меняет деньги, значит на NoGhost при
  ответе «саблейбл первым» нужна пятая схема. Комбинаторика начинается раньше, чем написано. Плюс
  `calculate()` сейчас передаёт **один** `layers` на все юниты (`opts.layers`), выбор по юниту — новый код.
- **Оценка:** простота 3, риск 4, поддержка 3, **3.5–4.5 д**.

### I. Стандарт + корректировки `disable` / `rebase` / `set_percent` (03 §2)

- **Что меняется:** `splits.adjustments`, `adjustmentsAt(isrc, labelId, rowArtists, date)`, ветки в
  `carve.ts`/саблейбле, `categorise` по документу корректировки, `adjustmentId` на ребре.
- **Риск:** средний — корректировка адресует узлы строкой (`sublabel`, `participation:<id>`, `kind:label_share`).
- **Проверка `labelShare@before:label_share`:** соответствует состоянию перед `labelShare()` в `carve.ts:133` — это
  `s.labelShare` после split (факт 3). Верно. Но `rebase sublabel → эта точка` оставляет порядок «A&R первым»:
  при недостаче урежется S, а не A&R — это Q11-B только когда всё помещается.
- **Скрытые ошибки:**
  1. «При отключении — нулевое ребро (Р6)». Рёбра выводятся из аллокаций; нулевое ребро = нулевая аллокация
     `sublabel`, а она (факт 4) **оставляет `q11`** и A&R в C `assumption`, и (факт 5) продолжает сигнал D-136 и
     `byRule`. Правильно — **никакой аллокации** и подпись узла. Тогда `disable sublabel` побочно переводит A&R
     из C `assumption` в B — это изменение денег другого получателя, его надо явно описать в D-записи и golden.
  2. `label_unmapped`: `labelOfRecord` даёт `rule = null`, саблейбл и так не работает (`carve.ts:150`); корректировка
     по `label` на такой строке не находится (нет `labelId`), по ISRC — пустая операция. Отказ `no_effect` при вводе
     этого не увидит: он зависит от строки лейбла юнита, а не от ISRC.
  3. «Узлы по-прежнему берут через `fund()`» — саблейбл не берёт (факт 1).
  4. Q11-C (A&R от «нашей половины») корректировками не выражается без составного `set_percent` 7.5.
  5. `node = participation:<id>`: участие закрыли и завели заново (новый id) — корректировка тихо отвалилась.
  6. Таблица в схеме `splits` описывает узел модуля `labels` — правило саблейбла и его поправка живут в двух модулях
     с двумя периодами: две точки выбора по дате на одно число.
- **Оценка:** простота 3, риск 3, поддержка 3, **4.5–5 д**.

## 2. Объединённая идея «параметры хвоста»: одна реализация

### 2.1 Выбор формы

| Критерий | M: параметры на строках | I: таблица корректировок | C: ключи наследования |
|---|---|---|---|
| новых сущностей | 1 таблица (исключения) + колонки | 1 таблица с адресом узла строкой | 1 таблица ключ-значение |
| точек выбора по дате на одно число | **одна**: строка правила (исключение — своя, но про «где», не «как») | две: правило и корректировка | две + приоритет уровней |
| `chain` из `код/graph.ts` | один узел, вход/выход не меняются | без перестановки — да | перестановка не собирается без вариантов |
| Р22 | это и есть колонка `base` | `rebase` (Р22 «не нужен») | ключ `sublabel.base` |
| Р18 (1б) | заменяет два последних слоя одним | ветки в двух слоях | `layersFor` с перестановкой |
| типы в БД | CHECK на колонках | CHECK по комбинациям | `value text` |

**Беру форму M (параметры на строке правила саблейбла) с тремя поправками:** вместо свободного `seq` — закрытый
`stage` из двух значений; `NULL` = «владелец не ответил» (держит Q11-допущение), явное значение = ответ;
исключения ссылаются на **лейбл**, а не на строку правила. От I беру только «отключение = нет аллокации, есть
подпись»; от C — ничего (ключи и уровни не нужны: уровень «лейбл» — это строка правила, уровень «ISRC/артист» —
исключение).

`split.ts` пишет `labelShareAtSplit: s.labelShare.sub(sumOf(amounts))` (и `no_split`: `= labelShare`); значение
состояния, не новая арифметика. `allocation.ts`/`initialState`: `labelShareAtSplit: unit.net`, `ruleExcludedBy: null`.

После Р18 слой `carve` разбит на `carve:pool`, `carve:artist_share` и **один** `label-tail` (а не два слоя
`carve:label_share` + `sublabel`): в 1б он делает ровно сегодняшнее, в шаге 2 получает параметры.

```ts
// layers/label-tail.ts
type Who = { id: string; artistId: string };

/** Правило саблейбла, которое действует на юните: есть, не 0 %, доля «наша», не исключено. */
function activeRule(s: UnitState, ctx: LayerContext): { rule: SublabelRule | null; excludedBy: string | null } {
  const r = s.rule;
  if (!r || r.percent.isZero() || s.labelShareCategory !== 'ours' || !s.sublabelId) return { rule: null, excludedBy: null };
  const rows = new Set(s.rows.filter((a) => a.kind === 'row').map((a) => a.artistId)); // уже канонические
  const ex = ctx.ruleExclusionsAt(s.sublabelId, reportDate(s.unit))
    .find((e) => e.isrc === s.unit.isrc || (e.artistId !== null && rows.has(canonical(ctx, e.artistId))));
  return ex ? { rule: null, excludedBy: ex.id } : { rule: r, excludedBy: null };
}

/** Участия label_share: цели от net или от доли после сплита, берутся вместе из того, что сейчас в корзине. */
function carves(s: UnitState, ctx: LayerContext, parts: ParticipationAtDate[]): UnitState {
  if (parts.length === 0) return s;
  const shortfalls = [...s.shortfalls];
  const targets = parts.map((p) => pct(p.base === 'net' ? s.unit.net : s.labelShareAtSplit, p.percent));
  const amounts = fund(s, ctx, parts, targets, s.labelShare, shortfalls);
  return { ...s, rows: [...s.rows, ...carveAllocations(ctx, parts, amounts)],
           labelShare: s.labelShare.sub(sumOf(amounts)), shortfalls };
}

/** Саблейбл. База по умолчанию — остаток: голый pct, как сегодня (всегда помещается). Иначе через fund(). */
function sublabelOf(s: UnitState, ctx: LayerContext, r: SublabelRule): UnitState {
  const base = r.base ?? 'remaining';
  let amount: Decimal;
  let shortfalls = s.shortfalls;
  if (base === 'remaining') amount = pct(s.labelShare, r.percent);           // байт в байт carve.ts:158
  else {
    const target = pct(base === 'net' ? s.unit.net : s.labelShareAtSplit, r.percent);
    shortfalls = [...s.shortfalls];
    amount = fund(s, ctx, [{ id: r.id, artistId: r.recipientArtistId }], [target], s.labelShare, shortfalls)[0]!;
  }
  const a = allocation(ctx, { artistId: r.recipientArtistId, layer: 'sublabel', kind: 'sublabel',
                              ruleId: r.id, documentId: r.documentId, percent: r.percent, amount });
  return { ...s, rows: [...s.rows, a], labelShare: s.labelShare.sub(amount), shortfalls };
}

export const labelTail: Layer = (s0, ctx) => {
  const parts = ctx.participationsAt(s0.unit.isrc, reportDate(s0.unit))
    .filter((p) => p.fundedFrom === 'label_share' && !p.percent.isZero());     // порядок participationsAt сохранён
  const { rule, excludedBy } = activeRule(s0, ctx);
  const s = { ...s0, ruleExcludedBy: excludedBy };
  if (rule?.stage === 'before_carves') return carves(sublabelOf(s, ctx, rule), ctx, parts);
  const after = carves(s, ctx, parts);
  return rule ? sublabelOf(after, ctx, rule) : after;
};
```

`fund()` в `carve.ts` переезжает в общий файл с сигнатурой `parts: readonly Who[]` — тело то же.
Исключённое правило **не даёт аллокации** (ни нулевой): иначе `q11`, D-136 и `byRule` (факты 4–5).

`categorise.ts`, одна строка:

```ts
const q11 = s.rule?.stage == null
  && s.rows.some((r) => r.kind === 'label_share') && s.rows.some((r) => r.kind === 'sublabel');
```

Явный `stage` снимает Q11 только вместе с утверждённым документом правила: неутверждённый документ даёт
`rule_unconfirmed` по общей ветке, деньги не переходят в B тихо.

**Узел в `chain` (`код/graph.ts`):** `labelShare` + `sublabel` заменяются одним
`node<Pick<Seed,'unit'> & Labelled & Pick<Split,'rows'|'labelShareAfterSplit'>, Closed>` — порядок внутри узла,
`chain` собирается, `layersFor` не нужен. `scheme` в explain остаётся `master/standard`, рядом — `tail: { ruleId,
base, stage, excludedBy }` юнита (аудит видит проводку данными). На ребре `labelShare → artist:S` — `base` числом и
`baseName` (`remaining | start | net`).

### 2.4 Как считается при значениях по умолчанию

После миграции у всех строк `base = NULL`, `stage = NULL`, исключений нет:
