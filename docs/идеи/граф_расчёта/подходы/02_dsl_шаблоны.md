## 0. Три кейса, на которых всё проверяется

Пример README §5 (юнит net 100.00): ремиксер R 10 % off-the-top; сплит A 40 / B 20; MC 5 % **от net** из пула;
A&R 15 % **от доли лейбла**; саблейбл S, правило 50 % **от остатка** доли лейбла. Сегодня: R 10, A 32.666666666667,
B 16.333333333333, MC 5, A&R 5.4, S 15.3, ours 15.3.

| Кейс | Что не выражается сегодня | Нужный ответ на примере §5 |
|---|---|---|
| **Q11 / 2f** (порядок: carve из доли лейбла или половина саблейбла раньше) | порядок зашит в `carve()`: label_share → sublabel; при встрече обоих — C `assumption` (`categorise.ts`, `q11`) | «саблейбл первым»: S = 50 % × 36 = 18; A&R = 15 % × 36 = 5.4 (вариант а) или 15 % × 18 = 2.7 (вариант б); ours = 12.6 или 15.3 |
| **C23** (NoGhost с 2026-06: 25 % от net по контракту) | у `label_rules` нет `base`, правило всегда от остатка доли лейбла | S = 25 % × 100 = 25; A&R 5.4; ours = 36 − 5.4 − 25 = 5.6 |
| **M58 / C03** (исключить строки артиста/ISRC из имприта саблейбла) | «open, not expressible»: правило лейбла действует на всю долю лейбла | на исключённых ISRC: S = 0; ours = 36 − 5.4 = 30.6 |

Важное наблюдение, которое пригодится в подходе 3: в корзине `labelShare` все суммы считаются от **зафиксированной
базы** (net или корзина на начало вида), а не от бегущего остатка, кроме саблейбла. Поэтому «порядок» двух
потребителей одной корзины влияет на деньги только через (1) от какой точки берётся база и (2) кто получает
недостачу при нехватке. Q11 и C23 — это вопросы про базу, а не про граф.

## 1. Текстовый DSL проводки (в духе Formance Numscript)

### 1.1 Суть

1. Схема проводки — короткий текст: блоки `from <корзина> { send …; rest to …; }`.
2. Текст хранится в БД (`flows.schemes`: имя, версия, текст, хэш, документ) и привязывается к лейблу или ISRC с периодом.
3. При сохранении текст разбирается в AST, проверяется статически и прогоняется в предпросмотре на реальных юнитах.
4. Исполняет его один интерпретатор: корзины — `Map<NodeId, Decimal>`, каждая инструкция — одно ребро.
5. Проценты **не пишутся в текст**, а берутся из данных: `send each top` = «все участия `top` в силе на дату».
   Литеральный процент (`25% of net`) разрешён только как условие контракта под документом схемы.
6. Внутри блока инструкции до `then` — одна группа: все берут от одной базы и финансируются вместе (`fund()`).
7. `rest` — единственный остаток блока, считается вычитанием; без `rest` блок не компилируется.
8. Точность — прежние функции `exact.ts`, интерпретатор вызывает `pct`, `fund`, `distributeCapped`, `capToBase`.
9. Рёбра Р1 не выводятся задним числом, а **являются** трассой исполнения; порядок рёбер = порядок текста.
10. Категория B/C остаётся кодом (`categorise`); схема даёт ему ещё один документ — документ привязки.

### 1.2 Грамматика (EBNF, 15 правил)

```
 1 program  = "scheme" name "version" int ";" { block } ;
 2 block    = "from" bucket [ "assume" ] "{" group { "then" ";" group } rest "}" ;
 3 group    = stmt { stmt } ;
 4 stmt     = send | draw ;
 5 send     = "send" amount "to" target [ "as" kind ] ";" ;
 6 draw     = "draw" amount "prorata" "to" target ";" ;           (* только в from row(*): взять из строк пропорционально *)
 7 rest     = "rest" "to" ( target | "c" "(" reason ")" ) ";" ;
 8 amount   = ( percent | "each" ruleset | ruleset ) [ "of" base ] ;
 9 percent  = number "%" ;                                        (* литерал: только под документом схемы *)
10 ruleset  = "top" | "split" | "artist_pool" | "artist_share" | "label_share" | "sublabel_rule" ;
11 base     = "net" | "start" | "left" | "rule_base" ;            (* start: корзина на входе блока; left: на входе группы;
                                                                     rule_base: поле base строки правила, net | bucket *)
12 bucket   = "net" | "scaledNet" | "labelShare" | "row" "(" "*" ")" ;
13 target   = "recipient" | "row" | "row_owner" | "sublabel" | "ours" | "bucket" bucket ;
14 kind     = "top" | "row" | "artist_pool" | "artist_share" | "label_share" | "sublabel" ;
15 reason   = ident ;                                             (* из C_REASONS *)
```

Условий (`if`, `unless`) в грамматике нет сознательно: исключение — это привязка другой схемы к ISRC (M58), а не
ветка внутри текста. Иначе текст становится программой, и бухгалтер его не прочтёт.

### 1.3 Пример README §5 полностью

```
scheme "master/standard" version 1;

from net {
  send each top of net to recipient;                    # R: 10 % × 100 = 10
  rest to bucket scaledNet;                             # 90
}
from scaledNet {
  send each split of start to row;                      # A: 40 % × 90 = 36; B: 20 % × 90 = 18 (capToBase)
  rest to bucket labelShare;                            # 36
}
from row(*) {
  draw each artist_pool of net prorata to recipient;    # MC: 5 % × 100 = 5, из строк 36 : 18 = 3.333333333333 + 1.666666666667
  then;
  send each artist_share of left to recipient;          # база = строка после пула (как сейчас)
  rest to row_owner;                                    # A 32.666666666667, B 16.333333333333
}
from labelShare {
  send each label_share of rule_base to recipient;      # A&R: 15 % × 36 = 5.4
  then;
  send sublabel_rule of left to sublabel;               # S: 50 % × 30.6 = 15.3
  rest to ours;                                         # 15.3
}
```

Трасса исполнения = рёбра README §5, строка в строку: `net→artist:R 10 top p1`, `net→scaledNet 90 remainder`,
`scaledNet→row:A 36 row s1`, …, `labelShare→ours 15.3 remainder`. Порядок рёбер (Р8) задаёт текст.

### 1.4 Q11, C23, M58 на DSL

```
# Q11, «саблейбл первым», вариант (а): A&R от доли лейбла на входе блока
scheme "master/sublabel-first-a" version 1;
...                                                    # блоки net, scaledNet, row(*) как в standard
from labelShare assume {
  send sublabel_rule of start to sublabel;              # S: 50 % × 36 = 18
  then;
  send each label_share of start to recipient;          # A&R: 15 % × 36 = 5.4
  rest to ours;                                         # 12.6
}
# вариант (б): вместо «of start» написать «of left» → A&R 15 % × 18 = 2.7, ours 15.3.
```

DSL заставляет записать то, что владелец так и не сказал (2f): от чего A&R берёт 15 % после саблейбла. Это плюс:
неоднозначность становится видна в тексте, а не в комментарии к `carve()`.

```
# C23: NoGhost с 2026-06, контракт «25 % of net»; привязка к лейблу, документ = контракт
scheme "master/sublabel-of-net" version 1;
...
from labelShare {
  send each label_share of rule_base to recipient;      # A&R 5.4
  then;
  send 25% of net to sublabel as sublabel;              # S: 25 % × 100 = 25 (литерал из контракта); при нехватке — fund(), shortfall
  rest to ours;                                         # 5.6
}

# M58: ISRC вне имприта саблейбла; привязка к списку ISRC с периодом и документом
scheme "master/no-sublabel" version 1;
...
from labelShare {
  send each label_share of rule_base to recipient;      # A&R 5.4
  rest to ours;                                         # 30.6
}
```

Литерал `25%` в C23 — компромисс: если процент саблейбла живёт и в `label_rules.percent`, и в тексте, это два
источника правды. Правильнее `send sublabel_rule of net to sublabel;` (процент из правила, база из текста) — тогда
литералы можно вообще запретить, и правило 1.1 п. 5 сводится к «проценты только в данных».

### 1.5 Валидация

Статически (при сохранении, до привязки):

| Проверка | Пример ошибки |
|---|---|
| ровно один `rest` в каждом блоке | `labelShare`: два остатка |
| каждая корзина, в которую идёт `rest to bucket X`, потребляется ровно одним блоком `from X`, и блок стоит после производителя (ацикличность = порядок текста) | `from labelShare` раньше `from scaledNet` |
| каждая корзина-источник кроме `net` кем-то произведена | `from pool` без производителя |
| Σ литералов одной группы ≤ 100 % | `60% + 50%` из одной корзины |
| `draw` только в `from row(*)`; `row_owner` только там же; `base rule_base` только с `each <ruleset>` | `draw` из `labelShare` |
| известные `ruleset`, `kind`, `reason`; `as kind` совпадает с видом правила | `send each label_share … as top` |
| каждый `ruleset`, который есть в данных на привязанных ISRC/лейбле, встречается в схеме | на ISRC есть участие `artist_share`, а в схеме его нет — деньги участника молча не начислятся |

Последняя проверка — самая важная и нестатическая: её нужно повторять при каждой записи участия или правила
(«схема привязки не умеет этот вид участия») и в `calculate()` как сигнал. Без неё DSL тихо теряет начисления.

Динамически: тот же `fund()` и shortfall, что сейчас; инвариант «Σ стоков = net» проверяется на каждом юните
в тестах и как assert в трассировке.

### 1.6 Как показать ошибку бухгалтеру

Три уровня, все по-русски, с номером строки и подсветкой в редакторе:

```
Строка 18: у корзины «доля лейбла» два остатка (строки 15 и 18).
Остаток может быть один: это деньги, которые не забрали правила выше. Оставьте один «rest to …».

Строка 21: «artist_share» встречается в данных ISRC FR…123 с 2026-03, а в схеме его нет.
Если сохранить, участнику не начислится 4.12 USD за 2026-03…2026-08. Добавьте блок или не привязывайте схему.
```

Главное — **предпросмотр**: до сохранения привязки схема прогоняется на привязанных юнитах за 3–6 месяцев и
показывает разницу с текущей проводкой по получателям («S: −2.70, ours: +2.70, 14 юнитов») и по оплаченным месяцам
(«затронуты выплаченные месяцы 2026-06, 2026-07: к выплате у S уйдёт в минус на …», E20). Это тот самый «что будет,
если» из `консилиум/итог.md` §6.

### 1.7 Тестирование

- Парсер: таблица «текст → AST или ошибка с позицией», 40–60 кейсов.
- **Эквивалентность:** текст `master/standard` через интерпретатор против `allocateUnit(MASTER_LAYERS)` на всех
  golden-кейсах и на генераторе `exactness` (10 000 случайных юнитов, 6-знаковые проценты): совпадение аллокаций
  и рёбер до пико. Пока это не зелёное, интерпретатор не включается.
- Теневой режим: месяц `calculate()` считает обоими способами на `data/real` и сравнивает хэш балансов.
- Золотые кейсы на каждую сохранённую схему (sublabel-first-a/б, sublabel-of-net, no-sublabel).
- Фаззинг грамматики: случайные валидные схемы → Σ стоков = net, знак юнита, ни одной корзины < 0 при положительном net.
- Хэш текста схемы в explain и (позже) в снимке выплаты.

### 1.8 Что хранится, откуда данные, кто выбирает по дате

- `flows.schemes(id, name, version, text, ast_hash, document_id, created_at)` — версии неизменяемы, правка = новая версия.
- `flows.bindings(id, label_id | isrc, scheme_id, valid_from, valid_to, document_id)` с EXCLUDE по периоду (как `label_rules`).
- Данные: `calculate()` читает `flows` в том же `db.snapshot`, парсит каждую версию один раз (кэш по хэшу), кладёт в
  `ctx.schemeFor(unit)`; правила (сплиты, участия, правило лейбла) по-прежнему из `splits.index()` и `labelOf()`.
- Выбор по дате: `reportDate(unit)` (первое число месяца, M52), привязка ISRC сильнее привязки лейбла, нет привязки —
  `master/standard`. Тот же код, что `index().at()`.

### 1.9 Новый вид участия

- Новая **комбинация** существующих примитивов (например, «лицензиар Q1 берёт от остатка после строк»:
  `from row(*) … then; send each licensor of left …`): текст схемы + значение `funded_from` в CHECK миграции + zod +
  i18n + проверка 1.5 «вид в данных есть в схеме». 5–6 мест вместо 12–14, но **каждая** схема, где он может
  встретиться, правится отдельно.
- Новый **смысл** (фиксированная сумма, потолок, порог, погашение M44): грамматика + интерпретатор + валидатор +
  предпросмотр + всё из чеклиста README §8. 15–17 мест — дороже, чем сейчас.

### 1.10 Точность

Интерпретатор не считает сам: `send` = `pct(base, p)`; группа = `fund()` (масштабирование, residue к наибольшему);
`draw` = `distributeCapped`; строки сплита = `capToBase`; `rest` = вычитание. Риск в другом: в текущих слоях есть
неочевидные места, которые надо воспроизвести один в один — группировка artist_share по каноническому id и
`carve.ts:99` (берётся первая строка), пропуск правил с 0 %, «аллокация есть даже при 0», отрицательные юниты,
`label_unmapped` (саблейбл пропускается). Каждое из них в DSL становится неявной семантикой интерпретатора, а не
текста — то есть текст **не** полностью описывает деньги.

### 1.11 Риск для золотых тестов, объём, риски

- Golden: высокий, если интерпретатор заменяет слои; нулевой, пока он идёт тенью. Q11-допущение в `categorise`
  придётся переписать на «документ привязки», это меняет C-причины на тех же суммах.
- Объём: парсер и ошибки 2 д; интерпретатор с `exact.ts` 2 д; эквивалентность с `MASTER_LAYERS` и тень 2–3 д;
  `flows` (миграция, модуль, индекс по дате, API, `operations.ts`, контракт-тест) 1.5 д; редактор с подсветкой и
  предпросмотр 3 д; `categorise`, сигналы, D-записи, docs 1 д; e2e 1 д. **Итого 12–14 дней.**
- Риски: (1) два источника правды (текст против строк правил); (2) тихая потеря денег, если вид из данных не
  упомянут в схеме; (3) интерпретатор — третий «движок» после слоёв и B17-слоёв, его семантика неявна;
  (4) владелец/бухгалтер не будет писать текст сам — писать будет разработчик, и тогда это код без типов и без
  ревью; (5) ретро-изменение привязки пересчитывает оплаченные месяцы так же, как сейчас.
- Джуниору за 5 минут: «Это как Numscript: блок `from` — корзина, `send` — кому и сколько, `rest` — что осталось.
  Проценты — из сплитов и участий, текст говорит только откуда и в каком порядке. Интерпретатор вызывает те же
  `pct`/`fund`, что слои. Схема привязывается к лейблу или ISRC с даты. Ошибка — это строка текста».

## 2. Шаблоны проводки (Р20, развёрнуто)

### 2.1 Суть

1. Схема — **именованный список узлов в коде**: `FLOWS: Record<Scheme, readonly AnyNode[]>` (или `NamedLayer[]`).
2. Набор закрыт enum: `master/standard`, `master/sublabel-first`, `master/sublabel-of-net`, `master/no-sublabel`.
3. В данных — только привязка: `bindings(label_id | isrc, scheme, valid_from, valid_to, document_id)`.
4. Раннер не меняется: `allocateUnit(unit, ctx, layers)` уже принимает список третьим аргументом.
5. Точка выбора — `ctx.layersFor(unit)` (Р18): привязка ISRC → привязка лейбла → `master/standard`.
6. Каждый шаблон — это проверенный набор узлов с golden-кейсами; новый шаблон = код + D-запись.
7. Узлы для вариантов пишутся как варианты (`sublabelOfNet`, `sublabelFirst`), а не параметрами.
8. Документ привязки снимает допущение: Q11 не идёт в C, если привязка с утверждённым документом.
9. `scheme` — поле каждого юнита в explain и рёбрах (Р19), позже в снимке выплаты.
10. Предпосылка — шаг 1б: `carve` разбит на `carve:pool`, `carve:artist_share`, `carve:label_share`, `sublabel`.

### 2.2 Пример README §5

```ts
// layers/flows.ts
export const FLOWS = {
  'master/standard':        [labelOfRecord, perimeter, offTheTop, split, pool, artistShare, labelShare, sublabel,       categorise],
  'master/sublabel-first':  [labelOfRecord, perimeter, offTheTop, split, pool, artistShare, sublabelFirst, labelShareAfterSublabel, categorise],
  'master/sublabel-of-net': [labelOfRecord, perimeter, offTheTop, split, pool, artistShare, labelShare, sublabelOfNet,  categorise],
  'master/no-sublabel':     [labelOfRecord, perimeter, offTheTop, split, pool, artistShare, labelShare,                 categorise],
} as const satisfies Record<Scheme, readonly NamedLayer[]>;
```

Юнит §5 без привязки идёт по `master/standard` — цифры и рёбра ровно README §5.

### 2.3 Q11, C23, M58

| Кейс | Привязка | Узел | Результат на §5 |
|---|---|---|---|
| Q11 | `label_id = <саблейбл>`, `master/sublabel-first`, с даты ответа владельца, документ = ответ | `sublabelFirst`: `pct(labelShare, 50)` от доли на входе; `labelShareAfterSublabel`: A&R от `start` (вариант а) или от остатка (б) — **выбирается при написании узла раз и навсегда** | S 18, A&R 5.4, ours 12.6 (а) |
| C23 | `label_id = NoGhost`, `master/sublabel-of-net`, `2026-06-01 … null`, документ = контракт | `sublabelOfNet`: `pct(unit.net, rule.percent)` из остатка доли лейбла через `fund()`; процент 25 — в `label_rules.percent` | S 25, A&R 5.4, ours 5.6 |
| M58 | `isrc = <каждый исключённый>`, `master/no-sublabel`, период, документ | узла `sublabel` нет | S 0, ours 30.6 |

Если в `код/graph.ts` (типизированная цепочка): `sublabelFirst` выдаёт `labelShareAfterSublabel`, а существующий
`labelShare` ждёт `labelShareAfterSplit` — значит, нужен вариант `labelShare` с другим входом. Честная цена: **на
каждый шаблон с перестановкой — 1–2 узла-варианта**, а не только список.

### 2.4 Сколько схем понадобится (по 13_completeness_check и 09)

| Источник | Нужна схема? |
|---|---|
| C23 NoGhost 25 % of net | да: `sublabel-of-net` (если владелец скажет «контракт важнее решения 2») |
| Q11 / 2f | да: `sublabel-first`, только если ответ разный для разных саблейблов; если одинаковый — правка `MASTER_LAYERS` и D-запись, шаблон не нужен |
| M58 / C03 (77 Records, NoGhost Excluded Projects) | да: `no-sublabel` на ISRC |
| Q12 (прочие строки саблейблов) | нет: данные (`label_rules`) + допущение |
| Q1 (лицензиар «за вычетом других») | нет схемы — нужен новый вид узла; шаблон лишь ставит его в цепочку |
| M44 (погашение 100 % gross до доли артиста) | later; новый узел + шаблон на ISRC |
| M3a, M45, M36, M35 | данные (сплит, период, участие) |
| M48, M21 | out / `ads.ts` |

Реалистично **3–4 схемы** в первый год. C23 + Q11 на одном саблейбле не дают пятую: при базе `net` порядок с
label_share-участиями влияет только на недостачу.

### 2.5 Где предел

Схемы — **произведение** независимых осей, а привязка выбирает одну схему на юнит:

- ось лейбла (что делает саблейбл): standard / first / of-net / none — 4;
- ось ISRC (что происходит со строками): обычные / лицензиар после строк (Q1) / погашение до артиста (M44) — 3.

ISRC с Q1 на треке NoGhost требует `sublabel-of-net+licensor-after-rows`, и привязка ISRC должна **повторить**
выбор лейбла. 4 × 3 = 12 комбинаций; на 6–8 схемах подход ломается: имена комбинаторные, golden-кейсов на каждую
не хватает, привязку ISRC забывают обновить при смене схемы лейбла. Признак, что пора уходить: появилась вторая
независимая ось. Лечение — две привязки по сегментам (лейбл выбирает хвост `labelShare`, ISRC — середину `rows`), а
это уже подход 3.

### 2.6 Резолв по дате

```ts
// labels/service.ts, по образцу splits.index().at
flowAt(isrc, labelId | null, date): { scheme, bindingId, documentId } {
  const byIsrc  = bindingsByIsrc.get(isrc)?.find((b) => covers(b, date));
  if (byIsrc) return byIsrc;
  const byLabel = labelId ? bindingsByLabel.get(labelId)?.find((b) => covers(b, date)) : undefined;
  return byLabel ?? { scheme: 'master/standard', bindingId: null, documentId: null };
}
```

`labelId` — **саблейбл** строки лейбла (`ctx.labelOf(unit.labelName, date).id`), потому что все три кейса про
саблейблы; его надо знать до запуска слоёв, поэтому `layersFor` сам вызывает `labelOf` (то же, что делает слой 1).
Даты приведены к началу месяца (M52), `valid_to` исключающий, EXCLUDE по `(coalesce(isrc, label_id), daterange)`.
Хранение: `labels.flow_bindings` (меньше нового модуля; `flows.*` отдельной схемой — это ещё `schema.ts`,
`repository.ts`, `service.ts`, `CLAUDE.md`).

### 2.7 Карточка трека

- Плашка над таблицей-деревом: «Проводка: саблейбл 25 % от net · с 2026-06 · по привязке к лейблу NoGhost ·
  контракт утверждён». Для `master/standard` плашки нет.
- Если в трек-месяце юниты на разных схемах (смена с даты внутри истории, два UPC) — колонка «схема» в разрезе юнитов.
- Строка «чем отличается от стандартной» (текст из i18n на каждый шаблон, одна фраза).
- Ссылка на привязку и её историю; сигнал «юниты не на стандартной схеме» в очереди.

### 2.8 Остальное

- Данные: `calculate()` читает привязки в том же `db.snapshot`, `ctx.layersFor(unit)` = `FLOWS[flowAt(...).scheme]`.
- Новый вид участия: как сейчас (12–14 мест) **плюс** решение, в какие схемы его вставить, и golden на каждую.
- Точность: узлы-варианты пишутся теми же `pct`/`fund`/вычитанием; меняется только порядок вызова.
- Golden: нулевой риск для существующих кейсов (нет привязки = `MASTER_LAYERS`), если шаг 1б сделан без правок
  golden. `categorise`: Q11-допущение снимается только при утверждённом документе привязки — новая ветка, не правка.
- Объём: 1б (если ещё не сделан) 0.5 д; узлы-варианты 0.5–1 д; миграция, индекс, `layersFor` 0.5 д;
  API/zod/operations/контракт 0.5 д; форма привязки и плашка 1 д; golden на 3 схемы, D-запись 0.5 д. **3–4 дня**
  (адвокат оценивал 2–3 без узлов-вариантов и фронта).
- Риски: комбинаторика (2.5); ретро-привязка пересчитывает оплаченные месяцы (нужен тот же предпросмотр, что в DSL);
  выбор варианта «а/б» в Q11 зашит в узел, второй ответ = ещё шаблон.
- Джуниору: «Есть 4 готовых рецепта проводки, каждый — список слоёв в `flows.ts`. В таблице привязок написано,
  какой рецепт у лейбла или ISRC с какой даты. Нет записи — стандартный. Новый рецепт — это код и golden-кейс».

## 3. Свой подход: «точки замера» — база правила как данные, без схем

### 3.1 Суть

1. Топология одна и не меняется: `net → scaledNet → row:* → labelShare → ours`; порядок **финансирования** фиксирован.
2. Раннер записывает **точки замера** — значения корзин в известные моменты: `net`, `scaledNet`,
   `labelShare@split` (сразу после строк), `labelShare@carve` (после label_share-участий), `row@split`.
3. У любого правила, которое берёт из корзины, есть поле `base` — имя точки замера (сегодня у участий `net|bucket`,
   у правила лейбла поля нет: неявно `labelShare@carve`).
4. Сумма = `pct(точка, процент)`; берётся из корзины в фиксированном порядке через `fund()`; остаток — вычитанием.
5. Наблюдение §0: когда все берут от точек, а не от бегущего остатка, **порядок перестаёт влиять на суммы**, кроме
   недостачи. Q11 «саблейбл первым» = «база саблейбла — `labelShare@split`». C23 = «база — `net`».
6. M58 — таблица исключений правила: `label_rule_exclusions(rule_id, isrc | artist_id, период, документ)`; на
   исключённом юните правило не действует (процент 0, ребро с нулём не пишется, сигнал не нужен).
7. Нет схем, нет имён комбинаций: оси независимы (база у саблейбла, база у участия, исключение по ISRC).
8. Значение по умолчанию = сегодняшнее поведение; golden не трогаются.
9. Каждое значение — колонка у **той же строки правила** с её периодом и документом: проводка видна там, где её меняют.
10. Это обобщение Р22 (`base` у правила лейбла) на точки замера + исключения; ни README §10, ни консилиум не
    сводили Q11 к выбору базы и не предлагали исключения как строки правила.

### 3.2 Пример README §5

Хранится то же, что сейчас; новые поля по умолчанию:

```
label_rules  r1: label = S, percent 50, base = labelShare@carve (по умолчанию), recipient = S
participations p3: A&R, label_share, percent 15, base = bucket (≡ labelShare@split)
```

Расчёт как сейчас: A&R 15 % × `labelShare@split` 36 = 5.4; S 50 % × `labelShare@carve` 30.6 = 15.3; ours 15.3.
Рёбра — README §5 без изменений; у ребра `base` теперь ещё и имя точки (`labelShare@carve`), что прямо отвечает на
ловушку §5 «саблейбл берёт 50 % от 30.6, а не от 36».

### 3.3 Q11, C23, M58

| Кейс | Запись в данных | Расчёт на §5 |
|---|---|---|
| Q11 «саблейбл первым», вариант (а) | новая строка `label_rules` с даты ответа: `base = labelShare@split`, документ = ответ владельца (старая закрывается, M52) | S 50 % × 36 = 18; A&R 15 % × 36 = 5.4; ours 12.6 |
| Q11 вариант (б) «A&R от остатка после саблейбла» | у участия A&R `base = labelShare@sublabel` — **новая точка**, её нет до саблейбла; отказ при вводе (`base_after_funding`) | невыразимо без смены порядка финансирования; честный предел |
| C23 | `label_rules` NoGhost с 2026-06-01: `percent 25`, `base = net`, документ = контракт | S 25 % × 100 = 25; A&R 5.4; ours 5.6 |
| M58 | `label_rule_exclusions`: `rule_id = <77 Records>`, `isrc = DGA…` (или `artist_id`: все ISRC, где он строка сплита на дату), период, документ | S 0; ours 30.6 |

Q11-допущение в `categorise` становится точнее: «label_share-участие и саблейбл на одном юните, **и база
саблейбла — по умолчанию**, и документ правила не говорит о порядке». Правило с явной базой и утверждённым
документом — это ответ владельца, C `assumption` снимается данными.

### 3.4 Что хранится

```sql
-- новая миграция NNNN_rule_bases.sql
ALTER TABLE labels.label_rules ADD COLUMN base text NOT NULL DEFAULT 'label_share_after_carve'
  CHECK (base IN ('label_share_after_carve', 'label_share_after_split', 'net'));

CREATE TABLE labels.label_rule_exclusions (
  id text PRIMARY KEY, rule_id text NOT NULL REFERENCES labels.label_rules (id),
  isrc text, artist_id text, CHECK ((isrc IS NULL) <> (artist_id IS NULL)),
  valid_from date NOT NULL, valid_to date, document_id text, note text,
  created_at timestamptz NOT NULL DEFAULT now(),
  EXCLUDE USING gist (rule_id WITH =, coalesce(isrc, artist_id) WITH =, daterange(valid_from, valid_to, '[)') WITH &&)
);
-- участия: base 'net' | 'bucket' остаётся; 'bucket' документируется как точка начала вида (labelShare@split / row@pool)
```

### 3.5 Откуда данные и кто выбирает по дате

- Всё из уже существующего `labels`-индекса в том же `db.snapshot`: `ctx.labelOf(labelName, date)` возвращает
  `rule` с `base`; новый `ctx.ruleExcluded(ruleId, isrc, rowArtistIds, date)` — индекс по `rule_id`, `covers(…, date)`.
- Выбор по дате делает **сама строка правила** (у неё уже есть `valid_from/valid_to`, M52, EXCLUDE): смена базы с
  даты = закрыть строку и открыть новую. Никакой второй сущности «привязка» с собственным периодом.
- Точка `labelShare@split` должна лежать в `UnitState` (поле `labelShareAtSplit`, пишет `split.ts`); сегодня она
  есть только в `states` при трассировке.

### 3.6 Новый вид участия

Без изменений против сегодня: 12–14 мест (README §8). Подход помогает только на оси «от какой базы» и «где не
действует»: новая база — значение CHECK + ветка в одном месте (`baseValue(state, name)`) + i18n + golden, 4–5 мест;
новое исключение для участий (тот же приём) — одна таблица и одна проверка.

### 3.7 Точность и golden

- Сумма = `pct(точка, p)`, точка — уже квантованное значение состояния; финансирование тем же `fund()`, остаток
  вычитанием. Новая ловушка одна: база `net` или `labelShare@split` у саблейбла может **превышать** остаток корзины
  (C23 при доле лейбла < 25 % net) — значит, саблейбл переходит с голого `pct` на `fund()` с shortfall
  `bucket_short` (сегодня ему это не нужно: 50 % остатка всегда помещается). Golden-кейс на это обязателен.
- Golden: нулевой риск, все дефолты = текущее поведение; новые кейсы: C23 обычный и с недостачей, Q11-а, M58 по ISRC
  и по артисту, отрицательный юнит с базой `net`.

### 3.8 Объём, риски, джуниор

- Объём: миграция + Drizzle 0.25 д; `labels` индекс, валидация (база допустима, исключение не пересекается) 0.5 д;
  `split.ts` пишет `labelShareAtSplit`, `sublabel` с базой и `fund()`, исключения, `categorise` Q11 0.5 д;
  zod, `operations.ts`, контракт-тест 0.5 д; фронт: выбор базы в форме правила лейбла, список исключений на правиле
  и на карточке трека 1 д; golden и D-запись 0.5 д. **3–3.5 дня.**
- Риски: (1) порядок финансирования остаётся в коде — Q11-б и «другой порядок при недостаче» не выражаются (нужен
  `stage`, отложенный в анализе §7.1); (2) исключение по артисту зависит от сплита на дату (артист ушёл из сплита —
  исключение молча перестало действовать; нужен сигнал); (3) база `net` у саблейбла при отрицательной или маленькой
  доле лейбла — недостача, о которой владелец должен знать.
- Джуниору: «Порядок слоёв не трогаем. Каждое правило говорит, от какой суммы оно берёт процент: от net, от доли
  лейбла сразу после сплита или после участий. Это колонка `base`. Если правило не должно действовать на каком-то
  ISRC — строка в таблице исключений. Всё с периодом и документом, как у любого правила».

### 3.9 Отброшенный вариант 3б: поправочные проводки

Идея бухгалтерская: стандартная схема считает всегда, а исключения — строки «переклассифицировать: с ребра X на
сток Y, до цели Z» (как сторно/реклассификация). Отброшено: цель всё равно надо выражать формулой (`25 % net −
что дала стандартная`), в рёбрах появляются пары «туда-обратно», а сигналы и B/C считаются дважды.

## 4. Сравнение

Шкала 1–5, где 5 — лучше: простота для джуниора; гибкость под особые случаи владельца; прозрачность хранения
(видно ли из данных, как считали); точность (5 = риск минимальный); объём работ (5 = мало).

| Подход | Простота | Гибкость | Прозрачность | Точность | Объём | Q11 | C23 | M58 | Дни |
|---|---|---|---|---|---|---|---|---|---|
| 1. DSL проводки | 2 | 5 | 3 | 2 | 1 | а и б | да | да | 12–14 |
| 2. Шаблоны (Р20) | 4 | 3 | 4 | 4 | 3 | а или б (один на шаблон) | да | да | 3–4 |
| 3. Точки замера | 4 | 3 | 5 | 5 | 4 | только а | да | да | 3–3.5 |
| Сейчас (шаг 1 + 1б) | 5 | 1 | 2 | 5 | 5 | нет (C `assumption`) | нет | нет | 0 |

Прозрачность DSL — 3, а не 5: текст читается, но часть семантики (canonical, `carve.ts:99`, нулевые правила,
`label_unmapped`) живёт в интерпретаторе, и проценты в тексте не видны.

## 5. Вердикты

- **DSL проводки — не брать.** Гибче всех, но 12–14 дней, третий «движок», два источника правды и тихая потеря
  начислений при неполной схеме. Писать текст будет разработчик, а не бухгалтер, — это код без типов. Взять
  **частично и дёшево (0.5 д):** текстовое описание действующей проводки как **формат показа**, сгенерированное из
  `MASTER_LAYERS` и правил юнита («net: R 10 % → остаток 90 → строки A 40 %, B 20 % → …»), в explain и выписке.
  Вернуться, если владелец потребует собирать проводку сам и схем станет больше 6.
- **Шаблоны проводки — брать частично.** Только на ось, где меняется **порядок финансирования** (Q11-б,
  M44 «погашение до артиста», Q1 как новый узел в цепочке), и только после ответа владельца, что ответ разный для
  разных лейблов/ISRC. C23 и M58 шаблонами не закрывать: это плодит комбинации (§2.5).
- **Точки замера — брать первым**, как только владелец ответит на 2c (C23), 2f (Q11) и вопрос 6 (M58). Закрывает все
  три кейса, которые сейчас держат деньги в C, строками правил с периодом и документом, без новой сущности, без
  риска для golden, за 3–3.5 дня. Совместим с шагом 1 (рёбра получают имя точки в `base`) и с шагом 1б.
  Предел честный: другой порядок при недостаче и «A&R от остатка после саблейбла» он не выражает — это и есть
  сигнал запускать шаблоны.

Порядок, если владелец ответит «по-разному»: шаг 1 → шаг 1б → точки замера (C23, M58, Q11-а) → шаблоны только под
реальную смену порядка → DSL не раньше, чем шаблонов станет 6+.

Общее для всех трёх: смена проводки задним числом пересчитывает оплаченные месяцы (E20). Предпросмотр «что
изменится и в каких выплаченных месяцах» нужен в любом подходе, и это самая ценная часть всех трёх — его стоит
делать первым, на формах правил, ещё до гибкости.
