# Консилиум: старший бэкенд-архитектор о шаге 1 «граф расчёта»

Дата: 2026-11-04. Прочитано: `README.md`, `анализ.md`, `хранение_и_поток_данных.md`; `facade/layers/*`,
`calculation.ts`, `reports.ts`, `aggregates.ts`, `payouts.ts`, `api-responses.ts`, `tests/layers/exactness.test.ts`.
Код не менялся, ничего не запускалось.

## Вердикт

**Шаг 1 реализуем и полезен, но в предложенном виде переусложнён и в трёх местах неточен.** Рёбра можно получить
*без изменения слоёв вообще*: из состояния после `split` и финального состояния трассируемого юнита. Поле `from`
в `Allocation` почти полностью дублирует `kind`. Ребро «строка → участник пула» в коде не существует (см. П1),
поэтому нужен промежуточный узел `pool`. Рёбра в снимок выплаты в шаге 1 не класть. `NodeSpec` заменить таблицей
`kind → корзина` в 6 строк. Рекомендую: делать в урезанном виде (ниже), объём ~1 день бэкенд + 1–1.5 дня фронт.

## Ответы по пунктам

**1. Можно ли вывести рёбра без `from`.** Из одного *финального* состояния нельзя: строки сплита мутируются
в carve (`carve.ts:77-80`, `carve.ts:123`), исходная сумма строки теряется. Но с парой «состояние после split +
финальное» (обе уже есть в `states` при `traceIsrc`, `calculation.ts:234`) выводится всё:
- `net → artist:T` (top), `net → scaledNet` = `scaledNet` — из финала;
- `scaledNet → row:A` = сумма строки в состоянии после split; `scaledNet → labelShare` = `labelShare` после split;
- `row:A → artist:E` (artist_share) — аллокация + `fromArtistId` участия (`ctx.participationsAt`, тот же ключ);
- `row:A → pool` = gross − final − Σ artist_share из этой строки (вычитание, без новой квантизации);
- `pool → artist:M` — аллокации `artist_pool`; `labelShare → artist:P | artist:S` — аллокации label_share/sublabel;
- `labelShare → ours | c:<labelShareCategory>` = финальный `labelShare`; `row:A → artist:A` = финальная строка.
Где именно «нельзя»: pool — не из-за отсутствия поля, а потому что парных сумм (строка, участник) нет в самом
расчёте; artist_share — только `fromArtistId`, которого нет в `Allocation` (берётся из ctx). Минимальная форма
`from`, если всё же писать в слоях: скаляр `Bucket` для всех, а для pool `draws: {row, amount}[]` на **узле**
`pool`, а не на каждой аллокации участника.

**2. `row:<artistId>` как промежуточный узел.** Корректно, с оговорками:
- объединённые псевдонимы: merge не переписывает строки сплита (только `merged_into`), `allocation()` сводит id
  к выжившему (`allocation.ts:35`), поэтому в одном сплите возможны две строки с одним `artistId`. Узел
  `row:<canonical>` их склеит; баланс сохраняется (обе входят и обе выходят), но artist_share берёт базу только
  из *первой* строки (`carve.ts:99`) — это уже существующая странность, граф её лишь покажет;
- две строки одного владельца — это два псевдонима, два узла, проблем нет;
- строка с 0 % пропускается (`split.ts:15`) — узла нет; artist_share из неё даёт `no_source_row` и аллокацию 0
  (`carve.ts:100-117`): ребра нет, есть подпись-shortfall у участника;
- отрицательный юнит: все суммы со знаком юнита (D-130), Σ in = Σ out со знаком работает; полезно добавить
  проверку «каждое ребро знака юнита или 0», в т.ч. выведенные pool-draws.

**3. Где ломается Σ in = Σ out.** Нигде по деньгам: shortfall масштабирует *цели* к корзине (`carve.ts:19-38`,
`off-the-top.ts:29-45`), рёбра несут фактически взятое; `capToBase` снимает лишнее с наибольшей суммы до записи
(`split.ts:29-33`). Shortfall — подпись узла `{ruleId, missing, why}` на `net`/`pool`/`row:X`/`labelShare`.
Особые формы: perimeter (`index.ts:63`, `stopped`) — одно ребро `net → c:no_isrc|unknown_pair`, без
промежуточных узлов; `label_unmapped` — sublabel не работает (`carve.ts:150`), `labelShare → c:label_unmapped`;
`no_split` — `scaledNet → labelShare` целиком, pool целиком в shortfall. Ровно 100 % — ребро-остаток 0
(решить: нулевые рёбра выбрасывать, кроме перимeтра).
**Важно:** если остаток узла вычисляет сама `edgesOf` вычитанием, тест баланса этого узла тавтологичен. Тест
осмыслен только на узлах, где обе стороны независимы: `net` (top + scaledNet = net), `scaledNet` (строки и
labelShare после split), `labelShare` (вход после split = label_share + sublabel + финал), `pool`
(Σ выведенных draws = Σ записанных аллокаций пула). Это и надо проверять.

**4. Снимок выплаты.** Утверждение «снимок уже содержит аллокации» неверно: в нём агрегаты по псевдониму и до
200 треков (`payouts.ts:153-183`, `slice(0, 200)` на 175), поюнитных аллокаций нет. Рёбра всех юнитов владельца
(сотни ISRC × месяцы × месяцы продаж × 5–15 рёбер × ~250 байт) — десятки МБ JSON в `payload` на выплату.
Совместимость сама по себе не проблема (`z.object` нестрогий, поле optional), проблема — размер и смысл. Входы
владельца — это его аллокации, сгруппированные по (ISRC, kind, правило, документ, B/C); если нужна заморозка,
класть такую группировку, не граф. В шаге 1 — не делать.

**5. Производительность.** Рёбра только для `traceIsrc` — достаточно и дёшево. Для карточки владельца рёбра
не нужны: вход узла владельца — это `u.allocations` его псевдонимов (`balance.ts:185`), «откуда» определяется
`kind` по таблице (`top→net`, `row→scaledNet`, `artist_share→row`, `artist_pool→pool`, `label_share|sublabel→
labelShare`). Ноль новой памяти на 1M+ юнитов. Поле `from` на каждой аллокации, напротив, растит все ответы
с аллокациями и память `calculate()`.

**6. NodeSpec.** В предложенной форме — лишнее: «узлы» не совпадают со слоями (`carve` — один слой, 4 узла,
`carve.ts:168-175`), «пустая схема» дублирует `10_target_model.md` и будет дрейфовать. Полезное ядро — таблица
допустимых пар `kind → тип корзины-источника` и проверка на ней: в генераторе из `exactness.test.ts` (10 000
юнитов) каждое выведенное ребро должно иметь `(kind, from-тип)` из таблицы и знак юнита.

**7. Объём** — см. план. **8. Проще** — см. «Предложение»: вывод рёбер вместо записи `from`.

## Найденные проблемы дизайна

1. **Ребро «строка → участник пула» не существует в расчёте.** Пул берёт сумму целей из строк пропорционально
   (`carve.ts:61-75`) и отдаёт участникам их цели; пар (строка, участник) нет. Пример README §4 с одним MC
   выглядит правильно случайно; при двух участниках пула парные рёбра пришлось бы выдумать второй пропорцией
   с новым остатком — числа, которых нет в деньгах. Нужен узел `pool`.
2. **Процент на ребре не читается без базы.** pool — % от `net`, а берётся из строк; artist_share — % от строки
   *после* пула (`carve.ts:121`); sublabel — % от `labelShare` *после* label_share (`carve.ts:158`). На ребре нужен
   `base` (сумма, от которой взят процент), иначе «5 % = 3.33» на картинке непроверяем.
3. **Неверный маршрут в плане.** `/tracks/:isrc/breakdown/:month` — платформы/страны без расчёта
   (`aggregates.ts:221-224`). Вкладка «По слоям» живёт на `/tracks/:isrc/money` (`aggregates.ts:161`,
   `trackMoneyMonthSchema`, `api-responses.ts:760-783`); `/explain` фронт не использует (`coverage.ts:46`).
4. **Снимок не содержит аллокаций** (`payouts.ts:153-183`) — см. п. 4.
5. **Отображение состояния в API продублировано** в `reports.ts:283-295` и `aggregates.ts` (тот же маппинг
   `layers`); при добавлении `edges` вынести в одну функцию.
6. **«labelShare» в состоянии — бегущий остаток с начала** (`allocation.ts:20`, off-the-top вычитает из него,
   `off-the-top.ts:62`): узел графа `labelShare` = значение *после split*, не поле состояния на любом шаге.
   Легко ошибиться в `edgesOf`, если брать не то состояние.
7. **C-категория — атрибут ребра, а не сток.** У аллокаций C остаётся сток `artist:X` с `reason`; `c:<reason>`
   бывает только у остатка label share. В README оба смысла смешаны; в типе `Edge` развести.
8. Попутно (вне графа): artist_share при двух строках одного канонического псевдонима берёт только первую
   (`carve.ts:99`). Не трогать без D-записи, но отметить.

## Предложение минимального дизайна

Слои, `Allocation`, `exact.ts` не меняются. Новый файл `facade/layers/edges.ts`:

```ts
export type NodeId =
  | 'net' | 'scaledNet' | 'pool' | 'labelShare' | 'ours'
  | `row:${string}`      // строка сплита (канонический псевдоним; дубли после merge склеиваются)
  | `artist:${string}`   // сток-получатель
  | `c:${LabelShareCategory}`; // только остаток label share (label_unmapped, no_isrc, unknown_pair)

export interface Edge {
  from: NodeId;
  to: NodeId;
  amount: Decimal;              // фактически перенесено (≤ 12 знаков, знак юнита или 0)
  kind: AllocationKind | 'remainder' | 'draw'; // draw: row → pool
  ruleId: string | null;        // сплит / участие / правило лейбла; null у остатков
  documentId: string | null;
  percent: Decimal | null;
  base: Decimal | null;         // от чего взят процент (net, строка после пула, labelShare после carve)
  category: Category | null;    // только у рёбер в artist:*
  reason: CReason | null;
}

export interface NodeNote { node: NodeId; shortfalls: Shortfall[] } // подпись, не ребро

/** Какой корзиной питается вид аллокации: единственная «декларация портов». */
export const SOURCE_OF: Record<AllocationKind, 'net' | 'scaledNet' | 'row' | 'pool' | 'labelShare'> = {
  top: 'net', row: 'scaledNet', artist_share: 'row', artist_pool: 'pool',
  label_share: 'labelShare', sublabel: 'labelShare',
};

/** Чистая: рёбра юнита из состояния после split и финального; ctx — только fromArtistId участий. */
export function edgesOf(
  afterSplit: UnitState | undefined, final: UnitState, ctx: Pick<LayerContext, 'participationsAt' | 'artistIndex'>,
): { edges: Edge[]; notes: NodeNote[] };
```

Вызов — в `calculate()` рядом с `layers: states` только для `traceIsrc` (там есть `ctx`); в API `edges` в
`explainSchema.units[]` и `trackMoneyMonthSchema`, тип `edgeSchema` в `api-responses.ts`.
