## Вердикт

«Недоопределённое».** Без них нельзя написать ни один снапшот: неизвестно, есть ли ребро с нулём, как называется
узел при слиянии псевдонимов, как выглядит ребро-остаток при `labelShareCategory ≠ ours`, и какой именно

из `sources.breakdown`, аллокаций там нет; рёбра естественно ложатся в `/tracks/:isrc/explain` и `/money`).
Главный инвариант «Σ in = Σ out» уже есть в `exactness.test.ts` (Σ строк + labelShare = net после каждого слоя);
новое в нём только баланс **внутренних узлов** (`row:*` после pool и artist_share). Это и надо проверять в первую
очередь, потому что именно там рёбра могут разойтись с аллокациями.

## Сверка с API

Эндпоинт для рёбер уточнить (см. вердикт). Что с чем сходится (для одного ISRC и одного отчётного месяца):

1. `Σ edges[to=artist:X] (все kind)` = `Σ allocations[artistId=X].amount` в том же ответе `explain` (последний слой),
   без допусков, на decimal-строках с 12 знаками.
2. `Σ edges[to=artist:X, category=B]` для X одного владельца, по всем месяцам трека = вклад трека в
   `/owners/:id/balance.earned` (с учётом merge: вклад считается по `ownerId`, а не по `artistId`); C-рёбра
   = вклад в `waiting`, расписанный по `reason`.
3. `Σ edges[to=ours]` = `ourShare` юнита = поле «наша доля» в `/tracks/summary` и `/tracks/:isrc/money`;
   `Σ edges[to=c:<reason>]` = C этого трека по причине (`reconciliation().C_waiting`).
4. `Σ(рёбра из net)` по юнитам = `net` юнита = `A_received` из `reconciliation()`; `B + C + ours` = A.
5. Узел владельца (второй уровень): входы `artist:X` по всем трекам = `earned` (B), выходы аванс + реклама +
   выплаты = `recouped + adCharges + paid`, остаток = `payable` до обнуления (`payable` показывается ≥ 0, а
   внутренний остаток может быть < 0: G28/G39 — ребро-остаток не должно показывать минус как «к выплате»).
6. Расхождение полей — падение теста. Тест сравнения идёт по строкам, не по Number (`Number(` запрещён вне списка).

## Снапшоты золотых кейсов

Риск хрупкости: снапшот целого списка рёбер падает при любом переименовании корзины или порядке рёбер.
Предлагаю три уровня, в порядке жёсткости:

- **Жёсткий, ручной (рёбра по ключу):** для каждого G-кейса ожидаемые значения как `{ from, to, kind, amount }` в
  `Map` по ключу `from→to#kind`, посчитанные руками, как цифры в `golden.test.ts` (не сгенерированные). Сравнение
  без порядка, без `ruleId`/`documentId` (id случайные). Только то, что уже есть в строке G-кейса (G04, G18, G34, G46).
- **Инвариантный:** для всех G01…G49 (через общий `Case`) автоматические проверки: баланс узлов, рёбра = аллокации,
  Σ стоков = net, ни одно ребро не противоположного знака. Не зависят от конкретного списка.
- **Снапшот формы без цифр** (`toMatchInlineSnapshot` на отсортированных `from→to#kind`) для 5–6 кейсов, где
  важна топология: G18 (все виды), G08c, G30, G21, G46, G34. Цифры вшиты только в ручной уровень.
- Правило: снапшот не обновляется флагом `-u` без D-записи; цифры золотых не пересчитываются из кода.
- Остатки по 12 знакам (G34) ловить поштучно, а не через снапшот: именно там рёбра могут разойтись на 1 пико.
- Тест «рёбра не изменили цифры»: golden.test.ts запускается неизменным, рёбра добавляются отдельным файлом.

## Фронт и e2e

Читать суммы, а не пиксели. Хуки (data-testid + data-атрибуты у каждого ребра и узла):

- контейнер `trackflow` (`data-isrc`, `data-month`, `data-unit-key`), по одному на юнит;
- узел `flow-node-<корзина>` (`row:A`, `labelShare`, `ours`, `c:label_unmapped`), `data-in`, `data-out`, `data-balanced`;
- ребро `flow-edge` с `data-from`, `data-to`, `data-kind`, `data-amount` (decimal-строка как в API, не отформатированная),
  `data-category`, `data-rule-id`, `data-assumption`; подпись суммы с форматированием отдельно (`flow-edge-label`);
- таблица рядом (`layers-table`) читается тем же тестом: сумма `data-amount` ребёр = ячейка таблицы «Всего»;
- клик по ребру открывает панель `flow-edge-detail` с правилом и документом (ссылка на карточку документа);
- C-стоки и допущения: класс не проверять, а `data-category="C"` и `data-assumption`;
- пустое состояние `flow-empty` (нет юнитов, нет отчёта), состояние загрузки;
- карточка владельца: `owner-flow` с узлами `in:<isrc>`, `out:advance|ad|paid`, `payable`.

Сценарии e2e (приватные базы, замок `data/test-tmp/e2e.lock`): (а) сид G18-подобный: сумма рёбер в сток A = ячейка
«Начислено A» таблицы; (б) трек с двумя UPC: два контейнера; (в) `label_unmapped`: красный сток существует и сумма
= сигнал `labelUnmapped`; (г) карточка владельца: `payable` на картинке = блок баланса; (д) выплата → снимок:
перейти и сравнить `edges` снимка с картинкой до выплаты; (е) старый снимок без `edges`: страница не падает.
Скриншот-тесты картинки не писать (шрифты, анти-алиасинг): допустим только один smoke-скриншот без сравнения.

2. `no_source_row`: ребро на 0 из несуществующего `row:<from>` или вообще без ребра (только shortfall)?

   с суммой или два с разными ключами? `artistShare` сегодня берёт только первую строку (`findIndex`): это существующая

4. Ключ юнита: `from`/`to` без UPC/`salesMonth` склеивают корзины `net`, `scaledNet`, `labelShare` разных юнитов.
   Каким полем различаются рёбра (`unitKey`?) и что значит «карточка трека-месяца» при двух UPC или двух месяцах продаж?
5. Рёбра после `categorise`: категория, причина и `assumption` — свойства ребра-стока или аллокации? Что с рёбрами `c:*`
   (причина берётся из `labelShareCategory`, а не из аллокации)? Какой `ruleId`/`kind` у ребра `labelShare → ours`?
6. Эндпоинт и схема: в README `/tracks/:isrc/breakdown/:month`, но он про площадки и страны; ожидается `explain` и/или
   `/money`? Новое поле в существующем ответе (контракт `api-responses.ts`, обязательное или нет) и размер: для трека
   на 100 юнитов это ~1000 рёбер.
7. Публикации (B17): рёбра в шаге 1 только для мастера? Что отдаёт `explain` для издательского ISRC?
8. Снимок выплаты: какие юниты считаются «попавшими в выплату» (выплата по владельцу, юниты многих треков и месяцев)?

10. Сортировка рёбер в ответе: стабильный порядок обязателен (иначе снапшоты и e2e флейкают). Предлагаю

## Доказательство отсутствия регрессии

Должны остаться **без единой правки** (изменение любого = красный флаг, а не «обновить ожидание»):

  (хэш состояний до и после изменения);
- `tests/recoup.test.ts`, `participations.test.ts`, `labels.test.ts`, `rules-coverage.test.ts`
  (допуски `Number(` не расширять), `boundaries.test.ts`, `review-fixes`, `review-round2`, `review-round3`;

  читают старый снимок без `edges`;
- e2e `smoke.spec.ts`, `states.spec.ts` проходят без правок.

Дополнительно: (1) одноразовый регрессионный прогон «до/после» на реальном наборе данных (`data/real`, локально):
хэш JSON `/tracks/summary`, `/owners/*/balance`, `/reports/reconciliation` не меняется побайтно (кроме нового поля в explain);
(2) если слои меняют сигнатуру `allocation()` (добавляют `from`), тест «аллокации без поля `from` равны прежним»;
(3) `edgesOf` чистая функция, не мутирует состояние (замороженный объект, `Object.freeze`, в тесте);

(счётчик вызовов), иначе медленнее на всех юнитах; `LOG_TIMINGS=1` сравнить до/после.

Риск регрессии: низкий для цифр (слои не меняются), если `from` добавляется только как дополнительное поле;
средний для контракта API/снимка (формат рёбер, порядок) и для фронта (e2e-хуки).
