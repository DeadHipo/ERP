## Я не понял: список с предложениями формулировок

1. **Корзина (bucket).** В коде слова нет: есть `net`, `scaledNet`, `rows[]`, `labelShare`. Предложение: «Корзина — это
   поле состояния юнита, из которого берут деньги: `net` (всё), `scaledNet` (net минус «сверху»), `row:<псевдоним>`
   (строка сплита), `labelShare` (доля лейбла). Сегодня в коде корзин-объектов нет; `row:` и `labelShare` — поля `UnitState`».
2. **Остаток.** «Остаток — тот выход узла, который считается вычитанием `in − Σ остальных`, а не умножением на процент».
   Зачем: чтобы Σ out = in до пико. Добавить: «остаток всегда ровно один».
3. **Сток.** «Конечная корзина, из которой деньги дальше не идут: `artist:<id>`, `ours`, `c:<причина>`». Важно: в
   коде стоков нет как сущностей — они появятся только в `edgesOf`.
4. **Shortfall.** «Недостача: цель узла (5 % net) больше, чем есть в корзине. Узел берёт сколько есть, пропорционально
   уменьшает все цели, недостачу записывает в `state.shortfalls`; денег не создаёт». Пример с числами нужен.
5. **Допущение (assumption).** В примере `C assumption (Q11)` не объяснено ни «C», ни «Q11». Предложение: «Категория B —
   деньги подтверждены документом, можно платить; C — ждут (причина из `C_REASONS`); `assumption` — решение совета,
   документ не будет утверждён, деньги ждут. Q11 — открытый вопрос: доля лейбла без документа считается допущением».
6. **quantise.** «Округлить до 12 знаков half-up сразу после умножения (`q`, `pct` в `exact.ts`). Никогда не округлять
   суммы и не умножать остаток». Показать на 33.333333 %.
7. **canonical.** «`canonical(ctx, id)` — id псевдонима после слияний; всегда сравнивать и группировать по нему, не по
   сырому `artistId`». Без этого два псевдонима одного человека не сложатся в одну строку.
8. **Почему строка — узел.** README §5 «Разработчик» говорит «узел», а в коде строка — просто элемент `rows[]` с
   `kind: 'row'`. Нужна фраза: «`row:A` — узел только на картинке: это запись `rows[]`, из которой pool/artist_share
   вычитают, пока она не превратится в `artist:A`. Поэтому в таблице §4 две строки `row`: `scaledNet→row:A` и `row:A→artist:A`
   с одним `kind` и `rule` — это путает; нужен kind `row_in` / `row_out` или колонка «шаг»».
9. **Откуда дата.** Понятно из хранение §3, но в README §5 лишь строка. Добавить: «дата = `reportDate(unit)` = 1-е число
   отчётного месяца (`allocation.ts`); у юнита два месяца (отчётный и продаж), правило выбирают по отчётному».
10. **`funded_from`.** README §3: «это и есть откуда ребро» — неверно/непонятно: `funded_from` — вид участия
    (`top`, `artist_pool`, `artist_share`, `label_share`), он определяет, КАКОЙ узел обработает участие и в каком порядке.
    А откуда ребро (`from`) у `artist_share` — это `from_artist_id`, у `label_share` — `base`. Переписать.
11. **Юнит.** Нигде не сказано: юнит = ISRC + UPC + отчётный месяц + месяц продаж + строка лейбла + счёт. «Трек-месяц»
    в README и «юнит» в коде — разные уровни (на трек-месяц юнитов может быть несколько). Критично для моей задачи.
14. **«kind» vs «layer» vs «вид узла».** В §8.1 «вид узла» — функция; в ребре `kind` — вид аллокации; у `Allocation.layer` ещё

## Прогон задачи «новый вид узла»: шаги, где застрял, чего не хватает

Задача: «фикс. сумма в месяц с трека получателю, не больше остатка».

**Главное, где застрял (до кода): это не слой в нынешнем смысле.**
- `allocateUnit` сворачивает слои по одному юниту. «В месяц с трека» = по ISRC+месяц, а юнитов на него много (UPC,
  месяц продаж, аккаунт, строка лейбла, D-124). Фикс. сумма на каждом юните выплатится N раз. Нужна агрегация между
  юнитами (как `ads.ts` — отдельная чистая функция внутри `calculate()` после юнитов), а не слой. README этого вида узла
  («аддитивная величина, не процент») вообще не предусматривает; все примеры — проценты. Нужен раздел «узел не от процента».
- «Не больше остатка»: остатка чего? `labelShare` после carve? `scaledNet`? Порядок решает число, а порядок «менять нельзя без
  D-записи». Чек-лист не говорит, как выбрать место (нужно правило: «что стоит до, то и не видит»).
- Откуда сумма? Нет поля `amount` у участия: `percent` обязателен, `base` ∈ {net, bucket}. Значит, миграция + схема.

## Проверка примера §4 руками

Пересчитал: R 10 (net 100); scaledNet 90; A 36, B 18; labelShare 90−54=36; pool MC: цель 5 % net = 5.0, из строк 36:18 →
3.333333333333 и 1.666666666667 (сумма 5.000000000000 ✔); A 36−3.333…=32.666666666667, B 18−1.666…=16.333333333333 ✔;
A&R 15 % от 36 = 5.4 ✔; остаток 30.6; sublabel 50 % от 30.6 = 15.3 ✔; ours 15.3 ✔. Σ = 10+5+49+36 = 100 ✔. Цифры верны,
арифметической ошибки нет. Проверка узлов в тексте верна.
Замечания по форме (путают, но не ошибки):
- Саблейбл считается от `labelShare` ПОСЛЕ A&R (30.6), а не от 36: начинающий посчитает 18 и не сойдётся. Написать «50 % от остатка доли лейбла».
- «MC 5 % net из пула»: цель считается от net юнита (100), а не от scaledNet (90): ещё одна ловушка (5, а не 4.5). Дописать «база — net».
- Две строки `row` с одним `kind`/правилом (см. п.8); у `net → scaledNet 90` kind `remainder`, а `labelShare` из `scaledNet` — тоже
  `remainder`, но это разный смысл (после top и после split).
- `artist:R` — «B» без оговорок, хотя категория зависит от документа/владельца (`categorise`): в примере сказать «документ утверждён».
- Нет колонки «правило/процент/база», нельзя проверить 40/20/5/15/50 по таблице без чтения условия.
- Нет примера с недостачей или отрицательным юнитом (тот, где джуниор ломает деньги).

## Аналогия с Unity: помогает или путает

Помогает: разделение «тип узла (код) / значения (база) / картинка (рёбра)», понятие портов. Путает: (1) в Unity узлы
соединяет человек, у нас порядок фиксирован и «провода» выводятся из состояния — джуниор ищет, где их «соединяют»;
(2) «порты in/out» в Unity — типизированные поля узла, у нас корзины — поля одного общего `UnitState`, узел видит и меняет
всё состояние; `NodeSpec` — только декларация, ничего не запрещает (если не будет теста «пишет только объявленные корзины»);
(3) «play mode» пугает: у нас нет движка. Не хватает: картинки (SVG/ASCII: список слоёв сверху, корзины как резервуары,
стрелки и номера слоёв), глоссария «Unity → код» с именами файлов, и явной строки «ЧЕГО НЕТ: движка, шины, событий, графа
как объекта в памяти».

## Три правила над столом

1. **Квантуй сразу после умножения (`pct`/`q`), остаток — только вычитанием; никакого `Number`, никакого деления без `q`.** Σ out = in до пико.
2. **Знак выхода не противоположен знаку входа; деньги не создаются** (`fits`/`usable`/`capToBase`/`distribute`): цель больше корзины — масштабируй и пиши shortfall, не выдумывай.
3. **Узел чистый и работает на одном юните: никакого чтения базы, никакого состояния между юнитами, порядок слоёв и виды `funded_from` не менять без D-записи и прогона золотых G1…G49.**
