# Консилиум по графу расчёта: итог и решение

Дата: 2026-11-04. Пять независимых рецензентов (отчёты в этой папке): `продакт.md`, `архитектор.md`, `qa.md`,
`адвокат_гибкого_графа.md`, `джуниор.md`. Председатель: автор идеи (эта сессия). Все факты рецензентов, на которые
опирается решение, проверены по коду и документам.

## 1. Вердикты

| Роль | Вердикт | Главный тезис |
|---|---|---|
| Продакт | согласен с правками | картинка одного юнита отвечает на редкий вопрос; ежедневные вопросы требуют выборки по артистам × трекам × месяцам и выписки на одного получателя |
| Архитектор | реализуемо, но переусложнено | рёбра выводятся из двух уже имеющихся состояний без правки слоёв; поле `from` и `NodeSpec` лишние; снимок выплаты не трогать; нужен узел `pool` |
| QA | тестируемо после ответов на 6 вопросов | нулевые рёбра, ключ юнита, слияние псевдонимов, эндпоинт, категория на ребре, стабильный порядок |
| Адвокат гибкости | частично согласен | редактор и движок не нужны; но «кейсов ноль» неверно: Q11, C23, M58, Q1 уже держат деньги в C как допущения; порядок записан в трёх местах |
| Джуниор | понятность 3/5 | термины не определены, `funded_from` описан неверно, «пять мест» занижено вдвое, не различены юнит и трек-месяц |

Общее: **никто не предложил вернуться к настраиваемому по ISRC редактору** и никто не отверг явные рёбра.
Спор шёл о форме шага 1 и о том, насколько закрыта топология.

## 2. Решения председателя

Нумерация Р1… для ссылок из README.

**Форма результата**

- **Р1. Рёбра выводятся, слои не меняются.** Функция `edgesOf(afterSplit, final, ctx)` в `layers/edges.ts` строит рёбра
  из состояния после `split` и финального состояния (оба уже лежат в `states` при трассировке). Поля `from` в
  `Allocation` нет. Риск для золотых кейсов нулевой. (архитектор)
- **Р2. Узел `pool`.** Парных сумм «строка → участник пула» в расчёте нет, их нельзя выдумывать. Рёбра:
  `row:A → pool` (взятое из строки, вычитанием), `pool → artist:MC` (аллокация). (архитектор)
- **Р3. У ребра есть `base`** (сумма, от которой взят процент): без неё «5 % = 3.33» непроверяемо. (архитектор)
- **Р4. Категория B/C — атрибут ребра в сток `artist:*`**, а не отдельный узел; `c:<причина>` только у остатка доли
  лейбла (`label_unmapped`, периметр). (архитектор, QA в. 5)
- **Р5. Ребро несёт ключ юнита** (`upc`, `salesMonth`, `labelName`, `account`). Корзины разных юнитов не склеиваются.
  На «трек-месяце» фронт сначала суммирует одинаковые `from→to#kind#ruleId` по юнитам месяца и показывает число
  юнитов; раскрытие — по юниту. (QA в. 4, продакт п. 1)
- **Р6. Нулевые рёбра:** ребро есть там, где есть аллокация (в т.ч. с нулём: саблейбл при 100 % артиста); ребро-остаток
  внутреннего узла есть всегда, даже 0 (узел виден закрытым); `no_source_row` — без ребра, shortfall подписью у
  получателя. (QA в. 1–2, архитектор)
- **Р7. Слияние псевдонимов:** один узел `row:<канонический id>`, две строки одного id входят в него двумя рёбрами.
  Существующая особенность «artist_share берёт только первую строку» (`carve.ts:99`) графом не исправляется, а
  показывается; вопрос совету отдельной D-записью. (QA в. 3, архитектор п. 8)
- **Р8. Стабильный порядок рёбер:** по порядку слоёв, затем `to`, затем `ruleId`. (QA в. 10)
- **Р9. Shortfall — подпись узла**, не ребро; тест баланса считается только на узлах с независимыми сторонами:
  `net`, `scaledNet`, `labelShare`, `pool`. (архитектор)
- **Р10. Декларация портов — таблица `SOURCE_OF[kind] → тип корзины`** (6 строк) и проверка на генераторах
  `exactness`, что каждое ребро имеет допустимую пару и знак юнита. `NodeSpec` и «пустая схема» отменяются.
  (архитектор, продакт)

**Где и что показываем**

- **Р11. Эндпоинты:** рёбра в `/tracks/:isrc/money` (там живёт вкладка «По слоям») и в `/tracks/:isrc/explain`.
  `/breakdown/:month` — площадки и страны, в README была ошибка. (QA, архитектор)
- **Р12. Сначала таблица-дерево, картинка потом.** Раскрываемые узлы, суммы, правило, документ по клику; печатается,
  читается e2e по `data-`атрибутам. Граф как рисунок — после приёмки таблицы. (продакт, архитектор)
- **Р13. Снимок выплаты в шаге 1 не трогается.** В нём нет поюнитных аллокаций, рёбра всех юнитов владельца — десятки
  МБ. Если владелец захочет «как считали в день выплаты», замораживается группировка входов владельца по
  (ISRC, вид, правило, документ, B/C), не граф. Вопрос владельцу. (архитектор, продакт)
- **Р14. Карточка владельца без рёбер:** блок «входы / выходы» строится из баланса по `SOURCE_OF[kind]`;
  отрицательный внутренний остаток не показывается как «к выплате». Отдельная задача после шага 1. (архитектор, QA)
- **Р15. B17 и реклама — не в шаге 1.** Для издательских строк `edges` пустой; блок владельца помечается «мастер»,
  чтобы не ждать совпадения с полным балансом. (продакт п. 7, QA в. 7)
- **Р16. `GET /allocations` с фильтрами (артисты, ISRC, месяцы, владелец) и экспорт CSV входят в шаг 1.**
  Это фильтр по уже посчитанным аллокациям, без рёбер и без трассировки; по ценности для бухгалтера выше картинки
  и это исходный запрос владельца идеи («выборка по N артистам»). (продакт, анализ §7.2)
- **Р17. Подписи для людей:** центы в таблице, 12 знаков по наведению; одна ось цвета (B / C / ours), причина
  текстом; «начислено, ждёт» вместо стрелки «дошло»; у остатков подпись «остаток = вход − Σ правил»; пометка
  «расчёт на сегодня». (продакт)

**Топология**

- **Р18. Порядок сводится в одно место (шаг 1б, после рёбер):** `carve` разбивается на четыре именованных слоя в
  `MASTER_LAYERS` (`carve:pool`, `carve:artist_share`, `carve:label_share`, `sublabel`); `FUNDED_ORDER` остаётся
  только валидацией; хук `ctx.layersFor(unit)` с дефолтом `MASTER_LAYERS`. Цифры не меняются, золотые кейсы —
  доказательство. Комментарий «the only place the order is written» становится правдой. (адвокат п. 1–2)
- **Р19. В ответе explain — `scheme: 'master/standard'`** (константа), чтобы смена проводки была видна в аудите
  данными, а не только в git. В снимок — вместе с Р13, не сейчас. (адвокат п. 3)
- **Р20. Шаблоны проводки (enum 2–3 списков слоёв с привязкой к лейблу/ISRC, периодом и документом) — первый
  кандидат шага 2**, запускается только ответом владельца: если Q11, C23 или M58 решаются **по-разному** для разных
  лейблов или ISRC. Оценка адвоката 2–3 дня принимается как ориентир. Редактор проводов, хранимые рёбра и общий
  движок остаются вне плана. (адвокат)
- **Р21. Критерии возврата расширены:** другая корзина-источник у вида узла на части каталога (C23), отсутствие
  узла на части ISRC (M58), смена проводки с даты (Q11), разный порядок одинаковых узлов. (адвокат п. 6)
- **Р22. `base` у правила лейбла (`labelShare` | `net`)** — не граф, а ответ на C23; делается, когда владелец ответит
  на 2c; в вопросы владельцу. (адвокат)

**Понятность**

- **Р23. README получает глоссарий** (корзина, остаток, сток, shortfall, допущение, B/C, квантование, canonical, юнит
  против трек-месяца, вид узла / слой / kind) с именами в коде. (джуниор)
- **Р24. Исправления:** `funded_from` — вид участия, определяющий узел и порядок, а не «откуда ребро»; пример §4 с
  узлом `pool` и колонками «база / процент»; второй пример с недостачей и отрицательным юнитом; раздел «чего не
  умеет слой» (всё между юнитами — отдельная функция в `calculate()` по образцу `ads.ts`); честный чеклист нового
  вида участия (12–14 мест) и шпаргалка `exact.ts`. `docs/agents/10` — агентский гайд, его обновлять можно и нужно.
  (джуниор)

## 3. Вопросы владельцу лейбла (до начала фронта)

1. Кому показываем разбор трека: только своим или артисту и его менеджеру? Можно ли раскрывать доли других
   участников и долю лейбла? (продакт 1)
2. Какой вопрос задают чаще: трек-месяц, релиз за квартал, владелец за период? (продакт 2)
3. При споре нужно доказать «как считали в день выплаты», или хватает аллокаций по псевдонимам в снимке? (продакт 3, Р13)
4. **Q11 / 2f:** порядок «A&R или settlement из доли лейбла» и «половина саблейбла» одинаков для всех саблейблов? (адвокат, продакт 4)
5. **C23 / 2c:** саблейбл по одобренному контракту получает 25 % от net или половину доли лейбла? Один ответ для всех
   месяцев? (адвокат, Р22)
6. Ждём ли в ближайший год договоров вида M44 (погашение до доли артиста), M58 (исключение артиста из саблейбла),
   M3a (лейбл держит фиксированную долю)? (продакт 5)
7. Формат выписки артисту: xlsx или PDF, разрез треки × месяцы, с рекламой и авансами? (продакт 7)

Ответы 4–6 решают, запускается ли Р20.

## 5. Что отклонено и почему

| Предложение | Решение | Почему |
|---|---|---|
| поле `from` в `Allocation` (автор) | отклонено | дублирует `kind`, трогает слои, растит память всех ответов; рёбра выводятся из двух состояний |
| `NodeSpec` + «пустая схема» (автор) | отклонено | узлы не совпадают со слоями, дублирует 10 §3; достаточно `SOURCE_OF` |
| рёбра `row → участник пула` (автор) | отклонено | таких сумм нет в деньгах; узел `pool` |
| рёбра в снимке выплаты (автор) | отложено | снимок не поюнитный; десятки МБ; ждём ответ владельца 3 |
| картинка-граф первой (автор) | отложено | таблица-дерево закрывает вопрос, печатается, тестируется |
| `stage` у участия сейчас (автор, анализ §7.1) | отложено | шаблон проводки прозрачнее (один документ на проводку); ждём Q11 |
| хранимые шаблоны проводки сейчас (адвокат) | отложено до Р20 | нет ответа владельца; без него схема будет угадана |
| редактор проводов по ISRC, движок узлов | отклонено всеми | узлы с правилами 12 знаков живут в коде в любой модели |
