# Граф расчёта: что хранится, как узлы получают данные, кто выбирает по дате

Дата: 2026-11-04. Третий круг обсуждения (после `README.md` и `анализ.md`). Описывает шаг 1
(явные рёбра) так, как он ложится на текущий код. Ничего ещё не реализовано.

## 1. Три вещи, три места

Чтобы было просто: в графе есть **правила** (параметры узлов), **рёбра** (что узлы сделали)
и **снимок** (что было в момент выплаты). У каждой своё место, и только первое хранится по-настоящему.

| Что | Где живёт | Хранится? | Новое для шага 1 |
|---|---|---|---|
| Правила: сплиты и строки, участия, правила лейбла, документы | PostgreSQL, как сейчас: `splits.splits`, `splits.split_shares`, `splits.participations`, `labels.label_rules`, `owners.documents` | да | ничего |
| Топология: какие узлы и в каком порядке | код: список `MASTER_LAYERS` в `facade/layers/index.ts` | нет (это код) | ничего |
| Рёбра: «из корзины X в корзину Y сумма S по правилу R» | результат `calculate()`, отдаётся API | **нет**, пересчитываются каждый раз | поле `from` в аллокации + функция `edgesOf(state)` |
| Снимок выплаты | `settlements.payout_snapshots.payload` (JSON текстом, байт в байт) | да, уже сейчас | в JSON добавляется массив `edges` |

Правило проекта остаётся в силе: ничего не копится, любой ответ пересчитывается из сырых строк,
замораживается только снимок выплаты. Рёбра — такой же производный результат, как сегодня аллокации.

## 2. Как узел получает данные

Узел **никогда не ходит в базу**. Он получает два аргумента: состояние юнита и контекст.

```
calculate()
  ├─ sources.snapshot()            ← юниты из ClickHouse (ISRC, UPC, месяцы, строка лейбла, net)
  ├─ db.snapshot(() => ...)        ← ОДНО согласованное чтение PostgreSQL:
  │     owners.artistIndex()           псевдоним → владелец
  │     owners.knownPairs()            известные пары ISRC|UPC
  │     splits.index()                 все сплиты, строки, участия → индекс в памяти
  │     labels.index()                 строки лейбла → лейбл, правила саблейблов
  │     owners.documentInfo(ids)       статус и вид каждого документа
  │     ads.list(), publishing...
  ├─ ctx = { splitAt, participationsAt, labelOf, artistIndex, documentStatus, ... }
  └─ для каждого юнита: allocateUnit(unit, ctx) = свёртка по MASTER_LAYERS
         state₀ = { net }
         state₁ = labelOfRecord(state₀, ctx)
         state₂ = perimeter(state₁, ctx)
         state₃ = offTheTop(state₂, ctx)        ← ctx.participationsAt(isrc, 1-е число отчётного месяца)
         state₄ = split(state₃, ctx)            ← ctx.splitAt(isrc, та же дата)
         state₅ = carve(state₄, ctx)            ← ctx.participationsAt(...) (pool, artist_share, label_share) + state.rule
         state₆ = categorise(state₅, ctx)       ← ctx.documentStatus / documentKind / confirmedOwners
```

Контекст — это обычные функции над индексами, собранными из одного снимка. Поэтому:

- один расчёт видит одну версию данных (D-012): правило не может поменяться «между узлами»;
- узел можно вызвать в тесте с контекстом, собранным руками, без базы (так и устроены `tests/layers/`);
- узлы не знают, откуда данные: из PostgreSQL, из фикстуры или из будущего источника.

Что каждому узлу нужно из контекста (это и есть «in» узла, кроме денег):

| Узел | Берёт из ctx | Берёт из состояния |
|---|---|---|
| label-of-record | `labelOf(строка лейбла, дата)`, `labelName` | строка лейбла юнита |
| perimeter | `knownPairs` | ISRC, UPC |
| off-the-top | `participationsAt` (только `top`) | `net` |
| split | `splitAt` | `scaledNet` |
| carve | `participationsAt` (pool, artist_share, label_share) | строки, `labelShare`, `rule`, `net` |
| sublabel (внутри carve) | — | `rule`, `labelShare` |
| categorise | `documentStatus`, `documentKind`, `artistIndex`, `confirmedOwners` | все аллокации |

## 3. Кто выбирает сплит по дате

Не узел и не фасад, а **индекс модуля сплитов** (`splits.index()` в `modules/splits/service.ts`),
который строится один раз на расчёт:

1. читает все сплиты, строки и участия одним снимком;
2. группирует по ISRC;
3. `at(isrc, date)` находит сплит, у которого `valid_from ≤ date < valid_to` (`valid_to` исключительный,
   D-025; пустые периоды не действуют);
4. `participationsAt(isrc, date)` фильтрует участия тем же `covers` и сортирует:
   сначала по виду (`top` → `artist_pool` → `artist_share` → `label_share`), затем по `valid_from`, затем по `id`.

Дата — всегда **первое число отчётного месяца** (`reportDate(unit)`), потому что все даты правил
приведены к началу месяца (M52). Узел не думает о датах вообще: он спрашивает «что действует на эту дату»
и получает готовый список.

Тот же приём у лейблов: `labels.index().labelOf(строка, дата)` → лейбл и правило саблейбла, действующее
в эту дату.

Если захочется порядок по ISRC (из `анализ.md` §7.1): поле `stage` у участия и правила лейбла, и этот же
индекс сортирует по нему. Узлы не меняются, меняется только порядок, в котором раннер их вызывает или
в котором carve обрабатывает виды.

## 4. Как выглядит ребро (результат, не таблица)

```json
{
  "from": "scaledNet",                  // "net" | "scaledNet" | "row:<artistId>" | "labelShare"
  "to":   "row:<artistId>",             // "row:<id>" | "artist:<id>" | "ours" | "scaledNet" | "labelShare" | "c:<reason>"
                                        // строка сплита — промежуточный узел: затем row:<id> → artist:<id> (остаток строки)
  "amount": "36.000000000000",          // decimal-строка, 12 знаков
  "layer": "split",
  "kind":  "row",                       // row | top | artist_pool | artist_share | label_share | sublabel | remainder
  "ruleId": "<splitId|participationId|ruleId>",
  "documentId": "<id>|null",
  "percent": "40",
  "category": "B",                      // только у стоков-получателей; у остатков null
  "reason": null,
  "assumption": null
}
```

Это сегодняшняя `Allocation` плюс `from`, а остатки (`net → scaledNet`, `scaledNet → labelShare`,
`labelShare → ours`) добавляет функция `edgesOf(state)` из уже посчитанных полей состояния.
Один юнит даёт 5–15 рёбер. Для карточки трека это список из `explainTrack`; для схемы владельца —
те же рёбра, сгруппированные по `to`.

Инвариант для теста: для каждого внутреннего узла Σ `amount` входящих = Σ `amount` исходящих,
для корня `net` Σ исходящих = net юнита. Это та же проверка, что в `exactness.test.ts`, но
сформулированная на рёбрах.

## 5. Где рёбра замораживаются

Только в снимке выплаты. `createPayout` уже сохраняет JSON с аллокациями по псевдонимам
в `settlements.payout_snapshots.payload`. В этот же JSON добавляется `edges` для юнитов,
попавших в выплату. Таблица не меняется, старые снимки без поля остаются валидными
(схема ответа делает `edges` необязательным).

## 6. Для сравнения: если бы топологию хранили

Чтобы было видно, почему шаг 1 лёгкий, а «гибкий граф» нет:

| | Шаг 1 (рёбра) | Хранимая топология по ISRC |
|---|---|---|
| новые таблицы | 0 | `flows` (схема), `flow_nodes`, `flow_edges`, `isrc_flows` (привязка ISRC + период + документ) |

## 7. Итог третьего круга

- В базу для графа не пишется ничего нового: правила уже лежат, рёбра считаются, снимок уже есть.
- Узлы получают данные только через контекст из одного снимка; в базу они не ходят.
- Выбор по дате делает индекс модуля (сплиты, лейблы) один раз на расчёт; дата — начало отчётного месяца.
- Единственное изменение в коде: `from` в аллокации, `edgesOf`, `edges` в explain/breakdown и в снимке, тест баланса узлов.

## 8. Уточнения четвёртого круга: id узла и несколько out

### 8.1 «Узел = функция, и у него id, который есть в базе»

Почти. Надо различать **вид узла** и **узел на конкретном юните**:

| | Что это | Где живёт | Как называется |
|---|---|---|---|
| вид узла | функция `(state, ctx) → state` | код, `facade/layers/*.ts` | строковое имя: `off-the-top`, `split`, `carve:pool`, `carve:label_share`, `sublabel` |
| узел на юните | вид узла, применённый к одному правилу на одном юните | нигде не хранится, появляется в расчёте | `вид + id правила`: `split:<splitId>`, `carve:pool:<participationId>`, `sublabel:<ruleId>` |
| правило | строка в базе, которой узел параметризуется | PostgreSQL: сплит, участие, правило лейбла | её `id` и есть «id в базе» |

Так что отдельной таблицы узлов нет и не нужно: id правила в базе уже однозначно называет узел,
а вид узла задаётся тем, в какой таблице правило лежит и чем оно заполнено (`funded_from` у участия).
В рёбрах это поля `layer`/`kind` (вид) и `ruleId` (правило). Новый вид узла = новая функция в `layers/`
с новым именем + при необходимости новое значение `funded_from` или новая таблица правил + D-запись.

Один нюанс: у одного правила может быть несколько узлов, если оно действует на нескольких юнитах
(каждый месяц продаж, каждый UPC — свой юнит). Поэтому полный ключ узла в результате:
`вид + ruleId + ключ юнита`. Для карточки трека-месяца ключ юнита фиксирован, и остаётся `вид + ruleId`.

### 8.2 «А если out несколько?»

Это обычный случай, не исключение. Сегодня:

| Узел | in | out |
|---|---|---|
| off-the-top | 1 (`net`) | N участников + 1 остаток (`scaledNet`) |
| split | 1 (`scaledNet`) | N строк + 1 остаток (`labelShare`) |
| carve pool | **N** (строки, пропорционально) | M получателей; строки уменьшаются |
| carve artist_share | 1 (одна строка) | M получателей; строка уменьшается |
| carve label_share | 1 (`labelShare`) | M получателей; `labelShare` уменьшается |
| sublabel | 1 (`labelShare`) | 1 саблейбл + 1 остаток (`ours`) |

Правило для любого числа out одно и то же (D-127, D-130), и оно уже реализовано в `layers/exact.ts`:

1. каждый out считается своим умножением и сразу квантуется до 12 знаков (`pct`);
2. **ровно один** out объявлен остатком и считается вычитанием: in − Σ остальных (`scaledNet`, `labelShare`, `ours`);
3. если остатка нет (проценты ровно 100 или узел «берёт всё»), лишние пико после округления снимаются
   с самого большого out (`capToBase`), чтобы ни один out не стал другого знака, чем in;
4. если Σ out больше in — все out масштабируются к in пропорционально, разница записывается как shortfall,
   деньги не создаются (`distribute`, `fund`).

Несколько **in** (pool) — зеркальная операция: сумма берётся из входов пропорционально их размеру,
каждая доля квантуется, остаток к самому большому входу (`distributeCapped`).

Пример узла split с тремя out на `scaledNet` = 90:

```
in  scaledNet                 90.000000000000
out row A  40 %               36.000000000000   (умножение, квантование)
out row B  20 %               18.000000000000
out row C  33.333333 %        29.999999700000
out labelShare (остаток)       6.000000300000   (вычитание: 90 − 36 − 18 − 29.9999997)
Σ out = 90.000000000000 = in
```

В рёбрах каждый out — отдельное ребро с одним и тем же `from` и своим `to`; у ребра-остатка
`kind: 'remainder'`. Тест баланса узла проверяет Σ out = in независимо от их числа.

Для нового вида узла с несколькими out нужно написать только «как считаются цели» и «какой out — остаток»;
квантование, остаток, cap и масштабирование берутся готовыми из `exact.ts`.

| Не хранится | Почему | Где живёт |

### Как один запрос проходит по этим таблицам

1. `calculate()` одним снимком читает **все** строки таблиц правил (не по ISRC: индексы строятся на весь каталог)
   и все юниты из `believe.units` по загруженным файлам.
2. Индекс сплитов: `splits` → по ISRC → `at(isrc, 2026-03-01)` даёт `s1`; `participationsAt` даёт `p1, p2, p3`
   в порядке top → artist_pool → artist_share → label_share. Индекс лейблов: `s records` → `LS` → правило `r1`.
3. Для юнита `(QZTST2600001, 1234567890123, 2026-03, 2026-02, S Records, 100)` граф запускается один раз и даёт
   13 рёбер из README §5. Для следующего юнита — заново, те же индексы.
4. Ответ на запрос — фильтр и группировка рёбер (или аллокаций) всех юнитов: по трекy, по псевдониму, по владельцу.

Если завтра на этом ISRC появится новый договор, в базу добавится **одна строка** в `participations` или новый
`splits` с датой; ни одна таблица «графа» не меняется, а следующий расчёт покажет новые рёбра на всей истории с этой даты.

## 10. Хранение узлов и связей: три уровня

Ключевая мысль: **связи не нужно хранить отдельно**, потому что они задаются именами полей. Узел объявляет, какие
поля состояния он читает (`In`) и какие пишет (`Out`); ребро «кто кого питает» выводится: поле `rows` у `carve:pool`
берётся у последнего предыдущего узла, который это поле выдал (`split`). Это как порт по типу в Unity: достаточно
списка узлов по порядку плюс объявленные порты, и граф восстановлен однозначно. Поэтому «схема» на любом уровне —
это упорядоченный список имён узлов, а не таблица рёбер.

### Уровень 0 — принято сейчас: узлы и схема в коде

| Что | Где | Как версионируется |
|---|---|---|
| вид узла (функция + `In`/`Out`) | `код/<узел>.ts` (в реальности `facade/layers/`) | git, D-запись |
| схема (порядок) | `MASTER_GRAPH = chain(...)` в `graph.ts` | git, D-запись; имя `scheme: 'master/standard'` в ответе explain и (позже) в снимке |
| связи | не хранятся: выводятся из `In`/`Out` | — |
| привязка к ISRC | нет: одна схема на источник | — |

Проверка связей — компилятором (`chain`): узел, которому не хватает поля, не соберётся.

### Уровень 1 — шаг 2 по ответу владельца (Р20): схема как данные, узлы в коде

Нужен, если Q11 / C23 / M58 решаются по-разному для разных лейблов или ISRC. Узлы остаются функциями; в базе —
**реестр схем** и **привязки** с периодом и документом, как у любого правила:

`flows.schemes` — упорядоченный список имён узлов (узлы из реестра кода `NODE_REGISTRY: Record<name, AnyNode>`):

| id | name | nodes |
|---|---|---|
| master/standard | стандарт | `["label-of-record","perimeter","off-the-top","split","carve:pool","carve:artist_share","rows-to-artists","carve:label_share","sublabel","categorise"]` |
| master/sublabel-first | саблейбл до carve из доли лейбла | `[…,"rows-to-artists","sublabel","carve:label_share","categorise"]` |
| master/no-sublabel | без правила саблейбла на этом ISRC | `[…,"carve:label_share","close-label-share","categorise"]` |

`flows.bindings` — к чему и с какой даты применяется схема (исключающее ограничение на пересечение периодов, как у
`label_rules`):

| id | label_id | isrc | scheme_id | valid_from | valid_to | document_id |
|---|---|---|---|---|---|---|
| b1 | LNG | null | master/sublabel-first | 2026-06-01 | null | ответ владельца 2f |
| b2 | null | QZTST2600777 | master/no-sublabel | 2026-01-01 | null | письмо об исключении (M58) |

Без привязки — `master/standard`. `nodesFor(unit)` = привязка по (лейбл юнита или ISRC, дата) → схема → список
функций из реестра. Проверка связей здесь делается **при сохранении схемы**: та же проверка, что в `chain`, только по
объявленным именам полей узлов во время выполнения (у каждого узла в реестре есть `reads: string[]` и `writes: string[]`).
Схема, в которой узлу не хватает поля, в базу не попадает. Ацикличность проверять не нужно: это список, не граф.

Цена (оценка адвоката, принята): миграция на две таблицы, реестр узлов, форма «привязать схему», сигнал «юнит не на
стандартной схеме», `scheme` в снимке выплаты, золотые кейсы на каждую схему, D-запись. 2–3 дня.

### Уровень 2 — отклонён консилиумом: граф целиком как данные

Для полноты, чтобы было видно, за что платить не стоит:

| Таблица | Поля |
|---|---|
| `flow_nodes` | id, scheme_id, kind (из реестра), params jsonb (процент, база…), position |
| `flow_links` | from_node, from_port, to_node, to_port |
| `isrc_flows` | isrc, scheme_id, период, документ |

Здесь связи хранятся явно, и появляется всё, чего нет на уровнях 0–1: проверка ацикличности, совместимости типов
портов, полноты (все деньги дошли до стока), редактор проводов, миграция всех треков, и главное — параметры правил
переезжают из справочников (сплиты, участия) в `params` узлов, то есть второе место хранения тех же договоров. Это
и есть «редактор в духе Unity»; его отклонили, потому что проводка — решение совета, а не настройка трека.

### Итого

- Связи никогда не хранятся: они следуют из портов узлов. Хранится только порядок.
- Сейчас порядок в коде (уровень 0); при необходимости — список имён узлов в базе с периодом и документом (уровень 1).
- Параметры узлов всегда остаются в справочниках: сплиты, участия, правила лейблов. Узел — функция, строка правила — её «инспектор».
