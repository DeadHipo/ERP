# Как собрать данные демо (`cases.js`) и что прототип сказал о дизайне

Дата: 2026-11-04. Прототип решений консилиума Р1–Р10 (`../консилиум/итог.md`) на настоящих слоях
`packages/backend/src/facade/layers`. Основной код не менялся.

## Запуск

```sh
cd <корень репозитория>
npx tsx docs/идеи/граф_расчёта/демо/build-cases.ts
```

Базы не нужны (слои чистые, контекст — `makeContext` из `packages/backend/tests/layers/world.ts`). Импорты
относительные, `@erp/shared` в рантайме не нужен (в слоях он только `import type`), поэтому tsx из корня работает без
`--tsconfig`. Результат: `cases.js` (`window.CASES = [...]`) и `cases.json` (тот же массив). Сейчас:
**16 кейсов, 17 юнитов, 126 рёбер**, все проверки зелёные. При любом расхождении скрипт печатает список и выходит с
кодом 1, файлы не пишутся.

## Что проверяется

На каждом юните (поле `checks`, при `false` — падение):

- `nodeBalance`: Σ in = Σ out строго (сравнение строк `toFixed(12)`) для `net` (in = net юнита), `scaledNet`,
  `labelShare`, `pool` и каждого `row:*`;
- `sinksEqualNet`: Σ рёбер во все стоки (`artist:*`, `ours`, `c:*`) = net;
- `edgesEqualAllocations`: Σ рёбер в `artist:X` = Σ аллокаций X в финальном состоянии;
- `signOk`: каждое ребро знака net или 0.

Дополнительно (без поля в схеме, но тоже падение):

- **base воспроизводит ребро**: для каждого ребра с `percent` и `base`, правило которого не имеет shortfall,
  `q(base × percent / 100)` = `amount`. Это проверка Р3: если `base` выбран неверно, число на ребре непроверяемо;
- **ожидания `docs/agents/12_golden_cases.md`**: B, C, ours и сумма по каждому псевдониму для каждого юнита (точное
  сравнение decimal), лишняя аллокация — тоже ошибка; для G24 ещё агрегат трек-месяца по `to` (A 75, P 7.5, ours 67.5);
- без пула из строки ничего не убывает, кроме artist_share (иначе вычитание `draw` прячет ошибку).

## Пробы (не попадают в `cases.js`)

В конце скрипт прогоняет пять краевых миров и печатает, что с ними стало; их провалы — находки, не ошибка:
P1 слияние псевдонимов (A2 → A) + artist_share из A; P2 `no_source_row`; P3 строки 50 + 50 на net 1 пико (`capToBase`);
P4 top выше 100 %; P5 строка A 100 и саблейбл (нулевое ребро NG).

## Расхождения дизайна с реальностью

1. **Р1 работает как задумано.** Пары «после split + финал» хватает на все 16 кейсов; `carve` в `MASTER_LAYERS` один
   слой (Р18 не сделан), и это не мешает. Поле `labelShare` в состоянии — бегущий остаток (архитектор, проблема 6):
   правильно брать именно `afterSplit.labelShare`, иначе `scaledNet → labelShare` неверен при top.
2. **Баланс `row:*` при пуле — тавтология.** `draw` выводится вычитанием (Р2), поэтому Σ in = Σ out у строки верно
   по построению и ничего не проверяет. Независимые стороны есть только у `net`, `scaledNet`, `labelShare`, `pool`
   (как и сказано в Р9). Реальную защиту даёт `edgesEqualAllocations` и проверка «без пула draw = 0».
3. **base при слиянии (P1) неверен.** Узел `row:A` склеивает две строки (Р7), а `carve.ts:99` берёт базу artist_share
   только из первой: ребро E = 2.5 при base 50 и 10 %. Ни «строка после пула» узла, ни что-либо в состоянии не даёт
   правильную базу 25 без поля в слое; граф честно показывает странность, но число на ребре непроверяемо. Нужна
   D-запись (уже предложено в Р7) или base = строка-источник по индексу.
4. **Два ребра с одним ключом (P1).** При слиянии `scaledNet → row:A #row #split-…` и `row:A → artist:A #remainder`
   встречаются дважды (две строки одного сплита). Суммирование по ключу (Р5) их склеит, что для сумм верно, но у
   двух строк могут быть разные документы и категории: ребро-остаток строки надо держать по аллокации (так сделано),
   а ключ Р5 дополнить `documentId` (или индексом строки), иначе склеятся B и C.
5. **У остатка строки есть правило и категория.** Архитектор пишет `ruleId: null` у остатков, но `row:X → artist:X`
   — сток с категорией строки (`split_unconfirmed` и т. п.), которая зависит от документа строки. В прототипе у
   этого остатка `ruleId` = id сплита и `documentId` строки; у остальных остатков null.
6. **Процент × base ≠ сумма при недостаче.** G22: ребро `pool → artist:P` 10 при 20 % от 100. Р9 вешает shortfall на
   узел, но читателю ребра нужна связь: на ребре стоит хранить цель (`target`) или флаг `short`, иначе ребро выглядит
   ошибкой. Проверка base в прототипе пропускает правила с shortfall.
7. **base у строки неточен на пико (P3).** `capToBase` срезает пико с наибольшей строки, когда строки дают ровно
   100 %: ребро 0 при base 1 пико и 50 %. Аналогично top при сумме 100 % (`off-the-top`). Нужна пометка «срезано
   capToBase» или допуск в проверке; в золотых кейсах не встречается.
8. **У `draw` нет процента и base.** Доля строки в пуле — `distributeCapped` пропорционально строкам с остатком
   (G34: A отдаёт 4.333333333334, B и C по …333). Пико-остаток виден только на ребре `draw` и затем в остатке строки
   (A 12.266666666666); `base`/`percent` на draw пусты, подпись «пропорционально строкам, остаток наибольшей (тай —
   первой по id)» надо давать текстом.
9. **Порядок Р8 буквально ставит все остатки в конец.** «Слой, затем `to`» кладёт `net → scaledNet` последним
   (`to = scaledNet` после `ours`). Для таблицы-дерева лучше ставить остаток узла сразу за выходами этого узла (порядок
   по узлу-источнику, затем вид).
10. **Ключ юнита (Р5) в схеме лежит на юните, не на ребре.** Для демо достаточно; в API, где рёбра трек-месяца
    плоские, ключ должен быть на каждом ребре. При агрегации G24 суммы и base складываются корректно только потому,
    что 10 % от 50 и 25 считаются без остатка; в общем случае Σ q(base_i × p) ≠ q(Σ base_i × p), и агрегированный base
    не воспроизводит агрегированное ребро на пико.
11. **Нулевые рёбра (Р6) подтверждены.** P5: `labelShare → artist:NG` 0 есть (аллокация есть), остатки 0 есть всегда;
    P4: при top > 100 % `net → scaledNet` = 0, подпись `top_above_100` у `net`. P2 `no_source_row`: аллокация E 0 есть,
    ребра нет, подпись у `artist:E`, но узел `artist:E` без входящих рёбер — фронту нужно рисовать его по подписи.
12. **G21 (нет сплита):** узлов `row:*` нет, `scaledNet → labelShare` = весь scaledNet, саблейбл берёт от него
    (base 100). Узел `scaledNet` с одним выходом — допустимо, но «после top» без top выглядит лишним: можно скрывать
    `scaledNet`, если нет top.
13. **G30 (периметр):** одно ребро `net → c:unknown_pair` вида `perimeter` (в Р6/Р8 этого вида нет в списке порядка;
    поставлен первым). `c:*` здесь — сток не остатка доли лейбла, а целого юнита: Р4 надо формулировать «c:* —
    остаток доли лейбла или весь юнит периметра».
14. **Категория C у `artist:*` смешивается с `c:*` в цвете.** G18b: P и NG — C assumption (Q11) на рёбрах в
    `artist:*`, а G08c — C label_unmapped как отдельный сток. Одна ось цвета (Р17) работает, только если причина
    подписана текстом на ребре (сделано: `reason`, `assumption`).
