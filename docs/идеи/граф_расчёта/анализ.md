# Граф расчёта: подробный разбор

> **После консилиума 2026-11-04** (`консилиум/итог.md`): поле `from` в аллокации, `NodeSpec`, рёбра в снимке выплаты и оценка «день + полдня» в этом файле устарели; действуют решения Р1–Р24 и `README.md`. Аргументация §1–§3, §7 в силе.

Дата: 2026-11-04. Пара к `README.md` (короткая версия с решением). Действующие документы
(`docs/01…09`, `docs/agents/10_target_model.md`, журнал 97) не трогались; при реализации шага 1
понадобится D-запись и строка в `docs/agents/03_decision_index.md`.

## 1. Что именно предлагалось

Узел графа с параметрами, у которого один или несколько входов и выходы; выход либо финальный
(получатель), либо вход другого узла (например, из сплита во взаиморасчёты). Порядок узлов по ISRC
меняется свободно или берётся дефолтный (текущий). Цель: видеть по каждому узлу его входы и выходы
и быть гибкими по каждому ISRC.

Вопрос: имеет ли смысл, и не станет ли сложнее понимать и хранить.

## 2. Что есть сейчас, в терминах графа

### 2.1 Уровень юнита (ISRC + UPC + отчётный месяц + месяц продаж + строка лейбла)

`allocateUnit` — свёртка состояния `UnitState` по списку `MASTER_LAYERS`
(`packages/backend/src/facade/layers/index.ts`). Состояние: `scaledNet`, `rows: Allocation[]`,
`labelShare`, `shortfalls`, категории. Каждый слой — чистая функция.

Корзины (узлы), которые существуют неявно:

- `net` — корень, вход = net юнита;
- `scaledNet` — остаток после off-the-top;
- `row:<artistId>` — строка сплита (одна на псевдоним);
- `labelShare` — остаток после строк;
- стоки: псевдонимы участников (top, pool, artist_share, label_share), псевдоним саблейбла, `ours`,
  и C-стоки периметра (`no_isrc`, `unknown_pair`, `label_unmapped`).

Рёбра задаются:

- порядком слоёв (кто после кого берёт из какой корзины);
- полями участия `base` (чего процент) и `funded_from` (откуда брать) — это буквально
  «источник ребра» и «формула веса»;
- правилом саблейбла (процент от `labelShare`);
- сплитом (проценты строк от `scaledNet`).

Вывод: топология уже графовая и уже параметризована на уровне ISRC контрактными данными.
Чего нет — явного представления рёбер в результате. `explainTrack` отдаёт состояния после слоёв
(`states`), по ним ребро «A → MC 3.33» восстанавливается только вычитанием соседних состояний.

### 2.2 Уровень владельца

`balance.ts` + `layers/recoup.ts` + `ads.ts`: входы — все B-аллокации владельца по всем юнитам
и месяцам (по псевдонимам), выходы — погашение авансов (только с дохода того же псевдонима),
реклама (D-157: сразу и целиком), выплаты, возвраты, кредиты. Остаток — к выплате.

Это узел «с несколькими входами» из идеи. Но он не продолжение графа юнита: аванс и реклама не
привязаны к юниту, они позиции на псевдониме и месяце. Граф тут двухуровневый:
граф юнита (чистый, по ISRC-месяцу) → агрегация → граф владельца (по псевдониму/владельцу).

### 2.3 Паблишинг

`PUBLISHING_LAYERS`: строка B17 → равные части авторам → доля автора по условиям → B/C.
Тоже граф, свой список слоёв. Уже сегодня это второй «порядок», и он не настраивается по
произведению — он задан источником.

## 3. Разбор по критериям

### 3.1 Понятность

| | Состояния после слоёв (сейчас) | Явные рёбра | Настраиваемая топология |
|---|---|---|---|
| Человек на карточке трека | нужно вычитать соседние состояния | читается прямо: кто → кому → сколько → по какому правилу | плюс ещё надо смотреть, какая схема у этого трека |
| Разработчик | один список, 6 функций, таблица в 10 §3 | то же + поле `from` в аллокации | движок, валидация схем, тесты на каждую допустимую схему |
| Аудит / сверка | правила на ISRC + одна схема | то же | третий источник отличий: индивидуальная схема |

Явные рёбра — чистый выигрыш. Настраиваемая топология — проигрыш в понятности при нуле
известных случаев, где она нужна.

### 3.2 Хранение

- Явные рёбра: ничего не хранится, они часть результата `calculate()`; снимок выплаты может их
  заморозить (он уже замораживает аллокации по псевдонимам). Принцип «ничего не копится» соблюдён.
- Настраиваемая топология: новый справочник «схема распределения» (узлы, рёбра, привязка к ISRC и
  периоду, документ), миграция всех треков на дефолт, UI, валидация (ацикличность, существование
  корзин, совместимость с правилом «строка или участие, не оба»). Это модуль размером со splits.

### 3.3 Точность (D-127, D-130)

Правила 12 знаков написаны по видам узлов: квантование после умножения, остаток вычитанием,
pro rata с остатком к наибольшему, масштабирование к корзине с shortfall, `capToBase` при ровно
100 %. Универсальный узел «процент входа на выход» не воспроизводит pool (берёт из нескольких
строк пропорционально), artist_share (одна конкретная строка, группировка по источнику),
label_share (общая база на вид, масштабирование вместе). Значит движок графа всё равно
вызывал бы эти же функции, а «общим» стала бы только проводка — которая сейчас шесть строк.

### 3.4 Гибкость по ISRC

Она уже есть там, где её требуют контракты: проценты, базы, источники, периоды, документы на
строку. Что фиксировано — порядок видов. Фиксированный порядок — это решения совета:
top до сплита (M4), pool до artist_share, label_share до половины саблейбла (Q11 — допущение,
отмечено), sublabel после всех carve. Если появится контракт, который требует другого порядка,
правильный ход — новая D-запись и, возможно, новый вид узла; индивидуальный порядок на треке
спрятал бы такое решение в данные.

### 3.5 Будущее: выгрузка треков и новые источники

- Выгрузка треков выиграет от явных рёбер (их можно отдавать как таблицу «кто → кому»), схема
  при этом остаётся одна и описывается один раз.
- Новый источник (SoundOn, ASCAP) — свой список слоёв, по образцу `PUBLISHING_LAYERS`. Это
  «несколько графов по источникам», а не «граф по треку».

## 4. Решение

1. Принять граф как **язык описания и формат результата**: «ребро = перенос суммы из корзины в
   корзину по правилу под документом с категорией». Он объединяет мастер, паблишинг, рекламу и
   погашение одним словарём.
2. **Не делать** настраиваемую по ISRC топологию, хранимые схемы, редактор и общий движок.
3. Держать дверь открытой: названия корзин и видов узлов зафиксировать в одном месте
   (каталог в `layers/types.ts`), чтобы при реальной нужде шаблоны по ISRC добавлялись поверх,
   а не переписывали слои.

## 5. Шаг 1 по шагам (если решено делать)

Уточнённая версия с четырьмя взглядами и чеклистом закрытия — `README.md` §5–§6 (пятый круг):
строка сплита стала промежуточным узлом `row:<псевдоним>`, pool пишет `from` массивом долей,
рядом со слоями появляется объявление портов `NodeSpec`.

1. `layers/types.ts`: `type Bucket = 'net' | 'scaledNet' | { row: artistId } | 'labelShare'`;
   `Allocation.from: Bucket | Bucket[]` (pool берёт из нескольких строк — либо массив долей,
   либо одно ребро на строку-источник; второе честнее для графа).
2. Слои проставляют `from` там, где уже знают источник: off-the-top (`net`), split (`scaledNet`),
   pool (строки с долями `shares`), artist_share (`row:<from>`), label_share и sublabel
   (`labelShare`).
3. `edgesOf(state)` — чистая функция из финального состояния в список рёбер, включая остатки
   (`net → scaledNet`, `scaledNet → labelShare`, `labelShare → ours` или C-сток).
4. `explainTrack` и `/tracks/:isrc/breakdown/:month` отдают `edges`; схема ответа в
   `api-responses.ts`; `operations.ts` без новых маршрутов.
5. Карточка трека: вкладка «слои» показывает рёбра (таблица; схема — по желанию).
6. Снимок выплаты: добавить `edges` к аллокациям (расширение формы; старые снимки без поля
   остаются валидными).
7. Тесты: `tests/layers/edges.test.ts` — в каждом узле Σ входов = Σ выходов, корень = net; golden
   кейсы не меняются; `exactness` дополнить проверкой на рёбрах.
8. D-запись: «граф как формат результата; топология одна; рёбра не хранятся».

Оценка: один рабочий день бэкенд + полдня фронт, без изменений в данных и в цифрах.

## 6. Условия возврата к гибкому графу

- Два и более реальных ISRC с разным порядком одинаковых видов узлов (не параметров).
- Владелец хочет собирать схему распределения сам, без разработчика.
- Внешняя интеграция требует схему как данные (тогда схема всё равно одна и выгружается из каталога).

## 7. Второй круг: возражения владельца идеи (2026-11-04)

### 7.1 «Владелец захочет особое решение для артиста или ISRC, и мы не сможем переделать»

Какие «особые решения» бывают, и что их стоит в каждой из моделей:

| Желание | Сейчас | С настраиваемым графом |
|---|---|---|
| другой процент, база, источник, период, документ на одном ISRC | данные: сплит, участие, правило лейбла, документ-допущение | то же |
| новый смысл: фиксированная сумма, потолок, порог по стримам, комиссия, валюта | код: новый вид узла + D-запись | код: новый вид узла (движок с «узлом-процентом» этого не выразит) |
| другой порядок известных видов на одном ISRC | код: поле `stage` у участия/правила и сортировка по нему в раннере (аддитивно, день работы) | данные |
| другая гранулярность: правило по платформе, стране, релизу (UPC), месяцу продаж | код + данные: измерение в ключе юнита (как `label_name` в D-124), правило с этим ключом | то же — граф не меняет ключ юнита |

Вывод: граф «бесплатно» даёт только третью строку. Первая уже есть, вторая и четвёртая стоят
одинаково в обеих моделях. Третья добавляется позже аддитивно и не блокируется текущей архитектурой:
слои чистые, порядок — один список, раннер — цикл.

Главное, что защищает от «не сможем переделать», — не граф, а **пересчёт с нуля** (принцип 7,
D-012): любое изменение правила применяется ко всей истории сразу, выплаты заморожены снимками,
миграция денег никогда не нужна. Настоящее место, где особое желание дорого, — четвёртая строка
(ключ юнита): сейчас платформа и страна агрегируются во `units` и до слоёв не доходят. Это
стоит помнить, но это задача про источник, не про граф.

### 7.2 «Выборка по N артистам по конкретным ISRC с графом проще: большой пул in → корзины out»

Тут поправка. Результат `calculate()` уже и есть «корзины out»: плоский список аллокаций
`(isrc, upc, месяц, месяц продаж, псевдоним, владелец, слой, правило, документ, сумма, B/C)`.
Выборка «артисты X, Y, Z на ISRC a, b, c» — фильтр по этому списку, в обеих моделях одинаковый.

Чего не хватает — **маршрута**: в API есть `/tracks/:isrc/money`, `/owners/:id/balance`,
`/queue/:reason`, но нет `GET /allocations?artists=&isrcs=&months=` (и после шага 1 —
`GET /edges?…`). Это пробел API, закрывается без изменения модели.

Где «много in → несколько out» действительно другое вычисление — правила **над несколькими юнитами**
(продюсер получает 5 % от всего альбома, порог «после 1 млн стримов», минимум на релиз).
Процентные правила над суммой равны процентным правилам по каждому юниту (процент линеен),
поэтому они уже выражаются участием с одним процентом на каждом ISRC. Нелинейные (порог, потолок,
минимум) — новый смысл, которого нет ни в одной из моделей без кода; место для них — уровень
владельца/агрегата (там узел уже «много in»), M23 сознательно вне охвата.

### 7.3 «Визуализация каждого узла — для техников и для менеджеров»

Согласен без оговорок, и это ровно шаг 1 (явные рёбра). Два экрана из одних данных:

- трек-месяц: схема `net → … → получатели` с суммами и правилами на рёбрах, C-стоки красным,
  допущения пунктиром;
- владелец: слева входы (откуда, по каким трекам и псевдонимам), справа выходы (аванс, реклама,
  выплаты), в центре «к выплате».

Ничего из этого не требует настраиваемой топологии: рисуется граф фактических рёбер, а не схема.

### 7.4 Итог второго круга

Решение из §4 не меняется, уточняется список «что сделать, чтобы не бояться»:

1. шаг 1 (рёбра) — визуализация и формат;
2. `GET /allocations` / `GET /edges` с фильтрами по артистам, ISRC, месяцам, владельцам — выборки;
3. зарезервировать в дизайне поле `stage` у участий и правил лейбла (не вводить, пока не нужно);
4. записать как известный риск: правила с гранулярностью ниже ISRC-месяца потребуют нового
   измерения в ключе юнита.
