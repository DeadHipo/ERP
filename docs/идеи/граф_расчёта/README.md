# Граф расчёта: решение в коротком виде

Дата: 2026-11-04, после консилиума из пяти независимых рецензентов (`консилиум/итог.md`, решения Р1…Р24).
Статус: решение принято, в коде ничего не менялось, действующие документы не трогались.
Остальные файлы папки: `анализ.md` (аргументы, возражения), `хранение_и_поток_данных.md` (что хранится, как узлы
получают данные), `консилиум/` (пять отчётов и итог), **`демо/`** (входы узлов, 16 кейсов, прогнанных через настоящие
слои, и визуальное демо `index.html`), **`код/`** (эскиз кода каждого узла «в стиле графа», компилируется и
считает те же цифры, что слои), **`подходы/`** (13 других подходов к гибкости от четырёх архитекторов, оценка пятью
ролями и выбор одного: `подходы/итог.md`, §12 ниже). Там, где они расходятся с этим файлом, прав этот файл.

## 1. Ответ в пяти строках

1. **Граф — да, как формат результата и как таблица-дерево на карточке трека.** Каждый цент уже идёт по графу
   «корзина → корзина по правилу»; рёбра выводятся из уже имеющихся состояний расчёта, слои не меняются (Р1).
2. **Редактор графа и движок — нет.** Правила редактируются в формах; граф рисует их результат. Проводка остаётся
   в коде, но сводится в одно место (Р18) и получает имя `scheme` в ответе (Р19).
3. **Хранить ничего нового не надо.** Правила уже в базе, рёбра пересчитываются; снимок выплаты в шаге 1 не трогаем (Р13).
4. **Вместе с рёбрами делаем выборку:** `GET /allocations` по артистам, ISRC, месяцам, владельцу с экспортом CSV (Р16).
   Это исходный запрос «выборка по N артистам», и бухгалтеру он нужнее картинки.
5. **Топология не «закрыта навсегда», но гибкость нужна в одном месте.** Q11, C23, M58 уже держат деньги в C как
   допущения, и все они про долю лейбла после сплита. Шаг 2 — **«хвост как данные»** (§12): база и очерёдность на
   правиле саблейбла плюс исключения по ISRC/псевдониму, с периодом и документом; шаблоны проводки (Р20) остаются
   запасным вариантом, если порядок окажется разным на стороне артистов.

## 2. Аналогия с визуальным скриптингом Unity

| Unity | У нас | Делаем? |
|---|---|---|
| тип узла (C#-класс с портами) | функция слоя `(state, ctx) → state`; её корзина-источник объявлена в таблице `SOURCE_OF[kind]` | таблица из 6 строк вместо `NodeSpec` (Р10) |
| порты in/out | корзины: `net`, `scaledNet`, `row:<псевдоним>`, `pool`, `labelShare`; стоки `artist:<id>`, `ours`, `c:<причина>` | именуем явно |
| значения в инспекторе узла | строка правила в базе: процент, база, источник, период, документ | уже есть |
| graph asset (сохранённая схема) | один список `MASTER_LAYERS` (`scheme: master/standard`); второй для B17 | одна схема на источник; шаблоны — шаг 2 по ответу владельца |
| редактор графа | формы сплитов / участий / правил лейбла | редактор не пишем |
| play mode: значения текут по рёбрам | рёбра в `/tracks/:isrc/money` и `/explain`, таблица-дерево во вкладке «По слоям» | **шаг 1** |

Что берём: разделение «тип узла в коде / значения в данных / живые числа на рёбрах». Что не берём: сохранённые схемы
на объект и провода, которые тянет человек. **Чего у нас нет:** движка, шины событий, графа как объекта в памяти;
«провода» выводятся из состояния после расчёта.

## 3. Глоссарий (слово → смысл → где в коде)

- **Юнит** — ISRC + UPC + отчётный месяц + месяц продаж + строка лейбла одного аккаунта Believe (`MasterUnit`).
  **Трек-месяц** — несколько юнитов (второй UPC, поздние месяцы продаж). Слой работает на одном юните.
- **Корзина** — откуда берут деньги: поле состояния `net`, `scaledNet`, строка `rows[]` (`row:<id>`), `labelShare`;
  `pool` — виртуальная корзина пула артистов (сумма строк). Объектов-корзин в коде нет, это поля `UnitState`.
- **Сток** — конечная корзина: `artist:<id>` (псевдоним-получатель), `ours` (наша доля), `c:<причина>` (ждёт).
  Появляется только в `edgesOf`.
- **Остаток** — тот выход узла, который считается вычитанием `in − Σ остальных`, а не процентом. Ровно один на узел.
- **Квантование** — округление до 12 знаков half-up сразу после умножения (`q`, `pct` в `exact.ts`). Остаток не
  умножается никогда.
- **Shortfall (недостача)** — цель больше корзины: узел берёт сколько есть, цели масштабирует пропорционально,
  недостачу пишет в `state.shortfalls`. Деньги не создаются. На графе — подпись узла, не ребро.
- **B / C** — B: подтверждено документом, можно платить; C: ждёт, причина из `C_REASONS` (`split_unconfirmed`,
  `owner_unconfirmed`, `label_unmapped`, `assumption` …). **Допущение (assumption)** — решение совета без
  утверждённого документа; деньги ждут в C. **Q11** — открытый вопрос порядка «carve из доли лейбла / половина саблейбла».
- **canonical** — id псевдонима после слияний (`canonical(ctx, id)`); группировать только по нему.
- **Вид узла / слой / kind** — вид узла = функция (`split`, `carve:pool`); `Allocation.layer` — грубое имя слоя
  (`split` | `top` | `carve` | `sublabel`); `Allocation.kind` — вид аллокации (`row`, `top`, `artist_pool`,
  `artist_share`, `label_share`, `sublabel`). В рёбрах используется `kind` плюс `remainder` и `draw`.
- **`funded_from`** у участия — **вид участия** (`top` | `artist_pool` | `artist_share` | `label_share`): он
  определяет, какой узел его обработает и в каком порядке. Откуда ребро, задаёт `SOURCE_OF[kind]`
  (для `artist_share` — `from_artist_id`).
- **Дата правила** — первое число отчётного месяца (`reportDate(unit)`); все `valid_from`/`valid_to` приведены к началу
  месяца (M52); выбор по дате делает индекс модуля (`splits.index().at`, `participationsAt`).

## 4. Узлы и рёбра

| Узел | in | out | Правило |
|---|---|---|---|
| `net` | net юнита | `artist:*` (top) + остаток `scaledNet` | участие `top` |
| `scaledNet` | остаток | `row:*` + остаток `labelShare` | сплит |
| `row:X` | строка | `pool` (draw), `artist:*` (artist_share), остаток `artist:X` | участия `artist_pool`, `artist_share` |
| `pool` | Σ draw из строк | `artist:*` (artist_pool) | участие `artist_pool`; остатка нет, Σ in = Σ out |
| `labelShare` | остаток после сплита | `artist:*` (label_share), `artist:S` (sublabel), остаток `ours` или `c:*` | участие `label_share`, правило лейбла |
| периметр | net | одно ребро `net → c:no_isrc` / `c:unknown_pair` | — |

Ребро: `{ unitKey, from, to, amount, kind, ruleId, documentId, percent, base, category, reason }`. Категория только у
рёбер в `artist:*` (Р4). Порядок рёбер стабильный: слой → `to` → `ruleId` (Р8).

Инвариант: в узлах `net`, `scaledNet`, `labelShare`, `pool` Σ in = Σ out (стороны считаются независимо). Σ рёбер в
`artist:X` = аллокация X. Σ стоков = net юнита. Знак каждого ребра = знак юнита или 0.

## 5. Пример: юнит на 100.00 net

Правила: ремиксер R 10 % off-the-top; сплит A 40 / B 20; MC 5 % **от net** из пула; A&R 15 % **от доли лейбла**;
строка лейбла — саблейбл S, правило 50 % **от остатка доли лейбла**. Все документы утверждены, кроме Q11.

```
from        to          amount           kind         base    %    rule   category
net         artist:R    10.000000000000  top          100     10   p1     B
net         scaledNet   90.000000000000  remainder    —       —    —      —
scaledNet   row:A       36.000000000000  row          90      40   s1     —
scaledNet   row:B       18.000000000000  row          90      20   s1     —
scaledNet   labelShare  36.000000000000  remainder    —       —    —      —
row:A       pool         3.333333333333  draw         36      —    p2     —   (пропорционально 36:18)
row:B       pool         1.666666666667  draw         18      —    p2     —
pool        artist:MC    5.000000000000  artist_pool  100     5    p2     B
row:A       artist:A    32.666666666667  remainder    —       —    s1     B
row:B       artist:B    16.333333333333  remainder    —       —    s1     B
labelShare  artist:AR    5.400000000000  label_share  36      15   p3     C assumption (Q11)
labelShare  artist:S    15.300000000000  sublabel     30.6    50   r1     C assumption (Q11)
labelShare  ours        15.300000000000  remainder    —       —    —      ours
```

Проверка узлов: `net` 100 = 10 + 90; `scaledNet` 90 = 36 + 18 + 36; `row:A` 36 = 3.33… + 32.67…; `pool` 5 = 5;
`labelShare` 36 = 5.4 + 15.3 + 15.3. Ловушки: цель MC считается от net (5), а не от scaledNet (4.5); саблейбл берёт
50 % от 30.6 после A&R, а не от 36.

**Пример с недостачей.** net 100, сплит A 4 %, MC 5 % от net из пула. Пул = 4, цель 5: MC получает 4,
`row:A → pool` 4, `row:A → artist:A` 0 (остаток показывается нулём, Р6), подпись узла `pool`: shortfall p2 missing 1.
`scaledNet → labelShare` 96 → `ours` 96. Денег не создано: Σ стоков = 100.
**Отрицательный юнит** (возврат −100): те же рёбра со знаком минус, ни одного положительного.

Второй уровень — узел владельца: входы `artist:A` со всех юнитов (B), выходы аванс (тот же псевдоним), реклама,
выплаты; остаток — «к выплате» (≥ 0 на экране). Строится из баланса по `SOURCE_OF[kind]`, рёбра не нужны (Р14).

## 6. Чего не умеет слой

Слой видит один юнит. Всё, что считается **между юнитами** (фиксированная сумма в месяц с трека, потолок на релиз,
порог по стримам, минимум на период), — не слой, а отдельная чистая функция в `calculate()` после юнитов, по образцу
`ads.ts`; её результат — позиции на уровне владельца. Иначе сумма выплатится по разу на каждый юнит трек-месяца.
Правила по платформе, стране или релизу требуют нового измерения в ключе юнита (как строка лейбла в D-124).

## 10. Что не делаем и когда вернуться

Не делаем: редактор проводов, хранимые рёбра, общий движок узлов, `NodeSpec`, поле `from` в аллокации, рёбра в снимке.

C23, M58 и Q11 закрывает шаг 2 «хвост как данные» (§12), не шаблоны. Вернуться к шаблонам проводки (Р20), если:
разный порядок одинаковых узлов на стороне артистов на ≥ 2 ISRC (M44, Q1) или третье значение очерёдности хвоста;
к DSL или графу как данным — если владелец хочет собирать схему сам и схем больше шести (`подходы/итог.md` §8).

Что прототип подтвердил и что уточнил (подробно в `демо/01_как_собрать.md`):

- **Р1 подтверждён:** пары «состояние после split + финал» хватает на все 16 кейсов; слои не тронуты. Разбивка
  `carve` на четыре слоя (Р18) для рёбер не нужна, остаётся только ради «порядок в одном месте».
- **Р6 подтверждён:** нулевые рёбра и остатки рисуются, G31/G16 читаются. При `no_source_row` у получателя нет
  входящего ребра, только подпись: фронт рисует сток по подписи.
- **Р4 расширить:** у периметра `net → c:unknown_pair` — весь юнит, а не остаток доли лейбла.
- **Р5 уточнить:** ключ агрегации `from→to#kind#ruleId` дублируется при двух строках одного канонического
  псевдонима; добавить `documentId` (иначе при сумме склеятся B и C). Агрегированный `base` может разойтись на
  пико: Σq(base_i × p) ≠ q(Σbase × p).
- **Р7 подтверждён как проблема:** при слиянии псевдонимов `base` у artist_share не воспроизводит сумму
  (`carve.ts:99` берёт только первую строку). Нужна D-запись.
- **Р8 уточнить:** порядок «по узлу-источнику, остаток сразу за выходами», `perimeter` первым.
- **Ребро-остаток строки** `row:X → artist:X` несёт категорию строки, поэтому у него `ruleId` = id сплита и документ
  строки, а не null.
- **На ребре нужен `target`** (цель до масштабирования) или флаг недостачи: при shortfall `percent × base ≠ amount`
  (G22: 20 % от 100 → 10). На пико `capToBase` тоже даёт расхождение с формулой (строки 50 + 50 на 1 пико).
- **У draw нет процента и базы:** пико-остаток G34 виден только на draw и в остатке строки; правило распределения —
  подписью узла `pool`.
- Баланс `row:*` при пуле проверяет сам себя (draw считается вычитанием); реальная защита — «рёбра = аллокации» и
  «без пула draw = 0».

## 12. Другие подходы и выбранный шаг 2 (`подходы/`, 2026-11-04)

Вопрос «как быть гибче и лучше» прошёл второй круг: четыре независимых архитектора проработали 13 подходов
(водопад-таблица, наследование с исключениями, поправка к стоку, DSL, шаблоны Р20, точки замера, леджер,
корректировки, вилка вариантов, реестр видов, граф как данные, водопад доли лейбла), пять ролей (продакт,
разработчик, QA, джуниор, владелец-финансист) оценили каждый. Итог и таблица вердиктов — `подходы/итог.md`.

**Сходимость.** Четыре архитектора независимо пришли к одной идее: гибкость нужна не всей проводке, а **хвосту**
(доле лейбла после сплита), где и живут все открытые кейсы; на стороне артистов открытых кейсов нет.

**Выбрано: «хвост как данные» (слой `label-tail`).**
- У правила саблейбла два новых поля с периодом и документом: **база** (`remaining` как сейчас | `start` доля
  лейбла после сплита | `net`) и **очерёдность** (`after_carves` как сейчас | `before_carves`). `NULL` = владелец не
  ответил, Q11 остаётся допущением; явное значение с документом снимает допущение, в том числе явный ответ «как сейчас».
- Таблица исключений `labels.rule_exclusions (label_id, isrc | artist_id, период, документ)` — M58; ссылка на
  лейбл, не на строку правила.
- Один слой `label-tail` вместо `carve:label_share` + `sublabel` (это шаг 1б); саблейбл при базе ≠ `remaining`
  проходит `fund()` с недостачей (сегодня `carve.ts:158` считает без `fund`). Реклама (`ads.ts`) и сигналы
  (`reports.ts`) учитывают исключения.
- Умолчания воспроизводят сегодняшний расчёт до пико (дифференциальный тест на генераторе `exactness`, хэши на
  `data/real`). Ничего другого: ни схем, ни `seq`, ни DSL, ни редактора.

На юните §5: Q11-A 5.40 / 15.30 / 15.30 (A&R / S / нам), Q11-B 5.40 / 18.00 / 12.60, Q11-C 2.70 / 18.00 / 15.30
(база `remaining` у участия A&R, отдельная миграция), C23 5.40 / 25.00 / 5.60, M58 5.40 / 0 / 30.60. Деньги артистов
не меняются ни в одном варианте. Объём 4–4.5 дня после шага 1б; до кода — ответы владельца с этими цифрами,
