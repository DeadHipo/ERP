# Консилиум «арендатор как граница»: безопасность

Роль: инженер по безопасности приложений. Дата: 2026-11-05. Вход: `вопрос.md`, `CLAUDE.md`, бриф D-172,
`src/api/{app,audit,http,upload}.ts`, `routes/{sources,owners,index}.ts`, `shared/{pg-db,private-stores,files,
clickhouse,postgres,timing,errors}.ts`, `modules/sources/{service,loader,columnar}.ts`, `facade/{payouts,
payment-service}.ts`, фронт `api/client.ts`, `lib/{label,operator}.ts`. Код не менялся. Имён из данных здесь нет.

**Вердикт: B** (пара баз на арендатора + контрольная база), с тремя обязательными оговорками: арендатор
определяется только из сессии, имена баз генерирует сервер, у ClickHouse отдельный пользователь на арендатора.
Без них B по изоляции не лучше A.

---

## 1. Сравнение A / B / C по изоляции

| Критерий | A: `tenant_id` + WHERE | B: пара баз на арендатора | C: схема на арендатора (PG) + база (CH) |
|---|---|---|---|
| Где живёт граница | в каждом SQL (~40 таблиц, все репозитории, все представления CH) | в одном месте: выбор фасада по сессии | в `search_path` соединения + в каждом DDL |
| Одна забытая фильтрация | утечка строк чужого арендатора, тихая | невозможна: фасад видит одну базу | утечка через соединение пула, у которого не сброшен `search_path` после ошибки |
| Защита на уровне СУБД | только с RLS (`SET app.tenant` на каждое соединение; в CH row policy нужен пользователь на арендатора, то есть всё равно N пользователей) | `GRANT CONNECT` на базу: СУБД сама отказывает | PG: `GRANT USAGE ON SCHEMA`; но Drizzle `pgSchema('owners')` статичен, надо переписать на динамику |
| Уникальные ключи | **общие**: `source_files (account, reporting_month)` уникален на всех; счёт Believe, зарегистрированный у двух арендаторов, даёт 409 `duplicate_period` с именем файла и sha чужого арендатора (`loader.ts`), то есть сам ключ становится каналом утечки | внутри базы | внутри схемы |
| Advisory lock записей | один `pg_advisory_xact_lock(72011301)` на всех: арендаторы блокируют друг друга, DoS одной долгой загрузкой | lock локален базе: сериализация внутри арендатора, как и просит владелец | локален базе = общий на всех схем, как в A |
| ClickHouse | `rows` получает колонку, ключ партиции и проекция `units_by_label` переписываются; row policy per user | база = каталог, `believe_<t>` + `_stage` уже делает `createPrivateStores` | как B |
| SQL-инъекция в одном арендаторе | добирается до всех строк | PG: не добирается (кросс-базовых запросов нет без dblink). **CH: добирается**: один пользователь `erp` видит `believe_b.rows` из запроса в `believe_a` | как B |
| Удаление арендатора, бэкап, вынос | `DELETE WHERE` по 40 таблицам; в CH строки живут в партах до слияния; бэкап всех или никого | `DROP DATABASE` ×3 + каталог файлов; `pg_dump` одной базы; `BACKUP DATABASE` в CH | `DROP SCHEMA CASCADE` + CH; `pg_dump -n` |
| Правовой вынос (писатели, ФИО, D-090) | данные одного арендатора физически в тех же страницах и бэкапах, что чужие | отдельные файлы и дампы | PG общая база, дампы общие |
| Что переписывать | модули, фасад, golden, тесты, CH-миграции | `main.ts`, `connect-sources`, карта арендаторов, контрольная база, миграции циклом | Drizzle-схемы, миграции с подстановкой имён, пул |

Итог: A даёт самую слабую границу и самую большую поверхность ошибки; C наследует худшее от обоих
(динамические имена **и** общий пул). B структурно изолирует данные, но переносит весь риск в три точки, которые
ниже и описаны: кто выбирает фасад, кто придумывает имена баз, что видит общий пользователь ClickHouse.

## 2. Модель угроз

Активы: деньги владельцев (балансы, снимки выплат), отчёты Believe (75 млн строк, коммерческая тайна
дистрибьютора), выписки B17 с **юридическими именами авторов** (персональные данные, D-090), договоры (`fileRef`),
журнал аудита, учётные данные пользователей.

| T2 | Перебор идентификаторов чужого арендатора | то же | id это `newId()` (случайные), но при A они были бы в одной таблице | при B: 404 по построению; при A: `GET /owners/:id` чужого |

| T8 | Кража/перехват сессии | XSS, соседний сайт | план: cookie `httpOnly` + CSRF; альтернатива в отчёте senior (`localStorage`) слабее | действия от имени пользователя |
| T9 | Отключённый пользователь продолжает работать | бывший сотрудник арендатора | JWT без состояния; `disabled_at` проверяется только при входе, если не сделать иначе | доступ до истечения токена |
| T10 | Перебор пароля, DoS через scrypt | внешний | `POST /auth/login` без лимитов; scrypt с параметрами по умолчанию (N=16384) дёшев, с правильными (N=2^17, 128 МБ) каждая попытка стоит памяти | подбор; исчерпание памяти |

| T12 | Инсайдер: администратор системы читает деньги арендаторов | свой сотрудник | роль «все арендаторы» | нарушение обещания владельцу |

| T14 | Бэкап как канал | тот, кто получил архив | дампы с ФИО авторов B17 | утечка персональных данных |

## 3. Контроли по слоям

### 3.1. Транспорт и определение арендатора

- **Арендатор только из сессии.** После D-172 subject токена = `user_id`, из контрольной базы читается
  `tenant_id` пользователя; `req → facade` делается по этому `tenant_id`, и ни заголовок, ни путь, ни cookie
  `X-Tenant`, ни `?tenant=` не читаются вовсе (если пришли, игнорируются; в тесте: присутствие заголовка не меняет
  ответ). Пользователь принадлежит ровно одному арендатору; «один человек в двух арендаторах» = два логина
  (вопрос В1).
- **До пользователей (доверенная LAN).** Приемлем только один вариант: **процесс на арендатора** с собственным
  `.env` (`DB_DATABASE`, `CLICKHOUSE_DATABASE`, `ERP_DATA_DIR`, порт), как сегодня. Это ноль нового кода, изоляция
  процессом и ОС. Заголовок/поддомен для выбора арендатора в одном процессе **без** пользователей неприемлем даже в
  LAN: `X-Operator` уже показал, что клиентская самодекларация становится нормой и попадает в журнал. Если очень
  нужно, допустим поддомен, но только когда его выставляет обратный прокси (vhost → `X-Tenant`, клиентский
  заголовок стирается), и этот режим `TENANT_MODE=proxy` запрещён вместе с `AUTH_MODE=on`.
- **Cookie.** `__Host-erp_session` (`Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`), JWT HS256 через
  `node:crypto`, срок 12 ч, обновление скользящее не дольше 7 суток. Секрет `AUTH_SECRET` ≥ 32 байта, отказ старта при
  коротком или отсутствующем в `AUTH_MODE=on`. `Secure` требует TLS: в LAN терминировать на прокси, в dev
  `localhost` разрешён браузерами.
- **CSRF.** Каждая запись уже требует нестандартный заголовок `X-Operator` (в режиме `on` его значение
  игнорируется, а присутствие остаётся обязательным как CSRF-маркер) плюс проверка `Origin`/`Sec-Fetch-Site`
  (`same-origin`) на всех POST/PATCH; multipart-загрузки идут тем же путём. Этого достаточно: кросс-доменная форма не
  может поставить заголовок, `SameSite=Strict` не отправит cookie. Двойная cookie не нужна.
- **Отзыв сессии.** Таблица `auth.sessions (jti, user_id, issued_at, expires_at, revoked_at)` в контрольной базе; на
  каждый запрос проверка `jti` и `users.disabled_at` (кэш 30 с в памяти процесса). `PATCH /users/:id` с
  `disabled` отзывает все сессии; смена пароля тоже. `POST /auth/logout` ставит `revoked_at`.
- **Вход.** `crypto.scrypt` с явными параметрами (`N=2^15, r=8, p=1`, 64 байта, соль 16 байт; хранить
  `scrypt$N$r$p$salt$hash`); сравнение `timingSafeEqual`; одна и та же ошибка `401 invalid_credentials` для
  неизвестного логина и неверного пароля (на неизвестный логин всё равно считать scrypt от фиктивного хэша);
  лимит 5 попыток / мин на логин и 20 / мин на IP (в памяти, `429 too_many_attempts`, `Retry-After`); не более 4
  одновременных scrypt на процесс (семафор), остальные ждут.
- **Поверхность.** `/api/v1/openapi.json`, `/docs`, `/health` не содержат данных: можно оставить открытыми, но в
  `AUTH_MODE=on` `/docs` разумно закрыть за сессией (меньше подсказок сканеру). Заголовки
  `Cache-Control: no-store` на все `/api` ответы (балансы не должны оседать в прокси и истории браузера).

### 3.2. Авторизация

- `operations.ts`: поле `access` обязательно у каждой операции (`api-contract.test.ts` падает без него), значения
  как в брифе: `system` | `label` | `label_write` | `approve`, плюс новое **`control`** для `/tenants*`,
  `/users*`, `/auth/*`. Проверка в одном middleware по таблице, не в маршрутах.
- Матрица ролей (всё «внутри арендатора», кроме первой строки):

| Действие | system_admin | tenant_admin | label_manager |
|---|---|---|---|
| Создать арендатора, прогнать миграции, список арендаторов, пользователи арендатора | да | пользователи своего арендатора: да; остальное нет | нет |
| Читать деньги (балансы, ведомости, сверка) | **нет** (вопрос В2: break-glass) | все книги арендатора, «Все» | только `?label=` ∈ свои лейблы |
| Загрузить Believe / B17 под лейблом | нет | да | да, под своим лейблом |
| Зарегистрировать счёт Believe за лейблом | нет | да | нет |
| Создать владельца, псевдоним, трек, документ | нет | да | да |
| Утвердить документ, подтвердить сплит, кнопка выплаты, смена лейбла операции | нет | да | нет |
| Слияние владельцев / псевдонимов | нет | да (видимых одному лейблу); видимых двум лейблам тоже да, это один арендатор | нет |
| Удалить арендатора, выгрузить его целиком | да, по заявке tenant_admin, двухшагово | запросить | нет |

«Все» = все книги моего арендатора; роль `system_admin` в фасад арендатора не входит вообще (у неё нет
`tenant_id`), поэтому «Все» у неё не существует, а не «запрещено». Это и есть ответ на пункт 10 владельца.
- Чтение под чужим `?label=` → `403 label_forbidden`, чужой `labelId` в теле → тот же код; запись без лейбла там, где
  он нужен → `400 label_required` (как в брифе). Чужой **арендатор** никогда не даёт 403: его id не существуют в
  базе → `404`, чтобы не подтверждать существование.
- Лейбл в `localStorage` и `?label=` остаётся: после D-172 сервер проверяет `label ∈ user_labels`, значит ссылка с
  чужим `?label=` даёт 403, а не чужие данные. Арендатор на фронте не хранится никак.

### 3.3. Данные: контрольная база, имена, ClickHouse, пул

- **Контрольная база `erp_control`** (отдельная база, не схема в базе арендатора, чтобы дамп арендатора не нёс
  хэши паролей, а компрометация базы арендатора не давала учёток): `tenants (id, slug, display_name, pg_database,
  ch_database, ch_stage_database, ch_user, files_dir, status, created_at)`, `users (id, tenant_id NULL для
  system_admin, login UNIQUE (tenant_id, login), password_hash, role, disabled_at)`, `user_labels`, `sessions`,
  `control_audit (at, user_id, action, tenant_id, summary)`: действия администратора системы (создание арендатора,
  миграции, отключение пользователя) логируются здесь, потому что в базе арендатора им места нет.
- **Имена баз генерирует сервер**: `erp_t_<16 hex>` / `believe_t_<16 hex>` / `..._stage`, слаг арендатора только
  для показа. Тогда проверка `[a-z0-9_]+` становится защитой в глубину, а не единственной. Дополнительно: один
  regex для PG и CH, длина ≤ 63 байт с учётом суффикса `_stage`, идентификаторы в DDL в кавычках (`"erp_t_…"`,
  в CH backticks), `CREATE DATABASE` только из онбординга, никогда из запроса пользователя.
- **ClickHouse: пользователь на арендатора.** `CREATE USER erp_t_<hex> IDENTIFIED WITH sha256_password`,
  `GRANT SELECT, INSERT, ALTER, CREATE TABLE, DROP TABLE ON believe_t_<hex>.*` и на `_stage`; пароль в контрольной
  базе (зашифрован ключом `CONTROL_KEY` из `.env`). Тогда T4 закрыт самой СУБД: `SELECT FROM believe_other.rows`
  = `ACCESS_DENIED`. Пользователь `erp` с правами на всё остаётся только у миграций и онбординга. Для PostgreSQL
  достаточно одной прикладной роли без `CREATEDB`: `GRANT CONNECT` на базы арендаторов; кросс-базовых запросов
  нет. (Если захочется симметрии, роль на арендатора тоже дёшева.)
- **Две роли PostgreSQL**: `erp_migrate` (владелец баз, DDL, `CREATE DATABASE`) и `erp_app` (DML; на
  `audit.actions` только `INSERT, SELECT`; на `auth.users` только через контрольный сервис). Это даёт T15 и
  «append-only» не договорённостью, а грантом; миграция `REVOKE UPDATE, DELETE ON audit.actions FROM erp_app`.
- **Пул.** Карта `tenant_id → { pg pool (max 3), ch client (max_open_connections 4), facade }`, ленивое открытие,
  закрытие после 10 мин простоя, жёсткий потолок открытых арендаторов (например 20; дальше LRU-закрытие).
  `max_connections` PostgreSQL поднять до 200 или поставить pgbouncer в режиме transaction (advisory lock
  `pg_advisory_xact_lock` транзакционный, с transaction pooling совместим). Проверка при старте: Σ `max` всех пулов
  при полной карте < `max_connections` − 10.
- **Миграции циклом**: `migrate-postgres.sh` на каждую `pg_database` из `tenants`, `migrate-clickhouse.ts` с
  подстановкой имён (как `createPrivateStores` делает regex-заменой: лучше вынести подстановку в одну функцию и
  тестом проверить, что `believe_stage` заменяется раньше `believe`, иначе `believe_t_x_stage` ломается); версия
  схемы в `tenants.schema_version`; арендатор со старой версией не открывается (`503 tenant_migrating`), а не
  работает с кривой схемой.
- **Оптимистичный контроль** двух администраторов (из вопроса): `updated_at` в теле PATCH сплита/документа →
  `409 stale_record`. Это не безопасность, но закрывает «последний молча победил» и попадает в аудит обоих.

### 3.4. Файлы

- Каталог арендатора `data/tenants/<tenant_id>/{files/sources, tmp}`, `tenant_id` только из контрольной базы;
  `receiveUpload(req, tmpDir)` получает каталог из фасада арендатора, не из `opts`. Общий `tmp` недопустим: имя
  `${newId()}.upload` случайно, но `cleanup()` и аварийная очистка при рестарте работают по каталогу.
- Загрузка: лимит 2 ГиБ на файл и 16 ГиБ распаковки оставить, добавить **квоту на арендатора** (диск
  `files/sources` + партиции CH; `413 quota_exceeded` до `copyFile`) и не более одной загрузки в полёте на арендатора
  (уже так: очередь в `createBelieveLoader` живёт в сервисе арендатора) **и** не более двух на процесс (новый
  семафор над всеми арендаторами), чтобы два арендатора не держали четыре гигабайта в stage одновременно.
- Zip: `yauzl` сверяет объявленный размер с распакованным, одна запись, только `.csv`, имя записи не используется как
  путь: zip-бомба и traversal закрыты. Оставить. Добавить проверку magic-байтов (`PK\x03\x04`) по расширению
  `.zip`, чтобы `.csv.zip` с CSV внутри не падал в середине 500-й.
- `documents.fileRef` это свободная строка, сервер её никогда не открывает; так и оставить (ссылка на внешнее
  хранилище), в OpenAPI это описать явно, чтобы никто не сделал `GET /documents/:id/file` по ней без проверки пути.
- `storedPath` не покидает сервер (уже так) и не попадает в снимок выплаты (там `fileName`, `sha256`: так и
  оставить).

### 3.5. Журнал, ошибки, логи, платежи

- **Аудит арендатора** в его базе (`audit.actions`): `user_id` + `operator` (= логин) + `label_id` (R11) на каждой
  строке; `tenant_id` в строке не нужен, он равен базе, но в экспорте журнала ставится. Append-only грантом
  (3.3). Аудит администратора системы в `control_audit`.
- **Ошибки.** В `AUTH_MODE=on` 500 отдаёт `{ code: 'internal', message: 'Internal error', requestId }`; настоящее
  сообщение только в лог с тем же `requestId`. 4xx из `AppError` оставить как есть (они наши, без имён баз), но
  `ConflictError('duplicate_file' / 'duplicate_period')` внутри арендатора безвредны, а при A были бы утечкой: ещё
  один аргумент за B.
- **Логи.** Один формат строки `[tenant=<id> user=<id> req=<id>]`; `LOG_TIMINGS` печатает тот же префикс в корне
  дерева; в логах нет имён владельцев, псевдонимов, писателей, названий файлов (имя файла Believe содержит номер
  счёта: допустимо, ФИО нет). `console.error('audit record failed …', e)` печатает объект ошибки с `message`: хватит
  `e.message`. Проверка: тест прогоняет сценарий с писателем из фикстуры и ищет его имя в перехваченном stdout.
- **Платёжный стаб.** Интерфейс расширить сейчас, пока это стаб: `send({ tenantId, ownerId, amountCents,
  idempotencyKey: operationId })`; реализация на арендатора (реквизиты в контрольной базе, зашифрованы), общего
  клиента платёжного сервиса быть не должно. Ответ стаба не меняется.
- **Минимизация.** Писатели B17 (ФИО) живут только в базе арендатора, в контрольной базе ни одного имени; поиск
  `/search` не выходит за базу (B даёт даром); экспортов журнала с ФИО нет; срок хранения дампов (3.6). Правило D-090
  (никаких имён в коде, тестах, логах, документах) остаётся и переносится в `tests/no-personal-data` для логов.

### 3.6. Бэкапы и удаление

- Бэкап = на арендатора: `pg_dump -Fc erp_t_<hex>` + `BACKUP DATABASE believe_t_<hex> TO Disk(...)` + `tar`
  каталога файлов; контрольная база отдельно и чаще. Шифрование: ключ на арендатора (`age`), ключи в контрольной
  базе под `CONTROL_KEY`; удаление арендатора = `DROP DATABASE` ×3 + каталог + удаление ключа (старые дампы
  становятся нечитаемыми, crypto-shredding). Без ключа на арендатора «удалить арендатора» нельзя выполнить честно:
  его ФИО останутся в общих архивах до ротации.
- Восстановление одного арендатора не трогает других: ещё одно место, где A проигрывает.

второй `externalRef`); break-glass для sysadmin (T12; тест: без явного `support_grant` любой `label`-маршрут → 403);
бэкап с ключом на арендатора (T14; проверяется процедурой, не тестом).

Сквозной инвариант для e2e (`tenancy.spec.ts`, два seed-арендатора): пользователь A, залогиненный в браузере,
открывает каждый путь из `routes/paths.ts` с id сущностей B (владелец, псевдоним, трек, документ, операция, файл,
лейбл в `?label=`) → страница показывает «не найдено»/«нет доступа», ни один сетевой ответ не содержит строк из seed B
(проверка по перехвату `page.on('response')` на уникальные маркеры seed B: названия без ФИО). Загрузка файла из A
не меняет `GET /sources/files` в B. Контракт-тест вызывает каждую операцию под `tenant_admin` A **и** повторяет
все GET под `label_manager` A с `label=B` (403) и с id сущностей B (404).

## 5. Что требуется от D-172

Бриф D-172 написан для «один арендатор, много лейблов». При B он меняется так:

1. **Схема `auth` переезжает в контрольную базу** `erp_control`, а не в базу данных арендатора; `users.tenant_id`
   (NULL только у `system_admin`); уникальность `(tenant_id, login)`; `tenants`, `sessions`, `control_audit`.
   Миграции контрольной базы отдельным каталогом `migrations/control/`.
2. **Транспорт: cookie, не `localStorage`** (вариант senior §6 п. 12, подтверждаю; `__Host-` префикс, `Strict`).
   `AUTH_MODE=off` допустим только при `TENANT_MODE=single` (один процесс = одна пара баз, как сегодня); комбинация
   «много арендаторов в одном процессе без аутентификации» отказ старта.
3. **Middleware-цепочка**: `authenticate` (cookie → user, session) → `resolveTenant` (user.tenant_id → facade из
   карты, `404 tenant_unknown` / `503 tenant_migrating`) → `authorize` (по `access` операции и лейблам пользователя)
   → `operatorTrace` (operator = login, user_id в аудит) → маршруты. Маршруты получают фасад из `res.locals`, а не
   из замыкания `createV1Router(facade)`: роутер строится один раз, `buildOpenApiDocument()` один раз.
4. **Роли**: три как в брифе, но `label_admin` переименовать в `tenant_admin` (он администрирует арендатора, а не
   лейбл); «Все» = книги арендатора; `system_admin` без `label`-операций вовсе. Пункт «слияние владельцев, видимых
   двум лейблам, только `system_admin`» снимается: оба лейбла одного арендатора, это `tenant_admin`.
5. **Новые маршруты** класса `control`: `POST /tenants` (создаёт пару баз через `createPrivateStores`-путь с
   серверными именами, прогоняет миграции, создаёт пользователя CH, первого `tenant_admin`), `GET /tenants`,
   `POST /tenants/:id/disable`; `POST /users` создаёт пользователя **своего** арендатора для `tenant_admin`.
6. **Отзыв, лимиты, CSRF, генерик 500, `Cache-Control: no-store`**, две роли PostgreSQL и пользователь CH на
   арендатора: в тот же этап, иначе D-172 закрывает подмену личности, но не подмену арендатора.
7. **Тесты**: `tests/tenancy.test.ts` и `e2e/tenancy.spec.ts` из §4 входят в definition of done D-172; `api-contract`
   требует `access` у всех; `scripts/check-owner-scope.ts` без изменений.
8. **Существующие данные**: пара `erp`/`believe` регистрируется в `tenants` как первый арендатор (имена не по
   шаблону `_t_<hex>`: разрешить явные имена только в `tenants`, не в онбординге); первый `tenant_admin` через
   `scripts/create-user.ts --tenant`.
9. Оценка senior 4–5 дней относится к однопользовательскому D-172; с контрольной базой, картой арендаторов,
   миграциями циклом, грантами и двумя тестовыми файлами реалистично **8–10 дней**.

## 6. Вопросы владельцу продукта

- **В1. Один человек в двух арендаторах?** Предложение: нет, это два логина. Иначе нужна смена арендатора в сессии
  (кнопка, как переключатель лейбла), и это та самая клиентская подмена, которую хочется исключить.
- **В2. Может ли администратор системы видеть деньги арендатора?** Предложение: по умолчанию нет; «поддержка»
  только через явный, срочный (24 ч) грант от `tenant_admin`, записанный в оба журнала. Если владелец хочет
  «видеть всех» как сейчас, это другая роль с другим обещанием клиентам.
- **В3. Удаление арендатора**: право `system_admin` по заявке `tenant_admin`, с задержкой (7 дней) и бэкапом перед
  `DROP`? Нужен ли вынос данных (экспорт пары баз арендатору) и в каком формате.
- **В4. Шифрование бэкапов ключом на арендатора** (возможность честно «забыть» арендатора) или одним ключом
  сервера (проще, но его ФИО остаются в архивах до ротации)?
- **В5. Где терминируется TLS** в предполагаемом развёртывании (LAN за прокси, VPS)? От этого зависит `Secure` cookie
  и проверка `Origin`.
- **В6. Какие юридические основания и срок хранения** для имён авторов B17 у каждого арендатора: нужна ли дата
  «удалить писателей после N лет без выписок»?
- **В7. Платёжный сервис**: реквизиты на арендатора (у каждого свой счёт) или платит платформа? От этого зависит,
  где лежат секреты платёжного API.
- **В8. Доверенная LAN до D-172**: подтвердить «один процесс на арендатора» как единственный допустимый временный
  режим, без выбора арендатора заголовком.
