# Архитектор данных: арендатор как граница изоляции

Дата: 2026-11-05, вечер. Роль: архитектор данных. Вход: `вопрос.md`, код хранилищ (`connect-sources.ts`,
`private-stores.ts`, `pg-db.ts`, `postgres.ts`, `clickhouse.ts`, `facade/index.ts`, `main.ts`, `api/app.ts`,
`sources/{registry,columnar}.ts`), миграции, раннеры, compose, бриф D-169…D-172, D-121. Числа ниже сняты с
локального стека 2026-11-05 (PostgreSQL 18.6, ClickHouse 26.8.36.3) запросами только на чтение. Код не менялся.

## 1. Вердикт

**B: пара баз на арендатора плюс контрольная база `erp_control`.** Почему:

1. Изоляция структурная, а не по дисциплине: в A утечка это одна забытая `WHERE tenant_id` среди 130 ORM-запросов
   репозиториев, 9 сырых запросов и ~15 запросов ClickHouse; в B чужих данных в соединении физически нет.
2. Уже работает: `createPrivateStores` создаёт пару баз с настоящими миграциями, на ней живут 400+ тестов и e2e; на
   dev-стеке прямо сейчас 83 базы PostgreSQL и 236 баз ClickHouse (следы тестов) при 179 MiB RSS у PostgreSQL и
   1,36 GiB у ClickHouse: «N баз» это не гипотеза, а измеренное состояние.
3. Сериализация записей (advisory lock на базу), очереди загрузок (на экземпляр сервиса), `REPEATABLE READ` снимок,
   уникальные ключи (`source_files_scope`, `label_accounts.account`, sha256 файла) становятся «на арендатора» сами,
   без единой строки в модулях; в A их 32 уникальных индекса пришлось бы переписать, а общий lock заставил бы
   загрузку B17 одного арендатора (5–6 с под замком) ждать кнопку выплаты другого.
4. Бэкап, восстановление, перенос на другой сервер и удаление арендатора это операции над базой (`pg_dump`,
   `BACKUP DATABASE`, `DROP DATABASE`), а не хирургия по 27 таблицам и партициям.
5. Цена B это три вещи, и все три решаемы без модулей: карта пулов с ленивым открытием и закрытием по простою
   (бюджет соединений), цикл миграций с журналом и допуском отстающих арендаторов, обзор «все арендаторы» без денег.
   C (схема на арендатора) берёт издержки A в коде (динамические `pgSchema`, 7 схем × N) и издержки B в миграциях,
   выигрывая только один пул, который B получает через PgBouncer без кода. C отклоняю.

Один уточняющий факт в пользу B, которого нет в `вопрос.md`: **клиент ClickHouse может быть один на всех.** Всё в
`columnar.ts` обращается к таблицам с префиксом базы (`${DB}.rows`, `${STAGE_DB}.rows_<id>`, в том числе
`ch.insert({ table })`); опция `database` клиента задаёт только умолчание. Значит, под B «N пулов» это только
N пулов PostgreSQL; ClickHouse даёт один HTTP-клиент на процесс (10 keep-alive соединений) и N × 2 баз-каталогов.

## 2. Модель контрольной базы

Отдельная база `erp_control` (не схема в `erp`): у неё свой `pg_dump`, свои миграции `migrations/control/NNNN_*.sql`
со своим `public.schema_migrations`, и ни один арендатор её не видит. Тот же раннер, другой каталог и другая база.
Пул: `max: 2`. Всё, что про деньги, остаётся в базах арендаторов; контрольная база знает «кто, куда, в каком
состоянии».

```sql
CREATE SCHEMA control;

-- Организация-владелец одного или нескольких лейблов. Имена баз хранятся явно: соглашение erp_<slug> это умолчание
-- для новых арендаторов, а не инвариант (арендатор №1 живёт в erp / believe как есть).
CREATE TABLE control.tenants (
    id                    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    slug                  text NOT NULL UNIQUE CHECK (slug ~ '^[a-z][a-z0-9_]{1,30}$'),
    name                  text NOT NULL,
    status                text NOT NULL DEFAULT 'creating'
                          CHECK (status IN ('creating','active','suspended','deleting','deleted')),
    pg_database           text NOT NULL UNIQUE,
    ch_database           text NOT NULL UNIQUE,
    ch_stage_database     text NOT NULL UNIQUE,
    files_dir             text NOT NULL,            -- data/files/<slug>: sources/, publishing/, tmp/
    payout_threshold_cents integer NOT NULL DEFAULT 10000,  -- сегодня PAYOUT_THRESHOLD_CENTS из env: становится настройкой арендатора
    settings              jsonb NOT NULL DEFAULT '{}',      -- валюта, часовой пояс отчётов и т. п., без денег
    created_by            uuid NOT NULL REFERENCES control.users (id),
    created_at            timestamptz NOT NULL DEFAULT now(),
    suspended_at          timestamptz,
    deleted_at            timestamptz
);

-- Пользователь существует до выбора арендатора: вход происходит раньше, чем известна база. Поэтому auth из брифа
-- D-172 переезжает сюда целиком.
CREATE TABLE control.users (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    login           text NOT NULL UNIQUE,
    password_hash   text NOT NULL,
    is_system_admin boolean NOT NULL DEFAULT false,
    created_at      timestamptz NOT NULL DEFAULT now(),
    disabled_at     timestamptz
);

-- Членство с ролью внутри арендатора. system_admin не членство, а флаг пользователя: он видит все арендаторы,
-- но без кнопок денег (решение овнера №10).
CREATE TABLE control.memberships (
    user_id     uuid NOT NULL REFERENCES control.users (id),
    tenant_id   uuid NOT NULL REFERENCES control.tenants (id),
    role        text NOT NULL CHECK (role IN ('tenant_admin','label_manager')),
    created_by  uuid NOT NULL REFERENCES control.users (id),
    created_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, tenant_id)
);

-- Лейблы менеджера. label_id ссылается на labels.labels в базе арендатора: мягкая ссылка, как между модулями
-- (D-121); фасад арендатора проверяет, что лейбл существует.
CREATE TABLE control.member_labels (
    user_id     uuid NOT NULL,
    tenant_id   uuid NOT NULL,
    label_id    text NOT NULL,
    PRIMARY KEY (user_id, tenant_id, label_id),
    FOREIGN KEY (user_id, tenant_id) REFERENCES control.memberships (user_id, tenant_id) ON DELETE CASCADE
);

-- Журнал действий над арендаторами (создан, приостановлен, мигрирован, удалён): это аудит контрольного уровня,
-- audit.actions внутри арендатора его не заменяет.
CREATE TABLE control.tenant_events (
    id          bigserial PRIMARY KEY,
    tenant_id   uuid NOT NULL REFERENCES control.tenants (id),
    kind        text NOT NULL,             -- created | migrated | suspended | resumed | deleting | deleted | failed
    detail      jsonb NOT NULL DEFAULT '{}',
    by_user     uuid REFERENCES control.users (id),   -- NULL = раннер миграций
    at          timestamptz NOT NULL DEFAULT now()
);

-- Журнал прогонов миграций по арендаторам. Истина о версии остаётся в schema_migrations каждой базы; здесь только
-- «когда, что, чем кончилось», чтобы видеть отстающих одним запросом.
CREATE TABLE control.migration_runs (
    id          bigserial PRIMARY KEY,
    tenant_id   uuid REFERENCES control.tenants (id),  -- NULL = сама контрольная база
    store       text NOT NULL CHECK (store IN ('postgres','clickhouse')),
    to_version  integer NOT NULL,
    ok          boolean NOT NULL,
    error       text,
    started_at  timestamptz NOT NULL,
    finished_at timestamptz NOT NULL
);
```

Что сознательно не хранится в контрольной базе: деньги, владельцы, псевдонимы, ISRC, файлы. Статистика для обзора
(§4, «обзор») это производная таблица `control.tenant_stats`, если понадобится, и она перестраивается.

Идентификация арендатора в запросе: после D-172 из токена (`tenant` claim: выбран при входе, при одном членстве
неявно, при нескольких `POST /auth/tenant`); до D-172 заголовок `X-Tenant: <slug>` с умолчанием `DEFAULT_TENANT` из
`.env` (= арендатор №1), чтобы скрипты, контракт-тест и e2e не менялись.

## 3. Создание арендатора и миграции

### 3.1. Создание: `createPrivateStores` как production-путь, но после трёх правок

Сегодняшняя функция смешивает четыре вещи: создание баз, прогон миграций, помощники тестов (`reset`,
`resetModules`) и `drop`. Для production нужно вынести ядро `provisionStores({ pgName, chName, chStageName })`,
которым пользуются и тесты, и `createTenant`. Три правки обязательны:

1. **Миграции без журнала.** `createPrivateStores` выполняет файлы `migrations/postgres/*.sql` и
   `migrations/clickhouse/*.sql` напрямую (`pg.pool.query(migration)`, `ch.command`) и **не пишет
   `schema_migrations`**. Арендатор, созданный так, для раннера выглядит немигрированным, и следующий прогон
   попытается применить все 14 файлов заново; большинство идемпотентно (`IF NOT EXISTS`), но `0013` (`CREATE
   MATERIALIZED VIEW IF NOT EXISTS`) и `0003 MATERIALIZE PROJECTION` в ClickHouse сделают работу повторно, а любой
   будущий неидемпотентный файл упадёт. Решение: один TypeScript-раннер `src/shared/migrate.ts` с теми же правилами,
   что у bash-скрипта (один файл = одна транзакция с строкой `schema_migrations`, sha256, запрет правки применённого,
   запрет версии ниже применённой), и функция `renameClickHouseSql(sql, names)` (сегодняшняя подмена
   `\bbelieve\b` → имя базы из `private-stores.ts`, в одном месте). И `createPrivateStores`, и `createTenant`, и
   compose-сервис зовут его. Побочный выигрыш: тесты начинают проверять настоящий путь миграции, а не его копию.
2. **Имена и права.** Имя из `slug`: `erp_<slug>`, `believe_<slug>`, `believe_<slug>_stage`; уникальность имён
   держит контрольная база (`UNIQUE`), а не `CREATE DATABASE` (его ошибка приходит после того, как строка уже
   создана). В production роль приложения получает `CREATEDB`, не суперпользователя (в контейнере `erp` сегодня
   суперпользователь, потому что `POSTGRES_USER`).
3. **Размер пула.** Тесты открывают `max: 4` плюс административный `max: 1`. Для арендатора: пул открывается не при
   создании, а при первом запросе (§4), `TENANT_POOL_MAX` по умолчанию 4: все записи сериализованы одним замком,
   `calculate()` читает одним соединением снимка, а параллельные чтения внутри снимка и так стоят в очереди
   `queued()`; четырёх хватает на «две вкладки и загрузка».

Порядок создания (всё под одной записью в `tenant_events`, со статусом `creating` → `active`):

1. `INSERT control.tenants (status = 'creating')` в транзакции контрольной базы: имена заняты.
2. `CREATE DATABASE erp_<slug>` (вне транзакции: PostgreSQL не умеет `CREATE DATABASE` внутри неё), миграции
   PostgreSQL через раннер (с журналом), затем `CREATE DATABASE IF NOT EXISTS believe_<slug>`, `…_stage`, миграции
   ClickHouse через раннер.
3. Каталог файлов `data/files/<slug>/{sources,publishing,tmp}`.
4. `status = 'active'`, событие `created`. Падение на любом шаге оставляет `creating`: отдельная команда
   `tenants:repair` либо доводит (раннер идемпотентен), либо удаляет остатки по именам из строки. Пока строка в
   `creating`, карта фасадов такого арендатора не открывает (503 `tenant_not_ready`).

Стоимость одного пустого арендатора, измеренная по следам тестов: PostgreSQL 7,6–10,2 MB (каталог шаблона 7,7 MB +
27 таблиц, 32 уникальных индекса, пустое материализованное представление), ClickHouse 2 базы × 9 объектов (1
`MergeTree` `rows` с проекцией, 7 представлений, `schema_migrations`) в килобайтах; создание на dev-стеке
занимает около секунды на пару (так работает каждый тестовый файл).

### 3.2. Миграции по N арендаторам

Один прогон `scripts/migrate-all.ts` (заменяет два compose-сервиса одним `migrate` на образе node с
подмонтированными `scripts/`, `migrations/`, `src/shared/`):

1. Контрольная база: создать, если нет; её миграции первыми (цикл читает её таблицы).
2. Арендаторы со статусом `active` и `suspended` по `created_at` (арендатор №1 первым), для каждого PostgreSQL,
   потом ClickHouse, как в сегодняшнем compose. Каждый результат в `control.migration_runs`.
3. Падение посередине: **остановиться на этом арендаторе, остальных не трогать, выйти с ненулевым кодом**, статус
   арендатора не менять (это не его вина). Внутри PostgreSQL файл и строка журнала одна транзакция, половинок нет;
   в ClickHouse DDL не транзакционен, поэтому правило «каждая команда идемпотентна» остаётся законом, повторный
   прогон доделывает.
4. **Приложение не падает из-за отстающего арендатора.** При открытии фасада карта сравнивает `max(version)` в
   `schema_migrations` обеих баз с версией кода (список файлов миграций) и при расхождении отвечает 503
   `tenant_migrating` для этого арендатора; остальные работают. Это главное, что отличает «миграции × N» от
   «миграции × 1»: частичный успех должен быть нормальным состоянием, а не аварией.
5. Арендаторы независимы, поэтому цикл можно вести с параллелизмом K (по умолчанию 1, флаг `--parallel 4`);
   единственный общий ресурс серверы, и PostgreSQL ограничен тремя воркерами autovacuum и `max_worker_processes =
   8`, ClickHouse `background_pool_size = 16` на слияния.

Время: 14 файлов PostgreSQL на пустой базе ~1 с, 3 файла ClickHouse ~0,5 с; **схемная** миграция по 100
арендаторам ≈ 3–5 мин последовательно. **Миграция данных** (вроде `0013`: материализованное представление по
1,16 млн строк B17, или `MATERIALIZE PROJECTION` по 75,7 млн строк, 9 с на нашем объёме) масштабируется объёмом
арендаторов, а не их числом: у 100 арендаторов нашего размера это полчаса, у 100 обычных (в 10 раз меньше) минуты.
Для них параллелизм и окно обслуживания; раннер и так пишет журнал на каждого.

Запрет двух раннеров одновременно (сегодня «не параллелить») переносится в `pg_advisory_lock` на контрольной базе:
второй прогон завершается сразу с сообщением.

## 4. Соединения, ClickHouse, бэкапы, удаление

### 4.1. Бюджет соединений PostgreSQL

Факты: `max_connections = 100`, `superuser_reserved_connections = 3` (97 доступно), сегодня 11 сессий. Пул `pg`
открывает соединения лениво и закрывает простаивающие через `idleTimeoutMillis` (10 с по умолчанию): пул
арендатора, которым никто не пользуется, через 10 с держит **ноль** соединений без всякого кода. Ограничение не «N
× max», а «одновременно активные арендаторы × всплеск».

| Арендаторов | Пулов max 4 + control 2 + раннер 1 | При `max_connections = 100` | Что нужно |
|---|---|---|---|
| 10 | ≤ 43 при всех активных | помещается | ничего |
| 100 | ≤ 403 при всех активных; реально активны ≤ 20 → ≤ 83 | помещается, пока активны ≤ 23 | карта с LRU и закрытием по простою (обязательна); `max_connections = 300` для запаса (один backend PostgreSQL ≈ 5–10 MB RSS, 300 × 10 MB = 3 GB в худшем случае) |
| 1000 | ≤ 4003 | нет | PgBouncer в transaction-режиме (совместим с кодом: замок `pg_advisory_xact_lock` и `REPEATABLE READ` живут внутри транзакции на одном серверном соединении; `SET` сессии код не использует), или шардирование арендаторов по серверам (§6) |

Карта `tenant → { pg, db, sources, facade, router, refs, lastUsed }`: открывается при первом запросе, `refs`
считает запросы в полёте (загрузка B17 или кнопка выплаты не должны увидеть `pool.end()` под собой), по таймеру
закрывается всё с `refs = 0` и `lastUsed` старше `TENANT_IDLE_MS` (15 мин), плюс верхняя граница `TENANT_MAX_OPEN`
(LRU). `express` получает диспетчер: middleware определяет арендатора, берёт из карты его `router` (сегодняшний
`createV1Router(facade)` строится один раз на арендатора и кэшируется вместе с фасадом), `operatorTrace(facade)`
тоже на арендатора. Контрактный тест и фасад не меняются.

ClickHouse: один клиент на процесс (§1), `max_open_connections = 10`; сервер `max_connections = 4096`,
`max_concurrent_queries = 1000`. Не ограничение до сотен одновременно считающих арендаторов.

### 4.2. Стоимость N баз ClickHouse с одинаковой схемой

База в ClickHouse (engine Atomic) это каталог с метаданными; стоимость определяют **куски (parts)**, а не базы.
Измерено на нашей `believe.rows`: 75,7 млн строк, 1,63 GiB на диске (~23 байта на строку), 47 партиций (месяц ×
файл), 138 активных кусков, первичный индекс в памяти 205 KiB (≈1,5 KiB на кусок), метки 707 KiB, проекция
`units_by_label` 20 MiB. Весь сервер: 495 активных кусков, 236 баз, 885 таблиц, 1,36 GiB resident (большая часть
это системные логи и кэши, `MemoryTracking` 604 MB).

| Арендаторов | Баз | Кусков (50 файлов × 3 куска) | Память на индексы кусков | Диск при нашем объёме / при 10× меньшем | Оценка |
|---|---|---|---|---|---|
| 10 | 21 | ~1 500 | ~2 MB | 16 GB / 1,6 GB | ничего не меняется |
| 100 | 201 | ~15 000 | ~25 MB | 163 GB / 16 GB | норма; `max_part_num_to_warn = 100 000`, `max_database_num_to_warn = 1 000` далеко |
| 1000 | 2 001 | ~150 000 | ~250 MB | 1,6 TB / 160 GB | предупреждения сервера (баз > 1000, кусков > 100 000), загрузка метаданных при старте минуты, `system.parts` медленный; слияния делят один пул из 16 потоков; здесь либо шардирование по серверам, либо общая таблица строк (§6) |

Слияния: `MergeTree` сливает куски внутри партиции; у нас партиция = один файл с 1–5 кусками после загрузки, так
что фоновых слияний почти нет (`BackgroundMergesAndMutationsPoolTask = 0` в момент снятия). N баз не добавляют
фоновой работы, пока в них не пишут. Кэши меток и несжатых блоков общие на сервер (по 3,8 GiB верхней границы),
заполняются по требованию: холодный арендатор ничего не занимает. Память запроса считается на запрос, не на базу.

Stage-базы: `believe_<slug>_stage` держит таблицы только во время загрузки; на dev-стеке висят две забытые
стадии по 200 000 строк (`believe_t_22e2147184_stage`, `believe_t_7df2a3ce03`) — следы упавших тестов, а в
production это сигнал для `tenants:repair`: стадия старше суток без записи `loading` в реестре удаляется.

### 4.3. Бэкапы

Арендатор целиком восстанавливается независимо от соседей, и это главный операционный аргумент B.

- PostgreSQL: `pg_dump -Fc erp_<slug>` на арендатора (431 MB у нас, из них 377 MB строки B17; у пустого 10 MB),
  `pg_dump -Fc erp_control` и `pg_dumpall --globals-only` (роли). Цикл по `control.tenants`.
- ClickHouse: `BACKUP DATABASE believe_<slug> TO Disk('backups', '<slug>/<дата>')` (нативный `BACKUP/RESTORE`, нужен
  диск `backups` в `config.d/ops.xml`; инкрементальные бэкапы `base_backup` поддерживаются). Стадии не бэкапятся.
- Файлы: `data/files/<slug>/` (оригиналы отчётов и выписок; снимок выплаты хранит их `sha256`).
- Порядок и согласованность: сначала PostgreSQL (реестр `source_files` это истина о том, какие файлы `loaded`),
  потом ClickHouse. После восстановления проверка на арендатора: для каждого `loaded` файла партиция существует и
  `file_totals.line_count` равен `source_files.line_count` (представление уже есть). Файл без партиции это не
  «меньше денег», а **молча пропавшие юниты**, поэтому проверка обязательна, а не желательна. Скрипт
  `scripts/verify-tenant.ts <slug>`; его же гонять после миграций данных.
- Под A всё это было бы «выгрузить строки одного `tenant_id` из 27 таблиц и `rows`» и восстановить без затирания
  соседей: выполнимо, но это отдельная программа, а не две штатные команды.

### 4.4. Удаление арендатора

Двухфазно, никогда одной кнопкой:

1. `suspended`: карта закрывает фасад и больше не открывает (503 `tenant_suspended`), входы членов отклоняются,
   данные целы. Это же состояние для «не оплатил» и для спора.
2. `deleting` → после срока хранения (решение овнера, §8) последний бэкап, затем `DROP DATABASE erp_<slug> WITH
   (FORCE)`, `DROP DATABASE believe_<slug> SYNC`, `DROP DATABASE believe_<slug>_stage SYNC`, удаление
   `data/files/<slug>/`, `status = 'deleted'`, `deleted_at`; строка в `control.tenants` и события остаются (имена баз
   заняты навсегда: `slug` повторно не выдаётся, иначе старый бэкап восстановится «в чужое» имя).

Под A удаление это `DELETE` по 27 таблицам в порядке ссылок плюс `ALTER TABLE rows DROP PARTITION` на каждый файл
(ключ партиции не содержит арендатора) — и ни одной гарантии, что в какой-то таблице не осталась строка.

## 5. Текущие данные как арендатор №1

Без копирования и без переименования:

```sql
INSERT INTO control.tenants (slug, name, status, pg_database, ch_database, ch_stage_database, files_dir, created_by)
VALUES ('<slug владельца>', '<название организации>', 'active', 'erp', 'believe', 'believe_stage',
        'data/files', <id первого системного администратора>);
```

Почему это работает: имена баз в контрольной базе явные (§2), `erp.public.schema_migrations` уже содержит 14 строк,
`believe.schema_migrations` 3 строки, так что цикл миграций видит арендатора №1 как любого другого; каталог файлов
остаётся `data/files/{sources,publishing}` (для новых арендаторов `data/files/<slug>/…`). `DEFAULT_TENANT=<slug>`
в `.env` делает его арендатором всех сегодняшних скриптов (`mvp:load`, `reconcile-erp`, `check-*`), тестов и e2e,
пока нет входа. Лейблы 0to8 и Echo8 остаются двумя книгами одного арендатора (D-168/D-169), владельцы и псевдонимы
общие внутри него.

Переименовать `erp → erp_<slug>` можно позже одной командой `ALTER DATABASE … RENAME TO` без подключений (и
`RENAME DATABASE` в ClickHouse для Atomic), но это косметика; делать не нужно. `erp_demo` (D-112, не поддерживается)
арендатором не регистрируется.

Второй арендатор из существующих данных (если Echo8 когда-нибудь станет отдельной организацией): это не перенос, а
новый арендатор с нуля, куда грузятся файлы счёта 1055956; строки «Echo8» внутри счёта 1052428 остаются историей
0to8 по R6 (решение овнера №8). Данные между арендаторами не делятся (§7, ISRC).

## 6. Где ломается и при каком масштабе

| Место | 10 арендаторов | 100 | 1000 |
|---|---|---|---|
| Соединения PostgreSQL | 43 из 97 | только с ленивой картой; `max_connections = 300` | PgBouncer или шарды |
| Миграции (схемные) | ~30 с | 3–5 мин, параллелизм 4 | часы без параллелизма; версия арендатора отстаёт от кода как нормальное состояние (503 на отстающего) |
| Миграции данных | минуты | полчаса при нашем объёме у всех | окно обслуживания или раскатка волнами |
| Каталог PostgreSQL | 100 MB | 1 GB пустых каталогов; autovacuum (3 воркера) запускает воркер каждые `naptime / N` = 0,6 с и обходит 100 почти пустых баз за минуты, достаточно для нашей частоты записи | 10 GB; `\l`, мониторинг и autovacuum заметно медленнее, воркеров на 1000 баз уже не хватает |
| ClickHouse | незаметно | 200 баз, 15 000 кусков: норма (dev-стек сейчас 236 баз) | предупреждения, старт минуты; общая таблица строк или шарды |
| Бэкапы | 10 дампов | 100 дампов за ночь, суммарно ≤ 50 GB | нужна очередь и инкременты |
| Обзор «все арендаторы» | цикл | цикл по статистике без денег | только из `tenant_stats` |
| Перенос владельца между арендаторами | экспорт/импорт | то же | то же |

Два способа, которыми B **не** ломается, а растёт:

- **Шардирование даром.** `control.tenants` получает `pg_host`, `ch_host`; арендатор переезжает на другой сервер
  бэкапом и восстановлением, код не меняется. A этого не умеет вовсе: общая таблица одна.
- **Гибрид для ClickHouse при 500+.** Если когда-нибудь кусков станет слишком много, строки Believe всех арендаторов
  сводятся в одну таблицу с колонкой `tenant_id`, а `believe_<slug>` остаются только для стадий. Чтение и так всегда
  идёт `file_id IN (loaded-файлы этого арендатора)`, то есть изоляция чтения держится на реестре PostgreSQL, а не
  на базе ClickHouse. Перенос строк это `ATTACH PARTITION FROM` на каждый файл (жёсткие ссылки, секунды) — ровно
  то, что загрузчик делает сегодня. Решение откладывается до реальной цифры, но путь есть.

Где B ломается принципиально, а не числом: **одна транзакция на два арендатора невозможна.** Перенос владельца,
псевдонима или каталога это экспорт и импорт с двумя журналами, а не `UPDATE`. По уточнению овнера это и не нужно
(между арендаторами общего нет), см. §7.

Честный список, где B хуже A: кросс-арендаторный запрос = цикл, `dblink`/`postgres_fdw` или `merge()` в ClickHouse;
дрейф версий схем между арендаторами (лечится проверкой при открытии фасада); исправление данных скриптом
гоняется N раз (тем же скриптом, циклом); в мониторинге N + 1 баз PostgreSQL и 2N + 1 баз ClickHouse; у
тестов появляется новый слой (карта, вытеснение, 503 отстающего, контрольная база), которого под A не было бы.

Обзор «все арендаторы»: что нужно и чего не нужно. Нужно системному администратору: список, статусы, пользователи,
последний вход, размеры (`pg_database_size` одним запросом по всем, `system.parts` по `database` одним запросом),
число загруженных файлов и дата последней загрузки, последняя выплата (дата, без суммы), версия схемы, последний
прогон миграций. Всё, кроме файлов и выплат, читается из каталогов серверов одним запросом; файлы и выплаты
собирает периодический сбор в `control.tenant_stats (tenant_id, files_loaded, last_load_at, last_payout_at,
owners, pg_bytes, ch_rows, collected_at)` раз в час. Денег в обзоре нет по решению овнера №10, и это хорошо: сводный
`calculate()` по всем арендаторам стоил бы Σ (6 с на наш объём) на каждый показ. Если когда-нибудь понадобится
кросс-арендаторный разрез строк Believe, ClickHouse читает все базы одним запросом: `SELECT _database, … FROM
merge(REGEXP('^believe_[a-z0-9_]+$'), '^rows$')`.

## 7. Что меняется в D-169…D-172

- **D-169 (книга по счёту файла): без изменений.** Книга, `source_files.label_id`, загрузка под лейблом, реклама по
  плательщику, B17 под лейблом, слои и охват — всё внутри базы арендатора. Два следствия, которые надо записать в
  D-запись как факты, а не как изменения: `labels.label_accounts.account` уникален **внутри арендатора**, то есть
  один номер счёта Believe может быть зарегистрирован в двух арендаторах (каталог со счётом продан; овнер №9 говорит
  «пока нет», механизм это допускает без кода); `source_files_sha` тоже на арендатора, то есть один файл могут
  загрузить два арендатора — это их право, перекрёстной проверки нет и быть не должно.
- **D-170 (ведомость, виды операций, `asOf`, импорт операций): без изменений.** Пути импорта и выгрузки под
  `data/files/<slug>/`.
- **D-171 (онбординг через UI): без изменений в модели**, но порядок шагов чек-листа начинается на уровень выше:
  «создать арендатора» (системный администратор) → «создать лейбл, зарегистрировать счёт» (администратор арендатора)
  → загрузки. История принадлежности ISRC (`0017_catalog.sql`) выводится из файлов **этого** арендатора.
- **D-172 (пользователи и роли): меняется.** Схема `auth` из базы арендатора переезжает в `erp_control`
  (`users`, `memberships`, `member_labels`), потому что вход происходит до выбора базы. Роли: `system_admin` флаг
  пользователя (все арендаторы: список, создание, приостановка, миграции, обзор без денег); `tenant_admin`
  членство (все лейблы арендатора, «Все» внутри арендатора, approve-операции); `label_manager` членство с
  `member_labels` (один или несколько лейблов). Токен несёт `user_id` и `tenant`; middleware арендатора стоит
  **перед** `authenticate` и `operatorTrace`. `audit.actions.user_id` остаётся в базе арендатора как мягкая ссылка на
  контрольную; `operator` по-прежнему логин. `scripts/create-user.ts` пишет в контрольную базу. `AUTH_MODE=off`
  работает только с `DEFAULT_TENANT`. Из брифа уходит «слияние владельцев, видимых двум лейблам, только
  `system_admin`» в формулировке про лейблы — это остаётся как есть, но «видимых двум арендаторам» не бывает.
- **Новая D-запись (граница арендатора) идёт между D-170 и D-172**: контрольная база и её миграции, единый
  TS-раннер с журналом (чинит и `createPrivateStores`), карта фасадов с ленивым открытием, `X-Tenant` /
  `DEFAULT_TENANT`, регистрация арендатора №1, `scripts/migrate-all.ts` и compose-сервис `migrate`, приостановка и
  удаление, `verify-tenant`. D-169 и D-170 от неё не зависят и идут первыми; D-172 зависит; D-171 удобнее после
  D-172 (чек-лист начинается с создания арендатора).
- **«Все» = все книги моего арендатора.** Бриф отдаёт «Все» только системному администратору «без кнопок денег».
  При границе-арендаторе «Все» внутри арендатора безвредно: это сумма книг одного владельца. Предлагаю отдать его и
  `tenant_admin` (кнопки денег по-прежнему закрыты под «Все», как в D-168); решение овнера, §8.

**Общий каталог ISRC между арендаторами: не нужен.** ISRC это глобальный идентификатор IFPI, и два арендатора могут
законно отчитываться одним ISRC (сборник, лицензия); уникальность между арендаторами не нужна и вредна. Поиск
«где этот ISRC» для системного администратора даёт один запрос `merge()` по ClickHouse (выше), таблица в
контрольной базе не нужна.

**ISRC переезжает из арендатора X в арендатор Y под B:**

1. Деньги не переезжают никогда. По R6 юниты файлов X остаются книгами X, включая месяцы после даты T, пока счёт X
   продолжает отчитывать этот ISRC (решение овнера: «нет передачи, есть два арендатора, чьи счета пересеклись»).
   Файлы, которые Y загрузит на свой счёт, дают книги Y.
2. Переезжает справочник: трек (ISRC, UPC), псевдонимы, владельцы с их документами (метаданные и копии файлов
   документов), действующие строки сплита и участия по этому ISRC. Это пакет экспорта `catalog-transfer.json`
   (той же природы, что снимок выплаты: самодостаточный, с `sha256` файлов), экспортируемый из X администратором X
   и импортируемый в Y администратором Y как **новые** записи с новыми id и пометкой `transferred_from
   (tenant_slug, исходный id, дата)` в заметке/аудите. Личные данные в пакете есть (имена владельцев), поэтому пакет
   живёт в `data/files/<slug>/transfers/`, а не в репозитории и не в логах.
3. В X ничего не удаляется: строки сплита и участия закрываются датой T (`valid_to = T`, правило начала месяца M52),
   чтобы история X оставалась пересчитываемой; документы и владельцы остаются (у них могла быть другая история).
4. Кто решает, что владелец в X и «тот же» владелец в Y одно лицо: никто на уровне системы; это два владельца в двух
   арендаторах. Если когда-нибудь потребуется единая личность (один человек, налоговые данные, выплаты из двух
   арендаторов), появится `control.persons` с внешним идентификатором и мягкие ссылки из `owners.owners` обоих
   арендаторов; не сейчас.

## 8. Решения для владельца продукта

1. **Подтвердить B** и порядок: D-169 → D-170 → граница арендатора (новая D) → D-172 → D-171.
2. **Арендатор №1:** название организации и `slug` (латиница, без личных данных); база `erp` / `believe` как есть,
   без переименования.
3. **«Все» внутри арендатора:** только `system_admin` (как в брифе) или также `tenant_admin` (предложение: да, без
   кнопок денег).
4. **Срок хранения приостановленного арендатора до удаления** (предложение: 90 дней) и кто вправе удалить (только
   `system_admin`, с последним бэкапом).
5. **Один файл Believe в двух арендаторах** и **один счёт Believe в двух арендаторах**: допускать молча (предложение)
   или показывать системному администратору сигнал в обзоре.
6. **Перенос ISRC между арендаторами:** нужен ли пакет экспорта/импорта в ближайшие этапы, или до первого случая
   (предложение: до первого случая; механизм описан в §7, код не пишется).
7. **Порог выплаты и прочие настройки на арендатора** (`payout_threshold_cents`, валюта) задаются при создании
   арендатора системным администратором или администратором арендатора?
8. **Регистрация арендатора:** только руками системного администратора (предложение на этот год) или
   самостоятельная регистрация с подтверждением.
9. **Бэкапы:** куда (диск сервера, S3), как часто (предложение: ночной `pg_dump` + `BACKUP DATABASE` на
   арендатора, инкрементально в будни, полный в воскресенье), срок хранения.
10. **Лимит на арендатора** на первом этапе: `TENANT_POOL_MAX = 4`, `TENANT_IDLE_MS = 15 мин`,
    `TENANT_MAX_OPEN = 20` — согласиться с умолчаниями или назвать свои.
