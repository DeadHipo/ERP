# Консилиум: арендатор как граница изоляции (вопрос и факты)

Дата: 2026-11-05, вечер. Статус: вопрос к ролям, не решение. Контекст: `../README.md`, `../бриф_для_агента.md`
(D-169…D-172, лейбл как книга), `../роли/`. Отчёты этого консилиума пишутся в эту папку, по файлу на роль.

## Уточнение владельца продукта (05.11, вечер, дословно по смыслу)

«Мы хорошо сделали калькулятор и вводные для него. Но думать шире: я как владелец прихожу, регистрирую свой лейбл
или даже два, задаю им саблейблы, если были, загружаю данные. Мои отчёты Believe никак не пересекаются с другими
отчётами, даже если два администратора ведут один лейбл параллельно. Мои псевдонимы и владельцы тоже не
пересекаются с чужими.»

То есть **граница изоляции это не лейбл, а арендатор** (организация, владелец одного или нескольких лейблов).
Внутри арендатора лейблы остаются книгами (D-168/D-169: 0to8 и Echo8 одного владельца делят людей и ISRC, книги
разные). Между арендаторами общего нет: ни файлов, ни владельцев, ни псевдонимов, ни документов, ни операций.
«Два администратора одного лейбла параллельно» это два пользователя одного арендатора: их записи не мешают друг
другу (сегодня все записи сериализованы одним advisory lock, загрузки сериализованы по модулю).

Прежний вывод «владельцы и псевдонимы общие» уточняется: **общие внутри арендатора, изолированы между арендаторами.**

## Факты о коде (2026-11-05)

- Хранилища открываются один раз из `.env`: `connectSources()` (`src/connect-sources.ts`) создаёт один пул
  PostgreSQL (`DB_DATABASE`) и один клиент ClickHouse (`CLICKHOUSE_DATABASE`, плюс `<name>_stage`); `openFacade({ db,
  sources, dataDir, payoutThresholdCents })` строит фасад над ними; `createApp(facade)` строит один Express с одним
  фасадом. Каталог данных (`main.ts <dir>`) хранит только исходные файлы и временные загрузки.
- **Набор данных уже переключается базой** (D-121): `DB_DATABASE` / `CLICKHOUSE_DATABASE`. Тесты создают приватные
  пары баз `erp_<name>` / `believe_<name>` / `believe_<name>_stage` с настоящими миграциями и удаляют их
  (`src/shared/private-stores.ts`, `createPrivateStores(name)`); e2e живёт на `erp_e2e` / `believe_e2e`. То есть
  «фасад над парой баз» уже рабочий путь, проверенный 400+ тестами.
- Миграции: PostgreSQL `scripts/migrate-postgres.sh` (psql, `schema_migrations`, на одну базу из `PGDATABASE`, не
  параллелится), ClickHouse `scripts/migrate-clickhouse.ts` (на одну базу из env, `CREATE DATABASE IF NOT EXISTS`).
  Compose запускает их как one-shot сервисы.
- Записи: один advisory lock `pg_advisory_xact_lock('erp-writes')` на базу сериализует все транзакции записи
  (`src/shared/pg-db.ts`); загрузки Believe и B17 сериализованы по модулю внутри процесса (D-034). Чтения:
  `db.snapshot()` REPEATABLE READ.
- Модули: одна база, схема на модуль (`owners.*`, `splits.*`, `labels.*`, `settlements.*`, `publishing.*`, `audit.*`,
  `ads.*`), реестр файлов `public.source_files`, строки в ClickHouse `believe.rows` (75,7 млн строк, партиция по
  месяцу × файлу). Внешних ключей между модулями нет (D-121). ClickHouse не транзакционен; загрузка = реестр
  PostgreSQL + партиции ClickHouse (D-108: неудача = `failed`).
- Идентификация: `X-Operator` строка на каждой записи, аудит в `audit.actions`. Пользователей, ролей, JWT нет
  (D-172 в брифе: схема `auth`, три роли, «Все» только администратору системы).
- Фронт: один SPA, оператор и лейбл в `localStorage` и URL (`?label=`), переключатель лейбла в шапке (D-168).
- Деньги: `calculate()` читает все модули в одном снимке и все `loaded` файлы; охват владельца и фильтры юнитов
  (D-161…D-165) сужают чтение, не меняя ответ. Пико-доллары, 12 знаков, слои чистые.

## Варианты

**A. Колонка `tenant_id` везде.** Каждая таблица модулей, реестр файлов и строки ClickHouse получают `tenant_id`;
каждый репозиторий фильтрует; фасад получает арендатора из запроса. Одна пара баз на всех. Плюс: одна миграция, один
обзор по всем арендаторам. Минус: ~40 таблиц и все SQL меняются; одна забытая фильтрация = утечка между
арендаторами; ClickHouse `rows` получает колонку и смену ключей; advisory lock общий на всех; тесты и golden
переписываются; производительность чтений зависит от индексов по `tenant_id`.

**B. Пара баз на арендатора.** `erp_<tenant>` + `believe_<tenant>` (+ `_stage`), ровно как приватные базы тестов.
Контрольная база `erp_control` (или схема `control` в одной из баз): арендаторы, пользователи, членство, роли, пары
баз. Сервер держит карту `tenant → { db, sources, facade }`, открывает лениво, закрывает по простою; middleware
определяет арендатора по пользователю (после D-172) или по заголовку / поддомену до него; `createV1Router` получает
фасад на запрос. Миграции прогоняются по всем базам арендаторов циклом (тот же runner). Плюс: изоляция структурная,
модули и фасад не меняются вовсе (D-169…D-171 как написаны), advisory lock и загрузки сериализуются внутри
арендатора, бэкап и удаление арендатора = базы. Минус: N пулов соединений (лимит `max_connections`), миграции × N,
обзор «все арендаторы» только циклом, ClickHouse: N баз с одинаковой схемой (дёшево, БД в ClickHouse это каталог).

**C. Схема на арендатора в одной базе PostgreSQL** (`t_<tenant>_owners` …) и база на арендатора в ClickHouse.
Плюс: один пул, одна база. Минус: все `pgSchema('owners')` Drizzle становятся динамическими, `search_path` на
соединение, миграции × N схем, DDL с подстановкой имён; изоляция слабее, чем у B, а кода больше.

Предварительное мнение сессии: **B**, потому что он уже существует в коде как «приватные базы», модули и фасад не
трогаются, а всё новое сосредоточено в трёх местах: контрольная база с пользователями (сливается с D-172),
карта арендаторов в сервере, миграции циклом. Консилиум должен это подтвердить или опровергнуть.

## Что меняется в брифе при B (гипотеза, проверить ролями)

- D-169…D-171 без изменений: лейбл как книга внутри арендатора.
- D-172 расширяется: контрольная база `control` (арендаторы, пользователи, членство с ролью, пары баз), регистрация
  арендатора = создание пары баз с миграциями (`createPrivateStores` как production-путь), вход → арендатор → фасад.
- Роли: администратор системы (все арендаторы: список, создание, миграции, без денег), администратор арендатора
  (все лейблы арендатора, «Все» внутри арендатора), менеджер лейбла (один лейбл). «Все» = «все книги моего
  арендатора», а не «все арендаторы».
- Текущие данные 0to8 + Echo8 = один арендатор (один владелец), база `erp` / `believe` как есть; регистрация
  арендатора переносит их имя в контрольную базу без копирования данных.
- Два администратора параллельно: ничего нового, advisory lock и сериализация загрузок уже внутри базы арендатора;
  нужен только оптимистичный контроль там, где два человека правят одну запись (сплит, документ): `updated_at` в
  теле PATCH или «последняя запись побеждает» с аудитом.
