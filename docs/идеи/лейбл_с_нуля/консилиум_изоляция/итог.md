## 1. Вердикт: вариант B, единогласно

**Пара баз на арендатора** (`erp_tenant_<slug>` в PostgreSQL, `believe_tenant_<slug>` и `_stage` в ClickHouse) плюс
контрольная база `erp_control` (арендаторы, позже пользователи и членство). Почему:

- Это уже существующий путь: приватные базы тестов и стенд e2e и есть «арендатор»; 400+ тестов и 37 сценариев e2e
  доказывают, что фасад над парой баз работает. Модули и фасад не знают, на какой базе живут.
- Изоляция структурная: нет `WHERE tenant_id`, который можно забыть; advisory lock записи и очереди загрузок уже
  живут в базе и в экземпляре сервиса, то есть на арендатора, без единой строки кода. Чужая загрузка не задерживает
  мою выплату.
- Владелец лейбла требует, чтобы «моё» было вещью: своя база и папка файлов, которые можно сохранить, выгрузить,
  восстановить и удалить отдельно. Колонка и фильтр для него недоказуемы при споре и уходе.
- A (колонка везде) меняет ~40 таблиц, все репозитории, ключ `believe.rows` и проекцию на 75,7 млн строк; C (схема на
  арендатора) ломает `pgSchema` Drizzle и `boundaries.test.ts`, не давая ничего сверх B.

Замеры на стенде: пара баз создаётся за 0,25–0,28 с; пустой арендатор это 8–10 MB PostgreSQL и килобайты ClickHouse;
`max_connections = 100`; клиент ClickHouse один на процесс (все имена в `columnar.ts` квалифицированы базой), растут
только пулы PostgreSQL: при пуле 4 на арендатора это ~23 одновременно активных арендатора на 100 соединений, 100
арендаторов требуют `max_connections = 300` и ленивую карту с закрытием по простою; PgBouncer или второй кластер
(`cluster_id` в контрольной базе) после ~50 одновременно активных. ClickHouse: стоимость определяют куски, не базы;
100 арендаторов это норма, 1000 это предупреждения сервера.

## 2. Три находки, которые нужно исправить до всего

1. **`createPrivateStores` не пишет `schema_migrations`** (ни PostgreSQL, ни ClickHouse): как production-путь он
   непригоден, следующий `migrate` применил бы всё заново. Нужен TS-runner PostgreSQL, зеркалящий
   `scripts/migrate-postgres.sh` (та же таблица, та же контрольная сумма без `\r`), и `provisionStores` как общее ядро
   для тестов, e2e и production.
2. **500 отдаёт `err.message`** (`api/http.ts`): с картой арендаторов это утечка имён баз. Константный текст плюс
   `requestId`, имена баз только в лог сервера.
3. **Имена баз только от сервера**, одна регулярка и лимит 63 байта (PostgreSQL молча обрезает идентификаторы:
   два длинных slug могли бы совпасть); арендатор никогда не берётся из заголовка клиента, когда есть пользователи.

На стенде 78 брошенных `erp_t_*` и 230 `believe_t_*` баз от тестов (ничего не удалялось): нужен `npm run
stores:clean` (dry run по умолчанию) и уборка в globalSetup vitest.

## 3. Как это устроено (по senior backend, с поправками остальных)

- `src/tenants/{types,static,pool,middleware,control,provision,connect}.ts`; модули и фасад её не импортируют
  (`boundaries.test.ts`). Карта `slug → { db, sources, facade, router }`, single-flight открытие, пул `max 4`, закрытие
  по простою 10 мин, один клиент ClickHouse на процесс.
- **Роутер на арендатора**, не фасад на запрос: `createV1Router(facade, opts)` кэшируется в записи арендатора; одиннадцать
  файлов маршрутов, `operatorTrace`, хук аудита и контракт-тест не меняются. Системный роутер (`/health`,
  `/openapi.json`, `/docs`, `/tenants`) вынесен над арендаторами.
- `main.ts`: с `DB_CONTROL_DATABASE` реестр из контрольной базы, без него статический арендатор `main` из
  `DB_DATABASE` / `CLICKHOUSE_DATABASE` (сегодняшнее поведение, e2e и частные стенды без правок).
- Контрольная база `erp_control` (отдельная база, не схема в `erp`): `control.tenants (slug, name, status
  provisioning|active|suspended|failed|deleted, pg_database, ch_database, ch_stage_database, data_dir, error, created_by)`,
  `control.tenant_events`; свои миграции `migrations/control/`. D-172 кладёт сюда `users`, `memberships (user_id, slug,
  role)`, `user_labels`.
- Provisioning: `INSERT provisioning` → `CREATE DATABASE` → runner PG с журналом → runner CH с переименованием
  `believe` → каталог `<dataDir>/<slug>/{files/sources,files/publishing,tmp}` → `active`; ошибка = откат баз, `failed`,
  повтор разрешён; slug не переиспользуется.
- Миграции: `scripts/migrate-tenants.ts` циклом по контрольной базе (control первой, арендаторы последовательно, PG потом
  CH), упавший арендатор не останавливает остальных, exit 1 со списком; сервер отвечает 503 `tenant_schema_outdated`
  отставшему и не падает целиком; никакой миграции «на лету».
- Скрипты: `connectTenant({ tenant: --tenant | ERP_TENANT })`, fallback на `DB_DATABASE`; скрипты D-169 писать сразу
  через него.
- Текущие данные = арендатор №1 одной строкой `register-tenant.ts --pg erp --ch believe --data-dir <repo>/data`: имена
  баз хранятся явно, ничего не копируется и не переименовывается (`stored_path` абсолютный). Проверка: `GET /overview`
  байт в байт как сегодня, `check-owner-scope` 0 differing. Echo8 остаётся книгой внутри этого арендатора.
- Два администратора одного арендатора: двойная выплата невозможна уже сейчас (баланс считается внутри транзакции
  под advisory lock), загрузки одного месяца разводят `serial` и уникальные индексы реестра, утверждение документа
  идемпотентно. Потерянное обновление закрывается **ожидаемым значением в теле** трёх денежных PATCH
  (`expectedCurrentSplitId`, `expectedLabelId`, `expectedRecoveryPercent` → 409 с текущим значением), без колонок
  `updated_at`; остальное «последний побеждает, оба в аудите».
- Удаление двухфазно: `suspended` (фасад закрыт, данные целы) → по сроку хранения бэкап (`pg_dump -Fc` + `BACKUP
  DATABASE` ClickHouse + папка файлов) → `DROP` ×3 + файлы, строка остаётся со статусом `deleted`. Файлы арендатора №1
  (`data_dir` указывает на корень) не удаляются никогда.
- Экспорт по кнопке администратора арендатора (владелец лейбла): все данные с контрольными суммами, ведомости и
  снимки выплат, журнал; требование воспроизводимости: импорт в пустой арендатор даёт те же балансы до цента. Это
  отдельный шаг после границы.

## 4. Роли и «Все» (поправка к ответу овнера №10)

Все семь ролей сходятся: **системный администратор не видит денег**. Он видит список арендаторов, статус, версию
схемы, размеры, пользователей, последнюю загрузку; деньги только через «войти как поддержка» по разрешению
администратора арендатора, на срок, по умолчанию чтение, в журнале арендатора. Следовательно **«Все» = все книги
моего арендатора и принадлежит администратору арендатора**, без кнопок денег. Роли: `system_admin` (глобальная, без
членства), `tenant_admin`, `label_manager` (членство с лейблами); «администратор лейбла» из брифа растворяется в
`tenant_admin`. Один человек у двух арендаторов: один логин, членство с ролью в каждом, явный переключатель; владелец
и псевдоним у двух арендаторов это две записи без связи, слияние через границу запрещено всем.

Безопасность, условия B: арендатор только из сессии после D-172 (до неё в системе ровно один арендатор, `X-Tenant`
принимают только скрипты, тесты и системный ключ `SYSTEM_ADMIN_KEY`); JWT в `__Host-` httpOnly cookie SameSite=Strict,
CSRF через обязательный `X-Operator` и проверку Origin, таблица сессий для отзыва, scrypt с явными параметрами, лимит
попыток входа; две роли PostgreSQL (`erp_admin` для provisioning и миграций с CREATEDB, `erp_app` для пулов без
UPDATE/DELETE на `audit.actions`); пользователь ClickHouse на арендатора с грантами на его базы; чужой id под своим
арендатором это 404, никогда 403 и никогда данные; порт 8123 только на 127.0.0.1; строка лога с `tenant` и
`operator`, `LOG_TIMINGS` с префиксом арендатора; платёжная заглушка получает `tenantId` и ключ идемпотентности.

## 6. Решения для овнера

1. Подтвердить B и порядок этапов 1 → 2 → 3 → 4 → 5.
2. «Все» переходит администратору арендатора; системный администратор без денег (поправка к ответу №10).
3. Slug и имя арендатора №1; Echo8 становится отдельным арендатором только когда у него свой администратор вне
   команды овнера (до этого книга внутри №1).
4. Арендаторов создаёт системный администратор по приглашению (без самостоятельной регистрации до третьего
   арендатора).
5. Один человек у двух арендаторов: один логин с двумя членствами (по умолчанию да).
6. Один счёт Believe или один файл в двух арендаторах: допускается молча (отчёты не пересекаются по условию) или запрет
   по контрольной таблице; по умолчанию допускается.
7. Срок хранения приостановленного арендатора до удаления (по умолчанию 90 дней); бэкапы куда и как часто.
8. Поддержка: механика «войти как поддержка» по разрешению со сроком (по умолчанию чтение).
9. Лимиты: `TENANT_POOL_MAX=4`, простой 10–15 мин, `max_connections=300` при второй десятке арендаторов.
10. Перенос каталога между арендаторами: пакет файлом руками, без кнопки, до первого случая.
