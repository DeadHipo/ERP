# Инструкция оркестратору: «лейбл с нуля» на чистом стеке

Для ИИ-агента (Claude Fable как оркестратор), которого запускают с нуля в ветке `feature/fable-002`. Текст цели для
`/goal` лежит рядом в `goal.md` и ссылается сюда. Эта инструкция дополняет `CLAUDE.md` репозитория, не заменяет его.

## 1. Что сделать

Пять этапов из `бриф_для_агента.md`, строго по порядку, каждый со своей D-записью и коммитами:

1. **Этап 1 «D-169»**: книга по счёту файла, загрузка под лейблом, реклама по плательщику, B17 под лейблом,
   `documents.label_id`, `audit.label_id`.
2. **Этап 2 «Граница арендатора»** (вариант A): таблица `organizations`, `org_id` на каждой строке, фильтр
   централизованно при открытии модулей, минимальный логин с JWT в cookie, организация только из токена, лейбл в каждом
   запросе, `/orgs` для системного администратора, константное 500.
3. **Этап 3 «D-172»**: роли и членство, слой способностей (CASL-подобный), «Все» у администратора организации,
   системный администратор без денег.
4. **Этап 4 «D-171»**: онбординг через UI: импорт сплитов с предпросмотром, «принять как допущение», чек-лист,
   история ISRC из файлов, релизы из экспорта.
5. **Этап 5 «D-170»**: виды операций, прощение, списание, `asOf`, выгрузка ведомости, замена B17.

Ответы владельца продукта на все ⚠ уже в брифе (разделы «Решения овнера» и «Ответы владельца продукта»). Что там
помечено «позже», не делать.

## 2. Главный запрет: модуль расчёта не трогать

Расчёт это `packages/backend/src/facade/calculation.ts`, `facade/layers/*` (включая `exact.ts`, `recoup.ts`,
`label-of-record.ts`), `facade/owner-scope.ts`, `facade/scope.ts` в части unit scope, математика `balance.ts`. Этапы
строятся **вокруг** него: новые поля юнита (`bookLabelId`), ключи книг, фильтры чтения, организация в репозиториях.
Ни одного нового умножения, ни одного изменения порядка слоёв. Тесты `tests/layers/*`, `tests/golden.test.ts`
(кроме добавления кейсов и регистрации счетов в фикстурах) и `tests/scope.test.ts` в части reach не правятся под
новые числа: если они краснеют, неправ код этапа, а не тест.

Единственное исключение, заранее разрешённое брифом: прощение аванса в `layers/recoup.ts` на этапе 5, со своим тестом.

После каждого этапа, когда данные заново загружены на чистый стек, сравнивать:

- **Должно совпасть точно** (это и есть «расчёт не тронут»): `overview.totals.all` и `byAccount`, и в каждой из
  54 строк `reconciliation` (ключ `source`, `account`, `month`) поля `A_received`, `B_notOurs`, `C_waiting`,
  `C_breakdown`, `ourShare`, `ourShareNoSplit`, `discrepancy` (0), `fileTotal`, `fileDiscrepancy`; `check-owner-scope` 0 differing; `total.earned/waiting/adsCharged/paid` каждого владельца в

- **Меняется по решению, и только так:** `byLabel` и `ourShareByLabel` строк сверки и `overview.totals.byLabel`: строка «Echo8» счёта 1052428 (2024-12…2025-07, 222 129,81 net)

## 4. Как работать: оркестратор и субагенты

Оркестратор (Fable) держит план, принимает решения, пишет D-записи, проверяет результат и коммитит. Работу
делегирует субагентам через `Agent`, выбирая модель под задачу:

| Задача | Модель | Агент |
|---|---|---|
| поиск по коду, чтение документов, сбор фактов из базы, подготовка списка файлов к правке | `sonnet` | `Explore` или `general-purpose`, только чтение |
| написание и правка кода, миграций, тестов; прогон тестов и починка | `opus` | `general-purpose`, в своей ветке файлов |
| ревью диффа этапа, независимая сверка с эталоном, проверка D-записи | `opus` или `fable` | `general-purpose`, только чтение |
| синтез, решения, спорные места, финальная проверка | сам оркестратор | |

Правила делегирования:

- Бриф субагенту пишется полным: цель, правила в силе (с номерами из брифа), точные имена таблиц, полей, файлов,
  кодов ошибок, тестов; что не трогать; критерий готовности. Субагент не читает эту переписку.
- Два пишущих субагента никогда не правят одни файлы одновременно. Поиск и чтение можно запускать параллельно
  (несколько `sonnet` сразу).
- Vitest запускать из `packages/backend` или `packages/frontend`, не через `-w @erp/backend` (зависает как watch).
- Каждый коммит проходит definition of done из `CLAUDE.md`: typecheck, lint, `REQUIRE_STACK=1 npm test`,
  `npm run build:client`, e2e для фронта, D-запись в 97 и строка в индексе 03, обновлённые `CLAUDE.md` папок.
- Результат субагента проверять, не пересказывать: прочитать дифф, прогнать тесты, сравнить числа.

## 5. Старт с чистого стека

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
npm ci && npm run migrate:pg
```

Затем загрузка как в рецепте 9 и D-111: лейблы и счета (на этапе 1 лейблы ещё без организации), отчёты Believe из
`context_data/ERP_data/believe` через `POST /sources/believe` (47 файлов, два счёта), справочники загрузчиком стадии 4
(`npm run mvp:load -w @erp/backend -- all --apply` по шагам), B17 через `load-b17.ts`, реклама шагом `ads`. После
загрузки сравнение с эталоном (раздел 3). Со второго этапа первым шагом создаётся организация и пользователь, и
загрузка идёт под ними.

## 6. Постоянные правила

- Никогда не `git push`; коммитить по завершении этапа или шага, прошедшего definition of done.
- Никаких имён авторов B17 и личных данных в коде, тестах, фикстурах, логах, документах (D-090).
- `context_data/` не менять; архитектурные документы `docs/01…09` не править, только 97 и `docs/agents/`.
- Решения ⚠ из индекса не менять без владельца; вопросы владельцу копить в D-записи (Open) и в конце этапа, не
  блокировать работу, если в брифе есть умолчание.
- Любое отклонение от брифа фиксировать в D-записи с причиной.

## 7. Готово, когда

Все пять этапов закоммичены с D-записями; эталон раздела 3 совпадает по инвариантным полям, а изменения книг ровно те,
что перечислены; `npm test`, e2e и lint зелёные; владелец продукта может с чистого стека создать организацию,
пользователя, два лейбла с саблейблами, загрузить отчёты, сплиты, документы, владельцев, выписку и увидеть ту же
ведомость, что в эталоне.
