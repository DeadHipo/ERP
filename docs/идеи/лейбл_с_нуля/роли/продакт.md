# Лейбл с нуля: взгляд продукта (2026-11-05)

Источники: `черновик.md`, `docs/идеи/разделение_по_лейблу/README.md` §1–3, 6, D-168, `context_data/разбор_01/*` (документы
владельца 05.11, данные), `packages/frontend/CLAUDE.md` (P1…P22). Код не менялся. Точка зрения: лейбл, который ведёт в ERP
свой бизнес, в том числе лейбл **не 0to8** (без истории, без скриптов стадии 4) и 0to8 с ноябрьской выплатой через две недели.

## 1. Вердикт в пять строк

1. Черновик правильно расставляет принадлежность данных (книга денег = счёт-получатель, R6; владельцы и сплиты глобальны;
   лейбл каталога = навигация), и этого менять не надо. Но он написан от схемы, а не от задачи лейбла: **ни один из десяти
   шагов сегодня не доводит новый лейбл до выплаты через UI**: сплиты грузятся только скриптом, документы по группе строк
   ставятся только скриптом, ведомости и даты среза нет, стартовых остатков нет.
2. Ближайший измеримый результат — не онбординг, а **ноябрьская ведомость 0to8 как контроль** (разбор владельца §3):
   книга по счёту 1052428, срез по отчёт 2026-09, выгрузка «владелец → к выплате» построчно против их ERP. Пока две
   ведомости не совпадут, кнопка выплаты в ERP разработчика никому не нужна. Это должно стать этапом 0, а не D-170.
3. **«Принять без документов» ≠ `assumption`.** Допущение держит деньги в C и не платится никогда; владелец, говоря «верно
   без документов», хочет *платить*. Нужен утверждённый документ-основание на группу строк (и, по ответу владельца, на
   владельца без договора). Без этого онбординг заканчивается на экране «ждёт: 730 владельцев, $1,26M».
4. Лишнее для ближайших этапов: `sublabel_id` в ClickHouse (черновик сам отказывается, верно), история принадлежности
   ISRC (`catalog.track_labels`): после R6 деньги не зависят от каталога, перенос Echo8 решён счётом; импорт релизов из
   экспорта Believe: нужен для контроля полноты, не для денег. Пользователи и JWT — последними, но «Все» уже сейчас
   стоит считать видом владельца системы, а не менеджера лейбла.
5. Порядок этапов переставить: 0) ведомость-контроль под 0to8; 1) онбординг через UI (загрузка под лейблом со счётом,
   сплиты из файла с предпросмотром, «принять без документов», чек-лист на P1); 2) договор-лейбл, B17 под лейблом,
   аудит; 3) пользователи и роли; 4) каталог и переносы вместе с отгрузкой треков.

## 3. Первый запуск нового лейбла (сценарий)

Лейбл «Третий» (условно), один менеджер, 40 артистов, один счёт Believe, два года отчётов, таблица сплитов в Excel,
договоры в папке. Цель: через час видеть, кому сколько к выплате.

1. Открывает ERP, вводит имя оператора. Шапка: лейблов нет → P17 «Создать лейбл»: название, юрлицо, счёт Believe
   (можно позже). После создания переключатель сам встаёт на «Третий» и запоминается.
2. P1 под «Третий» пуст и показывает чек-лист: лейбл ✓ → счёт → отчёты → нераспознанные строки → сплиты → владельцы →
   документы → к выплате. Каждый пункт — ссылка и счётчик.
3. P19: загружает zip отчётов. Счёт из файла не зарегистрирован → диалог «счёт 10xxxxx никому не принадлежит,
   зарегистрировать за «Третий»?» → да → загрузка идёт, строки ложатся. (Если счёт чужой — отказ с именем лейбла-владельца
   счёта только для владельца системы, менеджеру — «счёт занят».)
4. P1: A = C полностью (сплитов нет), «нераспознанных строк лейбла: 3». P21 `labelUnmapped`: две — его саблейблы
   (создать саблейбл + правило), одна — опечатка Believe (алиас own-лейбла).
5. P15 «Загрузить сплиты из файла»: скачивает шаблон, заполняет (ISRC, псевдоним, %, с какого месяца, владелец),
   загружает → предпросмотр: 180 строк, 42 псевдонима (3 похожи на существующие в системе — показать, дать выбрать «тот
   же / новый», как `DuplicateDialog`), 2 ISRC не встречаются в его отчётах (предупреждение), 1 строка с суммой 90 %
   (ошибка, строку пропустить или остановить файл — выбор). Применить.
6. Там же: «принять строки как верные без документов» → создаётся один утверждённый документ-основание «решение лейбла
   «Третий» от 05.11» на все строки файла, подпись оператора. Деньги строк уходят из C `split_unconfirmed` в B.
7. P11 дубликаты/без владельца: 42 псевдонима → владельцы (из колонки файла большинство уже созданы; остальным —
   «назначить»). P9 показывает 40 владельцев, все `owner_unconfirmed`.
8. Договоры: P13 «создать договор» на владельца с файлом, утвердить. Для тех, у кого договора нет, но лейбл платит —
   ответ владельца (вопрос 5 ниже): либо документ «решение лейбла» подтверждает владельца, либо он остаётся в C.
9. Стартовые остатки: если лейбл уже платил артистам до ERP — одна операция «стартовый остаток на дату» на владельца
   (сегодня это `credit`/`deduction` с документом; хочется явного смысла и массового ввода из файла), иначе ERP предложит
   заплатить всё с начала времён.
10. P9 «Выплаты» под «Третий»: к выплате, ворота, кнопка. Экспорт ведомости на дату среза — которого пока нет.

Где сценарий ломается сегодня: шаг 3 (счёт не привязывается в потоке загрузки, под «Все» грузится что угодно), шаги 5–6
(только скрипт, «принять» = `assumption` = не платится), шаг 7 (поштучно), шаг 9 (нет смысла операции и массового ввода),
шаг 10 (нет среза и ведомости). Шаги 1–2, 4, 8 работают.

## 4. Приоритеты и порядок этапов

Разбор владельца §3 задаёт дедлайн: ведомость ноября считается в их ERP, наша — **контроль построчно**, переход после
совпадения. Значит, ценность ближайших двух недель — совпасть, а не онбордить. Отсюда порядок.

| Этап | Содержание | Зачем сейчас | Из черновика |

Ведомость-контроль 0to8** (≈ 4 дня) | книга по счёту файла (`source_files.label_id`, фильтр по лейблу файла; Echo8-строка счёта 1052428 → 0to8; счёт 1055956 из расчёта 0to8 уходит сам); дата среза `asOf` по отчётному месяцу (Believe по 2026-09, паблишинг исключён); выгрузка ведомости под лейблом (csv: владелец, псевдонимы, заработано, удержано, реклама, выплачено, к выплате, ворота); «выкуп ≠ роялти» (R5) и прощение аванса D6 как операции; массовый ввод операций из файла (кассы Tipalti/EasyStaff по дату среза; сегодня только миграционный флаг в API); «стартовый остаток» как смысл операции с документом (кабинет 15.10); замена выписки B17 (Q2 Updated); `check-label-books` на SXLLX = −1 091,77 и 237 расхождений как тест | без этого 05.11 ERP показывает к выплате $1,13M, из которых платить можно ~$0,45M, и 41 владельца с чужими деньгами Echo8 | D-169 (часть: книга по счёту, отказ на счёт), D-170 целиком |

Что бы я вычеркнул из D-169 черновика как первого этапа: `documents.label_id` с воротами (риск закрыть выплаты, которые

срочно). Что бы добавил: массовый ввод операций и стартовый остаток — без них ведомость не сойдётся ни по одному
владельцу с историей.

Переключатель «Все» vs менеджер лейбла: после книги по счёту каждая страница под лейблом становится **полной** (файл
целиком принадлежит лейблу, A = B + C + наше сходится по файлу), и «Все» превращается в сумму книг, нужную только владельцу
системы для сверки и слияний. Менеджеру лейбла «Все» не показывать вовсе; владельцу — показывать, но кнопки записи под
«Все» (загрузка, операция, выплата, реклама) закрыть подсказкой «выберите лейбл», как уже сделано с выплатой.
