## 1. Роли и что каждая может

Роли хранятся в базе (`auth.memberships.role`, `auth.users.is_system_admin`), правила в коде (`src/auth/abilities.ts`).
Принципал запроса один из пяти видов:

| Вид | Откуда | Организация | Лейблы | Что может |
|---|---|---|---|---|
| `org_admin` | членство, роль `org_admin` | организация сессии | все книги (own-лейблы) организации, «Все» | всё в своей организации: чтения с деньгами и без, «Все», записи, `approve`, `pay`, `admin` (лейблы, счета, правила, пользователи организации, грант поддержки) |
| `label_manager` | членство, роль `label_manager` + `auth.user_labels` | организация сессии | только свои own-лейблы; «Все» нет | чтения с `?label=` своего лейбла (без него `400 label_required`, чужой `403 label_forbidden`); каталожные чтения и записи без денег; загрузки и реклама под своим лейблом; **ни одной** `approve`, `pay`, `admin` |
| `system` | `auth.users.is_system_admin` или `X-System-Key` | нет | нет | `system`-операции: организации, пользователи и членства всех организаций, отключение, сброс пароля; ни одной `org`-операции и денег без гранта |
| `support` | `system` с `X-Org` при действующем гранте `org_admin` этой организации | `X-Org` | все книги, «Все» | `read` и `read_money` всего; с `write: true` в гранте ещё `write` (не `approve`, не `pay`, не `admin`); каждая запись в журнале организации под его логином с `summary.support = true` |
| `local` | `AUTH_MODE=off` | `ERP_DEFAULT_ORG` | все | как `org_admin` (тесты, скрипты, `compare-reference`, локальный стенд) |

Решения по спорным местам: `org_admin` может заводить пользователей своей организации и менять их роль и лейблы
(К5); отключить учётную запись глобально и сбросить пароль пользователя, у которого есть членство в другой организации,
может только системный администратор (иначе администратор одной организации захватит вход в другую); последний
`org_admin` организации не снимается и не понижается (`409 last_org_admin`). Системный администратор не бывает членом
организаций (сервис отказывает), в организацию входит только как поддержка.

Классы действий (`action`): `read` чтение без денег; `read_money` чтение денег; `write` запись каталога или данных
без денег и без подтверждения; `approve` утверждение, подтверждение, перенос между книгами, привязка дохода к
владельцу; `pay` денежная операция; `admin` настройка организации (лейблы, счета, правила, пользователи, поддержка);
`system` системная операция; `self` своя сессия. `scope`: `label` лейбл из запроса (`?label=`, `body.labelId`,
`body.items[].labelId`), для менеджера обязателен и из его лейблов; `record` лейбл записи, проверяет фасад по
`Viewer` (§2); `org` без лейбла, вся организация.

Матрица правил (одна таблица `RULES` в `abilities.ts`; «L» = только со своим лейблом, «R» = фасад проверяет лейбл записи):

| `action` \ вид | `org_admin` / `local` | `label_manager` | `support` read / write | `system` |
|---|---|---|---|---|
| `read` | да | `label`: L; `record`: R; `org`: да | да / да | нет (`support_required`) |
| `read_money` | да | `label`: L; `record`: R; `org`: **нет** | да / да | нет |
| `write` | да | `label`: L; `record`: R; `org`: да | `support_read_only` / да | нет |
| `approve`, `pay`, `admin` | да | нет (`forbidden`) | нет | нет |
| `system` | нет | нет | нет | да |
| `self` | да | да | да | да |

## 2. Слой способностей

Решение: **своя таблица**, `src/auth/abilities.ts`, без `@casl/ability`. Причины: правил ~20 строк (вид × `action` ×
`scope`), условия только «лейбл ∈ лейблы пользователя» и «грант на запись»; CASL ценен для условий над полями
документов в запросах к базе (`accessibleBy`), которых здесь нет: данные-зависимые проверки идут в фасаде по `Viewer`;
зависимость в бэкенде реестр D-154 не охраняет (К14). Если правил станет больше (тонкие права менеджеров, «Позже»
брифа), переход на CASL меняет только этот файл: интерфейс `can()` тот же.

```ts
// src/auth/abilities.ts (чистые функции, без express и базы)
export type Action = 'read' | 'read_money' | 'write' | 'approve' | 'pay' | 'admin' | 'system' | 'self';
export type Scope = 'label' | 'record' | 'org';
export interface Ability { action: Action; subject: Subject; scope?: Scope }   // scope только у org-операций
export interface Principal { kind: 'org_admin' | 'label_manager' | 'support' | 'system' | 'local';
  userId: string | null; login: string | null; orgId: string | null; sessionId: string | null;
  labelIds: ReadonlySet<string> | 'all'; supportWrite: boolean }
export type Decision = { ok: true } | { ok: false; status: 400 | 403; code: 'forbidden' | 'label_required' | 'label_forbidden' | 'support_required' | 'support_read_only' };
export function can(p: Principal, a: Ability, req: { labelIds: string[] }): Decision;   // labelIds из запроса
export function allowedOperations(p: Principal): string[];                              // для GET /auth/me
export const viewerOf = (p: Principal) => ({ labelIds: p.labelIds });                   // в фасад
```

| Часть | Решение |
|---|---|
| поле операции | `ability: Ability` обязательно в типе `ApiOperation` у всех, кроме `access: 'public'`; `access` остаётся (К2). Контракт-тест: (а) у каждой не-public операции `ability` есть; (б) `scope: 'label'` ⇒ в схеме `query.label`, `body.labelId` или `body.items[].labelId`; обратное неверно только для явного списка `RELABEL_OPERATIONS` (`labelId` тела = цель переноса между книгами): `PATCH /documents/:id` (A, O), `PATCH /settlements/operations/:id` (A, O), `PATCH /ads/:id` (W, R), тест требует, чтобы любая другая операция с `labelId`/`label` в схеме была `label`; у каждой операции ровно один `scope`; (в) `access: 'system'` ⇔ `action: 'system'`; (г) `GET` никогда не `write/approve/pay/admin` |
| сопоставление | `operationOf(method, path)` из `API_OPERATIONS` (статические сегменты сильнее `:param`: `/owners/payables` раньше `/owners/:id`); путь нормализуется как Express 5 его сопоставляет (Router `caseSensitive: false`, `strict: false`): статические сегменты в нижнем регистре, хвостовой `/` снят, метод в верхнем регистре. **Нет операции = `404 not_found`** (как `unknownApiRoute`), не `next()`. Тесты: каждая операция на своём конкретном пути находит себя; `POST /Owners/merge` и `POST /owners/merge/` под менеджером дают 403, не 200; путь без операции → 404. Маршруты не меняются |
