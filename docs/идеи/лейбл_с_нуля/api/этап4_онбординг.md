### 1.1 Импорт сплитов (`src/api/routes/splits.ts`, `tag: 'splits'`)

Файл: csv или xlsx. Csv разбирает существующий потоковый `parseCsv` (BOM, кавычки, разделитель параметром),
**перенесённый** из `modules/sources/csv.ts` в `src/shared/csv.ts` (sources и его тест `sources.test.ts:13` импортируют
оттуда; разделитель `,` или `;` определяется по строке заголовка). Xlsx: первый лист, потоковый `readRows` B17
выносится из `modules/publishing/b17-format.ts` в `src/shared/xlsx-rows.ts` (publishing импортирует его оттуда).
Колонки (`SPLIT_IMPORT_COLUMNS` в `packages/shared/src/split-import.ts`, заголовки без регистра):
`isrc, pseudonym, percent, from, to?, owner?, document?, artist_id?, note?` (`document_number` = синоним `document`;
`artist_id` снимает неоднозначность псевдонима и нужен равенству с загрузчиком). Лимит **5 000 строк** и 10 МБ:
больше = `413 import_too_large` (поток обрывается на 5 001-й строке).

Группа = (`isrc`, `from` после округления M52): одна группа = один сплит, её строки = строки артистов. Фаза 1
(чтение в `db.snapshot()`, без блокировки записи) классифицирует группы **в порядке файла по модели сплитов ISRC,
которую обновляет каждая предыдущая группа** (как `ctx.model` загрузчика: вторая группа нового ISRC видит сплит
первой и становится `change`). Фаза 2 (`dryRun=0`, только если ошибок нет) в **одной** `db.transaction()` повторяет
фазу 1 (данные могли измениться) и зовёт по порядку файла `owners.createOwner` / `owners.createArtist` (новые, один раз
на имя) и `facade.createSplit` / `facade.changeSplit` (вложенные транзакции присоединяются; любой отказ откатывает
всё: `422 import_invalid` с `details.group` и `details.cause` = исходный код фасада, например `split_overlap`).

Кэш на транзакцию (FIX-4): `createSplit` / `changeSplit` / `resolveShares` получают необязательный последний
аргумент `opts?: { index?: ArtistIndexCache }` (`facade/context.ts`): индекс псевдонимов (`owners.artistIndex()`),
построенный один раз в начале транзакции импорта и дополняемый каждым `createArtist` / `createOwner` импорта;
`getArtist` по id отвечает из него же. Маршруты и прочие вызовы фасада аргумент не передают: их поведение и
сигнатура для API прежние. Модули не обходятся (запись только их методами). Тест времени: синтетика 5 000 строк
(≈ 2 000 групп) применяется за ≤ 30 с на стеке тестов, и число вызовов `owners.artistIndex` за импорт = 1.

| Решение группы | Когда | Вызов |
|---|---|---|
| `create` | у ISRC нет ни одного сплита (как `ctx.model.of(isrc).length === 0` загрузчика) | `createSplit({ isrc, validFrom, validTo, shares, documentId, note })` |
| `change` (`replaces`) | у ISRC есть сплит; строки в силе на `from` отличаются | `changeSplit({ isrc, from, shares, documentId })`; строки с тем же процентом сохраняют прежний документ (`keepRowDocs … 'same_percent'`, как загрузчик) |
| `unchanged` | строки в силе на `from` равны строкам файла (артист и процент) | ничего (загрузчик: `already_equal`) |

Документ группы: если у всех строк один `document` → документ сплита; иначе каждая строка несёт свой, у сплита нет
(для `change` это `document_required`). Строки без документа грузятся без него → C `split_unconfirmed`, **не**
допущение. Происхождение `origin = 'import'`, `note` из колонки.

### 1.2 «Принять как допущение» (`POST /splits/assume`)

`S.assumeSplitsBody = z.object({ labelId, isrcs: z.array(isrc).optional(), splitIds: z.array(z.string()).optional(),
reason: z.string().min(3).max(2000) }).refine(ровно одно из isrcs/splitIds)` · 201 → `R.assumeResultSchema = { documentId,
assigned: [splitId], skipped: [{ splitId, code: 'has_document' | 'empty_period' }] }`. Фасад `assumeSplits(input, viewer)`
в одной `db.transaction()`: сплиты группы (все версии ISRC из `isrcs` или перечисленные `splitIds`) без документа
сплита, с непустым периодом и хотя бы одной строкой без своего документа; создаётся **один** документ
`{ kind: 'assumption', title: 'Допущение: ' + reason (≤ 200), labelId, requiresApproval: true }` (файл не нужен,
не утверждается: `assumption_not_approvable`), затем `splits.confirmSplit(id, doc)` каждому. Деньги строк без своего
документа уходят из C `split_unconfirmed` в C `assumption` (`categorise.ts` не меняется). Ошибки: `400
label_required`, `404 not_found` (лейбл, сплит), `400 label_not_own`, `422 nothing_to_assume` (ни одного сплита),

**Вывод из файлов (FIX-1).** Наблюдение = (ISRC, отчётный месяц, лейбл): пары (ISRC, файл) по `loaded` файлам одним
`GROUP BY` (`columnar.isrcFilePairs`, новый), лейбл = `source_files.label_id`, месяц = `reporting_month` файла; файлы
без лейбла пропускаются с числом. По ISRC месяцы идут по возрастанию, ведётся «текущий» лейбл (первый = лейбл самого
раннего наблюдения, интервал начинается с этого месяца):
1. Месяц, где наблюдается только текущий, продолжает его прогон; месяцы без наблюдений тоже.
2. **Новый** лейбл X (прогона у него ещё не было) в месяце m открывает прогон X, даже если текущий тоже есть в m:
   побеждает позднейшее наблюдение (лейбл, чей прогон начался позже). Ничья (два новых лейбла в одном месяце, сейчас
   0): позже загруженный файл (`loaded_at`), затем `label_id` по возрастанию; печатается `ties`.
3. **Прежний** лейбл A (прогон у него был) в месяце m: если текущий лейбл наблюдается в m или позже, это хвост, а не
   прогон (сигнал `catalogOutsideAccount`); если текущий после m больше не наблюдается, это **возврат**: A открывает
   третий (и далее) интервал с m.
4. Граница между прогоном A и следующим прогоном B: `clamp(last_A + 1 мес., start_B, first_B)` =
   `min(max(last_A + 1, start_B), first_B)`, где `last_A` последний месяц A до `first_B`, `first_B` первый месяц B у
   ISRC, `start_B` первый отчётный месяц любого `loaded` файла лейбла B (начало его счёта). Начало первого интервала =
   первое наблюдение; последний интервал открыт.
5. Результат по ISRC = прогоны минус периоды интервалов `operator` (они режут выведенные: выведенный интервал
   укорачивается или делится); строки `source='files'` ISRC заменяются целиком, `operator` не трогаются никогда.
Печать: ISRC с 1 / 2 / ≥ 3 интервалами, `returned`, `ties`, хвосты (`catalogOutsideAccount`), ISRC с интервалом
оператора, вставлено / удалено / без изменений; по каждой границе обе цифры (`first_B` и граница). **Ожидание на
реальных данных:** 2 436 ISRC на обоих счетах с двумя интервалами (0to8 → Echo8); `first_B` = 2025-08 у 2 343, позже
(2025-09 … 2026-08) у 93; граница у всех 2 436 = 2025-08 (`start_B` счёта 1055956); хвост 1 ISRC = 1 строка
`catalogOutsideAccount`; возвратов и ничьих 0.

**Правка оператора (FIX-2)** не замораживает файлы: интервал `source='operator'` выигрывает только в своих месяцах,
вывод его не перезаписывает, а прочие месяцы ISRC по-прежнему строятся из файлов (п. 5). Запись в одной транзакции:
- **замена** = `POST` с `from`, равным `valid_from` существующего интервала `operator` этого ISRC: тот интервал
  получает новые `label_id`, `valid_to`, `note` (одна строка, прежние значения в аудите). Так правится ошибка с
  первого месяца и так интервал закрывается («как удаление» на хвосте): та же `from` с `to` = месяц конца. Замена без
