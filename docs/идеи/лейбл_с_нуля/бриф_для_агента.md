## D-169. Книга по счёту файла; загрузка под лейблом; реклама по плательщику; B17 под лейблом

### Цель

Каждый юнит Believe лежит в книге лейбла, за которым зарегистрирован счёт его файла (R6). Файл и выписка грузятся
под лейблом и помнят его. Реклама списывается с книги плательщика. Документ и запись аудита могут нести лейбл.
`calculate()`, слои `facade/layers/*`, `recoup.ts`, охват (`owner-scope.ts`) математически не меняются.

Уточняет D-168 (решение 1 «лейбл денег = строка лейбла юнита», видимость по строкам, «B17 только в «Все»»), D-123,
D-130. Не трогает D-051, D-126, D-127, D-130 (12 знаков), D-161…D-165.

### Правила (войдут в D-запись дословно)

- **R6.** Книга юнита = own-лейбл из `source_files.label_id` его файла. Строка лейбла юнита по-прежнему решает
  саблейбл-правило и «наше / `label_unmapped`» (`layers/label-of-record.ts` без изменений). Два поля у юнита:
  `bookLabelId` (счёт, книга) и `ourLabelId` (строка). Файл без `label_id` (история до разметки) = книга `'?'`.
- **R7.** Файл Believe грузится под own-лейблом: `POST /sources/believe?label=<id>`. Счёт из имени файла обязан быть
  зарегистрирован за этим лейблом в `labels.label_accounts`. Иначе отказ до чтения файла, без строки реестра, без
  строк ClickHouse, без аудита. `source_files.label_id` записывается при загрузке и больше не меняется (нет PATCH).
  Строки чужого own-лейбла **внутри своего счёта** по-прежнему грузятся (сигнал `labelOutsideAccount` остаётся).
- **R8.** Выписка B17 грузится под own-лейблом: `POST /publishing/b17?label=<id>`; `pub_statements.label_id`; строки
  наследуют через материализованное представление; доход паблишинга в книге лейбла выписки. Под `?label=L` читаются
  строки B17 лейбла L (сегодня под лейблом не читаются). Один квартал на источник (PK `pub_statement_periods` не
  меняется; второй лейбл с тем же кварталом это ограничение, записать в Open).
- **R9.** Реклама: `ads.expenses.label_id` обязателен у каждой записи и означает плательщика; книга списания =
  плательщик. Строка ISRC в месяц расхода решает только правило саблейбла (кто несёт невозвращённую часть). Новый
  сигнал `adOutsideBook`: доход ISRC в месяц расхода идёт в другую книгу (информация).
- **R10.** `owners.documents.label_id` необязателен; пусто = «любой лейбл». Ворота выплаты и аванса под L требуют
  утверждённый договор с `label_id ∈ {L, NULL}`. Категоризация C (`owner_unconfirmed`) договор лейбла не смотрит.
  Историю (1 400 документов) **не размечать** ⚠.
- **R11.** `audit.actions.label_id` = `?label=` запроса, иначе `labelId` тела, иначе пусто. Историю не заполнять.
- Переключатель «Все»: все кнопки записи (загрузка, операция, реклама, документ, выплата) закрыты подсказкой
  «выберите лейбл», как кнопка выплаты в D-168.

## D-170. Операции под ведомость: явный вид, прощение, списание, корректировка, `asOf`, выгрузка, замена B17

Зависит от D-169 (книги по счёту). Цель: ведомость-контроль ноября под 0to8 построчно против ERP овнера.

### Модель

Миграция `0016_operation_kinds.sql`:

- `settlements.operations.kind text CHECK IN ('payout','advance','deduction','credit','return','buyout','forgiveness',
  'writeoff','adjustment')`; заполнить историю детерминированным выражением из `meaningOf`; `meaning` = `kind`.
  Ограничения 0004 (`operations_out_rules` и др.) заменить (DROP + ADD) с учётом `kind`: `buyout` = `out`, владелец,
  документ вида `buyout`, без области, **не входит в `paid`** (README §5: выплата за выкуп не роялти), поле книги
  `buyouts_L`; `forgiveness` = `in`, `operation_ref` на аванс, документ, сумма ≤ непогашенного, дата; `writeoff` = `in`
  на владельца с областью `publishing` и документом; `adjustment` = `in`/`out` на владельца с документом (стартовый
  остаток / корректировка к кабинету), в `payable_L` со знаком, поле `adjustments_L`.
- `settlements.operations.label_source text CHECK IN ('one','default','operator','payout')`: откуда лейбл (D-168
  разметил 1 315 операций «по умолчанию» 0to8; `assign-operation-labels.ts --mark-source` проставляет); список
  `default` овнеру; сигнал `operationsRelabelled` по аудиту.
- `PATCH /settlements/operations/:id { labelId, reason }`: `reason` обязателен, в `summary` аудита,
  `label_source = 'operator'`.
- `labels.labels.legal_name text`, `currency text NOT NULL DEFAULT 'USD'` (юрлицо печатается в ведомости и снимке).

### Прощение в `layers/recoup.ts` (единственное изменение слоя, со своим тестом)

Позиция получает `forgiven` (Σ прощений по `operation_ref`) и дату: ёмкость позиции для доходов с месяца ≥ даты
прощения = `amount − recouped_до_даты − forgiven`. Поле книги `forgiven_L`; `unrecouped` уменьшается, `payable` не
меняется. `tests/layers/recoup.test.ts`: прощение с даты, гашение до даты не меняется, Σ книг = итог.

### `asOf` и выгрузка ведомости

- `asOf` = `PeriodFilter.to` по отчётному месяцу для юнитов и выписок **плюс** операции и позиции с `date ≤ asOf`
  (сегодня период-фильтр операции не режет). Ничего не хранится: ведомость воспроизводима из сырых данных и `asOf`.
  Пин в `scope.test.ts`: «баланс `asOf` = полный баланс без поздних операций и файлов».
- `GET /owners/payables?label=&asOf=2026-09&area=master|publishing|all&format=csv`: одна полная калькуляция (как
  `ownerPayables`), строка на владельца × псевдоним: лейбл и юрлицо, владелец, псевдоним, договор с этим лейблом
  (номер, дата, кем утверждён), earned, recouped (с остатком незакрытых авансов), ads, paid, buyouts, forgiven,
  writtenOff, adjustments, payable, ворота (`payout_blocked` с пометкой «другим лейблом», без суммы), «ниже порога».
  Отдельные листы: «ждёт» по причинам (с уже выплаченным), выкупы. Итоги: Σ payable; Σ B книги; контроль A = B + C +
  наше по счёту и месяцу внутри среза; число операций с изменённым лейблом. В `operations.ts` операция с
  `response: z.string()` (csv) или флаг как у `upload`; контракт-тест вызывает её.
- Кнопка выплаты под лейблом получает `area` (по умолчанию `master`), снимок хранит область.

### Массовый ввод операций из файла

6. **Открыто.** Замена Q2 на Updated: механизм делать (D-170), прогон после подтверждения.
7. **Решено.** «Решение лейбла, платим без договора» = новый вид документа `label_decision` (в `DOCUMENT_KINDS`),
   утверждаемый, принимается `createContract` наравне с `contract` и как документ строки сплита; в ведомости отдельная
   колонка «по решению, без договора». Всё вручную через API, массовых кнопок нет. Н3: без срока.
8. **Решено, без кода.** Писатели «за артиста» зарегистрированы лейблом: привязать их к владельцу-компании лейбла и
   поставить условия паблишинга 0 % с документом (`setTerms` допускает 0); B = 0, всё «наше». Связь «писатель →
   псевдоним» не делать.

Прочее: ноябрьская ведомость считается у овнера (п. 1), `asOf` и выгрузка не срочны; счёт у лейбла без периода (п. 9);
Echo8 не видит файлы счёта 1052428 (п. 8); «Все» только администратору системы (п. 10).

## Граница арендатора (этап 2): организация как ключ изоляции в одной базе (вариант A, решение владельца 05.11)

Решение владельца продукта (05.11, поздно вечером): **не база на арендатора, а колонки**: таблица `organizations` с
настоящими id, `org_id` на каждой строке данных, `label_id` на деньгах (как в D-169). Организация может иметь N
лейблов (компаний) и их саблейблы; у 0to8 и Echo8 одна организация. Отчёты консилиума в `консилиум_изоляция/`
остаются как разобранная альтернатива; из них действуют: константное 500 с `requestId`, ожидаемые значения на трёх
денежных PATCH, пользователи и членство, «Все» у администратора организации, системный администратор без денег,
генерируемые сервером идентификаторы. Данных для миграции нет: всё восстанавливается с нуля загрузчиком.

### Правила

- **O1.** `organizations (id uuid PK, name, created_at, created_by)`; `labels.labels.org_id` обязателен; каждая таблица
  данных модулей несёт `org_id NOT NULL` (владельцы, псевдонимы, треки, слияния, документы, контракты, сплиты, участия,
  правила и алиасы лейблов, счета Believe, операции и снимки выплат, реклама, выписки, писатели, условия паблишинга,
  реестр файлов, аудит). Внешних ключей между модулями нет (D-121): `org_id` это непрозрачный текст, проверяемый фасадом.
- **O2.** Книга денег = лейбл файла (R6, D-169), не строка лейбла. Строка лейбла решает только саблейбл-правило и
  «наше / `label_unmapped`», и только внутри файлов своего лейбла: алиас уникален по `(org_id, alias_norm)`, одна и та же
  строка у двух организаций или у двух лейблов одной организации ничему не мешает, потому что файл уже назвал лейбл.
- **O3.** Фильтр по организации ставится **один раз, централизованно**: модули открываются с `orgId`
  (`openModules(db, orgId)`), репозитории подставляют `WHERE org_id = $org` через общий помощник, а не руками в каждом
  запросе; `tests/boundaries.test.ts` (или новый `tests/org-scope.test.ts`) проверяет, что каждая таблица модулей имеет
  `org_id` и каждый репозиторий читает через помощника. Фасад кэшируется на организацию (карта `orgId → facade`,
  как план консилиума, только над одной базой); маршруты не меняются.
- **O4.** ClickHouse без колонок организации и лейбла: чтения и так начинаются с реестра (`loaded` файлы организации
  → `file_id IN`), саблейбл через `label_name IN (алиасы)` внутри файлов лейбла. Колонка `label_id` в `believe.rows`
  допустима позже как обычная колонка для BI (вне ключа проекции), истина в реестре.
- **O5.** Уникальность с организацией: `(org_id, account, reporting_month)` и `(org_id, sha256)` у файлов, `(org_id,
  source, period)` у кварталов B17, `(org_id, name)` у лейблов, `(org_id, alias_norm)` у алиасов, `(org_id, account)` у
  счетов Believe (один счёт в двух организациях допускается ⚠ по умолчанию). Один advisory lock записи на базу остаётся
  (чужая транзакция задерживает мою на своё время; при росте нагрузки ключ блокировки = `hashtext(org_id)`).
- **O6.** **Организация берётся только из JWT и решается на бэкенде**; заголовка или параметра организации у клиента
  нет вообще. Минимальная аутентификация входит в этот этап: `auth.users (id, login, password_hash, org_id,
  is_system_admin)`, `POST /auth/login` → JWT `{ sub, org, sys }` в httpOnly cookie, `authenticate` на каждом запросе
  `/api/v1` (кроме `/auth/login`, `/health`), `res.locals.org` из токена; `system_admin` указывает организацию явно
  (`X-Org`, только ему). Первого пользователя создаёт `scripts/create-user.ts`. Роли, членство в нескольких
  организациях, лейблы пользователя, сессии с отзывом остаются в этапе 3. `AUTH_MODE=off` для тестов и скриптов =
  организация из `ERP_DEFAULT_ORG`.
  **Лейбл в каждом запросе**: `?label=` на чтениях и `labelId` в телах записей (как в D-168/D-169); бэкенд проверяет,
  что лейбл принадлежит организации токена (`404 label_not_found` иначе); пустой лейбл = «Все» = все книги организации.
  Чужой id любой сущности под своей организацией это 404, никогда данные. Ошибки 500 отдают константный текст и
  `requestId`.
- **O7.** Оптимистичный контроль = ожидаемое значение изменяемого поля в теле трёх денежных PATCH (`expectedCurrentSplitId`,
  `expectedLabelId`, `expectedRecoveryPercent`) → 409 с текущим значением; остальное «последний побеждает, оба в аудите».

### Модель данных

Миграция `0015_organizations.sql` (одна, идемпотентная): схема `orgs` с `orgs.organizations`; `ALTER TABLE … ADD COLUMN
org_id text NOT NULL` на каждой таблице данных (с чистой базы NOT NULL сразу; для существующей базы `DEFAULT '<id
организации №1>'` и снятие default после), индексы `(org_id, …)` впереди существующих ключей, уникальные ключи
пересобираются по O5. Drizzle: `orgId` в каждой схеме. `audit.actions.org_id`, `control`-таблицы пользователей (этап 3)
живут в той же базе в схеме `auth`.

`src/orgs/`: `types.ts`, `service.ts` (`createOrganization`, `list`, `get`), `middleware.ts` (`resolveOrg` из
`res.locals.user.org`; `org_not_found` 404), `pool.ts` (карта `orgId → { modules, facade, router }`), `scope.ts` (помощник `orgWhere`).
`openFacade({ db, sources, dataDir, orgId })`; `createSourcesService({ registry: createSourceFilesRegistry(pool, orgId), … })`;
`storageDir = <dataDir>/orgs/<orgId>/files/sources`, `tmp` там же. `src/api/app.ts`: системный роутер (`/health`,
`/openapi.json`, `/docs`, `/orgs`) над роутерами организаций; `createApp(facade)` single-режим остаётся для тестов.

### API (`src/api/routes/orgs.ts`, `tag: 'orgs'`, `access: 'system'`)

`GET /orgs` (id, name, число лейблов, файлов, владельцев), `POST /orgs { name }` → 201 (id генерирует сервер),
`GET /orgs/:id`. Удаления нет на этом этапе (данные восстанавливаются с нуля). Доступ: `requireSystemKey`
(`X-System-Key` = `SYSTEM_ADMIN_KEY`), записи с `X-Operator`, аудит в `audit.actions` с `org_id` организации-цели.
`POST /labels` требует организацию запроса; `GET /labels` отдаёт лейблы организации. OpenAPI: параметр `X-Org` (только для `system_admin`)
(header, optional) через `openapi.ts`.

### Данные

Чистая база: `npm run migrate:pg`, `POST /orgs { name }` → id, `.env` `ERP_DEFAULT_ORG=<id>`, затем загрузчик стадии 4
(`scripts/mvp/load.ts`) и отчёты Believe/B17 через API под этой организацией. Существующая база `erp`: миграция
создаёт организацию №1 и проставляет её `org_id` всем строкам; проверка `check-owner-scope` 0 differing и `GET
/overview` байт в байт. Скрипты: `connectOrg({ org: --org | ERP_ORG })`, `scripts/mvp/lib.ts` одна правка.

### Фронт

Организации у клиента нет нигде: ни в `localStorage`, ни в заголовке, ни в URL; она приходит из cookie после входа.
`LabelSwitch` показывает лейблы организации (`GET /labels` под токеном); `system_admin` выбирает организацию в своём
экране и шлёт `X-Org`.
`coverage.ts`: операции `orgs` как страница системного администратора (отказ до этапа 3). Страница входа и cookie
уже на этом этапе (минимальный логин), поле оператора остаётся как подпись в аудите.

### Тесты
