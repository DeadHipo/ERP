# Лейбл с нуля: онбординг и привязка всего к лейблу и пользователю (черновик для ролей)

Дата: 2026-11-05. Статус: **черновик, разобран пятью ролями; итог в `README.md` и `бриф_для_агента.md`**, при
расхождении правы они (в частности: `label_id` в ClickHouse не делать, `created_by` не добавлять, документы по
истории не размечать, передача Echo8 как шаг не нужна). Код не менялся, D-запись не писалась. Отчёты ролей в `роли/`.

## 0. Контекст

Сегодня ERP работает на старых данных одного лейбла (0to8), в которые случайно попал второй (Echo8: его каталог
восемь месяцев отчитывался внутри счёта Believe 0to8, с 2025-08 у него свой счёт). Владелец продукта уточнил
2026-11-05: **система не только для нас**. Echo8 дальше грузит свои данные сам, может появиться третий лейбл, потом
менеджеры с правами, потом отгрузка треков через систему. Математика (A = B + C + наше, слои, 12 знаков, охват)
решена и не меняется; нужна **чёткая принадлежность каждой записи лейблу и пользователю**, чтобы «как сейчас, но
понятно, что куда и где».

Что уже сделано в эту сторону (D-168, 2026-11-05): операции и реклама несут `label_id`; баланс и выплата по
владельцу × лейбл («книги»); чтения под `?label=`; переключатель в шапке; счета Believe у лейбла
(`labels.label_accounts`). Правило владельца R6 (05.11): **книга денег = счёт-получатель Believe**, не строка
лейбла трека (разбор в `context_data/разбор_01/`, проверка агентом: счёт 1055956 чистый, в счёте 1052428 одна чужая
строка «Echo8» за 2024-12…2025-07, 222 130 net, и она по R6 принадлежит 0to8).

## 1. Сценарий владельца продукта, шаг за шагом

Формат: **есть сейчас** → **добавить** → **вопросы**.

### Шаг 1. Вход: логин, пароль, user id, JWT

- Есть: `X-Operator` (строка, обязательна на каждой записи, попадает в `audit.actions.operator`). Ролей нет
  (вне объёма по README).
- Добавить (сейчас минимально): считать `X-Operator` идентификатором пользователя; все новые записи получают
  `created_by` через аудит, как сегодня. Таблицу `users` и JWT делать позже, но так, чтобы subject токена стал
  значением `X-Operator` без миграции данных.
- Вопросы: пользователь принадлежит лейблу или лейблам (менеджер двух лейблов)? Администратор системы отдельная роль
  от администратора лейбла?

### Шаг 2. Администратор создаёт лейбл (0to8)

- Есть: `POST /labels` (own-лейбл при `own_label_id = null`), алиасы, счета Believe (`POST /labels/:id/accounts`).
- Добавить: юрлицо лейбла (название для договоров и выплат), валюта отчётности (сейчас везде USD), `created_by`.
  Лейбл это **арендатор**: всё дальнейшее создаётся «под лейблом» (переключатель в шапке = текущий лейбл
  пользователя).
- Вопросы: нужен ли «системный» уровень над лейблами (суперадмин видит все)? Переключатель «Все» остаётся только
  для него?

### Шаг 3. Саблейблы и их алиасы

- Есть: саблейбл = лейбл с `own_label_id`, алиасы строк Believe, правило саблейбла (процент, получатель-псевдоним,
  документ, даты).
- Добавить: ничего структурного. UI «мастер онбординга» может показать после загрузки отчётов **нераспознанные
  строки лейбла** и предложить сделать из них саблейбл или алиас (сейчас это сигнал `label_unmapped`, деньги ждут
  в C).
- Вопросы: саблейбл может сменить own-лейбл (переход 77 Records от 0to8 к третьему)? Сейчас `own_label_id` без
  периода.

### Шаг 4. Загрузка отчётов Believe «своих»

- Есть: `POST /sources/believe` (zip/csv), реестр файлов `public.source_files` (счёт, месяц, статус), строки в
  ClickHouse `believe.rows`, чтения только по `loaded` файлам.
- Добавить: **файл грузится под лейблом**: счёт из файла должен быть зарегистрирован за текущим лейблом
  (`label_accounts`), иначе отказ `account_not_of_label` с предложением зарегистрировать счёт (если он ничей) или
  отказ (если он чужой). `source_files.label_id` (денормализация счёта на момент загрузки, неизменяемая) и
  `uploaded_by`.
- Вопросы: счёт может перейти от лейбла к лейблу (продажа каталога со счётом)? Если да, `label_accounts` с
  периодом, а `source_files.label_id` фиксирует лейбл на момент загрузки.

### Шаг 5. `label_id` / `sublabel_id` в строках ClickHouse

- Есть: строка лейбла как есть (`label_name`), сопоставление с лейблом при расчёте через алиасы (переименовали
  алиас — пересчитались все месяцы).
- Предложение владельца: добавить `label_id` и `sublabel_id` к строкам.
- Разбор:
  - `label_id` own-лейбла по R6 = лейбл счёта файла. Он **неизменен** (деньги пришли на счёт), поэтому его можно
    записать в строку при загрузке: `believe.rows.label_id` (денормализация `source_files.label_id`), фильтр
    `label_id IN` вместо списков `file_id`. Источник истины остаётся реестр файлов.
  - `sublabel_id` зависит от алиасов и правил, которые **меняются во времени** (правило 50 % с датами, новый алиас
    задним числом). Записывать его в строку при загрузке значит заморозить сопоставление на момент загрузки и
    пересчитывать строки при каждой правке справочника. Предложение: **не хранить**, оставить вывод по строке при
    расчёте, как сейчас. Если нужен быстрый фильтр по саблейблу в ClickHouse, достаточно `label_name IN (алиасы)`,
    как уже делает `SnapshotFilter.labelStrings`.
- Вопросы: нужны ли аналитические запросы напрямую в ClickHouse (BI) по `label_id`? Если да, колонка оправдана и
  для этого.

### Шаг 6. Каталог: треки по ISRC с метаданными, привязанные к лейблу / саблейблу

- Есть: `owners.tracks` (ISRC, UPC, название, заметка), атрибуты пар из отчётов (`believe.pair_attrs`: артист,
  релиз, название по последнему отчёту), страницы каталога P5/P6 из отчётов, псевдонимы ISRC по сплитам (D-166).
- Экспорт Believe `20261102_my_catalog_export.csv`: **по релизам (UPC), не по трекам**: Release Title, Version,
  Artist, Label, Release date, # of track, UPC, Cat. #, территории, магазины; 8 242 релиза. ISRC в нём нет.
  Значит, каталог по ISRC собирается из отчётов (пары ISRC × UPC), а экспорт даёт релизу дату, версию, лейбл
  Believe и число треков (контроль: все ли треки релиза встречались в отчётах).
- Добавить: модуль или расширение owners: `catalog.releases` (UPC, название, версия, артист-строка, лейбл Believe,
  дата релиза, число треков, `label_id`, источник, `imported_by`), `catalog.tracks` = `owners.tracks` +
  `label_id`, + история принадлежности `catalog.track_labels (isrc, label_id, from, to)` для переносов (случай
  Echo8: ISRC перешёл со счёта 0to8 на счёт 1055956 с 2025-08).
- Принцип: **лейбл каталога это навигация и права, не деньги.** Книга денег всегда по счёту файла (R6). Если
  каталог говорит «лейбл A», а отчёт пришёл на счёт лейбла B, это сигнал (`catalogOutsideAccount`), а деньги в
  книге B.
- Вопросы: кто ведёт каталог, когда треков ещё нет в отчётах (отгрузка через систему потом)? Переносы между
  лейблами: событие с датой (как Echo8) или просто смена `label_id` с записью в историю?

### Шаг 7. Сплиты из файла: артисты и их доли по ISRC

- Есть: модуль splits (строки с процентом, период с первого числа месяца, документ на строку), участия
  (participations: pool / artist share / label share), правило «строка или участие», загрузчик `scripts/mvp/load.ts
  splits` из нашего файла, страницы P7/P8.
- Добавить: загрузка сплитов **через UI под лейблом** (сейчас только скрипт): файл известного формата → предпросмотр
  (новые псевдонимы, ISRC не из каталога лейбла, пересечения периодов) → применение через фасад. Сплит остаётся
  **глобальным по ISRC** (ISRC в один момент у одного лейбла); `created_by` через аудит; псевдонимы, созданные при
  загрузке, «видны» лейблу через его ISRC (как в D-168).
- Вопросы: формат файла сплитов фиксируем наш (как в стадии 4) или даём шаблон? Строки без документа грузятся
  как `assumption` или как «ждёт документ» (`split_unconfirmed`)?

### Шаг 8. Документы по сплиту / группе сплитов, или «верно без документов»

- Есть: документы (виды: договор, выкуп, основание аванса, `assumption` = решение совета без утверждения),
  документ на строку сплита, `requires_approval`, срок загрузки, утверждение (`approved_by`).
- Добавить: `documents.label_id` (сторона договора = юрлицо лейбла), `uploaded_by`; «верно без документов» =
  существующий вид `assumption` на группу строк (сейчас это шаг загрузчика `assumption-rows`), нужна кнопка в UI
  «принять как допущение» на выбранные строки.
- Вопросы: договор одного лейбла подтверждает владельца и для другого лейбла? По смыслу нет: ворота выплаты под
  лейблом L требуют договор с L (D-168 пока проверяет «любой договор»). История без лейбла = «любой».

### Шаг 9. Владельцы псевдонимов

- Есть: владельцы (person / label), псевдонимы, слияния, подтверждение по договору, карточка P10, список P9.
- Добавить: ничего структурного; **владелец глобален** (человек один, у него могут быть договоры с двумя
  лейблами, его книги разные). Видимость под лейблом выводится из юнитов счёта (как сейчас). Ранний ответ
  владельца («другой договор = новый владелец под лейблом») остаётся возможностью, не правилом.
- Вопросы: слияние владельцев, видимых двум лейблам, кто вправе?

### Шаг 10. Отчёты паблишинга

- Есть: B17 по кварталам (`publishing.pub_statements`), писатели → владельцы, условия по владельцу (процент,
  период, тип операции), слои writer parts → author share → B/C; у выписки лейбла нет, деньги в книге «без
  лейбла».
- Добавить: **выписка грузится под лейблом**: `pub_statements.label_id`, строки наследуют; книга «без лейбла»
  исчезает. Замена выписки (сейчас `duplicate_period` без удаления) нужна для битого Q2. ASCAP как второй
  издательский источник позже, той же формы.
- Вопросы: условия паблишинга (процент автору) по владельцу или по владельцу × лейбл? Пока по владельцу.

## 2. Модель принадлежности (сводная таблица)

| Сущность | Ключ лейбла | Как определяется | Общая между лейблами? |
|---|---|---|---|
| Лейбл, саблейбл, алиас, правило, счёт | own-лейбл | создаётся под ним | нет |
| Файл Believe, строки ClickHouse | `source_files.label_id` = лейбл счёта на момент загрузки | R6 | нет |
| Юнит (деньги мастера) | лейбл файла | R6; строка лейбла решает только саблейбл и «наше» | нет |
| Релиз, трек каталога | `label_id` + история по ISRC | импорт / отчёты / ручная правка | ISRC один в момент времени |
| Сплит, участие | без ключа; через ISRC | ISRC → лейбл каталога | по сути нет |
| Псевдоним, владелец | без ключа | видимость через юниты и операции | **да** |
| Документ, договор | `label_id` (юрлицо) | загрузка под лейблом | нет |
| Операция, выплата, снимок | `label_id` | D-168 | нет |
| Реклама | `label_id` = плательщик | D-169 | нет |
| Выписка паблишинга, строки | `label_id` | загрузка под лейблом | нет |
| Условия паблишинга | владелец (пока) | | да |
| Аудит | `operator` + `label_id` (новое) | контекст запроса | |

Три сигнала лейбла у ISRC-месяца и их роли:

1. **счёт файла** → книга денег (кому пришло, кто платит) — R6;
2. **строка лейбла** → саблейбл-правило и «наше / не наше» (как сегодня, слой label of record);
3. **каталог** → навигация, права, отгрузка.

Расхождения между ними не меняют деньги, а дают сигналы: `labelOutsideAccount` (строка чужого own-лейбла в счёте),
`catalogOutsideAccount` (ISRC из каталога A пришёл на счёт B).

## 3. Пользователь и аудит

- Сейчас: `X-Operator` обязателен, хук аудита пишет `operator`, метод, маршрут, id сущностей, краткое содержание.
- Добавить: `audit.actions.label_id` (лейбл контекста запроса: `?label=` / `labelId` тела) и `created_by` там,
  где его сегодня нет (документы, сплиты, лейблы), заполняется из `X-Operator`. Пользователи и JWT: таблица
  `users (id, login, password_hash, labels[])`, subject токена = `X-Operator`. Роли минимум три: администратор
  системы, администратор лейбла, менеджер лейбла (чтение + операции без утверждения).
- Переключатель «Все» становится правом администратора системы, у администратора лейбла один лейбл или список.

## 4. Что происходит с текущими данными

- Лейблы, саблейблы, алиасы, счета: как есть.
- Файлы: `label_id` по счёту (1052428 → 0to8, 1055956 → Echo8), ClickHouse `label_id` заполняется тем же.
- Каталог: релизы из экспорта 2026-11-02 (0to8), треки из `owners.tracks` + пары отчётов; `label_id` по счёту
  файлов, где ISRC встречался; история: ISRC Echo8 2024-12…2025-07 под 0to8, с 2025-08 под Echo8.
- Документы: `label_id` = 0to8, кроме четырёх договоров Echo8 из архива (по данным разбора владельца).
- Операции, реклама: 0to8 (решение 05.11), семь операций Echo8 пересмотреть по плательщику.
- B17: `label_id` = 0to8.
- Проверка: Σ книг = полный баланс (как `check-label-books.ts`), SXLLX под 0to8 = −1 091,77 (разбор владельца).

## 5. Что не меняется

`calculate()`, слои `MASTER_LAYERS` и паблишинга, 12 знаков, правило «строка или участие», охват владельца
(reach), одна выплата кнопкой под лейблом, снимок выплаты. Сплиты и владельцы остаются глобальными.

## 7. Вопросы себе (с рабочими ответами)

- *Лейбл это арендатор (жёсткая изоляция) или книга (переключатель)?* Книга сейчас, арендатор после ролей; модель
  данных одна и та же, различие в правах.
- *Почему не своя база на лейбл?* Владельцы и ISRC общие; один человек с двумя договорами; слияния. Книги дают то
  же разделение денег без дублирования людей.
- *Зачем `label_id` в ClickHouse, если есть `file_id`?* Для прямых запросов и простого фильтра; истина в реестре.
- *Где ломается «ISRC у одного лейбла в момент времени»?* Только у Believe (чужая строка в счёте). На это сигнал,
  деньги по счёту.
- *Что с переключателем «Все» для менеджера лейбла?* Нет. Только свой лейбл.
- *Мастер онбординга это новая страница или те же страницы в порядке?* Те же страницы плюс чек-лист прогресса
  (лейбл → счета → файлы → нераспознанные строки → каталог → сплиты → документы → владельцы → паблишинг) на P1
  под лейблом.
