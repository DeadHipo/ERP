# Лейбл с нуля: итог (коротко, для владельца продукта)

Дата: 2026-11-05. Статус: **идея, прошедшая пять ролей**; код не менялся, D-запись не писалась. Подробный план для
исполнителя: `бриф_для_агента.md`. Отчёты ролей: `роли/` (продакт, владелец лейбла, QA, senior backend, junior dev).
Исходный черновик: `черновик.md`. Там, где роли расходятся с этим файлом, прав этот файл.

## 1. Ответ в десяти строках

1. **Ваша модель верна:** лейбл это арендатор, всё создаётся под ним, деньги каждого доллара принадлежат лейблу, на
   чей счёт Believe они пришли (правило R6 овнера). Владельцы и псевдонимы общие (человек один), книги разные.
2. **D-168 сделал книгу по строке лейбла трека. Это надо переключить на счёт файла.** Разница ровно одна: строка
   «Echo8» внутри счёта 0to8 за 2024-12…2025-07 (222 130 net) переезжает в книгу 0to8. Больше ни один доллар не
   меняет книгу, проверено агентом по всем 47 файлам.
3. **ClickHouse не трогать.** Фильтр по `file_id` уже отсекает партиции (0,05 с на 13 файлов). `label_id` у файла
   в реестре PostgreSQL, заполняется при загрузке из счёта, неизменяем. `sublabel_id` в строках нельзя: алиасы и
   правила меняются задним числом.
4. **Загрузка под лейблом:** файл грузится только на счёт, зарегистрированный за текущим лейблом; чужой или ничей
   счёт даёт отказ. Это единственное «арендаторское» поведение до появления ролей.
5. **Реклама по плательщику** (кто оплатил счёт), не по строке ISRC: иначе промо 0to8 за трек с меткой Echo8
   уезжает в книгу Echo8 (у SXLLX так уехали 6 659 из 7 122).
6. **Выписка B17 грузится под лейблом**, книга «без лейбла» исчезает. Все шесть выписок сегодня 0to8.
7. **Договор лейбла как ворота выплаты**: механизм сейчас (`label_id` у документа, пусто = любой лейбл),
   разметка истории только по вашему решению, иначе в неделю ведомости закроются открытые выплаты.
8. **Каталог это навигация, не деньги.** История принадлежности ISRC выводится из файлов (2 437 ISRC переехали со
   счёта 0to8 на счёт Echo8 с 2025-08), не вводится руками. Экспорт Believe по релизам (UPC), ISRC в нём нет.
9. **Порядок:** сначала книга по счёту и ведомость-контроль ноября, потом онбординг через UI (сплиты из файла с
   предпросмотром, «принять строки»), потом пользователи и роли, потом каталог и отгрузка.
10. **Передачу Echo8 как отдельный шаг (дата T, `transferred_at`) не делать.** Нет передачи, есть два арендатора,
    чьи счета пересеклись во времени; книга по счёту закрывает это сама.

## 4а. Консилиум по изоляции (вечер 05.11): арендатор как граница

Уточнение овнера: граница изоляции это не лейбл, а арендатор (владелец одного или двух лейблов); отчёты, владельцы и
псевдонимы арендаторов никогда не пересекаются, даже при двух администраторах. Семь ролей (`консилиум_изоляция/`,
итог в `консилиум_изоляция/итог.md`) единогласно: **пара баз на арендатора** (PostgreSQL + ClickHouse, как уже делают
приватные базы тестов) плюс контрольная база с арендаторами и пользователями. Модули, фасад и D-169 не меняются;
лейблы остаются книгами внутри арендатора; текущие `erp`/`believe` регистрируются арендатором №1 без копирования.

**Решение владельца продукта после консилиума: вариант A, не B.** База на арендатора отклонена как слишком тяжёлая
для первой итерации. Делается таблица `organizations` с настоящими id, `org_id` на каждой строке данных и `label_id` на
деньгах; организация может иметь N лейблов (компаний) с саблейблами. Фильтр по организации ставится централизованно
при открытии модулей, не руками в каждом запросе. ClickHouse без колонок организации и лейбла: выборка по лейблу через
файлы реестра, по саблейблу через алиасы внутри файлов лейбла; книга на строки лейбла не опирается, алиас уникален
внутри организации. Этап описан в брифе, раздел «Граница арендатора».

Что это меняет в плане выше: этап «граница арендатора» (5–6 дней) идёт сразу после D-169, перед пользователями;
пользователи и роли переезжают в контрольную базу; онбординг рождается в форме арендатора; ведомость последней
(ноябрь считается у овнера). Поправка к ответу №10: **системный администратор не видит денег, «Все» принадлежит
администратору арендатора**. Три вещи чинятся до всего: `createPrivateStores` не пишет `schema_migrations`; 500
отдаёт текст ошибки с именами баз; имена баз должен давать только сервер. Десять решений для овнера в итоге консилиума,
раздел 6.

### Ответы по управлению лейблом (05.11, поздно вечером)

Коротко: 0to8 и Echo8 два лейбла одной организации, не пересекаются даже по общему ISRC (книга по файлу); пользователей
заводит администратор руками; разметка договоров по лейблу руками потом; один счёт Believe в двух организациях
допускается; валюта USD, у организации только название; стартовые остатки позже как отдельная сущность «счета
компании»; «решение лейбла» без срока; реклама всегда на лейбл; переход саблейбла и конкурентные правки не
учитывать; права через слой способностей (CASL-подобный) на этапе 3; переключатель организаций при логине; состав
прав системного администратора позже; экспорт, перенос каталога, ASCAP, отгрузка после. Полная таблица в конце брифа.

## 5. Чего не делать

Колонки лейбла в ClickHouse; заголовок `X-Label`; база на лейбл; разметку документов по истории без решения;
период у счёта и у саблейбла до первого реального случая; `created_by` во всех таблицах; отдельный модуль
`catalog`; ручной ввод истории переносов там, где её дают файлы; автоматические переводы денег между книгами
(смена лейбла операции только с причиной и в журнале); переписывание `scripts/mvp/load.ts`.
