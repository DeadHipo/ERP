## Понятный владельцу образец (не обязательно лучший): паблишинг v2 + links (D-182…D-194)

- **pubv2 знает только отчёт:** файл, автор, песня, начисление. Своих связей с деньгами нет.
- **links хранит решения оператора:** автор → владелец, песня → ISRC, условия паблишинга. Записи не правятся: новое
  решение закрывает старое, отмена открывает предыдущее (D-188).
- **Система только рекомендует** (`facade/pubv2-links.ts`), ничего не ставит сама.
- **Деньги читают v2 через `facade/pubv2-source.ts`.** Переключатель `PUBLISHING_SOURCE` и теневой прогон
  `scripts/pubv2/shadow.ts` позволили перейти, не меняя чисел.

## Где связь держится на строке, а не на id

- `believe.rows.label_name` → `labels.label_aliases` (без периода) → лейбл: от этого зависят «наше» и доля
  саблейбла (`facade/layers/label-of-record.ts:10`, `facade/ads.ts:78`, охват `owner-scope.ts:60`).
  - **Цифры на 2026-11-15:** 21 199 ISRC и 34 строки, у каждой строки есть алиас. 17 ISRC сменили строку ровно один
    раз на границе месяца (16 × `0to8` → 77 Records). Двух строк в одном месяце ни у одного ISRC нет. Новых ISRC
    ≈ 1 000 в месяц.
  - **Совместные импринты** («0to8 x Ahh Music», «NoGhost Records / 0to8», «Bleached Records / 0to8») разнесены по
    алиасам непоследовательно. «Ahh Music» — алиас своего 0to8 без правила (≈ $81k считается «нашим»), хотя в
    таблицах владельца это саблейбл.
  - **Набросок решения**, прошедший три аудита:
    - `imprints` — строки с id, только для рекомендаций и отчётов;
    - `isrc_labels` — решение ISRC → лейбл с периодом, единственный вход денег;
    - без решения — C `label_unassigned`;
    - групповое подтверждение новых ISRC и блокирующий сигнал расхождения;
    - миграция непрерывными периодами за переключателем с теневым прогоном;
    - охват владельца перевести на решения.

    Совет может его пересмотреть.
- `source_files.account` → `label_accounts` → книга (D-169).
- B17 v1: `pub_lines.writer_norm` → `pub_writers` → владелец по имени (D-087). В v2 это заменено решением в links.
- `owners.releases.label_string`, `believe.rows.artist_name`: только для показа.

## Как сегодня появляется артист или автор

- **Мастер.** Псевдоним (`owners.artists`) создаётся загрузчиком, импортом сплитов (D-172) или вручную. Поиск дублей:
  `pseudonym_norm`, `GET /artists/duplicates`, слияние `merges` (`mergeOwners`).
- **Паблишинг v2.** Автор (`pubv2.songwriters`) создаётся из отчёта B17. Связь с владельцем — решение оператора в
  `links.songwriter_owner` с рекомендацией по имени (`facade/pubv2-links.ts`).
- **Владелец** (`owners.owners`) — это получатель денег; у него могут быть псевдонимы, автор паблишинга, договоры,
  получатель выплат (`settlements.payees`).
- **Менеджер лейбла** (роль `label_manager`, D-171) видит только свои лейблы.
- **Единой точки «кто это»** (человек → его псевдонимы, авторы, договоры, реквизиты) нет: каждая сторона связывается
  по-своему.
- **`owners` совмещает три темы:** люди (владельцы и псевдонимы), бумаги (документы и договоры), каталог (треки и
  релизы).
- **Аналог `links` в мастере не формализован.** В паблишинге решения оператора лежат отдельно (links), а в мастере
  те же по смыслу решения рассыпаны по разным модулям: сплиты, правила лейблов, договоры.
