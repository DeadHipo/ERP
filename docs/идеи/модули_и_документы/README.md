# Модули и документы: решение совета

Статус: **проект, 2026-11-16. Кода, миграций и записей в базу нет.** Совет прошёл все циклы `spec.md` §4: проверка
фактов, 35 голосов панели продукта, четыре независимых предложения ядра, перекрёстная критика, четыре проверки кодом в
одноразовых копиях, сведение и голосование в два круга, адвокат простоты, приёмка панелью (35 из 35 приняли с
замечаниями, блокеров нет).

## Решение коротко

1. **Новых модулей и таблиц не нужно.** ERP уже устроена по тому же правилу, что понятный владельцу паблишинг v2:
   *отчёт неизменен → решение ставит человек → деньги пересчитываются*. Мастер следует ему так же: отчёты Believe —
   сырьё, сплиты и правила лейблов — решения по id с периодом и документом, расчёт — проекция.
2. **Упрощение — это удаление.** Уходят второй паблишинг (v1), мёртвый архив стартовых остатков, таблицы-копии, отдельная
   запись «договор» рядом с документом и вторая история лейбла трека. Таблиц становится 37 вместо 48, модулей 9
   вместо 10, связей по строке 5 вместо 10.
3. **Модуль документов с провайдерами не строим.** Файл в ERP не хранится, а источник бумаги уже записан в её ссылке.
   Договор становится документом с признаком «договор»; провайдер подключается импортом с пробным прогоном, утверждает
   человек. Подробно — `документы.md`.
4. **«Кто есть кто» — это владелец.** Его карточка становится карточкой человека: ники, автор паблишинга, договоры,
   получатель выплат. При вводе нового ника система по ходу подсказывает похожих; решает человек. Отдельного реестра
   сторон нет: он стал бы четвёртым местом поиска.
5. **Лейбл трека** сегодня решает строка из отчёта, навсегда. Первый шаг — дать этой связи срок действия («строка →
   лейбл с месяца»): это решение человека с датой, ноль новых таблиц, числа те же. Отдельное решение «трек → лейбл»
   по каждому ISRC строим только после ответов владельца (вопрос В1).
6. **Расчёт не трогаем.** Ни одно решение не меняет числа и не открывает закрытые зоны (`calculation.ts`, слои,
   `owner-scope.ts`, математика `balance.ts`): это проверено четырьмя набросками кода. Всё, что могло бы изменить
   числа, вынесено в вопросы владельцу.

Все 27 решений с голосами, отклонённые предложения и ответ по каждой связи «по строке» — `консилиум/итог.md`.

## Какой подход выбран и почему

Совет сравнил шесть подходов из `spec.md` §1 на этом проекте.

| Подход | Вердикт | Почему |
|---|---|---|
| Сырьё → решения → проекции (как pubv2 + links) | **берём как правило** | уже действует во всём проекте; стоит 0 таблиц и 0 понятий; даёт простой тест «это решение или данные?» |
| Порты и адаптеры | берём точечно | только на входе и только там, где есть вторая реализация; интерфейс с одной реализацией будет выдуман неправильно |
| Ограниченные контексты | берём как словарь | граница модуля = граница языка; новых границ не проводим |
| Реестр сторон, «золотая запись» | нет | «золотая запись» уже есть: владелец и след слияний; реестр — ещё одно место поиска |
| Журнал решений одной таблицей | нет | меньше таблиц, но слабее проверки каждого вида решения; второе место правды |
| «Точка чтения» на каждый модуль | нет | +10 файлов; фасад знает модули через общий контекст, связность не падает |

**Чем решение отличается от данных.** Данные — то, что пришло извне, и то, что из этого выведено. Решение — запись
человека, которая меняет толкование неизменного сырья; её не правят, а закрывают новой. Модули сырья (`sources`,
`publishing`) решений не держат.

## Метрики простоты (spec §3)

| Метрика | До | После |

| Таблиц PostgreSQL | 48 | **43 без условий → 42 после В2 → 37 после удаления паблишинга v1** |
| Модулей | 10 | **9** (после удаления v1) |
| Понятий глоссария | 66 | **≈ 66: не улучшена** |
| Связей по строке | 10 | **5** (после удаления v1); деньги меняет одна |
| Межмодульных связей по id | 42 | **39 → 38 → 34** по тем же ступеням |
| Файлов фасада, знающих модуль | owners 26, паблишинг 15 + 3 | owners ≈ 25, паблишинг ≈ 12–13 + 3: **почти не улучшена** |
| Закрытых зон открыть | — | **0** |
| Пунктов меню | 21 | 20 сразу, 19 после v1, 18 с единой очередью |
| Изменение чисел расчёта | — | **нет** |

**Что улучшено:** таблицы, модули, связи по строке и по id, мёртвый груз; закрытые зоны не открываются.

**Что не улучшено и почему.**
- *Понятия.* Из 66 строк глоссария уходит одна. Из живого словаря уходят пары «две версии одного» (паблишинг v1 / v2,
  договор и документ, история лейбла и книга), но общее число слов для нового человека почти то же. Панель просила
  прежде всего словарь на экране (П-14): это подсказки интерфейса, а не структура модулей.
- *Фасад.* Владельца знают почти все ответы, потому что почти каждый ответ — про чьи-то деньги. Совет проверил оба
  способа улучшить метрику (деление `owners`, «точка чтения» на модуль) и отклонил: они убирают строки импорта, но не
  связность, и добавляют модули и файлы.
- *Главный выигрыш отложен.* Пять таблиц и модуль v1 уходят только после решения владельца (В6); до тех пор
  безусловный результат — 43 таблицы.

## Этапы перехода

Каждый этап — отдельная цель со своей D-записью, проверкой «деньги байт в байт» и откатом. Подробно — `этапы.md`.

| Этап | Что | Ждёт владельца |
|---|---|---|
| 1 | Удалить мёртвое и копии: архив стартовых остатков, алиасы паблишинга, связи «ник — трек», пустую колонку | — |
| 2 | Договор становится документом; загрузка договора — один шаг | — |
| 3 | Срок действия у связи «строка отчёта → лейбл» — вместе с первой переразметкой | В1 |
| 4 | История книги трека выводится из файлов | В2 |
| 5 | Удалить паблишинг v1 | В6; не раньше первой выплаты паблишинга под v2 |
| Э | Экраны без изменения таблиц: автор паблишинга на карточке владельца, подсказка дубля по ходу ввода, перенос допуска при слиянии, след скриптов | В5 для слияния ников |
| отдельные цели | Единая очередь решений (Р23); выписка артиста и партнёра (Р26) — это новые функции, а не упрощение | В7 |
| условный | Решение «трек → лейбл» по ISRC за переключателем с теневым прогоном | В1 |

Самое дешёвое упрощение — этап 1: деньги не читают ни одну из удаляемых таблиц. **Не делаем вообще:** модуль документов,
реестр сторон, журнал решений, деление `owners`, «точки чтения», разделение слитых, уникальность имён, автослияние,
автоплатежи.

## Словарь к этому тексту

| Слово | Что значит |
|---|---|
| Книга | свой лейбл (0to8, Echo8), под которым загружен отчёт; деньги и выплата считаются по книгам |
| Срез | состояние книги на выбранный момент; это вид, он ничего не хранит |
| Снимок выплаты | замороженный расчёт, по которому сделана выплата; не меняется |
| C, «ждёт» | деньги, которые посчитаны, но не подтверждены документом или связью; у каждой суммы названа причина |
| Допуск, шлюз выплаты | проверки перед выплатой: договор, порог, холд, получатель, ответ «платить» |
| Импринт, строка лейбла | название лейбла, как его напечатал дистрибьютор в отчёте |
| Алиас | запись «эта строка отчёта — такой-то наш лейбл»; по решению совета получает срок действия |
| Закрытая зона | код расчёта денег, который нельзя менять без отдельного решения |
| Проекция | то, что пересчитывается из отчётов и решений при каждом запросе и нигде не хранится |
| Р, В, С, ПК | номера решений совета, вопросов владельцу, сценариев и проверок кодом |

## Замечания адвоката простоты

Свежий участник, который видел только итог и факты, проверил метрики по коду и базе (`консилиум/адвокат.md`). Вердикт:

не открываются. По его замечаниям итог поправлен:

- метрики переписаны по ступеням (43 → 42 → 37 таблиц): главный выигрыш зависит от решения владельца по v1 (В6);
- метрики «понятия» и «фасад» честно помечены как не улучшенные;
- вопросы D-187 и D-018, которые ждут владельца, названы в В6 и В4 прямо;
- срок действия у алиаса лейбла (этап 3) делается вместе с первой переразметкой, а не «впрок»;
- единая очередь (Р23) вынесена из упрощения в отдельную цель: это новая функция;
- перенос выгрузки релизов в `sources` (Р15) убран из этапов: по метрикам он нейтрален.

Полная таблица «замечание → что сделано» — в конце `консилиум/итог.md`.
