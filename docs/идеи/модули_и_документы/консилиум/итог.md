# Итог совета: решения Р1…Р27

Полные формулировки вариантов и доводы сторон — `сведение_цикл3.md`. Голоса ядра — `<роль>_цикл3.md` и
`<роль>_цикл3_круг2.md` (М — минималист, А — архитектор границ, И — интеграции, Мн — менеджер). Проверки кодом —
`проверки/1…4` (ПК1…ПК4). Принято при перевесе не меньше 3 из 4. Ни одно решение не меняет числа расчёта; всё, что могло
бы их изменить, вынесено в вопросы владельцу (В1…В10, список с рекомендациями — в `README.md`).

## Одной фразой

**Новых модулей и таблиц нет.** Проект уже устроен как «отчёт → решение человека → пересчитываемые деньги»; упрощение —
это удаление второго паблишинга, дублей и мёртвого груза, один датированный алиас лейбла вместо «правды по строке
навсегда», договор как документ и владелец как единственный центр «кто есть кто». Модуль документов, реестр сторон,
журнал решений, деление `owners` и модуль решений мастера отклонены: каждый добавляет больше, чем убирает.

## Что отклонено и почему

| Предложение | Чьё | Почему отклонено |
|---|---|---|
| Модуль документов с N провайдерами | владелец (spec §1) | Файл в ERP не хранится: `file_ref` — метка источника, и провайдер уже записан её префиксом (pandadoc 542, mvp-load 509, legacy-erp 361). Деньги читают из документа четыре вещи, и ни одна не зависит от провайдера. Модуль дал бы +1 модуль, ≥ +1 таблицу, ≥ +2 понятия и открыл бы `calculation.ts`. Против отдельного модуля или экрана — 11 голосов панели |
| Реестр сторон (MDM, «золотая запись») | spec §1, панель П-2 | «Золотая запись» уже есть: владелец + `merged_into` + `ownerResolver`. Реестр стал бы «четвёртым местом поиска», против которого сама панель (менеджер ×3, паблишинг ×2). Потребность П-2 закрывается карточкой владельца (Р19) и подсказкой (Р20) |
| Журнал / ledger решений одной таблицей | spec §1, панель П-7 | У каждого вида решения своя проверка (периоды без пересечений, CHECK видов); в общей таблице она слабеет. Внешний аудитор сам против «второго места правды». Лента собирается из audit и таблиц решений (Р25) |
| Деление `owners` на три модуля | spec §5.1 | +2 модуля, +4 межмодульные связи, открытая закрытая зона; фасаду не легче (Р3) |
| Модуль решений мастера («links мастера») | spec §5.1 | Не убирает ни одной таблицы; `split_shares.artist_id` всё равно остаётся межмодульной связью (Р4). Где образец pubv2 + links ложится на мастер — см. ниже |
| «Точка чтения» на каждый модуль | spec §5.5 | Модули знают фасад через `ctx`, а не через `import`: +10 файлов без падения связности (Р18) |
| `imprints` + `isrc_labels` прямо сейчас | разбор 2026-11-15 | Не отклонено, а отложено до ответа владельца (Р6, В1). Замер: подтверждений «импринт × релиз» было бы 171–343 в месяц, а не 10–20; +1 таблица, +3 понятия, 3 закрытые зоны |
| Таблица исключений по ISRC | Мн, цикл 1 | Снята автором: сегодня исключений 0; три закрытые зоны |
| `links` внутрь `publishing` | М, цикл 1 | Снято автором: таблиц не убирает, «−3 связи» были перекраской; теряется граница «загрузка отчёта не пишет решений» |
| `label_accounts` колонкой лейбла | М | 1 : 3. Втаскивает имя провайдера в лейбл; второй аккаунт вернёт таблицу |
| Признак договора «вид документа» или «заполнены колонки» | М, И, Мн / А | Опровергнуто ПК3: номер пуст у 345 из 818 договоров; «по виду» сделал бы подтверждённым одного владельца (2 документа, 247 строк сплита) — это изменение чисел |
| Колонка «статус подписи провайдера»; живое чтение статуса на карточке | И / М | +1 понятие, которое деньги не читают; зависимость карточки от доступности провайдера (Р17) |
| Страница «Закрытие месяца», экран «Входящие» | панель (бухгалтер главный, оператор новичок) | Р23: связать существующее чек-листом и одной очередью; срез уже есть |

## Какой подход выбран и где образец pubv2 + links ложится (spec §5.2)

Сравнение шести подходов на этом проекте: `архитектор_границ_цикл1.md` §1. Вывод совета (Р1): образец pubv2 + links —
это частный случай правила «сырьё → решение → проекция», и мастер ему **уже** следует: `sources` — сырьё, `splits` и
`labels` — решения по id с периодом и документом, `calculate()` — проекция. Отдельный модуль `links` в паблишинге был
нужен только потому, что решение соединяет два чужих модуля (автор отчёта ↔ владелец). В мастере решения
принадлежат одному языку (сплит по ISRC, правило лейбла) и лежат у своих модулей.

Каждая связь «по строке» (красные 1–10 в `текущая_схема.dbml`):

| № | Связь | Деньги | Решение совета |
|---|---|---|---|
| 1 | `believe.rows.label_name` → `label_aliases` → лейбл | да | **остаётся строкой, но становится датированным решением** (Р6 шаг 1): «строка → лейбл с месяца». В id-связь «ISRC → лейбл» превращается только после ответа владельца (В1) |
| 2 | `source_files.account` → `label_accounts` | только допуск загрузки | **остаётся строкой**: это ключ адаптера на входе; после загрузки книга — id (`source_files.label_id`) |
| 3 | `pub_lines.writer_norm` → `pub_writers` | при v1 | **удаляется** с v1 (Р8) |
| 4 | `pub_lines.songwriters` → `pub_writers` | при v1 | **удаляется** с v1 |
| 5 | `pub_writers.writer_norm` → `owner_aliases` | при v1 | **удаляется** с v1 |
| 6 | `pub_terms.operation_type` → `pub_lines.operation_type` | при v1 | **удаляется** с v1 |
| 7 | имя автора pubv2 → `owner_aliases` | нет, рекомендация | **остаётся строкой**: подсказка; связь ставит человек по id (`links.songwriter_owner`) |
| 8 | имя автора pubv2 → `pub_writers` (`old_map`) | нет, рекомендация | **удаляется** с v1 |
| 9 | название песни → `owners.tracks.title` | нет, рекомендация | **остаётся строкой**: подсказка; связь по ISRC ставит человек (`links.song_isrc`) |
| 10 | `believe.rows.artist_name` → `pseudonym_norm` | нет, рекомендация | **остаётся строкой**: подсказка дублей |

Итог: из десяти строковых связей пять удаляются, одна (единственная, что меняет деньги) становится датированным
решением, четыре остаются строкой как подсказки или ключ входа. Импорты (сплитов, операций) ищут ник по
нормализованному имени на вводе и пишут id — это ввод, а не связь.

## Ответы на споры уровней панели (потребности.md §6)

| № | Спор | Ответ совета |
|---|---|---|
| У-1 | бухгалтер: страница «Закрытие месяца» или связать существующее | Р23: чек-лист закрытия поверх обзора, ведомости и срезов; новой страницы и таблицы нет (сторона младшего). Срез — точка сверки на момент, но он ничего не хранит; требование главного «цифры закрытого месяца нельзя тихо сменить» этой работой не закрыто — вопрос владельцу В10 |
| У-2 | разработчик: интерфейс источника или нет | Р24: без интерфейса (сторона сеньора); джуниору — карта из трёх шагов и тест «числа до и после» |
| У-3 | юрист: статусы подписи как данные или не больше трёх | Р16, Р17: статусов три, вычисляемых (сторона помощника). Договор из PandaDoc появляется импортом с пробным прогоном; расхождение со статусом провайдера видно в очереди. Срок и расторжение — вопрос владельцу (В8) |
