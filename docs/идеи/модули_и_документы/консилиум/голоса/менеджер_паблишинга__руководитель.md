# менеджер_паблишинга / руководитель

1. **Кто я и что делаю каждый месяц.** Отвечаю перед владельцем за паблишинг: грузится ли B17, у каждого ли автора есть человек и условие (процент, документ), куда ушли спорные суммы.

2. **Пять моих сценариев.**
   - **Загрузить квартал B17 и увидеть, что сошлось.** Файл, затем авторы и песни, затем деньги. Работает: страница «Паблишинг v2», вкладка «Авторы и файлы», `POST /publishing-v2/files` (`operations.ts:1676`); замена квартала с подтверждением (`i18n/ru/reference.ts`, `replaceTitle`). Сегодня 7 файлов, 34 автора, 1 169 песен, 4 321 начисление. Старый `/publishing/b17` отказывает в записи (`publishing_v2_active`).
   - **Связать автора с человеком один раз.** Вкладка «Связи»: рекомендация (по песням, по имени, из старого паблишинга), кнопка «Подтвердить». Работает: `POST /publishing-v2/links`, решение хранится и не правится, а закрывается новым (`links.songwriter_owner`: 33 связи на 34 автора, один без связи). Ограничение: связываю только с владельцем. Увидеть человека целиком (псевдонимы, договоры, реквизиты) нельзя.
   - **Задать условия: процент владельца с даты, с документом.** Работает: диалог «Сплит владельца», `POST /publishing-v2/terms`, отмена только последнего (`/terms/:id/cancel`); 101 условие. Без утверждённого документа деньги ждут в C `publishing_terms_unconfirmed` (`i18n/ru/reasons.ts`). Условие по типу операции (механика, исполнение, синхронизация) во второй версии я не нашёл.
   - **Привязать песню к ISRC (выкуп, 0 % на песне).** Вкладка «Треки», кандидаты по названию (`GET /publishing-v2/songs/:id/candidates`), условие по ISRC. Работает, но вручную: 18 песен с ISRC из 1 169. Если у ISRC песни разные условия, деньги ждут; об этом говорит только подсказка на странице.
   - **Разобрать спор: кому ушли деньги автора и почему.** Частично. Баланс владельца показывает `publishing[]`, очередь C называет причину. Цепочки «автор в отчёте, затем кто решил его связать, затем условие, затем документ, затем сумма» одной страницей нет. Решение читаю на «Связях» (`Решил: …`), условия на другой вкладке, документ в другом разделе.

3. **Три боли сегодня.**
   - **Два паблишинга в навигации** («Паблишинг» и «Паблишинг v2», `nav.ts`). Старый ничего не пишет, но лежит рядом, и я проверяю, на какой я.
   - **Человек разбросан.** Автор связан с владельцем в `links`, псевдонимы мастера лежат в другом модуле, получатель выплат в третьем. Что у человека с паблишингом, мастером и договором, собираю сам.
   - **Песня и ISRC связываются вручную и по названию.** 1 151 песня без ISRC. Совпадение «по названию» может оказаться чужой песней, а ошибку увидит только тот, кто знает каталог.

4. **Что нельзя ломать.**
   - Рекомендация ничего не решает: связь появляется только после моего «Подтвердить».
   - Решения не правятся, а закрываются новыми, и остаётся история с именем решившего.
   - Деньги без документа ждут в C и не уходят молча.
   - Паблишинг не влияет на числа мастера и балансы; расчёт и срезы остаются байт в байт.
   - Загрузка квартала через замену, а не дубль.

5. **Что я сочту усложнением.**
   - Ещё один реестр «людей» рядом с владельцами и авторами, если он не заменяет, а дублирует.
   - Второй шаг подтверждения (я утвердил, потом ещё кто-то должен), пока объёмы 34 автора.
   - Общий журнал решений, где связь автора лежит среди назначений лейблов и правил: мне нужен свой фильтр.
   - Любая страница, куда ради одного решения надо ходить после «Связей».
   - Разбор PDF с обязательной проверкой по каждому договору.

6. **Чего не хватает продукту.**
   - **Карточка человека** (владелец с его авторами, псевдонимами, договорами, условиями и получателем): иначе каждый спор собирается вручную из пяти мест.
   - **Подсказка о дубле при появлении нового автора** (то же имя или те же слова в другом порядке уже есть как владелец или псевдоним): сегодня она есть только на «Связях» и после загрузки.
   - **Одна очередь «паблишинг ждёт»** (автор без связи, условие без документа, песня без ISRC, версии условий расходятся) с действием в строке: сейчас это три вкладки и очередь C.
