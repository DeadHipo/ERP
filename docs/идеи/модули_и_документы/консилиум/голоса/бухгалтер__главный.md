# бухгалтер / главный

1. **Кто я и что делаю каждый месяц.** Главный бухгалтер: закрываю месяц (A = B + C + наше по аккаунту и месяцу), сверяю payroll с кассой, отвечаю владельцу и проверяющему за каждую цифру.

2. **Пять моих сценариев.**
   - **Сверка месяца A = B + C + наше.** Открыть «Обзор», выбрать месяц, увидеть строки по источнику, аккаунту и месяцу, и что A сошлось. Работает: `OverviewPage.tsx`, `GET /overview` (одна калькуляция со строками сверки, очередью C и сигналами, `operations.ts:1070`). `GET /reconciliation` на экране нет: сверка ушла в обзор (`api/coverage.ts:137`).
   - **Payroll месяца.** Выбрать лейбл, `asOf`, область, получить строки владелец × псевдоним, итог с гейтом, листы «ожидание», «выкупы», «контроль», выгрузить csv. Работает: `GET /owners/payroll`, csv по листам (`operations.ts:1652`), кнопка `owners/components/PayrollExport.tsx`. Считает хорошо. Но у лейбла один сквозной отчёт по всем книгам не собирается, только по одному лейблу.
   - **Срез на дату («Кабинет 15.10»).** Показать состояние книги на момент и движение после. Работает: `/settlements/cuts`, `/owners/:id/cuts`, страницы `operations/cuts/*`, баланс `?cut=`. В живой базе один срез.
   - **Объяснить цифру проверяющему.** От суммы владельца дойти до ISRC и месяца, оттуда до строк отчёта. Работает: `GET /tracks/:isrc/money`, `/explain`, `/breakdown/:month`, страница строк источника `SourceLinesPage.tsx`. Путь длинный: баланс владельца, трек, месяц, строки.
   - **Закрыть выплату с основанием.** Видеть снимок выплаты и подтверждение. Частично: `GET /settlements/operations/:id/snapshot` есть, но в базе 0 снимков из 4 058 операций: почти всё внесено как `migration`, кнопкой выплат почти не пользовались. Основание лежит в документе, а не в снимке. Журнала аудита как экрана нет: `GET /audit` показан только вкладками истории (`coverage.ts:177`); 251 запись.

3. **Три боли сегодня.**
   - **Сходимость доказываю тремя местами.** Обзор показывает A = B + C + наше, payroll имеет лист «контроль», баланс владельца считает по позициям псевдонимов. Совпадение этих трёх проверяю сам; единой страницы «месяц закрыт, вот почему сошлось» нет.
   - **«Ники не сальдируются» (D-181).** `payable` по формуле и `payableShown` (то, что платят) различаются. Для отчёта владельцу нужно помнить, какое число брать. Это правильно по сути, но без подсказки на экране объяснять разницу приходится устно.
   - **Книга и лейбл по строке.** Доля «наше» зависит от строки лейбла в Believe через алиасы (`label-of-record.ts`). Совместные импринты разнесены непоследовательно: «Ahh Music» считается нашим (около $81k) без правила. Это прямо влияет на мою итоговую цифру, а найти это можно только знанием.

4. **Что нельзя ломать.** Расчёт из сырых строк, ничего не хранится как начисление. Пересчёт байт в байт: `calculation.ts`, слои, `balance.ts`. Причина C всегда названа (`C_REASONS`). Срезы и `asOf` как вырезка входов, а не новый расчёт. Снимок выплаты замораживает числа. Позиция по псевдониму. Целые центы и точные десятичные. Любое разделение модулей обязано дать те же ответы.

5. **Что я сочту усложнением.**
   - Любая новая сущность между отчётом и итогом: ещё одна «версия правды» для суммы.
   - Новое понятие вместо «срез» (я уже знаю срез, `asOf`, `cut`: три слова на один смысл) и дополнительные страницы вместо одной точки проверки месяца.
   - Решения о лейбле ISRC, которые меняют «наше» без показа разницы до и после на моих цифрах.
   - Обязательное подтверждение на каждый новый ISRC (около 1 000 в месяц), если его нельзя сделать группой.
   - Провайдерные адаптеры документов, видимые мне как ещё один экран.

6. **Чего не хватает продукту.** Страницы «Закрытие месяца»: одна на месяц и книгу, где сходится A = B + C + наше, открытые сигналы и очередь C, payroll и дельта к прошлому месяцу, с отметкой «закрыто» и неизменяемым снимком, чтобы цифры отчёта владельцу нельзя было тихо сменить задним числом. Ещё нужен читаемый журнал аудита (кто, когда, на каком основании), потому что проверяющий спросит именно это, а экрана нет.
