# Минималист, цикл 1: сначала удалить

Угол: минус таблицы и минус понятия. Новых таблиц и модулей в предложении **ноль**. Цифры из кода и SELECT от
2026-11-16 (`факты.md`, `цикл0/*`, свои запросы: они отмечены «SELECT»).

Подход §1: **«сырьё → решения → проекции» уже действует**, ничего поверх него не строить. Отчёты неизменны (Believe, B17),
решения человека уже лежат отдельными строками с периодом и документом (сплиты, участия, правила, алиасы, связи автора),
деньги — пересчёт. Порты/адаптеры, MDM, журнал решений и «точка чтения» добавляют понятия, а таблиц не убирают: отклонены.

Ответы на §5 в моём углу:

- **Делить owners на люди / бумаги / каталог — нет.** Деление не убирает ни одной таблицы, добавляет два модуля и
  межмодульные id (сегодня это синие связи внутри owners). Панель сама назвала это усложнением. Owners худеет удалением:
  11 → 7.
- **Модуль решений для мастера — нет.** В мастере ISRC есть в самом отчёте, поэтому сплит, участие и правило уже и есть
  «links»: строка решения с документом и периодом. В паблишинге v2 отчёт не знает ни владельца, ни ISRC, поэтому там
  связи нужны. **Решение** — строка, которую пишет человек (или загрузчик от его имени), с периодом или закрытием новой
  строкой; она меняет толкование неизменного отчёта. **Данные** — то, что пришло извне (отчёт, экспорт, индекс), и то,
  что из них выводится. Выводимое не хранится: отсюда удаление `track_labels`, `artist_tracks`, алиасов pubv2.
- **Лейбл ISRC (П-1, 17 голосов) — без `imprints` и `isrc_labels`.** Строка → лейбл уже решение оператора: 34 строки
  алиасов на 21 199 ISRC. Новая строка не меняет «наше» молча: она уходит в C `label_unmapped` (сегодня таких 0). Чего не
  хватает — **периода у алиаса**, чтобы смена (например, «Ahh Music») шла с месяца и не переписывала оплаченное.
  `labelOf(labelString, date)` уже принимает дату (`modules/labels/service.ts:279`, `layers/label-of-record.ts:10`,
  `ads.ts:79`), значит период ставится внутри модуля labels, без открытия слоёв. Решений в месяц: 0–2 на строку против
  ≈ 1 000 на ISRC. Ответ «чей ISRC с какого месяца и почему» — одно чтение: строки ISRC по месяцам из CH + алиас с
  периодом + книга файла. Хранимых историй лейбла: **две → ноль** (не три).
- **Модуль документов — нет; меньшее.** Деньги читают из документа четыре вещи: статус, вид `assumption`, `label_id`
  договора, порог. Провайдер уже записан префиксом `file_ref` (pandadoc 542, mvp-load 509, legacy-erp 361, pack 28,
  start-to-cut 2). Сущность остаётся одна (`owners.documents`). **Договор = документ** вида contract / label_decision с
  владельцем: колонки `number` и `payout_threshold_cents` переезжают в documents, таблица `contracts` уходит (818 строк,
  1:1 с документом, владелец совпадает у всех: SELECT). `contract_artists` (809) деньги не читают: удалить. Статусы те же
  три, вычисляемые. Перенос 1 447 документов: ноль строк, только 818 пар колонок. Подпись, срок и расторжение — у
  провайдера: карточка показывает ссылку и `legal_status` final_index по sha256, ERP это не хранит и деньги это не читают.
  Интерфейс провайдера — когда появится вторая живая интеграция (PandaDoc-вебхук), не раньше.
- **«Кто есть кто» — владелец как центр, без реестра сторон.** На карточке владельца уже есть псевдонимы, документы,
  допуск (`payees`); не хватает только автора pubv2 (связь уже есть в `songwriter_owner`): это чтение, не таблица.
  **Подсказка дублей** — одна функция по `normalizeName` над `owner_aliases` + `artists.pseudonym_norm` +
  `songwriters.name`, вызываемая и при вводе, и в `newArtistPseudonym` (сейчас там её нет). Предлагает система, связывает
  человек. Уникальность имён в базе не вводить (20 групп одноимённых псевдонимов законны).
- **Слияние:** `mergeOwners` оставить. Не переносимые им `payees`, `holds`, `payout_answers` читать через `ownerResolver`,
  как читает расчёт, без переписи строк. Разделение не строить (2 слияния за всё время). `mergeArtists` не удалять:
  других способов закрыть 20 групп одноимённых псевдонимов нет.
- **Фасад:** новой «точки чтения» на модуль не вводить (это слой ради слоя). Фасад худеет удалением: v1-ветки
  `sources.ts`, наследование `Object.create(publishing)` в `pubv2-source.ts:121`, запись `track_labels` в `catalog.ts`,
  мёртвый `openCatalog` (`catalog.ts:447`), маршруты `routes/publishing.ts` (58 строк).

## 4. Что открывается в закрытых зонах

**Ноль**, при одном условии: новый модуль `publishing` (бывший pubv2) сохраняет экспорт `parseSongwriters` и тип
`PublishingService`. Тогда `layers/writer-parts.ts:3` и `calculation.ts:7` не меняются ни строкой. Без условия — две
строки импорта, логика не трогается. Период алиаса — внутри `labels/service.ts`; `owner-scope.ts:64` получает алиасы
саблейбла за все периоды (надмножество, охват не сужается). Договор как документ — внутри `owners` (методы
`confirmedOwnerIds`, `confirmedContracts`, `approvedContracts` с прежними подписями).

## 5. Риски

- **Golden-тесты строят мир через v1** (18 файлов). Переписать на v2 — главная цена; слой `writer-parts` при v2 получает
  `songwriters: null` и остаётся живым, но непроверенным кодом закрытой зоны.
- **Договор = документ меняет числа у двух владельцев:** 11 документов вида contract / label_decision без записи
  `contracts`, у 2 из них есть владелец без другого договора (SELECT). После слияния они стали бы подтверждены → деньги
  из C в B. Вопрос 4.
- **История книги из CH:** `aggregates.ts:259` (видимость каталога менеджеру) сегодня читает PG; нужен вид CH и замер.
- **Период алиаса:** проверить, что `ads.ts:77` (строка ближайшего месяца) и охват дают те же числа при неизменных
  алиасах (теневой прогон должен совпасть байт в байт, потому что периоды открыты с начала).
- **Слияние links в publishing** может размыть понятный владельцу образец; граница остаётся на уровне таблиц и тест «загрузка
  отчёта не пишет в таблицы решений».
- Удаление алиасов pubv2 вернётся таблицей, если появятся два написания одного автора (сегодня 0).

## 7. Споры уровней

- **У-1 бухгалтер:** прав младший: чек-лист на обзоре поверх ведомости и срезов (срез уже неизменяемый снимок); ни
  страницы, ни таблицы «закрыто».
- **У-2 разработчик:** прав сеньор: интерфейса без второй реализации не вводить; Believe и B17 уже две загрузки — хватит
  одностраничной карты «куда добавить источник» и обязательного теневого прогона.
- **У-3 юрист:** статусов документа три, деньги читают только «утверждён»; подпись, срок, расторжение — показ из
  final_index на карточке, не хранение; холд на ISRC меняет допуск — вопрос владельцу.
- **У-4 аудитор:** прав внешний: журнал уже есть (`audit.actions`, 251 запись); «было/стало» — в его `summary`, не вторая
  таблица.
- **У-5 оператор:** прав опытный: одна очередь = существующая `queue.ts` с сигналами и чек-листом, чтение, без «входящих».
- **У-6 владелец:** прав операционный по модулям (ни реестра, ни модуля); основатель получает карточку владельца как
  «кто есть кто» — чтение поверх тех же таблиц.
