# Архитектор границ, цикл 1: граница «отчёт / решение / деньги»

## 0. Вывод в трёх строках

1. Мастер **уже** устроен как pubv2+links: сырьё (`sources`) → решения (`splits`, `labels`) → проекция (`calculate()`).
   Модуль решений для мастера не нужен, реестр сторон не нужен, модуль документов не нужен.
2. Единственная строковая связь мастера, которая меняет деньги, — `label_name` → `label_aliases`. Её чинит **период и
   основание у алиаса** (решение «строка → лейбл с месяца»), а не `isrc_labels`: 0 новых таблиц, 0 закрытых зон,
   потому что `labelOf(string, date)` уже принимает дату (`modules/labels/service.ts:279`, `layers/label-of-record.ts:10`,
   `ads.ts:79`).
3. Удаляется publishing v1 и `opening_balances`: −6 таблиц, −5 красных и −7 зелёных связей.

## 1. Целевая карта модулей

**Выбранный подход:** «сырьё → решения → проекции» как правило классификации, а не как новый модуль. Решения живут в
модуле, на языке которого они сказаны (ограниченные контексты); общей таблицы-журнала нет. Порты и адаптеры — только
там, где уже есть второй провайдер (метка в `file_ref`). Пофайловых «точек чтения» не добавляем: роль общего порта уже
играет интерфейс `Modules` в `calculation.ts`.

| Модуль | Таблицы | Что знает | Род | Кто читает |
|---|---|---|---|---|
| sources | `source_files` + CH `believe.rows` | строки Believe как в файле | сырьё | `calculate()` (снимок), отчёты |
| pubv2 | files, songwriters, songwriter_aliases, songs, song_aliases, accruals (6) | отчёт B17 | сырьё | `pubv2-source.ts`, `pubv2-links.ts` |

**Ответы на spec §5 в моём углу.**

- **Делить ли owners на три модуля? Нет.** Деление переводит 4 серые связи (FK `documents.owner_id`, `contracts.owner_id`,
  `contract_artists.artist_id`, `artist_tracks.artist_id`) в зелёные. Это +2 модуля и +4 связи на фасаде, а использование
  owners в фасаде (26 файлов) не уменьшится. Панель сама называет такое деление усложнением (разработчик-сеньор,
  менеджер-опытный).
- **Модуль решений для мастера? Нет.** Решения мастера уже есть, они по id и с периодом: строка сплита (документ,
  период, M52), правило саблейбла (документ, период), владелец псевдонима (ставится один раз, `artist_owner_fixed`).
  Перенос их в «links мастера» только переименует таблицы: зелёных связей не станет меньше (`split_shares.artist_id`
  останется межмодульной). У pubv2 `links` отдельный, потому что pubv2 — модуль сырья, а сырьё решений не хранит. У
  мастера сырьё лежит в ClickHouse, и решений там тоже нет. Правило одно: **модули сырья (sources, pubv2) решений не
  держат**.
- **Решение против данных модуля.** Решение — запись оператора, которая связывает сырьё (ключ или строку дистрибьютора)
  или две сущности, с периодом, основанием и автором. Его не правят: новое закрывает старое, отмена открывает
  предыдущее (дисциплина D-188). Проверка: если удалить запись, поменяется, кому идут деньги. Данные модуля —
  факты источника или собственные сущности (лейбл, владелец, документ). Дисциплина D-188 становится общим помощником в
  `shared`, а не таблицей.
- **Журнал решений (ledger) отвергнут.** У каждого вида решения своя проверка: exclusion по периоду ISRC, CHECK видов
  документа. В одной таблице она слабеет. Лента «было/стало» — это чтение по `audit.actions` и таблицам решений.
- **MDM / реестр сторон отвергнут:** «золотая запись» уже есть — `owners.owners` с `merged_into`, `owner_aliases` и
  `ownerResolver()`. «Кто есть кто» = **владелец как центр**. Псевдоним, автор (`links.songwriter_owner`), документ,
  договор и получатель уже связаны с ним по id. Карточка человека — это чтение `ownerDetail` плюс автор pubv2.
- **Подсказки дублей** — функция в `facade/search.ts` без таблиц. Она работает **до** нажатия «Создать», в том числе в
  `newArtistPseudonym` сплита. Признаки: `pseudonym_norm`, имя или алиас владельца, имя автора pubv2, ISRC в чужом
  сплите, совпадение `payee_ref`. Предлагает система, решает человек.
- **Слияние:** `mergeOwners` должен переносить `payees`, `holds`, `payout_answers` (сейчас они остаются на слитом id;
  на живых данных таких строк 0, числа не меняются). Разделение пока не делаем: слияний всего 2.
- **Модуль документов: меньшее.** Новой сущности и таблицы нет. Провайдер = адаптер-скрипт, который пишет через фасад
  с `file_ref = <провайдер>:<id>`: так уже сделано для 542 `pandadoc:`, 509 `mvp-load:`, 361 `legacy-erp:` и 28 `pack:`.
  Источник на экране — префикс `file_ref`. Деньги по-прежнему читают только статус «утверждён», вид `assumption`,
  `label_id` договора и порог. Переносить 1 447 документов не нужно. Слить `contracts` в `documents` **нельзя без
  изменения чисел**: 11 документов вида contract / label_decision без строки `contracts` стали бы договорами и
  подтвердили бы владельцев.
- **Фасад:** точку чтения на модуль не делаем. Модули знают фасад через `ctx`, а не через `import` (owners: 8 импортов
  и 26 использований), поэтому переименование ничего не снимет. Реальное сокращение даёт удаление v1:
  `pubv2-source.ts` становится единственным портом паблишинга.

## 3. Что удаляется

- `publishing.*` (5 таблиц), `modules/publishing`, `routes/publishing.ts`, страница P18, `oldPublishingClosed`,
  `old_map` в `pubv2-links.ts`, `Object.create(publishing)` в `pubv2-source.ts:121`. Сначала по умолчанию включаем
  `PUBLISHING_SOURCE=v2` и переносим 18 файлов тестов и 15 скриптов.
- `settlements.opening_balances` (по D-205 это архив, а архив живёт в бэкапе).
- Предложение `isrc_labels` / `imprints` как отдельные таблицы.
- **Не удаляю `track_labels`.** Идея заменить её вьюхой в ClickHouse отклонена: каталог-менеджер в «нельзя ломать»
  назвал операторские интервалы `[с, по)`. На экране таблица называется «Книга», рядом показывается «лейбл записи» из
  алиаса за месяц.

## 4. Что открывается в закрытых зонах

- `layers/writer-parts.ts`: одна строка импорта. `calculation.ts`: один импорт типа. Числа golden-тестов байт в байт.
- Алиас с периодом: **ни одной** зоны. Меняется `labels/service.ts` `index()`: `byAlias` → поиск по `(alias_norm,
  дата)`, плюс миграция. Все 34 алиаса получают открытый период, поэтому `labelOf` отвечает так же. Теневой прогон
  всё равно обязателен.

## 5. Риски

1. Одна строка Believe на разных лейблах у разных ISRC (совместный импринт на двух партнёров) этим не выражается.
2. Перепривязка задним числом (например, Ahh Music) **меняет числа** истории и срезов. По умолчанию она действует с
   открытого месяца; задним числом — только по слову владельца и с корректировкой на срез.
3. Удаление v1 — самая дорогая работа: golden и 17 других файлов тестов нужно перестроить на v2 с равенством байт в
   байт.
4. owners остаётся большим (1 847 строк); облегчаем его файлами внутри модуля, а не новыми модулями.
5. Чтения строк «без алиаса» (`reports.ts`, `onboarding.ts`) должны учитывать месяц алиаса, иначе сигналы и деньги
   разойдутся.

## 7. Ответ на споры уровней

- **У-1:** прав младший. Новой страницы и таблицы нет; «закрытие» = чек-лист `onboarding` + срез (он и есть
  неизменяемый снимок) + пункт «строки без решения за месяц».
- **У-2:** прав сеньор. Интерфейс источника появится вместе со вторым дистрибьютором; порт уже есть — снимок `Modules`.
- **У-3:** статус подписи — данные провайдера, деньги его не читают; деньги читают три статуса. Модуля нет.
- **У-4:** прав внешний аудитор. Журнала событий нет; лента «было/стало» — чтение по `audit` и таблицам решений с
  дисциплиной D-188.
- **У-5:** прав опытный. Одна очередь — это чтение поверх C и сигналов, новое хранилище не нужно.
- **У-6:** прав операционный. Реестра нет; «кто есть кто» — карточка владельца (чтение).
