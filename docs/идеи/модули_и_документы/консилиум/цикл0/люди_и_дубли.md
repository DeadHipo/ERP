## 3. Поиск дублей и подсказки

- **`GET /artists/duplicates`** (`facade/search.ts:59`): группы живых псевдонимов с одинаковым `normalizeName`, для каждого — число строк сплитов и участий, владелец, статус, и `candidateIsrcs`: ISRC без сплита, у которых имя артиста в Believe (`sources.pairAttributes`) после `normalizeName` совпало с группой, с `net`. Порогов нет. Менеджеру фильтруется по видимым артистам и ISRC.
- **`GET /search`** (`facade/search.ts:24`, `owners.search`): подстрока (`containsText`) по имени и алиасам владельцев, псевдонимам, трекам, названиям документов; по 10 на вид; точный ISRC/UPC первым. Дубли не ищет.
- **`findSimilarOwners`** (`modules/owners/service.ts:336`): совпадение `name_norm` → `['name']`; алиас → `['alias']`; те же слова в другом порядке (`tokens` = нормализованные слова, отсортированы, ключ из ≥2 слов) → `['name words']`. Слитые пропускаются.
- **`findOwnersByWriter`** (:373): точный нормализованный алиас или равный IPI, только `person`.
- **Рекомендации `facade/pubv2-links.ts`** (автор → владелец), порядок в `recommend` (:25) и `pubV2Links`:
  1. `songs`: владелец, к которому ведут песни автора (название → ISRC с тем же `baseTitle` → открытый сплит → псевдоним → владелец `person`); лидер, если у первого ≥ половины песен автора и (второго нет или у первого ≥ 2× второго) (:260-);
  2. `old_map`: любой алиас автора есть в карте v1 `pub_writers` с владельцем (владелец проходит `resolveOwnerId`);
  3. `exact_name`: ровно один `person`-владелец по `findOwnersByWriter`;
  4. `same_words`: ровно один `person` по `findSimilarOwners`.
  Рекомендация только показывается; запись в `links.songwriter_owner` — решение оператора (`source` = `recommended`, если совпало с подсказкой, иначе `manual`). Порогов в процентах и расстояния Левенштейна нет.
- **Кандидаты песня → ISRC** (`catalog()`, :52): `baseTitle` = `normalizeName` от названия без `(…)`, `[…]` и хвоста « - …»; кандидаты — все треки каталога с тем же базовым названием; `reason: owner`, если среди псевдонимов открытого сплита этого ISRC есть владелец автора, иначе `title`; в карточке песни дальше сортировка: owner → есть соавтор из другого автора → прочие (`setPubV2SongIsrcs` принимает только ISRC из каталога; один ISRC на двух песнях одного автора — `isrc_on_songwriter_song`).
- **UI при заведении**: `CreateArtistDialog.tsx` (`POST /artists`) и `CreateOwnerDialog.tsx` показывают `DuplicateDialog` (`components/DuplicateDialog.tsx`) только на ответ 409: список похожих, «тот же» (просто открывает найденного, ничего не связывает) и «новый» (повтор с `force`). Подсказки по автору паблишинга, ISRC в чужом сплите, договору нет; подсказка идёт после нажатия «Создать», а не по ходу ввода.

## 4. Слияние

- **`facade.mergeOwners`** (`facade/owner-view.ts:149`, `POST /owners/merge`, способность `approve`): одна транзакция; отказ `payout_blocked`, если у сливаемого есть выплата без подтверждения. Затем:
  - `owners.mergeOwners` (`service.ts:970`): только `person`↔`person` или `label`↔`label` (`merge_kind_mismatch`); сливаемый — без утверждённых документов, цель — подтверждённый (`merge_direction`); переносятся `artists.owner_id`, алиасы (`ON CONFLICT DO NOTHING`, затем удаляются у источника), `documents.owner_id`, `contracts.owner_id`; ставится `merged_into`; пишется `merges`;
  - `publishing.reassignOwner`: v1 `pub_writers.owner_id` + `resolution='merged'`; под v2 адаптер (`facade/pubv2-source.ts:118`) ещё и `links.songwriter_owner.owner_id` (D-194);
  - `settlements.reassignOwner` (`repository.ts:166`): **только `operations.owner_id`**.
- **Не переносится:** `settlements.payees`, `holds`, `payout_answers` (читаются точным `owner_id`, `facade/admission.ts:101`, `context.ts:266`), `links.publishing_terms`, `publishing.pub_terms` (D-194: условия остаются на своей записи, выбор в `ownerTermAt`/`isrcTermOf` берёт сначала условия цели, потом слитого), `ads.expenses` (там только `artist_id`), артисты и их ссылки в сплитах/операциях (артисты не меняются), `payout_snapshots.payload` (замороженный JSON с `ownerId` и `artistId`, 0 строк в живой базе).
- **Как читает расчёт:** `owners.ownerResolver()` (`service.ts:453`) — синхронный `resolve` по `merged_into` (до 50 шагов, длиннее — `ConflictError`, неизвестный id — сам себя). Расчёт получает его в `calculation.ts:184,263` (с мемо) и применяет в `layers/writer-parts.ts:99,123` и `layers/author-share.ts:23`; артисты резолвятся через `artistIndex` (`service.ts:536`: `id` слитого → живой id, владелец тоже резолвится). Чтения по `owners.resolveOwnerId` на входе методов (balance, payouts, admission, cuts, ads, onboarding).
- **История денег и снимки выплат:** строки операций и сплитов не переписываются (операции — только `owner_id`, перенос на цель); снимок выплаты хранит id как были, чтение идёт через `resolve`. Слитый владелец остаётся в таблице с `merged_into`, `merges` хранит причину.
- **Разделения (unmerge) нет:** в коде нет метода, роута и UI; перенесённые алиасы у источника удаляются, документы и договоры переписаны на цель, так что восстановить можно только вручную.
- **Слияние псевдонимов** `mergeArtists` (:1000): переносит `artist_tracks` и `contract_artists`, ставит `merged_into`, пишет `merges`; запрещено, если у сливаемого владелец не совпадает с целью (`merge_owner_conflict`); сплиты и операции не переписываются, их читают через `artistIndex`. Не вызывается нигде, кроме тестов (`tests/scope.test.ts`, `aggregates.test.ts`, `review-*.test.ts`).
- В живой базе: 2 слияния владельцев (D-215, `scripts/stage3/add-index-contracts.ts:77` через `f.mergeOwners`); на слитых владельцах строк в artists, payees, holds, operations, links.publishing_terms ноль.
