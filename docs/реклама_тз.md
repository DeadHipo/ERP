# ТЗ: рекламные расходы в ERP

Дата: 2026-11-03. Основание: решения владельца D-155 (модель) и D-156 (реализация), факты и вопросы в
[рекламные_расходы_вопросы_владельцу.md](рекламные_расходы_вопросы_владельцу.md).

## 1. Задача

Оператор вносит рекламные расходы. ERP решает, кто их несёт, и уменьшает «к выплате» у тех, с кого расход
возвращается. Как и всё в ERP, это пересчитывается с нуля при каждом запросе: хранятся только записи о расходах,
результат распределения не хранится.

## 2. Запись о расходе

Каждый приход данных даёт **новую запись**. Запись не меняется, кроме двух полей (процент и область) и
деактивации. Агрегация по ISRC и месяцу происходит при расчёте.

| Поле | Обязательно | Смысл |
|---|---|---|
| ISRC | да (кроме миграции с указанным псевдонимом) | трек, к которому привязан расход: по нему берутся сплит и лейбл записи |
| Месяц | да | месяц расхода; сплит берётся на первое число этого месяца |
| Сумма | да | USD, больше нуля, до центов |
| Процент возврата | да, по умолчанию 100 | 0–100: какую часть расхода возвращаем с артистов; меняется в любой момент |
| Область погашения | да, по умолчанию «весь баланс» | весь баланс / только паблишинг / только доход этого ISRC; после D-157 на деньги не влияет (реклама вычитается сразу), хранится для владельца |
| Псевдоним | нет | если указан, весь расход относится на этот псевдоним без сплита (история Main, где расход уже распределён) |
| Внешняя ссылка | нет | ссылка на пост или строку источника; повторная загрузка с той же ссылкой пропускается |
| Комментарий | нет | |

Документ-основание **не нужен** (D-155). Кто и когда внёс или изменил запись, видно в журнале действий.

## 3. Расчёт одной записи

1. **Кто артисты.** Сплит ISRC на месяц расхода. В расчёт идут только строки артистов: строки псевдонимов
   MC и строки владельцев-лейблов (бренд, саблейблы) не несут рекламу. Их доля перераспределяется на остальных.
2. **Доли.** Сумма делится между артистами пропорционально их процентам в сплите (12 знаков, остаток крупнейшей
   доле).
3. **Возврат.** С каждого артиста возвращается `доля × процент возврата`. Эта сумма **вычитается из «к выплате»
   сразу и целиком**, как выплата, даже если дохода не хватает (D-157, как в Main). Процент можно поменять задним
   числом: «к выплате» пересчитается и может уйти в минус.
4. **Невозвращаемая часть** (`сумма − Σ возврат`) несёт:
   - **саблейбл**, если лейбл записи трека саблейбл и в месяце расхода действует его правило: вычитается сразу у
     псевдонима-получателя правила;
   - иначе **мы**: минус в «нашем» по лейблу записи.
5. **Особые случаи.**

| Случай | Что происходит |
|---|---|
| У ISRC нет сплита | весь расход наш, запись в статусе «нет сплита»; появится сплит, пересчёт перенесёт расход на артистов |
| В сплите только MC и лейблы | артистов нет: весь расход невозвращаемый, несёт саблейбл или мы (п. 4) |
| Артист без подтверждённого владельца | долг считается, выплата заблокирована, как обычно |
| Псевдоним указан явно | доля одна, 100 % на этот псевдоним; невозвращаемая часть по п. 4 |

**Пример.** Трек 60/40 между двумя артистами, плюс MC 0 %. Реклама 100, процент возврата 50, область «весь баланс».
Доли: 60 и 40. Возврат: 30 и 20, это долги артистов. Невозвращаемое: 50. Трек саблейбла с правилом: долг 50 на
саблейбле. Трек 0to8: минус 50 в нашем.

Ещё пример базы (D-155): доход трека 100, сплит 50/50 артист/лейбл, реклама 40, 100 %. Артист получает
50 − 40 = 10, лейбл 50.

## 4. Где это видно

- **Баланс владельца:** список списанной рекламы (ISRC, месяц, псевдоним, кто несёт, сумма) и итог «реклама
  (списана сразу)», который уменьшает «к выплате».
- **Страница «Реклама»:** сводка по месяцам и лейблам записи (всего, вернуть с артистов, несут саблейблы, несём мы,
  без сплита), список записей с фильтрами (ISRC, псевдоним, месяц, статус), добавление записей, смена процента
  и области, деактивация.
- **Сверка A = B + C + наше не меняется:** она про доход. Реклама уменьшает «к выплате», а наш минус виден в
  сводке рекламы.

## 5. API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/ads` | записи с распределением; фильтры `isrc`, `artistId`, `ownerId`, `from`, `to`, `status`, `limit` |
| POST | `/ads` | пакет записей `{ items: [...] }`; записи с уже известной внешней ссылкой пропускаются |
| GET | `/ads/summary` | сводка по месяцам и лейблам записи, `from`, `to` |
| PATCH | `/ads/:id` | процент возврата и/или область |
| POST | `/ads/:id/deactivate` | деактивация с причиной |

Как и все записи, требуют `X-Operator`.

## 6. История из 0to8 Main

- Источник: колонка «expense posted» на строках INCOME/EXPENSE (и листа Echo8); на каждой строке ник артиста и
  отчётный месяц. Колонка «ОБНУЛИТЬ ADS расход»: `1` = не погашаемый (процент 0), иначе погашаемый (процент 100).
- В Main расход уже распределён по артистам, поэтому запись получает **псевдоним** этого ника и ISRC, подобранный
  по его трекам (метод подбора и цифры в отчёте загрузки). Область «весь баланс», как Main списывал с общего
  баланса ника.
- Загрузка через API-фасад, повторный запуск ничего не дублирует (внешняя ссылка `mvp:main:ads:<лист>:<строка>`).
- ISRC: название трека из поста PROMO того же или прошлого месяца, иначе самый доходный ISRC артиста в месяц
  рекламы или отчёта, иначе за всё время, иначе без ISRC. Итоги загрузки и открытые вопросы: раздел 6
  [файла вопросов](рекламные_расходы_вопросы_владельцу.md).
- Команды: `python3 -I packages/backend/scripts/mvp/extract-main-ads.py` (только чтение, строит
  `data/mvp-load/ads/main_ads_mapping.json`), затем `npx tsx packages/backend/scripts/mvp/load.ts ads --apply`;
  эффект на балансы: `npx tsx packages/backend/scripts/mvp/ads-effect.ts`.
