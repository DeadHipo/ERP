Цель: фронт ERP (/Users/nearlydeadhipo/Desktop/0to8/ERP, packages/frontend) — рабочее место оператора лейбла уровня zero-erp: всё можно прокликать, посмотреть и подтвердить на экране, без SQL и скриптов. Оператор отвечает на три вопроса: чей каждый доллар (по треку, релизу, владельцу, лейблу), что ждёт и почему (C с причиной и действием), сколько можно выплатить владельцу сегодня — и сразу делает действие: утверждает документ, заменяет допущение документом, привязывает владельца, заводит сплит, участие или правило лейбла, разрешает псевдоним, выплачивает. Цифры на экране совпадают с API до цента. Стоп только по достижении цели; владельца не спрашивать.

Идея (не менять): фронт ничего не считает. Каждое число приходит из API (фасад считает с нуля); фронт показывает, фильтрует, переходит и отправляет ввод. Деньги приходят строками; на экране два знака и разделители, точное значение по наведению; арифметики над деньгами во фронте нет. Правила (порог, блокировки, категории, кто может быть утверждён) решает бэкенд; фронт может спрятать или выключить кнопку с объяснением, но не быть единственной проверкой. Ключ трека — ISRC, релиза — UPC; имя артиста и название трека — подписи и поиск, не ключи. Авторизации и ролей пока нет: все действия доступны всем, но каждое действие оставляет след (кто/когда — поле «оператор» в форме, пока без входа), а необратимое (утверждение, выплата, закрытие правила, слияние) — через диалог подтверждения с тем, что изменится.

Как в zero-erp (стек): React 19 + Vite + TypeScript, HeroUI (как в zero-erp) + Tailwind 4, TanStack Query для данных (кеш запросов, инвалидация после действия, индикатор пересчёта), AG Grid для больших таблиц (24 тыс. сплитов, 26 тыс. треков, 1,1 тыс. владельцев, операции), Playwright для e2e, Heroicons. Без Refine, three.js, графиков и i18next, пока экран без них обходится; интерфейс на русском, строки в одном словаре. Каждая библиотека — D-запись; новая D-запись заменяет «минимальный фронт без UI-кита» (D-007, D-062). Типы запросов и ответов — только из @erp/shared; клиент API один.

Простота — главный критерий. Страница отвечает на один вопрос оператора; описание страницы — одно предложение в packages/frontend/CLAUDE.md. Единый каркас: боковое меню, глобальный поиск (ISRC, UPC, псевдоним, владелец, документ), хлебные крошки, карточка сущности с вкладками (обзор, деньги по месяцам, правила, документы, история). Одинаковые компоненты на всех страницах: таблица, карточка, статус-бейдж, сумма, форма, диалог подтверждения, пустое/долгое/ошибочное состояние. Каждое число кликабельно до своего источника: сверка → месяц → трек → слой → правило → документ.

Главное:
- Обзор: A / B / C / наша доля по источнику, счёту и месяцу, C по причинам, сигналы; клик ведёт в список.
- Трек «чей каждый доллар»: по месяцам net, слои по порядку, кому сколько, база и плательщик каждой доли, документ и статус, причина C; все правила трека на одной карточке (строки сплита, участия, правило лейбла, история периодов).
- Очередь разбора C: сгруппирована по причине; у каждой строки действие (утвердить документ, привязать владельца, завести сплит, разрешить псевдоним, заменить допущение документом — документ вида assumption не утверждается, D-125), после действия пересчёт и строка уходит.
- Владелец: деньги, что ждёт и почему, авансы и рекуп, операции, кнопка выплаты со снимком, история выплат.
- Справочники с вводом: лейблы и правила, сплиты и участия (с проверками бэкенда: сумма ≤ 100, строка-или-участие, месячные даты), документы с утверждением, условия паблишинга, операции.
Бэкенд можно дополнять только эндпоинтами чтения и действий, которые нужны экранам и которых нет (лёгкий explain трека вместо 4,5 МБ, очередь C с пагинацией, поиск, список релизов по UPC, история изменений сущности), каждый с тестом, контрактом в operations.ts и D-записью; денежные правила не трогать. Скорость: 7–10 с на пересчёт — норма, экран показывает, что идёт расчёт, и не блокирует навигацию.
