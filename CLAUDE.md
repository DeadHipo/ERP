# Context for Claude (and other agents) continuing this project

A royalty ERP for a music label: it takes distributor reports (Believe, master) and publisher statements (B17),
decides for every dollar **whose it is** (by split / writer mapping), **whether it is confirmed** (approved document),
and **how much an owner can be paid today**. Nothing is stored as accruals: every answer is recalculated from the
raw report lines; a payout freezes a snapshot. Iteration 1 is done; you are continuing it.

## Architecture in one screen
- All backend paths below are under `packages/backend/`.
- **The organization is the isolation boundary (D-170):** one database, `org_id NOT NULL` on every module table (migration 0016). Every module is opened under an organization: `openModules(db, org)` (`src/facade/modules.ts`), `openFacade({ db, orgId, sources, dataDir })`; repositories filter only through `src/shared/org-scope.ts` (`orgWhere`, `orgRow(s)`, `orgFree`, `orgQuery` refusing SQL without `org_id = $1`); `tests/org-scope.test.ts` checks every table and statement statically. `src/orgs` (organizations, the facade map `facades.ts`, `resolveOrg`) and `src/auth` (users, scrypt, JWT cookie) sit above the facade; modules and the facade never import them. Files live in `<dataDir>/orgs/<id>/files/{sources,publishing}`, uploads in `<dataDir>/orgs/<id>/tmp`.
- API chain (`src/api/server-app.ts`): `requestId → express.json → authenticateOrSystemKey → system router (/health, /openapi.json, /docs, /auth/*, /orgs*) → resolveOrg → the organization's router (operatorTrace → labelGuard → authorize → v1 routes)`; `noStore` and `originGuard` on all of `/api`. `POST /auth/login` sets the cookie `erp_session`; the organization comes only from the session; `X-Org` only for the system administrator; `X-System-Key` = `SYSTEM_ADMIN_KEY`. `.env`: `AUTH_MODE` (on by default; off = every request in `ERP_DEFAULT_ORG`, operator from `X-Operator`), `AUTH_SECRET` (≥ 32 bytes), `SYSTEM_ADMIN_KEY`, `ERP_DEFAULT_ORG`. Users: `npx tsx packages/backend/scripts/create-user.ts <login> --org <id> [--role org_admin|label_manager] [--label <labelId>]… | --system | --reset-password | --disable | --enable` (password from `ERP_NEW_PASSWORD` or stdin). Clean stack with a login: recipe 12 in `docs/agents/04_recipes.md`.
- **Roles and abilities (D-171):** a request has one principal (`src/auth/abilities.ts`): `org_admin` (everything in its organization, «Все»), `label_manager` (only its own labels from `auth.user_labels`, no money of the whole organization, no `approve` / `pay` / `admin`), `system` (only `/orgs*`, `/system/*`; no money), `support` (the system administrator with `X-Org` under a grant of the `org_admin`, ≤ 7 days, read or write; commit 4), `local` (`AUTH_MODE=off` = `org_admin`) and `reader` (`MCP_READ_TOKEN`, `Authorization: Bearer`: only `read` and `read_money` of `ERP_DEFAULT_ORG`, in both modes; D-177). Memberships in several organizations: the login answers `409 org_choice_required` until `orgId` is chosen; the token `{ sub, sid }` names a revocable row of `auth.sessions`, re-read on every request (migration 0017). Every non-public operation of `operations.ts` carries `ability: { action, subject, scope }` (actions `read | read_money | write | approve | pay | admin | system | self`, scope `label | record | org`); one `authorize` middleware asks `can()` of the one table `RULES` (`400 label_required`, `403 label_forbidden`, `403 forbidden`, `403 support_*`); `GET /auth/me.abilities` lists the allowed operations for the UI, which never repeats the rules. The label of a record is checked in the facade through its own `Viewer` (`facade/viewer.ts`, `ALL_VIEWER` default; routes pass `viewerOf(res)` from `src/api/viewer.ts`): another label's record reads as 404, a write on it is `403 label_forbidden`. `.env`: `AUTH_LOGIN_LIMIT` (5) / `AUTH_IP_LIMIT` (20) failed logins per minute (0 = off; `429 too_many_attempts`), `TRUST_PROXY` (`1` = one hop), `APP_ORIGIN` (extra origins a write may come from; else `403 csrf`), `AUTH_COOKIE_SECURE=1` (only behind https: `__Host-erp_session; Secure`).
- Every API write (POST/PATCH) must carry `X-Operator` (URI-encoded; 400 `operator_required` without it), except the public `/auth/login|logout`; the hook `src/api/audit.ts` records it in the `audit` module after a 2xx (D-140, D-150); with `AUTH_MODE=on` the recorded operator is the session's login (D-170).
- `src/modules/<m>/{schema.ts, repository.ts, service.ts, index.ts}` for owners (module 1: owners, artists = pseudonyms, tracks, documents incl. kinds `assumption` and `label_decision`, contracts, merge; the catalog tables `track_labels` and `releases`, D-172), labels (own labels, imprint aliases, sublabel rules), splits (artist rows with optional per-row document, participations), sources (Believe), settlements (operations with a stored kind of nine, D-173; payouts, scope shape), publishing (B17, terms by operation type), audit, ads (advertising expenses: ISRC, month, amount, recovery percent, scope; D-156). Each module has its own short `CLAUDE.md`.
  - owners, labels, splits, settlements, publishing, audit and ads: one PostgreSQL database, **one schema per module** (`owners.*`, `splits.*`, …), no foreign key across modules (D-121). DDL in `migrations/postgres/NNNN_*.sql` (applied by `npm run migrate:pg`, never edit an applied file: add a new one), Drizzle `pgSchema` tables in `schema.ts` (change both). **The sources module** has the file registry in PostgreSQL (`public.source_files`) and the report lines in ClickHouse (`believe.rows` plus views); `schema.ts` and `repository.ts` do not exist there, its SQL is in `registry.ts` and `columnar.ts` (D-102, D-104, D-109, D-110).
  - Access goes through `src/shared/pg-db.ts` (`Db`): repositories call `db.orm()` per query; `db.transaction()` is a write (one advisory lock serializes all writes, nested calls join), `db.snapshot()` a consistent read-only read. Every service and facade method that touches storage is async.
  - All SQL lives in the repository.
- `src/facade/` is the only place composing modules:
  - `index.ts` only opens the modules and merges the method groups: `context.ts` (shared checks), `splits.ts`, `sources.ts`, `reports.ts`, `owner-view.ts`, `payouts.ts` (the payout button with snapshot, writer resolution, merges, signals);
  - `calculation.ts`: recalculation from scratch; builds the pure context and runs `allocateUnit` per unit; `reconcile()` per source, account and month (the domain core, read it once);
  - `layers/`: the money as pure functions, one file each; the order is the list `MASTER_LAYERS` in `layers/index.ts`: label of record → perimeter → off the top → split → carves (pool, artist share, label share, sublabel) → categorise; publishing: writer parts → author share → categorise; `recoup.ts` too. Tests in `tests/layers/` and `tests/golden.test.ts`; design in `docs/agents/10_target_model.md`;
  - `balance.ts`: owner balance (earned/waiting also per label of record), payable; the ad charges (`calc.adPositions`) are taken off payable there at once (D-157); since D-173 the book fields `buyouts`, `forgiven`, `writtenOff`, `adjustments`, `byArea { master, publishing }` and `payable_L = earned − recouped − paid − adsCharged + returns + credits + adjustments − writtenOff`; since D-174 the **opening balances** (`settlements.opening_balances`, passed in as `index.starts`): an owner with a start row in a book loses that book's inputs up to the cut (units, publishing, ads ≤ `cutoff_month`; operations ≤ the day of `synced_at`, except a reopened advance) and `payable_L = start + …`;
  - `start.ts` (D-174: `POST /settlements/start/import` with a preview, `GET /settlements/start`, the soft rollback);
  - `admission.ts` (D-176: the payee and channel, the holds, the answers «pay», the contract threshold; `payout-gate.ts` reads them: owner_not_confirmed → no_contract_for_label → start_missing → nothing_to_pay → below_threshold → hold → payout_blocked → no_payee → needs_answer; the last two act once the organization has a payee row);
  - `payroll.ts` (`GET /owners/payroll`, json / csv, D-173) and `operation-import.ts` (`POST /settlements/operations/import`, D-173);
  - `split-import.ts` (the split import, D-172: preview in a snapshot, apply all or nothing through `createSplit` / `changeSplit`), `catalog.ts` (the label history of an ISRC), `release-registry.ts`, `onboarding.ts` (the checklists, no calculation);
  - `ads.ts`: advertising expenses as a pure function (split of the month without MC and label rows, recovery percent, the unrecovered part to the sublabel's pseudonym or to us), run inside `calculate()`; `ads-api.ts` the methods of `/ads`;
- `src/api/app.ts` assembles the app; the routes are in `src/api/routes/` (one router per topic: owners, labels, splits incl. participations, sources, publishing, reports, settlements, joined in `routes/index.ts`; new: `/labels`, `/labels/:id/aliases`, `/labels/:id/rules`, `/labels/rules/:id/close`, `/participations`, `/participations/:id/close`) under `/api/v1`; shared helpers (`parse`, error handler) in `api/http.ts`. It serves `packages/frontend/dist`. Request schemas are in `packages/shared/src/api-schemas.ts` (`@erp/shared/api-schemas`), response schemas in `api-responses.ts`; the frontend uses both. Every route must have an entry in `src/api/operations.ts` (with `access: public | user | system | org`, D-170, and `ability` on every non-public one, D-171): the OpenAPI document (`/api/v1/openapi.json`, UI at `/api/v1/docs`) is built from it and `tests/api-contract.test.ts` checks it against the real routes and responses and requires its scenario to call every operation (D-119).
- `packages/frontend/src/`: `pages/<domain>/` the React pages (21, D-139…D-149), `routes/` (path patterns in `routes/paths.ts`), `components/`, `api/client.ts` the typed fetch client and `api/coverage.ts` (every API operation → a page or a refusal), `i18n/ru/` the strings. Details: `packages/frontend/CLAUDE.md`.
- Data scripts: `packages/backend/scripts/mvp/` (stage 4 loader `load.ts`, `load-b17.ts`, stage 5 `compare-*.ts` and `decompose-main.ts`); the loader writes through the facade except three documented migration-only bypasses: the `normalise-dates` SQL update of split dates (D-131), the two splits-module deletes `deleteEmptySplits` / `deleteParticipations` (D-137) and the run-cached `owners.artistIndex` (D-131). The read-only Python extractors (`scripts/mvp/*.py`, stdlib only) read the workbooks, ClickHouse and `owners.*` directly (recipe 9).
- Shared file readers (D-172): `src/shared/csv.ts` (streaming `parseCsv`, used by sources, the split import and the release export) and `src/shared/xlsx-rows.ts` (streaming xlsx rows, used by B17 and the split import); pure, no module.
- Money: source amounts are pico-USD integers (BigInt sums), calculations use decimal.js, operations are integer cents, and JSON money is decimal strings. `tests/rules-coverage.test.ts` allows `Number(` in `src` only from a fixed list.

## Things that will bite you
- **12-decimal exactness (D-127, D-130):** in `facade/layers/` quantise each allocation to 12 decimals right after its multiplication (`exact.ts`), take every remainder by subtraction, give residues to the largest absolute amount. `tests/layers/exactness.test.ts` fails otherwise.
- **Month-start rule (M52):** every `valid_from` / `valid_to` / close date of a split, participation or label rule is floored to the first day of its month (the facade does it); a period that becomes empty is `empty_period`.
- **Row-or-participation rule:** a pseudonym is a split row or a participation on an ISRC and date, never both (D-126).
- **Every recipient is a pseudonym** (participant, sublabel, buyer): an advance is recouped only from income of the same pseudonym.
- **Document kind `assumption`** = a council decision that is never approved; its money waits in C `assumption`. C reasons are one enum (`C_REASONS`) with labels in `packages/shared/src/reasons.ts`; `label_unmapped` = the Believe label string maps to no label: "ours" waits, artists still get paid by their rows; `no_split` (D-175) = the ISRC has no split at the report date: the whole label share waits, no sublabel carve runs, and a «100 % label» split (no rows) is how an assigned work becomes ours (the split import takes a row with an empty pseudonym and percent 100).
- The handover demo data contains writer legal names (owner aliases from the old IMRO registry) on the owner's request (D-090). Never copy them into code, tests, fixtures, logs or docs.
- B17: `rights-holder name` is the payee; the authors are the comma-separated `songwriters`. A line goes to our listed writers in equal parts, otherwise to the holder (D-087).
- Sources: equal keys are never merged at load; the ClickHouse views sum them (`units`, `lines`). Reads take the `loaded` files from the registry first and ask ClickHouse with `file_id IN (...)`, so a file that is not loaded never counts. In ClickHouse never name a result alias like a column (`toString(file_id) AS file_id` silently breaks the WHERE). Money from ClickHouse is read as text; use `Decimal` from `shared/money.ts` (plain decimal.js keeps 20 digits). `calculate()` reads all modules in one `db.snapshot` (D-012, D-121).
- One PostgreSQL/ClickHouse store per `.env`: `main.ts <dir>` switches only the directory of original files. A data set is switched with `DB_DATABASE` / `CLICKHOUSE_DATABASE` (D-121); a tenant is an **organization inside** the store, not a store (D-170).
- **Organization (D-170):** every script opens its organization (`connectOrg`: `--org <id>` → `ERP_ORG` → `ERP_DEFAULT_ORG`, else exit 1 listing them); `main.ts` in `AUTH_MODE=off` needs `ERP_DEFAULT_ORG`. The live `erp` has organization №1 `00000000-0000-4000-8000-000000000001`. A new table of a module needs `org_id NOT NULL` and the helper, or `org-scope.test.ts` fails; a raw `q(...)` must name `org_id = $1`. Tests: `newFacade()` opens on `stores.orgId`. The Python extractors (recipe 9) assume one organization in the database.
- A forgotten `await` is a silent bug: lint has type-aware `no-floating-promises` / `await-thenable` for the backend (D-121). Tests: `await expect(f.x()).rejects…`, never `expect(await f.x()).rejects`.
- The demo package (`data/demo`) uses files reconstructed from erp.db (D-008, D-066); its platform/country/sales-month breakdowns are not real, and it has no Believe data since the move (D-112). Real Believe reports exist in `context_data/ERP_data/believe/raw` and `believe_echo8`, and load through the API (D-079 to D-081, D-111). Real B17 statements contain authors' legal names; on the owner's instruction they are loaded into `data/real` (local only, shipped in the separate data archive) and writers are linked to owners by name (D-086, D-087, D-090, D-093).
- Splits are chosen by report date = the first day of the reporting month. `valid_to` is exclusive (D-025). The Believe unit key includes the label string (D-124).
- **The admission (D-176):** the gate is one function (`payout-gate.ts`) for the button, the balance, the payables and the payroll; a hold, a missing payee and a first payout without an answer «pay» for exactly the amount refuse the payout; the checks «no payee» / «needs an answer» are on from the first `settlements.payees` row of the organization (a test world without one pays as before). The threshold of the contract (`owners.contracts.payout_threshold_cents`) wins over `PAYOUT_THRESHOLD_CENTS` (default $50, D-175).
- A plain payout is only possible through `createPayout` (the button). The operations endpoint refuses it (D-051); the exceptions are `migration` payouts and the import of operations, which writes every row as `migration: true` (D-173). The button takes `area` (default `master`) and pays `min(payable_{L,area}, payable_L)`; reads without `area` are `all`.
- **Operation kinds (D-173):** `settlements.operations.kind` is stored (`payout, advance, deduction, credit, return, buyout, forgiveness, writeoff, adjustment`; one list `packages/shared/src/operation-kinds.ts` with `KIND_DOCUMENT_KINDS`, CHECK `operations_kind_rules` of migration 0019); branch on `kind`, never on `direction`. `buyout` is outside `paid` / `payable` and never blocks (blocking = `kind IN ('payout','advance')` in three places: `settlements/service.ts`, `balance.ts`, `context.ts`); `forgiveness` only through `POST …/:id/forgive`; `writeoff` is publishing only; `adjustment` is `in` with a signed amount. `meaning` is a temporary alias of `kind`.
- **The one allowed layer change (D-173):** the forgiveness of an advance in `facade/layers/recoup.ts` (the capacity after its date; netting only if the position takes something, D-101; no new multiplication). Tested by the forgiveness `describe` of `tests/recoup.test.ts`, G57–G60 and an unchanged `tests/layers/exactness.test.ts`; without forgivenesses the result is byte for byte the old one. Every other layer and `calculation.ts` stay closed.
- **`asOf` (D-173)** is a cut of the inputs of `ownerBalance` (units, statements, operations, positions, ads ≤ the month), never an argument of `calculate()` and never stored; document statuses are those of now.
- **The start (D-174, D-175):** the cabinet position of 15.10.2026 is a row of `settlements.opening_balances` per pseudonym and book, never an operation, and **one number in the master area** (the publishing of the quarters after the cut is the publishing payroll); with an active row the book's history up to the cut is inside the start for the whole owner (a pseudonym without a row has a start of 0), the start is added to payable last, a `missing` row closes the payout (`start_missing`). A row is never edited: a correction is an `adjustment` row, a mistake a deactivation. `calculate()` and the layers do not know the start; it is read beside the operations. The live `erp` holds the start of 2026-08 (1 179 rows); 16 ambiguous nicks wait for the operator.
- **B17 replacement (D-173):** `POST /publishing/statements/:id/replace?label=` (same quarters, through the same `load()`): the old statement becomes `superseded` with `replaced_by`, its lines and sha stay for the payout snapshots. The Q2 2026 «Updated» run waits for the owner's confirmation (recipe 15).
- The owner balance and the payout snapshot are calculated over the owner's **reach** (`facade/owner-scope.ts`, D-163, D-164): a new way for money to reach a pseudonym (a new layer, rule kind or record kind) must extend `ownerReach`, with `tests/scope.test.ts` pinning balance-by-reach = full and `scripts/check-owner-scope.ts` run on the real data.
- Advertising (D-155…D-157): what an expense charges (an artist's recovered part, a sublabel's unrecovered part) is taken off payable at once and in full, like a payout, not recouped; no document is needed; the record's scope decides nothing about money.
- **Rights (D-171):** a new operation needs `access` **and** `ability` in `operations.ts` and a line in the frozen manager table `tests/helpers/manager-answers.ts` (never derived from `RULES`); a facade method whose right depends on the label of a record (or of an ISRC) takes a trailing `viewer: Viewer = ALL_VIEWER` and the route passes `viewerOf(res)`; the facade never imports `src/auth` and never names a role.
- **The catalog is navigation, not money (D-172):** `owners.track_labels` (the label history of an ISRC: `files` derived by `derive-track-labels.ts`, `operator` corrections win only their months) and `owners.releases` (the Believe export, key `(org, label, upc)`) are never read by `calculation.ts`, the layers, `scope.ts`, `owner-scope.ts`, `balance.ts`, `label-scope.ts` (`boundaries.test.ts`); `tests/catalog.test.ts` pins `calculate()` byte for byte. The catalog label of an ISRC is not its book (the book is the label of the file, D-169).
- **Document kind `label_decision` (D-172):** a label decision without a contract; approved, it confirms an owner like a contract (`createContract` takes it) and a row or participation like an appendix: money in B, no layer reads the kind.
